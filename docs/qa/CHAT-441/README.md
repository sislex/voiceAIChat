# CHAT-441 — проверка Web Reader, 2026-09-09

## Подтверждённая причина

В беседе `0990e11c-bb1e-4341-9289-8dffda5fc455` сохранён URL
`http://89.125.68.35:8787/#/chat/81caab96-6d29-4054-a5bd-8da334caaf79`.
Его получили точечным SELECT по id, без изменения данных. `exec_target` пустой;
алиас `machine.internal` в исходном адресе отсутствует.

Из контейнера `voiceaichat-voicechat-1` запрос к `89.125.68.35:8787` завершился
таймаутом через 12012 мс, а `127.0.0.1:8787` вернул 200 за 7 мс.
С хоста публичный адрес отвечает 200. Действующий browser-runner уже имеет
операторскую пару `89.125.68.35:8787=voicechat:8787`, но встроенный Web Reader
не получал переменную и не применял алиас. Код прокси превращает таймаут
исходящего запроса 10000 мс в HTTP 504 «Сайт не ответил вовремя».

После подключения алиаса обнаружен второй дефект: HTML отвечал 200, но импорты
ESM chunks разрешались относительно `/api/preview`, запрашивали
`/api/react-*.js`, `/api/monaco-*.js` и другие неверные пути с ответом 401.
Для операторских алиасов теперь применяется существующее переписывание ESM;
после этого приложение отрисовалось.

Сохранённый URL при инициализации передаётся через WebReaderFrame → host bridge
→ Recorder без машинной канонизации; команда MCP open разворачивает
`machine.internal` в разрешённую машину разговора. Это различие не является
причиной данного сбоя: исходный адрес — публичный IP.

## Проверка в настоящем standalone Web Reader

Временный QA-процесс с исправленным `registerPreviewProxy` запускался в сетевом
пространстве production-контейнера на отдельном порту 18899. Он раздавал
существующую standalone-сборку `/web-recorder/`, полученную с работающего
приложения. Небольшой host harness передавал сохранённый адрес через штатный
init/postMessage-контракт. Тестовый пользователь действовал только в этом
изолированном прокси; production-авторизация не изменялась.

Playwright использовался для управления окном с Web Reader. Продукт Playwright
Reader, его API сессий и команды browser-runner не использовались.
Чтение, снимок вложенной страницы и клик выполнены командами самого Web Reader.

- HTML и все 16 зафиксированных запросов preview при рабочем алиасе: HTTP 200.
- Hash исходного приложения сохранён во вложенном iframe.
- `read`: заголовок «Вход», поля пользователя/пароля, кнопки входа и регистрации.
- `screenshot`: возвращён непустой снимок вложенного приложения
  [reader-page.png](reader-page.png).
- Безопасный `click` по «Зарегистрироваться», затем `read`: «Регистрация».
  Учётная запись не создавалась, формы не отправлялись.
- Только в QA-процессе временно очищена карта алиасов. «Открыть» в Web Reader
  воспроизвёл HTTP 504 и «Сайт не ответил вовремя» без Storybook.
- Карта восстановлена. «Повторить» показал «Загрузка сайта…», отключил кнопку и
  скрыл старую причину. Запрос на время наблюдения задерживался браузером,
  но ответ не подменялся. Затем 16 новых запросов вернули 200; `read` снова
  вернул экран входа. Ошибка исчезла.

## Автотесты

- TC1 — `previewProxy.error.test.ts`: HTML реального ответа, текст ошибки,
  обработчик кнопки, видимое состояние загрузки и новая доставка после восстановления.
- TC3 — `previewProxy.alias.test.ts`: воспроизведение таймаута прямого транспорта,
  доставка по операторскому алиасу, исходные URL/hash/ссылки и ESM imports.
- TC3 — `WebReaderFrame.dom.test.tsx`: приоритет сохранённого адреса беседы.
- TC3 — `infra.caddy.test.ts`: переменная алиасов в обоих режимах Web Reader.
- TC4 — тесты alias/machine/actions: прямые private/loopback, смешанный DNS,
  редиректы в приватную сеть и на чужую машину, отсутствие вызова запрещённого
  транспорта. Над тестами стоят маркеры `// @testCase TC1|TC3|TC4`.

Истории `WebReaderApp.stories.tsx` проверены: они описывают оболочку приложения.
Фактический HTML ошибки формируется серверным `previewErrorPage`; его
Component QA выполнен DOM-тестом и описанным выше прогоном Web Reader.

## Ограничение приёмки

Исходная production-ссылка в чистом браузере показывает форму входа.
Авторизованной сессии владельца и настроенных тестовых пользователей проекта нет.
Поэтому проверена загрузка **сохранённого приложения до экрана входа** в
изолированном Web Reader, а не открытие содержимого личного чата в исходной
production-панели. Полную AC1/AC5 после выкладки необходимо подтвердить в
авторизованной сессии. Production не обновлялся.

## Гейт

Профильные тесты конфигурации и прокси прошли. Из-за изменения compose первый
`gate:fast` выбрал полный fallback; он остановлен до общего запуска тестов.
После отдельной фиксации проверенной конфигурации повторный `npm run gate:fast`
выполнил связанные тесты и typecheck пакетов web-reader, ui, server, web,
web-recorder и завершился с кодом 0. Локальные коммиты затем объединены без
изменения проверенного исходного кода.
