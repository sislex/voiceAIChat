# Как устроена и ведётся база знаний

## Зачем

Проект разрабатывают несколько агентов (Claude Code / Codex) на разных машинах.
Без KB каждая сессия начинается с исследования: чтение десятков файлов, поиск
контракта, повторное выяснение того, что уже выяснял кто-то другой. KB переносит
эту стоимость в один дешёвый файл, который читается на старте.

## Уровни (от дешёвого к дорогому)

1. **`AGENTS.md` в корне** — читается всегда, поэтому держится в пределах ~200 строк:
   карта монорепо, команды, гейт, «что нужно знать до первой правки», указатели.
   `CLAUDE.md` — одна строка `@AGENTS.md`, чтобы у Claude Code и Codex был один
   источник и не было расхождений между двумя файлами.
2. **`AGENTS.md` внутри пакета** (`apps/*/AGENTS.md`, `packages/*/AGENTS.md`) — то,
   что нужно только при работе в этом пакете. Рядом лежит `CLAUDE.md` с импортом
   `@AGENTS.md`: Claude Code подхватывает вложенный файл, когда трогает файлы в
   этом каталоге, — то есть контекст платится только при реальной работе там.
3. **`docs/kb/*.md`** — темы. Читаются по указателю из корневого `AGENTS.md`.
4. **`docs/kb/log/*.md`** — журнал сессий: что делали, что выяснили, куда занесли.
   Читать не обязательно; нужен для «почему так вышло» и для передачи между агентами.
5. **`docs/plans/*.md`** — исторические планы фич с чек-листами. Не источник истины
   о текущем состоянии кода: там есть и невыполненные шаги, и устаревшие решения.

## Устройство файла темы

YAML-фронтматтер:

```yaml
---
title: Протокол клиент↔сервер
updated: 2026-07-26          # дата последней сверки с кодом — для человека
checked: 4805be2             # sha HEAD на момент сверки — для проверки
areas:                        # пути/каталоги, за которыми следит проверка свежести
  - packages/shared/src/protocol.ts
  - apps/server/src/ws.ts
---
```

`node scripts/kb.mjs check` смотрит `git log <checked>..HEAD -- <areas>`: если после
сверки в этих путях были коммиты — тема помечена как устаревшая, с номером и темой
первого такого коммита. Оба поля ставит `kb.mjs touch`, руками их писать не нужно.

**Почему sha, а не только дата.** Дата ловит только правки прошлых дней. В этом
репозитории несколько агентов коммитят в один день, и сверка по датам молча
пропускала бы правки, сделанные после неё в тот же день, — то есть самый частый
случай. Дата остаётся фолбэком: если `checked` отсутствует или исчез после rebase
(sha перезаписан), проверка возвращается к сравнению дат и говорит об этом.

Это подсказка, а не запрет: команда всегда выходит с кодом 0 — кроме
`--strict`, где любая проблема даёт код 1 (для CI или pre-commit, если захочется
жёсткости).

## Правила ведения

- **Факты, а не планы.** В KB пишется то, что верно в коде сейчас. Намерения — в
  `docs/plans/`, ход работы — в журнале.
- **Одна тема — один файл.** Новая большая подсистема → новый файл + строка в
  таблице указателей корневого `AGENTS.md`.
- **Не дублируй код.** Вместо перечисления полей — ссылка на файл-источник
  (`packages/shared/src/protocol.ts`). Дублирование гарантированно разъедется.
- **Пиши абзацами по подтемам.** Один растущий список в конце файла — главный
  источник merge-конфликтов у параллельных агентов; разные абзацы правятся мирно.
- **Не трогай `docs/kb/README.md` руками** — это производный индекс. В ветке
  разработки его можно не коммитить: merge-ран безусловно перегенерирует файл по
  итоговому дереву после содержательной актуализации БЗ.

## Пробел базы знаний обязан стать записью

Обращение к базе, оставшееся без ответа или с неполным ответом, — это долг, а не
тупик: ответ, найденный потом в коде или полученный по итогам разработки, обязан
попасть в тот раздел, где его искали. Правило не пожелание, а часть директив
модели: текст живёт в `KB_GAP_RULE` (`packages/shared/src/kbGaps.ts`) и уходит в
системный хинт КАЖДОГО хода с инструментами базы (`kbToolHint`) — то есть в чат,
в работу модели CI-рана, в fix-loop и в резюме. Без него база работает в одну
сторону: ход платит за исследование кода, а следующий платит за него снова.

Три ограничения делают запись безопасной. Раздел **дополняется**, а не
дублируется: две статьи об одном — самый дорогой способ испортить базу. Факт
сначала **сверяется с кодом** — источник истины остаётся код, а не то, что модель
запомнила. Неподтверждённое **не записывается вовсе**: незакрытый пробел дешевле
записанной догадки.

Способ записи зависит от того, кто пишет. Руками (чат, локальная сессия) — как в
разделе «Правила ведения» и в `AGENTS.md`: правка темы, `kb.mjs touch`, `kb:log`,
`kb:index`, коммит вместе с кодом. В CI-ране модель в базу не пишет сама:
она называет пробел и найденный ответ блоком ```` ```kb-gaps ```` (формат —
`KB_GAPS_HINT`, разбор — `parseKbGaps`), пробелы копятся за ран в
`ci_run_kb_gaps`, а заносит их встроенный шаг (ниже). Вторым источником пробелов
шаг берёт телеметрию обращений: вопросы со статусом `empty`/`error` видны, даже
если модель про блок забыла. Подробности —
[features/ci-runner.md](features/ci-runner.md).

## Автоведение: обязательная стадия merge-рана

Ручная дисциплина «допиши KB после правки» ломается первой, поэтому запись
встроена в отдельный merge-workflow. После локального построения неизменяемого
merge SHA `MergeRunManager` одновременно запускает обязательный проектный гейт
и `kb_update` в двух изолированных detached worktree одного SHA. Стадия
переиспользует серверный хук из `apps/server/src/ci/modelHooks.ts` и общий
проверенный код промпта и разбора из `apps/server/src/kb/codeUpdate.ts`.

Стадия работает только в своём KB-worktree. Сервер проверяет его корень и
собирает merged diff относительно зафиксированного target ref, поэтому модель
видит тот же снимок, который проверяет параллельный гейт, и не может менять его
файлы. Один ход обновляет два адресата:

- **файловые темы `docs/kb/*.md`** — модель правит их в KB-worktree по правилам
  этого файла, ставит свежесть и добавляет журнал; после ответа менеджер
  перегенерирует индекс и создаёт отдельный дочерний `docs(kb)`-коммит в
  feature, только если дерево действительно изменилось;
- **статьи раздела «Разработка проекта»** (`scope='project'`) — модель возвращает
  их структурированным JSON, а сервер сохраняет через `db.saveKbDocument` только
  после корректного полного ответа. Ответ обязан содержать ровно один объект
  полного контракта; текстовый отчёт вокруг единственного ```` ```json ````-блока
  допустим, а вот второй JSON-кандидат, лишнее поле или один невалидный документ
  отменяют сохранение всего набора. Ненайденный, повреждённый и не отвечающий
  контракту JSON сервер один раз чинит коротким repair-ходом в той же сессии
  модели, без инструментов и без нового бюджета времени; неоднозначный —
  не чинит. Разбор — в [features/ci-runner.md](features/ci-runner.md).

Созданный KB-коммит проверяется ещё раз: если он трогает только `docs/**` (без
`generated|dist|build`), `.github/**` или корневые `*.md`, менеджер ограничивается
сокращённым `kb.mjs check`; правка любого другого пути заставляет его повторить
полный проектный гейт (подробности — [features/merge-runner.md](features/merge-runner.md)).

Кроме дифа стадия получает подтверждённые **пробелы базы знаний** (см. выше).
Пустой diff без таких пробелов завершается успешно без вызова модели. Если пробелы
есть, они должны стать правкой соответствующего раздела даже при пустом diff.
Число выбранных статей и длина переданного текста ограничены.

Обновление обязательно: ошибка проверки корня, сбора diff, вызова модели, разбора
ответа или сохранения данных останавливает merge без push; параллельный гейт к
этому моменту мог уже завершиться, но его успех сам по себе публикацию не разрешает. При таймауте
сервер отменяет CLI и проверяет `docs/kb`: если валидные файловые темы уже
изменены, merge может продолжиться с явным результатом стадии, но проектные статьи
без финального JSON не сохраняются; без файловых изменений таймаут остаётся
ошибкой. Development CI больше не создаёт шаг `kb_update`; строка builtin-команды
остаётся в справочнике только для истории и совместимости.

Ручной фолбэк — операция «Исследовать проект» в режиме «по изменениям с коммита
`<sha>`» (тот же промпт, но файлы репозитория не правятся: рабочая копия проекта
общая). Исполнение описано в
[features/merge-runner.md](features/merge-runner.md).

## Как обновлять

```bash
npm run kb            # = kb:check + kb:index
npm run kb:check      # что устарело + пакеты без AGENTS.md + битые ссылки
npm run kb:index      # перегенерировать docs/kb/README.md
npm run kb:log -- <slug>   # новая запись журнала (дата+машина+slug в имени файла)
node scripts/kb.mjs touch protocol   # поставить сегодняшнюю дату в updated
```

## Почему нет merge-конфликтов

- Журнал: имя файла — `<дата>-<машина>-<slug>.md`, машина берётся из `hostname`.
  Два агента физически не могут писать в один файл.
- Индекс: конфликт снимается автоматически независимо от остальных путей, а файл
  безусловно перегенерируется merge-раном после итоговой актуализации БЗ.
- Темы: агенты обычно работают в разных подсистемах → правят разные файлы.
  Совпало — конфликтуют максимум строки `updated:`/`checked:`; разрешаются
  повторным `kb.mjs touch` после мержа.
- Пакетные `AGENTS.md`: локальны для пакета, то есть для одной задачи.

## Конфликт в тематическом файле: не `checkout --ours`

`git checkout --ours <файл>` и `--theirs` берут **весь** файл из соответствующей
стороны, а не только конфликтный участок. На файле, где не сошлась одна строка
`checked:` во фронтматтере, это молча выбрасывает всё, что вторая сторона
добавила в остальной текст. Так однажды из `testing-operations.md` пропали 18
строк, которые в тот же день занесла параллельная сессия на другой машине —
включая её собственную находку про `mkdtempSync`.

Правильно — снять маркеры руками (`<<<<<<<`, `=======`, `>>>>>>>`), оставив нужную
строку и **сохранив оба набора абзацев**. Проверка после мержа:
`git diff origin/main HEAD -- docs/kb | grep '^-' | grep -v '^-checked:'` — всё, что
здесь показано как удаление, должно быть удалением осознанным.

Исключение — генерируемый `docs/kb/README.md`: его конфликт разрешать руками не
нужно, берётся любая версия и прогоняется `npm run kb:index`.
