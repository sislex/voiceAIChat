# Как устроена и ведётся база знаний

## Зачем

Проект разрабатывают несколько агентов (Claude Code / Codex) на разных машинах.
Без KB каждая сессия начинается с исследования: чтение десятков файлов, поиск
контракта, повторное выяснение того, что уже выяснял кто-то другой. KB переносит
эту стоимость в один дешёвый файл, который читается на старте.

## Уровни (от дешёвого к дорогому)

1. **`AGENTS.md` в корне** — читается всегда, поэтому держится в пределах ~200 строк:
   карта монорепо, команды, гейт, «что нужно знать до первой правки», указатели.
   `CLAUDE.md` — одна строка `@AGENTS.md`, чтобы у Claude Code и Codex был один
   источник и не было расхождений между двумя файлами.
2. **`AGENTS.md` внутри пакета** (`apps/*/AGENTS.md`, `packages/*/AGENTS.md`) — то,
   что нужно только при работе в этом пакете. Рядом лежит `CLAUDE.md` с импортом
   `@AGENTS.md`: Claude Code подхватывает вложенный файл, когда трогает файлы в
   этом каталоге, — то есть контекст платится только при реальной работе там.
3. **`docs/kb/*.md`** — темы. Читаются по указателю из корневого `AGENTS.md`.
4. **`docs/kb/log/*.md`** — журнал сессий: что делали, что выяснили, куда занесли.
   Читать не обязательно; нужен для «почему так вышло» и для передачи между агентами.
5. **`docs/plans/*.md`** — исторические планы фич с чек-листами. Не источник истины
   о текущем состоянии кода: там есть и невыполненные шаги, и устаревшие решения.

## Устройство файла темы

YAML-фронтматтер:

```yaml
---
title: Протокол клиент↔сервер
updated: 2026-07-26          # дата последней сверки с кодом — для человека
checked: 4805be2             # sha HEAD на момент сверки — для проверки
areas:                        # пути/каталоги, за которыми следит проверка свежести
  - packages/shared/src/protocol.ts
  - apps/server/src/ws.ts
---
```

`node scripts/kb.mjs check` смотрит `git log <checked>..HEAD -- <areas>`: если после
сверки в этих путях были коммиты — тема помечена как устаревшая, с номером и темой
первого такого коммита. Оба поля ставит `kb.mjs touch`, руками их писать не нужно.

**Почему sha, а не только дата.** Дата ловит только правки прошлых дней. В этом
репозитории несколько агентов коммитят в один день, и сверка по датам молча
пропускала бы правки, сделанные после неё в тот же день, — то есть самый частый
случай. Дата остаётся фолбэком: если `checked` отсутствует или исчез после rebase
(sha перезаписан), проверка возвращается к сравнению дат и говорит об этом.

Это подсказка, а не запрет: команда всегда выходит с кодом 0 — кроме
`--strict`, где любая проблема даёт код 1 (для CI или pre-commit, если захочется
жёсткости).

## Правила ведения

- **Факты, а не планы.** В KB пишется то, что верно в коде сейчас. Намерения — в
  `docs/plans/`, ход работы — в журнале.
- **Одна тема — один файл.** Новая большая подсистема → новый файл + строка в
  таблице указателей корневого `AGENTS.md`.
- **Не дублируй код.** Вместо перечисления полей — ссылка на файл-источник
  (`packages/shared/src/protocol.ts`). Дублирование гарантированно разъедется.
- **Пиши абзацами по подтемам.** Один растущий список в конце файла — главный
  источник merge-конфликтов у параллельных агентов; разные абзацы правятся мирно.
- **Не трогай `docs/kb/README.md` руками** — он генерируется (`npm run kb:index`).
  При конфликте бери любую сторону и перегенерируй.

## Автоведение: база пишется на каждом ране

Ручная дисциплина «допиши KB после правки» ломается первой, поэтому запись
привязана к CI-рану. В слоте «после модели» — перед шагом коммита — стоит
встроенный шаг **«Актуализировать базу знаний»** (`CiCommand.builtin = 'kb_update'`,
серверный хук `kbUpdate` в `apps/server/src/ci/modelHooks.ts`, общий код промпта и
разбора — `apps/server/src/kb/codeUpdate.ts`). Диф ветки к базовой собирает сервер
(`git diff` рабочего дерева к базе, патч с капом), после чего один ход модели
пишет сразу в двух местах:

- **файловые темы `docs/kb/*.md`** — модель правит их в рабочей копии рана по
  правилам этого файла, ставит свежесть (`node scripts/kb.mjs touch <topic>`),
  добавляет запись журнала (`npm run kb:log -- <slug>`) и перегенерирует индекс
  (`npm run kb:index`). Коммитить ей не нужно: правки забирает следующий шаг
  воркфлоу, тот же, что коммитит код;
- **статьи раздела «Разработка проекта»** (`scope='project'`) — модель возвращает
  их текстом, а записывает сервер (`db.saveKbDocument`), как в «Исследовать проект»:
  раздел, проект и владелец статьи не зависят от того, что модель себе придумала.

Правятся только те статьи, чьи `areas` пересекаются с путями дифа; число статей и
длина текста капнуты. Изменение, которого база не касается (тесты, форматирование),
закрывает шаг записью «нечего обновлять». Сбой, неразборчивый ответ или таймаут
(10 минут) ран **не валят**: шаг закрывается как `skipped` с предупреждением в
ленте — работа модели к этому моменту уже сделана. Убрать шаг можно там же, где
настраивается любой другой: в слотах проекта или задачи. Ручной фолбэк — операция
«Исследовать проект» в режиме «по изменениям с коммита `<sha>`» (тот же промпт,
но файлы репозитория не правятся: рабочая копия проекта общая).

Подробности шага — [features/ci-runner.md](features/ci-runner.md).

## Команды

```bash
npm run kb            # = kb:check + kb:index
npm run kb:check      # что устарело + пакеты без AGENTS.md + битые ссылки
npm run kb:index      # перегенерировать docs/kb/README.md
npm run kb:log -- <slug>   # новая запись журнала (дата+машина+slug в имени файла)
node scripts/kb.mjs touch protocol   # поставить сегодняшнюю дату в updated
```

## Почему нет merge-конфликтов

- Журнал: имя файла — `<дата>-<машина>-<slug>.md`, машина берётся из `hostname`.
  Два агента физически не могут писать в один файл.
- Индекс: генерируемый, конфликт решается перегенерацией.
- Темы: агенты обычно работают в разных подсистемах → правят разные файлы.
  Совпало — конфликтуют максимум строки `updated:`/`checked:`; разрешаются
  повторным `kb.mjs touch` после мержа.
- Пакетные `AGENTS.md`: локальны для пакета, то есть для одной задачи.
