# Reader — исправление падения истории действий по HTTP

## Что сделано

- От актуального `origin/main` (`81df383d`) создана отдельная ветка
  `codex/web-reader-http-uuid` в соседнем worktree. Исходное дерево не менялось.
- В опубликованном `index-B3Mxk4H3.js`, строка 384, позиция из пользовательского
  стека, найден прямой `globalThis.crypto.randomUUID()` в обработчике
  `window.preview.onChanged`. Он создавал ключ записи истории и обрушал React.
- `AppBody` использует общий `browserId()` и создаёт запись перед state-updater.
  DOM-тесты проверяют два одинаковых действия, игнорирование чужого разговора
  и повтор команды без `randomUUID`, а также без Web Crypto целиком.
- Новый E2E использует собранный App, временный сервер/БД, форму входа, cookie,
  CSRF, WebSocket и MCP open/read; после reload проверяет новое подключение
  Reader. Chromium открывает HTTP через имя `reader-http.test` и через loopback.

## Что выяснили (факты, которых не было в KB)

- На пользовательском HTTP-origin Chromium подтвердил `isSecureContext=false`,
  `typeof crypto.randomUUID === 'undefined'`, `getRandomValues` доступен.
  Без пользовательской сессии опубликованная страница показывает форму входа;
  действия модели проверялись только на локальном тестовом сервере.
- Начальная загрузка Reader не воспроизводит падение: нужен успешный ответ
  действия модели и событие `reader.changed`. Тест на localhost также пропускает
  ошибку, поскольку loopback считается доверенным контекстом.
- Наличие iframe не гарантирует завершения handshake; E2E ждёт новую регистрацию
  и открытый WebSocket перед MCP. Это ожидание готовности стенда, без повторов
  неуспешных MCP-команд и без искусственного удаления browser API.
