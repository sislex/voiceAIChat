# Прод переведён на Postgres

## Что сделано

- Освобождён диск (build cache Docker 7,5 ГБ): 87 % → 60 %.
- В `.env` прода добавлены `VC_PG_PASSWORD`, `COMPOSE_PROFILES=postgres`, затем `VC_DB_URL`; поднят сервис `postgres`.
- Пробная копия на живой базе (снимок `VACUUM INTO` за 24 с, ~1 ГБ; копия 78 с, 113 таблиц, расхождений 0),
  затем переключение: стоп ядра 12:04:23, свежий снимок, чистая схема, копия 72 с, старт на Postgres 12:06:08 —
  простой 108 с. Агенты переподключились, `last_seen` растёт уже в Postgres, файл SQLite не меняется.
- Ручной релиз 0.1.261 и штатный 0.1.262 до этого: исправление потолка кучи (PR #119) подтверждено — регрессия
  прошла без падения, событий у релиза 27.

## Что выяснили (факты, которых не было в KB)

- В файле SQLite прода 5,2 ГБ было ~1 ГБ живых данных: 79 % страниц — пустые после чистки событий релизов;
  в Postgres база заняла 639 МБ.
- `docker compose up -d <сервис>` вручную обнуляет метаданные релиза у ядра и Make — передавать
  `VC_RELEASE_VERSION`/`VC_RELEASE_COMMIT` в окружении команды.
- `docker stats` показывает RSS с файловым кешем и нативной памятью: куча JS ядра под нагрузкой 205 МБ при RSS
  ~500 МБ; анонимная память cgroup 431 МБ — нативные аллокации, не утечка кучи. Читать `memory.stat` контейнера.
- Любой читатель SQLite (даже `readonly`) трогает `-shm` — так фоновый монитор маскировал вопрос «кто пишет».

## Открытые вопросы / что осталось

- Включить отдельные процессы по одному: `kanban`, затем `machines`, затем `admin` (профили compose + режимы у ядра).
- Удалить снимок `/data/prod-copy.db` и файл SQLite через несколько дней после подтверждения; следить за нативной
  памятью ядра (`MALLOC_ARENA_MAX=2`, если растёт).
