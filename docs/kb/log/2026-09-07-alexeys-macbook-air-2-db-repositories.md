# db-repositories

## Что сделано

- `VoiceChatDb` (10,5 тыс. строк, 573 члена, 113 таблиц) разрезан на 11 доменных
  репозиториев `apps/server/src/db/repos/<домен>.ts` (identity, settings, llm, chat,
  machines, projects, tasks, ci, qa, releases, kb). Ядро `database.ts` — соединение, схема,
  `migrate()`, раздача репозиториев. Тела методов перенесены дословно, поведение не менялось.
- Все ~4 800 обращений на сервере переведены на адресную форму `db.<домен>.<метод>()`;
  структурные интерфейсы зависимостей и моки в тестах — той же формы `{ домен: { метод } }`.
- Манифест владения `db/ownership.ts` (`TABLE_OWNER`, `KNOWN_CROSS_WRITES`,
  `CROSS_READ_BUDGET`) и гейт `db/ownership.test.ts`: один владелец на таблицу, репозитории
  не импортируют друг друга, чужие записи только из списка (трещотка), чужие чтения — в бюджете,
  `better-sqlite3` только внутри `src/db`.
- План с картой владения и кругами 2–4 — `docs/plans/db-repositories.md`.

## Что выяснили (факты, которых не было в KB)

- Решение «начинать с Postgres» отвергнуто цифрами: в сервере ноль `await db.…`, весь слой
  синхронный (`better-sqlite3`), 895 `prepare()`, 64 транзакции-замыкания, 57 тестов на
  `:memory:`. Любой Postgres-драйвер асинхронный → это переписывание всего сервера разом без
  приближения к независимым релизам. Порядок: владение таблицами → async-порты → движок.
- Секционные комментарии `// ---- X ----` в старом `database.ts` давно не соответствовали
  содержимому (в «Статьях базы знаний» лежали 131 метод про QA, релизы и подготовку задач);
  распределять методы по доменам можно только по таблицам, в которые они пишут.
- Разрез сделан кодомодом на TypeScript compiler API (одноразовые скрипты вне репозитория):
  метод → домен по таблицам записи, спорные ~80 — вручную; переписывание вызывающих по
  ошибкам `tsc` («Property 'x' does not exist on type 'VoiceChatDb'» → вставить домен);
  плоские моки `as unknown as VoiceChatDb` / `as never` перегруппированы по AST. Итог
  проверялся только гейтом по коду возврата.
- Кросс-доменные записи, оставшиеся долгом: каскады `identity.deleteUserData` и
  `machines.deleteAgent`, `projects.createProject` → `kb_documents`, `projects.removeMember`
  → `tasks`, `tasks.createTask` → `projects` (счётчик), `ci.startMergeRun` /
  `recordIntegrationAutomationLinks` → `tasks`/`task_preparation_runs`. Больше всего чужих
  чтений у `tasks` (17 таблиц) — доска собирается JOIN-ами по всем доменам.
- Make таблиц в БД не имеет (состояние — файловые workspaces), поэтому он первый кандидат на
  отдельное приложение.
- Проверка в браузере: сессионная cookie не привязана к порту, поэтому второй dev-сервер на
  другом порту с копией БД (в ней те же строки `sessions`) принимает уже залогиненную сессию
  пользователя из основного dev-сеанса. Удобно для смоука, но помнить при отладке авторизации.

## Открытые вопросы / что осталось

- Круг 2 плана: закрыть `KNOWN_CROSS_WRITES` через методы владельцев.
- Круг 3: async-порты по доменам, миграции по доменам.
- `testing-operations.md` содержит исторические замеры покрытия по `db/database.ts`
  (609 функций) — цифры теперь относятся к `db/repos/*`; при следующем замере обновить.
