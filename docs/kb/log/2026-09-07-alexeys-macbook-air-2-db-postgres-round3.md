# Postgres как движок базы — круг 3: перенос прод-копии, compose, проверка

## Что сделано

- Перенос копии прод-БД (4,9 ГБ; самая тяжёлая таблица — `project_release_events`, 3,6 ГБ
  журналов релизов) в локальный Postgres 16: 107 с, 113 таблиц, счётчики совпали везде.
  Единственная правка по итогам — вырезание NUL-байтов из текстов (`ci_run_logs`, две строки):
  Postgres не хранит `0x00` в TEXT, SQLite хранит.
- Сервер на `VC_DB_URL` с прод-данными (dev-web на 8799): API-смоук по всем крупным разделам — 200
  (беседы со стоимостью, доска, карточка задачи, релизы, отчёт расхода, полнотекстовый поиск с
  курсором, админка, машины, Make, KB, команды CI); в браузере — главная, доска, релизы без ошибок.
- compose: опциональный сервис `postgres` (профиль), `VC_DB_URL` у ядра; `docs/docker.md`.

## Что выяснили (факты, которых не было в KB)

- Перенос идемпотентен: повтор поверх заполненной базы пропускает существующие строки
  (`ON CONFLICT DO NOTHING`), а последовательности выравниваются заново — можно докатывать.
- В прод-данных есть тексты с NUL-байтами (журналы ранов); любой перенос в Postgres обязан их
  чистить, иначе строки не лягут.
- 4,9 ГБ SQLite переезжают за ~2 минуты на ноутбуке — окно простоя при переводе прода небольшое.

- Резервное копирование Postgres на проде (pg_dump) — вне этого плана.
