# prod-502-container-created

## Что сделано

- Разобрали, почему прод отдавал `502`, и подняли приложение: `cd /root/voiceAIChat && docker compose up -d`
  (образ уже был собран, не хватало только `start`).
- Проверили: `/api/health` → `{"ok":true,"version":"0.1.0"}` и внутри (`127.0.0.1:8787`),
  и снаружи через Caddy (`https://45.135.182.251/` → `200`).

## Что выяснили (факты, которых не было в KB)

- **Деплой, запущенный из сессии внутри контейнера `voicechat`, убивает сам себя.**
  `docker compose up -d --build` сначала останавливает старый контейнер — вместе с ним
  умирает и процесс деплоя, поэтому новый контейнер остаётся в статусе `Created`
  и никогда не стартует. По `docker events` видно ровный обрыв: `create` образа →
  `create` контейнера → `kill`/`die`/`destroy` старого → и никакого `start`.
  В `/root/.bash_history` перед этим — `docker compose exec -u root voicechat bash`, `claude`.
- Симптомы такого состояния: Caddy в `Up`, порт 8787 снаружи закрыт, HTTPS отдаёт `502`,
  `docker compose ps -a` показывает `voicechat` в `Created` **без логов**.
- Хеш-префикс в имени (`<hash>_voiceaichat-voicechat-1`) — не поломка: так docker разводит
  конфликт имён при пересоздании. Уйдёт при следующем полном деплое.
- Доступ на прод: только парольный вход, `sshpass` на рабочей машине нет. Неинтерактивно
  надёжнее обёртка через `SSH_ASKPASS` + `SSH_ASKPASS_REQUIRE=force`, чем `expect`.

## Открытые вопросы / что осталось

- Деплой стоит запускать с хоста либо оборачивать в `nohup`/`systemd-run`, чтобы он
  переживал остановку контейнера. Автоматизации для этого пока нет.
