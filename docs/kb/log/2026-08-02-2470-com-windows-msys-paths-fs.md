# windows-msys-paths-fs

## Что сделано

- `apps/agent/src/fileOps.ts`: новая `toNativePath(path, platform)` — единственная
  нормализация пути для всех файловых операций (`absPath`), зовётся ДО
  `assertAllowed`. На win32 разворачивает MSYS/Git Bash-путь диска
  `/c/Users/...` → `C:\Users\...`, приводит букву диска к верхнему регистру.
- `allowedDirs` прогоняются через ту же функцию, сравнение на Windows —
  регистронезависимое (ФС там регистронезависима).
- Тесты `apps/agent/src/fileOps.test.ts`: регрессия исходного ENOENT, обе
  раскладки буквы диска, нативные `C:\`/`C:/`/UNC/`\c\`, неизменность POSIX,
  проверка allowedDirs по нормализованному пути; e2e `fsRead` по MSYS-пути —
  только на win32 (`it.runIf`).
- `AGENT_VERSION` 0.9.2 → 0.9.3 (машину надо обновить, чтобы фикс доехал).

## Что выяснили (факты, которых не было в KB)

- Модель на Windows работает в git-bash и отдаёт продукту MSYS-пути; это
  зеркало уже описанной нормализации `cwd` в MCP `bash` (там наоборот —
  бэкслеши в слэши). `node:path.resolve('/c/Users/x')` считает такой путь путём
  от корня ТЕКУЩЕГО диска → `C:\c\Users\x` → ENOENT на `fs.read` (показ картинки).
- `\c\...` (бэкслеш) MSYS-путём НЕ является — это корень текущего диска, поэтому
  преобразуем только форму с прямыми слэшами.
- `path.win32.resolve()` на POSIX-CI детерминирован для полностью
  квалифицированных путей (`C:\...`, UNC), но для rooted-без-диска отдаёт
  `\c\...` без буквы — на это опирается регрессионный тест.
