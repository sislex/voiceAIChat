# cookie-scheme-collision

Жалоба: «каждый раз при обновлении страницы приходится логиниться заново» на
проде `http://89.125.68.35:8787`.

## Что сделано

- Имена cookie сессии разведены по схеме запроса: по https — `__Secure-vc_session`,
  `__Secure-vc_csrf`, `__Secure-vc_preview_session`, `__Secure-vc_device` с флагом
  `Secure`, по http — прежние имена. `cookieNameFor`/`readCookie` в
  `apps/server/src/users/auth.ts`; чтение принимает оба имени, приоритет — у
  защищённого, поэтому правка никого не разлогинивает.
- `clearLegacySessionCookies`: вход по https дополнительно гасит старую пару
  обычных имён — лечение браузеров, где уже лежит `Secure`-cookie `vc_session`.
- Читатели обоих имён вне `auth.ts`: `cookieToken` (WS-upgrade, `server.ts`) и
  `getCsrf` (`packages/ui/src/remote/session.ts`).
- Мост сессии отдаёт `hasCookieSession()`; `App` после входа без cookie-сессии
  показывает тост с `duration: 0` — что случилось и что делать.
- Тесты: `routes/rest.test.ts` (https-имена, гашение старой пары, приоритет
  защищённого имени при обеих cookie, отсутствие гашения по http),
  `packages/ui/src/remote/remote.test.ts` (разбор обоих имён, признак моста).

## Что выяснили (факты, которых не было в KB)

- Cookie различаются по **хосту**, а не по схеме и порту, а прод виден по двум
  адресам одновременно: `https://<ip>` через Caddy и `http://<ip>:8787` — порт
  сервера опубликован наружу в `docker-compose.yml`. Вход по одному адресу ломает
  сессию на другом: по правилу «Leave Secure Cookies Alone» (RFC 6265bis §5.4)
  незащищённый origin не может ни прочитать `Secure`-cookie, ни перезаписать
  одноимённую, и `Set-Cookie` от сервера браузер отбрасывает **молча**.
- Симптом со стороны выглядит как поломка сессии: приложение работает (Bearer в
  памяти страницы), но `document.cookie` без `vc_csrf`, `/api/session/me` по
  cookie → `user: null`, и любая перезагрузка возвращает экран входа.
- Диагностический приём: со страницы записать cookie с НОВЫМ именем (получается и
  переживает F5) и cookie с именем `vc_csrf` (молча игнорируется) — разница и есть
  подпись экранирования `Secure`-cookie. Проверка «сервер вообще шлёт cookie?»
  делается без пароля: `POST /api/session/cookie` без авторизации отвечает 401
  JSON, если роут есть, и 404, если сборка старая.
- На проде страницы, открытые через прокси превью, исполняются **на origin
  приложения**: там лежат чужие `_ga`, `_ttp`, `ttcsid`, `cfz_facebook-pixel`.
  Сам прокси `Set-Cookie` проксируемых ответов отбрасывает
  (`routes/previewProxy.ts`), но их JS пишет cookie напрямую и может прочитать
  `vc_csrf`. Отдельная проблема, здесь не решалась.

## Открытые вопросы / что осталось

- Прошлое состояние браузера правкой не лечится само: пользователю нужно один раз
  либо очистить cookie сайта, либо войти по https (тогда `clearLegacySessionCookies`
  уберёт старую пару).
- Публиковать наружу оба адреса — источник этой ловушки. Стоит оставить один
  (https через Caddy — микрофон требует secure-контекста) и не публиковать 8787.
- Изоляция origin для прокси превью (чужой JS видит `vc_csrf`) — не сделана.
