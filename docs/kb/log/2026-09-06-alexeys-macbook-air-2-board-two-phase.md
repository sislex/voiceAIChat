# board-two-phase

Началось с жалобы: `GET /api/session/me` на проде висел 22 с при открытии страницы
проекта. Роут ни при чём — он отвечает за 42 мс; сервер в этот момент был занят
доской.

## Что сделано

- Доска разделена на две фазы: `GET /api/projects/:id/board` (скелет: колонки и
  карточки) и новый `GET /api/projects/:id/board/statuses` (состояние процессов и
  сводки CI). Мост `board:getStatuses`, тип `BoardStatuses`, склейка —
  `applyTaskStatuses` в `@shared/projects`. `db.getBoard` остался как композиция
  обеих фаз для MCP, автопрохода и тестов.
- Убраны N+1 в `getBoardStatuses`: оконные выборки на весь проект вместо
  коррелированных подзапросов на карточку (`latestTaskRunResults`, `latestByTask`).
- `latestCiRunSummaries` получила `scope` — сводки только по карточкам доски.
  История длительностей шагов вынесена в `ciStepDurationHistory` и считается один
  раз на доску.
- Скелет выбирает только свои колонки (`BOARD_TASK_COLUMNS`) и отсекает завершённые
  прямо в SQL через новую `completedVisibilityCutoff`.
- Индексы: `idx_ci_workspaces_task`, `idx_qa_sessions_task`, `idx_conversations_task`.
- Клиент всегда стартует доску в окне проекта; включённое «показывать завершённые»
  догружает архив вторым запросом (`projectsStore.openBoard`).

## Что выяснили (факты, которых не было в KB)

- Node-сервер однопоточный, а `better-sqlite3` синхронный: любой тяжёлый снапшот
  блокирует **все** соединения. Замер на проде: пока считалась доска,
  `/api/health` отвечал 1711 мс вместо 41 мс. Это и есть механизм «зависших»
  посторонних запросов на старте страницы.
- Вес ответа доски был не в задачах: 19 карточек весили 24 КБ, а `ciRuns` — 1067 КБ,
  потому что `latestCiRunSummaries` собирала раны всех 400 задач проекта за всю
  историю (383 сводки, из них к доске относились 11).
- `EXPLAIN QUERY PLAN` на реальной схеме: `SCAN` по `ci_workspaces` и `qa_sessions`,
  а подзапрос чата шёл по `idx_conversations_user_scope_project_updated` (user_id)
  с `USE TEMP B-TREE FOR ORDER BY` — то есть перебором всех бесед пользователя на
  каждую карточку.
- Частичный `idx_qa_sessions_one_active` (`WHERE status='active'`) не годится для
  поиска последней сессии задачи — нужен полный индекс по `task_id`.
- Замер до/после на одинаковых данных (400 задач, 20 в окне, 400 ранов): было
  62 мс / 344 КБ одним ответом, стало 0.22 мс / 14 КБ скелетом и 2.2 мс / 27 КБ
  статусами.
- Профиль запросов старта страницы проекта: ~30 REST-запросов разом, при лимите
  HTTP/1.1 в 6 соединений на origin ожидание в очереди браузера доходило до 8.8 с.

## Куда занесено

- docs/kb/projects.md — раздел «Доска приезжает двумя фазами», плюс правило
  «открытие проекта всегда начинается с окна» в разделе про завершённые задачи.

## Открытые вопросы / что осталось

- `GET /api/conversations/task-chats` — тот же паттерн N+1 (`latestCiRunSummary` в
  цикле по чатам), на проде 2.3 с и 1.09 МБ. Не трогали.
- `GET /api/conversations?scope=chat` — 1.0 с из-за `conversationCosts`
  (агрегат с `json_extract` по всем сообщениям).
- Клиент шлёт на старте ~30 запросов сразу (7 из них — `conversations?scope=…`);
  разнести по мере надобности пока не пробовали.
