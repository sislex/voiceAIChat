# пересборка-прода-chat-67-kb

Шаг «Актуализировать базу знаний» того же рана, что и
[2026-08-02-2470-com-пересборка-прода-chat-67](2026-08-02-2470-com-пересборка-прода-chat-67.md).
Кода ран не менял (диф к `main` — только `docs/kb/*`), поэтому запись —
про перенос фактов рана из журнала в тему.

## Что сделано

- Перенёс в `docs/kb/deploy.md` два факта, которые в журнале были, а в теме нет:
  лестницу проверки отставания прода и то, что health отложенного `up -d`
  снимается с хоста.
- Причесал рецепт двухфазной пересборки: имена временных файлов в примере — с
  суффиксом `<N>` (номер задачи), иначе параллельные пересборки затирают друг
  другу лог и файл кода выхода.

## Что выяснили (факты, которых не было в KB)

- Состояние прода на момент этого шага (14:07 UTC): образы `voicechat-server`,
  `voicechat-llm-runner-work`, `voicechat-llm-runner-personal` собраны 13:50–13:51
  UTC из вершины `8fe0064`, `/tmp/prod-build-67.exit` = `0`; контейнеры ещё на
  старых образах (созданы 10:47 UTC) — отложенный `up -d` (SID 1958195) стрелял
  в ~14:22 UTC. То есть на момент записи фаза 1 подтверждена, фаза 2 ещё не
  выполнена, и проверить её из рана уже нельзя.

## Куда занесено

- docs/kb/deploy.md — раздел «Прод мог обновиться и без рана»: абзац про лестницу
  проверок (`git status` → `git rev-list --count HEAD..origin/main` → время
  создания образов против времени коммита `HEAD` → один файл-маркер), и что
  полное сравнение `sha256sum` нужно только при подозрении на сборку из грязного
  дерева. Заодно — почему по этой лестнице сразу видно, какие из перечисленных в
  карточке задач уже на проде.
- docs/kb/deploy.md — раздел «Пересборка прода изнутри рана»: health проверяется
  с хоста на `127.0.0.1:8787/api/health` (в серверном образе нет ни `curl`, ни
  `wget`), лог второй фазы именуется по номеру задачи.
- Статья «Пересборка прода: сначала проверить, потом собирать» в разделе
  «Разработка проекта» — добавлены обе фазы как отложенные сеансы и лестница
  проверки отставания.
