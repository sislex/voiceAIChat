# Локальный запуск и браузерная проверка обоих движков Reader

## Что сделано

- По просьбе пользователя запущена уже проверенная сборка ветки
  `codex/web-reader-http-uuid`: сервер `127.0.0.1:8799`, browser-runner
  `127.0.0.1:8900`, TTS Runner `127.0.0.1:8901`. Данные, профили Chromium, тестовые учётные данные и логи
  размещены в отдельном временном каталоге; указатель на его state-файл —
  `/tmp/reader-local-state-path`. Процессы оставлены работать для пользователя.
- Проверка установленным Chromium на обычном HTTP-origin `reader-http.test`
  (DNS-алиас на loopback): `isSecureContext=false`, `randomUUID` отсутствует.
  Вход выполнен через форму, действия модели — через настоящий MCP endpoint,
  с cookie, CSRF, WS и без вызовов LLM.
- Быстрый режим: open/read, история и повтор команды, ввод модели в форму,
  отправка формы, чтение ручного ввода, reload, внешний `example.com`.
- Полный браузер: открытие и чтение `example.com`, взять/вернуть управление,
  сохранение движка и страницы после reload, формы входа Gmail и Instagram.
  Во внешние аккаунты не входили; окно cookies Instagram не подтверждали.
- Настройки собственного проекта: отдельный вход внутри iframe
  `https://app.internal/#/settings`, затем MCP прочитал заголовок «Настройки»,
  поля и вкладки страницы `#/settings/llm`. Ошибок JavaScript нет.

## Что выяснили (факты, которых не было в KB)

- Первый пробный open использовал backend-host `127.0.0.1`, хотя вкладка
  открыта на `reader-http.test`: чужой loopback ожидаемо отклонён защитой
  preview. После использования origin самой вкладки диагностика открывается.
- После open Instagram сначала показывает только загрузочный экран. MCP wait
  с условием непустого текста дождался формы входа и окна cookies; немедленный
  read с пустым текстом не доказывает готовность приложения.
- Снимок полного браузера нужно делать после обновления кадров панели:
  завершённый MCP open предшествует следующему screenshot/status polling.
- Визуальная проверка настроек обнаружила баннер HTTP 500, хотя `pageerror`
  был пуст. Причина — отсутствующий на стенде TTS Runner: запросы
  `/api/tts/voices` и `/api/tts/catalog` возвращали `fetch failed` снаружи и
  через proxy. Поднят настоящий TTS Runner с временными данными, перезапущен
  только собственный сервер с его URL/токеном. Повторный вход и MCP read/errors
  на странице настроек прошли: 0 HTTP 5xx, 0 ошибок страницы.

## Куда занесено

- `docs/kb/testing-operations.md`, раздел Development.
- Артефакты в `artifacts/` каталога стенда: `report.json`, `instagram.json`,
  `own-project.json`, снимки proxy, Chromium, Instagram и настроек проекта.
  Первый неуспешный пробный запрос сохранён отдельно в `report-initial.json`.

## Проверки и время

- 10 сентября 2026, около 12:56–13:05 (Минск): запуск стенда и живые проверки,
  включая подключение недостающего TTS-сервиса.
- Основной сценарий: 15 проверок прошли, исключений `pageerror` нет.
  Дополнительно подтверждены загрузка формы Instagram и авторизованных
  настроек проекта; соответствующие снимки и ответы MCP сохранены отдельно.
- Код приложения в этом шаге не менялся; используется сборка и `gate:fast`,
  прошедшие в шаге `reader-http-uuid`. Повторный полный гейт не запускался.
- In-app Browser недоступен (`missing field sandboxPolicy`); это проверка
  установленным Playwright Chromium, а не встроенной вкладкой приложения.

## Открытые вопросы / что осталось

- Стенд продолжает работать на localhost; он использует тестового пользователя
  и не подключён к данным опубликованного сервера. Коммит/push/PR не выполнялись.
