# Конвенции: код, тесты, гейты, коммиты

## Перенёс правки на свежий main — прогони гейт заново

Зелёный гейт действителен только для той базы, на которой он выполнялся. Если
правки готовились в отстающем дереве, а потом переехали на актуальный
`origin/main` (`git switch -c … origin/main`, rebase, перенос патчем), гейт надо
повторить: у соседней ветки мог измениться тест или фикстура, которых в старой
базе не было. Так в релиз уехало падение `taskPreparation.test.ts`
(`expected 'blocked' to be 'success'`): требование обязательного UI-сценария
готовилось на старой базе, а чужой коммит успел добавить в этот тест
`uiImpact: 'existing_components'` — обе ветки были зелёными по отдельности, а
вместе дали семантический конфликт, которого не видит ни один PR-гейт.

## Код

- **Write new comments and documentation in English.** Explain decisions and
  pitfalls rather than restating the code. Keep file introductions brief and
  follow the surrounding comment density. Effective 2026-09-11, Make maintains
  English comments and Markdown in `apps/make`, `packages/make-app`, and
  `packages/make-contracts`, including generated comments, exported Markdown,
  and its dedicated plans. The user also requests English communication.
- TypeScript strict везде; в `packages/ui` дополнительно `noUnusedLocals`,
  `noUnusedParameters`, `noImplicitOverride`.
- **Импорты**: в `apps/server` и `apps/llm-runner` — с расширением `.js`
  (`./config.js`), потому что
  запуск идёт через `tsx` в ESM без сборки. В `packages/*` — без расширений, общий
  код подключается алиасом `@shared/*` (прописан в tsconfig и в vitest-алиасах).
- Чистая логика выносится в `packages/shared` и покрывается юнит-тестами без
  моков; всё внешнее (spawn, fetch, сокет, БД) **инъектируется параметром** —
  отсюда `SpawnFn`, `BuildOptions`, `AgentSocket` и т.п. Новый модуль,
  дёргающий процесс или сеть напрямую без возможности подмены, — против конвенции.
- Никаких новых зависимостей без нужды: `packages/shared` вообще без `dependencies`,
  монорепо на голых npm workspaces (без turbo/nx/lerna).

## Тесты

`vitest run` в каждом воркспейсе. Файлы — рядом с исходником: `*.test.ts` для
логики, `*.dom.test.tsx` для компонентов (jsdom + Testing Library, setup —
`packages/ui/src/test/setup.ts`, фейковые мосты — `src/test/fakeApi.ts`). Сейчас в
репозитории ~465 тестовых файлов, из них 76% в трёх пакетах: `packages/ui` (149),
`apps/server` (130), `packages/shared` (78). Тест пишется в том же шаге, что и код.

Что принято покрывать: чистые функции (`shared`) — таблицей случаев; сервер —
через `fastify.inject()` и ws-клиент с моками движков; UI — поведением
(«клик → вызван мост → изменился экран»), не снапшотами.

**Тесты менеджеров синхронизируются по состоянию, а не по паузе (2026-09-08).** База асинхронна
(на Postgres — реально), поэтому `await new Promise(r => setTimeout(r, 0))` или «два тика» после события
(onDone хода, cancel рана, статус в базе) ничего не гарантируют: утверждение должно ждать наблюдаемое
следствие — `await turns.idle()`, `vi.waitFor(async () => expect(await db….).toBe(…))`, пустой
`activeRunIds()`, терминальный статус релиза. Тест WS-сессии ждёт первый кадр `claude.active`
(готовность сессии), а не `open` клиента: сервер ещё проверяет сессию в базе. То же правило и для
тестов межпроцессных мостов: RPC зеркала (`machinesBridge/httpMachines.test.ts`) — настоящий HTTP-запрос к
фейковому соседу, события — кадр WebSocket, и фиксированная пауза здесь такой же таймер. Пауза в 30 мс
проходила на свободной машине и разваливалась в полном прогоне: под параллельной нагрузкой тест падал
20 раз из 24 с пустым списком вызовов `ptyStart`, а с ожиданием состояния — ни разу (регрессия
release/0.1.265, 2026-09-08). Тесты, которым нужен сам
драйвер SQLite или файловая база, помечаются `it.skipIf(ON_POSTGRES)` с причиной; карантин «падает на
Postgres по таймингу» больше не заводим — так был пойден двойной development-ран.

```bash
npm run gate:fast                      # гейт приложений по рабочему диффу от HEAD
npm run -w @voicechat/ui test          # один пакет
npm run -w @voicechat/server test
npm run test:desktop                   # desktop — свой node_modules
npm run test                           # все воркспейсы
```

Полный гейт репозитория — `npm run verify`: typecheck + test всех воркспейсов,
сборка, плюс desktop и agent-tray (у них свой `node_modules`). Перед пушем удобнее
гонять его, чем собирать команды руками.

A fresh worktree needs separate installs for all three non-workspace Electron
apps before a gate that selects them: `npm ci --prefix apps/desktop`,
`npm ci --prefix apps/agent-tray`, and `npm ci --prefix apps/login-application`.
The root `npm ci` does not install their Electron or electron-vite dependencies.
Use `gate:fast -- --dry-run` and the application catalog to check the full selected
set; shared-code changes can select these consumers even during Make work.

## Покрытие: пороги по каталогам, когда пакет считать целиком бессмысленно

`packages/chat-app` — пример, когда порог на пакет ничего не защищает. `store/chatStore.ts`
(1994 строки) в покрытии своего пакета показывает 0%: его гоняют dom-тесты
`packages/ui` через домен-обёртку, а счётчик покрытия чужие пакеты не видит.
Порог на пакет пришлось бы поставить около 11%.

Поэтому пороги заданы по каталогам (`thresholds: { 'src/lib/**': …, 'src/routes/**': … }`):
чистая логика закрыта на 100% и обязана такой остаться, а стор порогом не
охвачен. Так же стоит поступать в любом пакете, где часть кода проверяется
тестами соседа.

## `noUnusedLocals` включён во всех пакетах

`apps/server` был единственным пакетом, где `noUnusedLocals` и
`noUnusedParameters` оставались выключенными, — и там же накопился мёртвый код:
неиспользуемые импорты, локальные переменные, которым только присваивают, и
целые функции, потерявшие вызывающих при переездах фич. Находилось это только
вручную, через счётчик вызовов в отчёте покрытия.

Флаги включены 1 сентября 2026; разбор дал 42 ошибки в 25 файлах. Полезное
правило из разбора: **неиспользуемый параметр не удаляется, а получает префикс
`_`** — позиция в сигнатуре значима, а имя документирует, что туда приходит.

## Инкрементальный typecheck

Во всех tsconfig, по которым идёт `typecheck`, включён `"incremental": true`. Файл
`tsconfig.tsbuildinfo` ложится рядом с конфигом и покрыт `.gitignore` (`*.tsbuildinfo`).
Выигрыш крупный и почти бесплатный: `packages/ui` — 10,2 с на холодном кеше против
1,4 с на тёплом, весь `npm run typecheck` — 47 с против 14 с. Ошибки кеш не прячет:
правка файла с ошибкой типа даёт красный прогон за 3 с.

Новый пакет тоже заводится с `incremental` — иначе он один держит гейт на десятки
секунд.

## Новая таблица — сначала владелец

Слой данных разрезан по доменам (`apps/server/src/db/repos/<домен>.ts`), и у каждой
таблицы ровно один репозиторий, которому можно в неё писать. Добавляя таблицу в
`schema.ts`, впиши её в `TABLE_OWNER` в `apps/server/src/db/ownership.ts` и положи
запросы в файл владельца; понадобилось прочитать чужую таблицу — читай через метод
владельца (`this.repos.<домен>.…`), а не `JOIN`, если это не горячий путь доски. Запись
в чужую таблицу гейт не пропустит вовсе: нужно изменить чужие данные — добавь метод у
владельца (как `tasks.unassignUserInProject` для выхода из проекта) и позови его; внутри
одного соединения он выполнится в той же транзакции. Гейт — `ownership.test.ts`, идёт в обычном `npm test` сервера.

## Async-порты БД: ловушки, которых компилятор не видит

После круга 3 (`docs/plans/db-repositories.md`) любой метод `db.<домен>.…` возвращает
`Promise`, и функции, зовущие его, стали `async`. TypeScript ловит забытый `await` только там,
где тип Promise не совпадает с ожидаемым. Молча проходят и обязательно ломаются в рантайме:
`if (!ownsAgent(u, id))` (Promise всегда истинен — проверка обходится), `'run' in result`,
`{ ...kbViewOf(db, u) }` (пустой объект), `` `${kbSummaryLine()}` `` («[object Promise]»),
`return launch()` внутри `try` (отказ уходит мимо `catch`), вызов-инструкция бывшей
синхронной функции без `await` (порядок теряется, ошибка становится unhandled rejection),
`.filter(async …)`/`.some(async …)` (всегда истина) и async-реализация под интерфейсом
`(): void` (`() => Promise<void>` присваивается `() => void`, промис теряется). Меняешь
интерфейс с `void` на `Promise<void>` — проверь каждого вызывающего. Порядок, который
раньше держала синхронность, теперь держится явно: очередь сообщений WS-сокета (`ws.ts`),
замок на выборе рана из очереди (`takeNextWaiter`), `TurnManager.idle()` для хвостов хода.
В тестах: `expect(() => f()).toThrow` → `await expect(async () => f()).rejects.toThrow`,
после события дожидайся хвоста (`await turns.idle()`), не закрывай БД раньше.


## Поток вывода команд пишется в базу через сток с обратным давлением (2026-09-08)

Чанки вывода машины приходят со скоростью сети, а запись в базу асинхронна. `onChunk: async () =>
appendCiLog(...)` без ожидания — это тысячи записей в полёте, каждая со своей копией данных: так ядро на
проде трижды упёрлось в потолок кучи. Правило: любой поток (вывод команды, дельты модели, живой лог шага)
идёт через `createChunkSink(write)` из `ci/chunkSink.ts` — он копит чанки, пишет их одной записью не чаще
интервала и держит не больше одной записи в полёте; в конце — `await sink.flush()`. Живой лог, который
переписывается целиком (`setProjectReleaseStep`), — только через сток с интервалом ≥ 1 с, и событие
таймлайна — на смену статуса, а не на каждое обновление лога.

## Репозитории асинхронны внутри — правила слоя данных (2026-09-07)

Репозитории `apps/server/src/db/repos/*` ходят в базу через адаптер `this.sql` (`db/sql/`), а не
через `better-sqlite3`; SQL — в диалекте SQLite с `?`, различия движков закрывает адаптер
(`docs/plans/db-postgres.md`). Отсюда правила:

- **Новый метод репозитория — `async`**, каждая операция под `await`: `await this.sql.get(...)`,
  `await this.repos.projects.isProjectMember(...)`. Промис как параметр запроса компилятор не
  поймает (`SqlParam = unknown`) — гоняй аудит `promise-audit.mjs` из журнала круга или смотри
  глазами: `[.., this.someAsync(...)]` без `await` уедет в базу строкой `[object Promise]`.
- **Циклы вместо async-колбэков**: `rows.forEach(async …)` не ждёт тел, `filter(async …)` оставляет
  всё (промис истинен), `find(async …)` берёт первый. Пиши `for (const [i, row] of rows.entries())`,
  для параллельных чтений — `await Promise.all(rows.map(async …))`.
- **Транзакция — `await this.sql.transaction(async () => …)`**; внутри не ждать внешних событий
  (сеть, таймеры, колбэки сервера): у SQLite остальные запросы процесса стоят до её конца.
- **Многошаговый метод атомарен только на SQLite** — благодаря полосе (`db/sql/lane.ts`),
  методы через порты идут по одному. На Postgres этой гарантии нет: если метод читает, а потом
  пишет на основании прочитанного, оборачивай в транзакцию или опирайся на ограничения базы.
- **SQL пишется в диалекте SQLite и должен пройти транслятор** (`db/sql/dialect.ts`): `?`/`@name`,
  `INSERT OR IGNORE`, `IFNULL`, `LIKE`, скалярные `MAX/MIN`, `rowid` — можно; JSON1 и `strftime` —
  только через хелперы по движку (`ChatRepo.j`); алиасы лучше snake_case; в `ON CONFLICT … DO UPDATE`
  ссылки на текущую строку — голым именем колонки (транслятор квалифицирует). Новая таблица или
  колонка — в `schema.ts` (Postgres строится из него), ALTER в `migrate()` — вдобавок, для старых файлов.
  Проверка на втором движке: `VC_TEST_DB_URL=postgres://… npx vitest run` при поднятом контейнере.
- **Тесты**: сырой драйвер (`(db as { db }).db`) и второй `VoiceChatDb` на том же файле — после
  `await db.ready`; `await db.close()`; с изменяемыми часами (`now: () => clock`) каждый вызов
  порта под `await`, иначе тело прочитает уже переставленные часы. Подмена метода —
  `db.impl.<домен>.<метод> = async () => …` (алиас `db.sync` оставлен).

## Гейт шага

Ни один шаг не считается готовым, пока не зелёные `typecheck` и `test` затронутых
пакетов; где менялась сборка/UI — плюс `build`. Планы в `docs/plans/` написаны
именно так: шаг → изменения → тесты → критерии. Если делаешь фичу по такому
плану, отмечай прогресс в его чек-листе.

## Коммиты

Use Conventional Commits with a scope and an **English description**:
`feat(agent): support Android installation with Termux`,
`fix(ui): correct the collapse icon`, `docs(console): record progress`.
Keep one coherent change per commit and include its knowledge-base updates.

Ветка по умолчанию — `main`, работа ведётся прямо в ней. Коммит и push делаются
**только по просьбе пользователя**.

Перед анализом или разработкой рабочая копия сверяется с origin: сначала
`git status --short --branch`, затем `git fetch origin`. Чистую `main`, которая
только отстаёт, агент обновляет командой `git pull --ff-only origin main`. Dirty
worktree, разошедшиеся истории и другая текущая ветка — причины остановиться и
запросить решение, а не делать reset, checkout или переносить чужие изменения.
До обновления разрешён read-only анализ `origin/main`, если в результате явно
сказано, что checkout устарел.

## Гейт нельзя объявлять зелёным по выводу команды

Проверять надо **код возврата**, а не наличие строк в выводе. Формулировка вида

```bash
npm run typecheck 2>&1 | grep -E "error TS" | head -3; echo "typecheck ok"
```

печатает «ok» всегда: `echo` выполняется независимо от результата, а `grep` в
конвейере ещё и подменяет код возврата. Так `apps/browser-runner` пять кругов
подряд не проходил typecheck (`document` в замыкании `page.evaluate` — у пакета
нет библиотеки DOM), а отчёты говорили «гейт зелёный». На поведение это не
влияло: ошибка была в тестовом файле, а раннер запускается через `tsx`, который
не типизирует. Но дыра пропустила бы и настоящую ошибку.

Правильно — **`npm run gate`**: планировщик определяет приложения по диффу ветки,
запускает их проверки и останавливается при ненулевом коде. `gate:fast` использует
дифф рабочего дерева от HEAD. `gate:app -- make` явно проверяет Make целиком;
`gate:all` запускает полный typecheck/test и сборки web/витрины. `verify` дополнительно
проверяет клиентские дистрибутивы и нужен для общего релиза.

Владельцы путей, зависимости сборки, runtime и контрактные наборы раздельно заданы
в `packages/shared/src/applicationCatalog.ts`. Внутренние изменения отделённого
приложения не втягивают все тесты ядра. Публичные контракты добавляют адресные мосты,
библиотеки — потребителей по графу. Lock diff проверяется с обеих сторон по npm-дереву;
неизвестный пакет, root-конфиг или неразрешимый diff включает `gate:all`.
`--dry-run` выводит выбор без запуска. Для старых CI-команд `npm run affected-check`
теперь является именем нового планировщика; старый JS-граф оставлен для общей
embedded-композиции и сравнительных тестов. Сохранённые пользовательские команды
не переписываются.

E2E приложения запускаются по его каталогу. Для самостоятельных UI-панелей
`applicationFrontend.e2e.test.ts` использует fixture host и выбирает только их id;
web-оболочка не пересобирается. Backend E2E использует собранный интеграционный
web-стенд. Публичный контракт добавляет typecheck потребителя и адресные тесты;
пустой контрактный набор отклоняется. Полный fallback сохраняет каталоговые E2E
после широких typecheck/test/build. Самостоятельный Docker backend не включает
исходники и сборку этого тестового web-стенда.
