# Исполнители LLM: контейнеры с claude/codex CLI

`spawn` CLI уезжает из контейнера сервера в отдельный процесс — **исполнитель**
(`apps/llm-runner`). Мотив не в изоляции ради изоляции: под одной установкой
Claude Code нельзя одновременно держать рабочую и личную подписку, а CLI ещё и
делят с сервером лимит памяти, которого не хватает STT-моделям. Полный замысел с
реестром исполнителей и выбором в UI — `docs/plans/llm-runners.md`; здесь описано
то, что уже есть в коде.

## Что сделано (срез 1) и что ещё нет

Воркспейс `apps/llm-runner` поднимает Fastify с `/v1/run`, `/v1/run/:id` и
`/v1/health`. Туда же **физически переехали** `claudeCli.ts`, `codexCli.ts`,
`childKill.ts`, `mcp.ts` (`claude mcp list`) и `cliProfiles.ts` — сервер их больше
не содержит.

Сервер при этом **ещё вызывает CLI сам**: `server.ts` и `routes/rest.ts`
импортируют классы из `@voicechat/llm-runner/cli`, то есть зависимость
`@voicechat/server` → `@voicechat/llm-runner` пока прямая, а не HTTP. Это
временно: `RemoteLlmClient` (срез 2) заменит вызовы на `POST /v1/run`, и импорт
уйдёт. Пока ходы работают как раньше — исполнитель поднимается, но в бою не
участвует, компоуз-сервиса у него нет.

## Контракт живёт в shared

`LlmRequest`, `LlmClient`, `LlmStreamHandlers` переехали из
`apps/server/src/claude/types.ts` в `packages/shared/src/llm.ts`: у контракта два
берега — промпт собирает сервер, argv по нему собирает исполнитель.
`claude/types.ts` остался реэкспортом, чтобы десятки импортов сервера не менялись.
Там же — `LlmRunBody` (тело `/v1/run`), кадры `LlmRunFrame`, `parseLlmRunFrame`,
`LlmRunnerHealth`, пути `LLM_RUNNER` и заголовок `x-run-id`. Туда же ушёл
`kbToolHint`: системный хинт про `mcp__kb__*` попадает в argv, а argv собирает
исполнитель.

## Исполнитель ничего не разбирает

`POST /v1/run` отдаёт NDJSON из сырых строк: `{t:'out',s}` — строка stdout,
`{t:'err',s}` — stderr, `{t:'exit',code}` — конец. `stream-json` Claude и JSONL
Codex парсит сервер (`packages/shared/src/streamJson.ts`, `codexStream.ts`), и это
намеренно: иначе смена формата вывода CLI ломала бы протокол, а исполнителя
пришлось бы разворачивать синхронно с сервером.

Отсюда требование к транспорту: Fastify-ответ **захватывается**
(`reply.hijack()`), строки пишутся в сырой `ServerResponse` по одной, заголовки
выталкиваются сразу (`flushHeaders`), Nagle выключен. Иначе живой стрим ответа
собрался бы в буфер и приехал в браузер целиком после конца хода.

`claudeArgs(req)` и `codexInvocation(req)` вынесены из CLI-классов и вызываются
двумя путями (класс с разбором и сырой ран), чтобы сборка argv и добавки к
системному промпту не разъехались в двух копиях.

`LlmRequest.cwd` и `LlmRequest.attachments` теперь трактуются исполнителем, а не
сервером. `cwd` приходит как желаемый каталог: `RunManager` проверяет его уже на
хосте исполнителя и при несуществующем пути просто не передаёт `cwd` в `spawn`,
вместо того чтобы уронить запуск `ENOENT`/`EACCES`. Вложения сервер шлёт байтами
(`serverPath`, `runnerName`, `dataBase64`), а `prepareRun()` раскладывает их во
временный каталог `voicechat-llm-run-*`, подменяет в prompt все вхождения
`serverPath` на локальные пути этого каталога и удаляет каталог при нормальном
завершении, отмене, обрыве клиента и даже если `spawn` бросил исключение. Так
удалённый CLI видит реальные файлы своей машины, хотя prompt собирался по путям
ФС сервера.

## Ран не переживает своего клиента

Отмена — `DELETE /v1/run/:id`: `killCliChild` (SIGTERM, через 5 с SIGKILL).
`{stopped:false}` значит «такого рана уже нет», это не ошибка: повторная отмена
безопасна, а сервер зовёт её и после самостоятельного завершения хода.

Два механизма против брошенного процесса:

- **обрыв соединения** (`close` на ответе) гасит CLI сразу — обычный случай
  перезапуска сервера;
- **таймаут-сирота**: если кадр лёг в буфер сокета и клиент не вычитал его
  `VC_RUNNER_ORPHAN_MS` (30 с), исполнитель убивает CLI сам. Живой, но не читающий
  клиент по-другому не детектируется, а брошенный ход жжёт токены подписки до
  конца разговора модели с собой.

Повторный `POST /v1/run` с уже живым `runId` — 409 `run_exists`: иначе второй
процесс занял бы тот же адрес, и первый остался бы без способа его погасить.

`id` рана известен клиенту до первого байта вывода (заголовок `x-run-id`, а лучше
свой `runId` в теле) — иначе отменить ход, пока модель думает, было бы нечем.

## Доступ и профили

Весь `/v1/*` закрыт одним Bearer-токеном (`VC_RUNNER_TOKEN`, сравнение за
постоянное время). Пользователей у исполнителя нет: клиент один — сервер, токен
лежит в его реестре. Без токена процесс не стартует: открытый `/v1/run` — это
shell на машине.

Профили CLI (`cli-users/<base64url(логин)>` внутри `VC_DATA_DIR`) живут внутри
исполнителя; сервер передаёт `userId`, о путях не знает. `GET /v1/health` отдаёт
бинари, версии, статус входа обоих CLI и число живых ранов; `ok` — «есть хотя бы
один рабочий бинарь», потому что личный исполнитель несёт только `claude`.
