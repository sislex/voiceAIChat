# CI-раннер канбана

Выполнение переиспользуемых серверных команд вокруг работы модели одной кнопкой
«Выполнить» на карточке задачи: команды слота **до** → работа модели → команды
слота **после** → резюме модели. Один **ран** с общим статусом, единой лентой,
потоковым логом, метриками длительности, fix-loop и диагностической консолью.
Заменил Feature Run полностью: UI, маршруты, координатор, контракт `features:*` и
таблицы `features`/`feature_events`/`agent_tasks`/`feature_deployments`/`repository_slots`
удалены (миграция сносит их при старте). Корень рабочих копий — `project_machines.repos_root`.

## Модель данных

Таблицы `ci_*` в `db/schema.ts`: `ci_commands` (справочник, soft-delete,
версия текста, `is_test` — команда-проверка), `ci_slot_commands` (привязка к слоту для проекта/задачи с
наследованием), `ci_runs`, `ci_run_steps` (kind: command/model_work/model_command/
model_summary, `parent_step_id` для вложенных вызовов), `ci_run_logs` (монотонный
`seq` для реплея после reconnect; `ci_runs.llm_provider/llm_model` фиксируют выбор модели),
`ci_run_usage` (расход модели по ходам — см. «Отчёт по задаче»), `ci_fix_attempts`, `ci_workspaces`,
`ci_command_suggestions` (группировка по причине), `ci_events` (аудит), `ci_settings`
(единственная строка глобальных настроек). CI-поля проекта (`ci_base_branch`,
`ci_branch_template`, `ci_reuse_strategy`, `ci_exec_auth_ref`) добавляются в
`migrate()`. Доступ — по членству проекта; CI-админ = владелец проекта.

## Выполнение

`createCiRunManager` (`ci/runManager.ts`) — процесс-глобальный менеджер по образцу
`TurnManager`: прогон слот-за-слотом, общая FIFO-очередь сервера по лимиту
`maxConcurrentRuns` (раны разных задач идут **параллельно**, см. ниже), отмена,
откат Task в `prev_column_id` при Исходе B,
`is_cleanup`/`allow_failure`/таймаут. Перед **любой** `is_cleanup`-командой раннер
вставляет системный шаг «Отправить ветку задачи в origin» (`pushTaskBranch`):
cleanup удаляет рабочую директорию вместе с коммитами модели, поэтому без пуша
результат рана терялся безвозвратно. Скрипт идемпотентен (нет новых коммитов —
ничего не делает), при незакоммиченных изменениях падает с кодом `69`, и тогда
cleanup **не выполняется**: ран становится `failed`, а рабочая копия остаётся на
машине. Модели в промпте сказано коммитить в `$BRANCH` и не пушить самой.

Рабочая копия, оставшаяся от **упавшего или отменённого** рана этой же задачи,
чинится сама: системный шаг «Подготовка рабочей директории» нового полного рана
видит `<workspace>/<slug>/.git` и приводит копию в чистое состояние
(`git stash push --include-untracked` → `reset --hard` → `clean -fd`; stash
оставляет работу восстановимой). Без этого следующий запуск падал на шаге
клонирования с exit `66`, и «починили → запустили снова» требовало ручного
«Откатить изменения и повторить», а карточка снова светилась красным. Стратегия
`clean` сносит папку целиком (чинить нечего), стратегия `fail` по-прежнему
защищает от **чужого** содержимого — но своя копия задачи под её запрет не
попадает, иначе повтор после падения был бы невозможен в принципе. Exit code `66`
остаётся страховкой на остальные случаи: ран останавливается, UI требует явного
подтверждения, затем `discardChangesAndRetry` выполняет `git reset --hard` +
`git clean -fdx`, пишет аудит и запускает новый полный ран. Команды выполняются на машине по умолчанию
проекта через `AgentCommandExecutor` (`ci/executor.ts`) поверх нового
`AgentRegistry.execStream` — потоковый форвард `exec.chunk` (агент не пересобирается);
cwd/env собираются с shell-escape (пользовательский ввод — только через env, не
конкатенацией). Секреты маскируются в логе.

## Параллельные раны

Раны **разных задач** одного проекта выполняются одновременно в пределах
`maxConcurrentRuns`; очередь при исчерпании лимита остаётся FIFO. Работает это
только потому, что раны изолированы по построению: рабочая директория —
`{repos_root}/{project}/{task_number}`, ветка — по шаблону
`feature/{task_number}-{slug}`, npm-кэш — `{repos_root}/.npm-cache/{project}-{task_number}`.
Инвариант закреплён проверкой на старте `execute`: если папку или ветку уже занял
другой активный ран (сломанный шаблон ветки, совпавший номер задачи), ран не
начинает работу — в ленте появляется шаг «Проверка изоляции рабочей директории»
со статусом `failed`, в аудите — `run.isolation_conflict`.

**Один активный ран на задачу.** `start`, `retryFromFailed` и
`discardChangesAndRetry` отказывают, пока у задачи есть незавершённый ран
(REST отвечает 409): два рана одной задачи неизбежно делили бы папку и ветку.

**Мьютекс общих ресурсов.** Шаги, которые трогают общее для всей машины —
«Влить ветку задачи в прод-ветку» (пишет в прод-ветку: параллельный `push`
отбивается) и «Обновить прод-контейнер», — раннер пропускает по одному.
Признак системный: `isSharedResourceCommand(command)` смотрит на назначение
(название/скрипт), а не на подпись команды в конкретном проекте — теми же
предикатами, что `isMergeToBaseStep`/`isProdRebuildStep`. Мьютекс берётся внутри
`runCommandStep`, поэтому закрывает и шаги слота, и команды, вызванные моделью
через MCP. Пока ресурс занят, шаг ждёт (в лог падает строка «жду, пока его
освободит другой ран»), а очередь за мьютексом — FIFO. Отмена рана снимает его
из очереди за мьютексом, а закрытие рана (в том числе принудительное по
сторожевому таймауту) отпускает мьютекс за зависший `execute`.

## Куда уезжает карточка после рана

После финализации карточка оказывается ровно в одном из состояний — решает
`settleTaskColumn` **одним** `moveTask` (двойной перенос дёргал бы доску лишним
`board.update`):

| Исход рана | Куда уезжает карточка |
| --- | --- |
| успех, мерж-шаг `success` | колонка с semantic type `done` («Готово») |
| успех, мержа не было (шага нет, упал, пропущен) | `awaiting_merge` («Ожидает мержа») |
| `failed` / `cancelled` / `timeout` | обратно в `prev_column_id` (`rollbackTask`) |
| нужной колонки в проекте нет | карточка остаётся где была |

Успешный ран сам по себе ещё не «Готово»: без мержа работа модели есть, ветка
запушена, а в прод-ветке её нет — и это должно быть видно на доске, а не
прятаться в «Готово». Зато **влитая** ветка — это и есть закрытая задача, поэтому
терминальный статус прошлого рана следующий успешный не переживает: «упало →
починили → запустили снова» доводит карточку до done, а не оставляет её с красным
лозенгом. То же верно для «Повторить с упавшего шага» (`retryFromFailed`): повтор
сначала возвращает карточку в `development` — как `start()`, — и заканчивается тем
же переносом, что и новый ран.

Факт мержа определяется по шагу рана (`isMergeToBaseStep`: `kind`
`command`/`model_command`, название «влить»/«merge» либо `git merge` в снапшоте
скрипта), а не по подписи колонки — пайплайн команд это данные проекта. Колонка
ищется по semantic type. Пуш ветки отдельно не проверяется: неудачный «Отправить
ветку задачи в origin» закрывает ран как `failed`, и до переноса дело не доходит.

Порядок в финализации важен вдвойне: `settleTaskColumn` зовётся строго **после**
`postSummaryMessage` (перенос в done убирает чат задачи из списка бесед — иначе
резюме уехало бы в уже скрытый чат) и **до** `queueProdRebuild` (тот ищет открытую
карточку «Пересборка прода» по названию, и наша карточка ему не мешает).
Скрытие завершённых по `done_retention_days` при пороге `0` теперь означает «до
конца дня», а не «в ту же секунду» — [projects.md](../projects.md#завершённые-задачи-уходят-с-доски-как-в-jira).

## Мерж без пересборки прода

Зеркальный случай: мерж прошёл, а прод в этом ране не пересобирался (шага нет,
он упал или был пропущен) — код в прод-ветке, а на проде его нет. Финализация
успешного рана (`queueProdRebuild`) заводит в проекте автозадачу учёта:
`ensureProdRebuildTask` держит ОДНУ открытую (не в done-колонке) карточку
«Пересборка прода» в колонке `ready`, тип `task`, без исполнителя; описание —
список строк `- KEY-N: заголовок задачи`, по строке на вмерженную задачу. Всё в
транзакции и идемпотентно: повторный ран той же задачи строку не дублирует,
уехавшая в done карточка не переиспользуется (следующий мерж заводит новую), нет
колонки `ready` — карточка не заводится. Саму пересборку раннер не запускает.
Шаг пересборки узнаётся по назначению (`isProdRebuildStep`): название про прод +
обновление/пересборку либо `docker compose up --build` / `npm run docker` в
снапшоте скрипта. В текущей docker-раскладке такой шаг обязан поднимать не
только `voicechat`, но и `runner-work`/`runner-personal`. В ленте рана остаётся
строка о добавлении, в аудите — `run.prod_rebuild_pending`.

Саму карточку обычно закрывают раном по ней же, а он идёт на том же хосте, что и
прод: как пересобирать, не убив собственный ран, — [deploy.md](../deploy.md#пересборка-прода-изнутри-рана-собрать-сразу-поднять-отложенно).
Карточка — след факта, а не состояния прода: обновление прода вне рана её не
снимает, поэтому ран по ней начинают с проверки, что нужный коммит на проде уже
есть, — [deploy.md](../deploy.md#прод-мог-обновиться-и-без-рана-сначала-проверь-потом-пересобирай).

## Отмена рана

`POST /api/ci/runs/:runId/cancel` → `CiRunManager.cancel`: строка в ленте
(«Отмена рана: останавливаю шаг…»), аудит `run.cancel_requested`, `abort()` у
`AbortController` рана и снятие возможной паузы. Дальше сигнал доходит до всех
уровней исполнения, и это главное отличие от прежнего поведения:

- **Команды шага** — `signal` уже был у `executor.run` → `AgentRegistry.execStream`
  шлёт агенту `exec.cancel`.
- **Работа модели** — `runTurn` (`ci/modelHooks.ts`) слушает `ctx.signal`
  (`CiRunPrimitives.signal`), вызывает `LlmHandle.cancel()` и **сам** закрывает
  промис хода: `cancel()` в клиенте глушит `onDone/onError`, поэтому раньше
  `execute` навсегда висел на этом `await`, ран оставался `running`, а очередь
  проекта (`projectChains`) стояла до перезапуска сервера. `modelWork` возвращает
  `{ ok: false, cancelled: true }`, `attemptFix` выходит из fix-loop.
- **Процесс CLI** — `killCliChild` (`apps/llm-runner/src/cli/childKill.ts`, общий для claude и
  codex): SIGTERM, через 5 с SIGKILL. Заодно обрывается MCP-запрос remote-bash,
  и его команда на машине отменяется по `close` ответа.
- **Дерево процессов на машине** — `exec.cancel` у агента снимает **группу**
  процессов (`killProcessTree`, `apps/agent/src/exec.ts`: команда запускается
  `detached`, сигнал уходит на `-pid`; Windows — `taskkill /T`). Раньше SIGTERM
  получал только shell, а `npm ci`/тесты продолжали работать сиротами. Правка
  живёт в бандле агента — на машинах она появляется после переустановки/рестарта
  компаньона.

Ран закрывается как `cancelled` (не `failed`) на любой стадии: в очереди (шагов
не появляется вовсе), в слоте команд, в фазе модели; карточка возвращается в
`prev_column_id`. Ран **из очереди** закрывается прямо в `cancel`, не дожидаясь
своего слота: иначе он висел бы `queued` до конца чужого рана, а карточка после
«Отменить» показывала «в очереди».

Задачу отменённый ран отпускает сразу: `hasActiveRunForTask` пропускает
закрывающиеся раны (`isClosingRun` — поднятый `abort` или терминальный статус в
БД), поэтому «Выполнить» сразу после «Отменить» стартует новый ран, а не отвечает
«Для этой задачи уже выполняется ран». Папку и ветку подвисший исполнитель может
держать ещё несколько секунд — новый ран не валится конфликтом изоляции, а ждёт
их освобождения (фаза «Жду освобождения рабочей директории», не дольше
`cancelGraceMs` + 1 с) и только потом сдаётся.

Сторож `guardCancel`: если `execute` не завершился за
`cancelGraceMs` (15 с, в тестах короче) после `abort`, `hardCancel` закрывает
незавершённые шаги и ран (`run.cancel_forced`), отпускает серверный слот и
**звено `projectChains`** — очередь проекта едет дальше даже с подвисшим
исполнителем. Подвисший `execute`, догребший до конца позже, ран уже не
перепишет: `finalize` не меняет статус `cancelled` ни на что другое.

## Изоляция кэша npm

Все раны идут на одной машине под одним пользователем, поэтому общий `~/.npm`
ломался, когда два `npm ci` работали одновременно: `EEXIST` при `rename` в
`_cacache/content-v2`, затем `ENOENT` на `stat` — шаг падал с кодом **254**, и
ретраи не помогали, пока кэш не чистили руками. Раннер даёт каждой задаче свой
кэш: в env шага уходят `NPM_CACHE_DIR` и `npm_config_cache` =
`$REPO_ROOT/.npm-cache/$TASK_KEY`. Каталог создаётся системным шагом «Подготовка
рабочей директории», там же `touch` (отметка «использован») и удаление кэшей, к
которым не ходили две недели. Кэш лежит **рядом** с рабочими копиями, а не внутри
рабочей директории: её сносит `is_cleanup` в конце рана, и каждый повтор качал бы
пакеты заново.

## Инфраструктурные ошибки шага

`classifyCiInfraFailure` (`ci/infraErrors.ts`) смотрит хвост вывода упавшего шага
и отличает сбой машины от ошибки задачи: повреждённый кэш npm (`EEXIST`/`ENOENT`/
`EINTEGRITY` в `_cacache`) и `ENOSPC`. Такой шаг **не идёт в fix-loop** — в
рабочей копии он не лечится, а модель уводит диагностику в проект (реальный
случай: три хода opus на `TAR_ENTRY_ERROR` от битого кэша). Вместо этого в лог
шага пишется диагноз с подсказкой («почистить кэш», «кэш изолирован не был»),
в аудит — `run.infra_error` с `kind`, фаза рана называет причину, и ран падает
сразу.

## Стандартный пайплайн проекта

Справочник команд — это **данные** (`ci_commands` + `ci_slot_commands`), дефолтов в
коде нет: набор и порядок задаются в UI на проекте. Рабочий пайплайн ChatAI —
разработка доезжает до прода одним раном:

**Слот «до модели»**

1. **Клонировать репозиторий задачи** — `git clone --branch $BASE_BRANCH
   --single-branch`; существующая копия с локальными правками → exit `66`
   (dirty workspace, дальше решает пользователь).
2. **Установить зависимости (npm ci)**.

**Слот «после модели»**

3. **Запустить проверки (typecheck + npm test)** — `npm run typecheck && npm test`,
   единственный прогон гейта в ране. Типы проверяются раньше тестов: vitest гоняет
   код через свой трансформер и ошибку типов пропускает, так что без `typecheck`
   она уезжала в `main` и всплывала следующим раном как чужое падение.
   Модель гейт сама не запускает (см. «Модель в цикле»), а упавший шаг крутит
   цикл «правка модели → повтор шага» до зелёного в пределах `maxFixAttempts`
   (3) и `fixTimeLimitMs` (10 мин). Зелёный — ран идёт дальше по слоту (4→9);
   попытки кончились — ран `failed`, диагнозы попыток видны в ленте.
4. **Актуализировать базу знаний** — встроенный серверный шаг (ниже).
5. **Закоммитить работу в ветку задачи** — `checkout -B $BRANCH`, `add -A`, коммит
   `«$TASK_KEY: работа CI-рана»`. Модель обычно коммитит сама, поэтому чистое
   дерево — это выход 0, а не ошибка.
6. **Отправить ветку задачи в origin** — `push HEAD:refs/heads/$BRANCH`, при
   разошедшейся ветке — `--force-with-lease`.
7. **Влить ветку задачи в прод-ветку** — `checkout -B $BASE_BRANCH
   origin/$BASE_BRANCH`, `merge --no-edit`, `push`. Конфликт — обычный упавший
   шаг: останавливает ран и попадает в fix-loop.
8. **Обновить прод-контейнер** — env шага: `PROD_DIR=/root/voiceAIChat`,
   `PROD_BRANCH=main`, `PROD_REBUILD_DELAY=180`, лог
   `/tmp/voicechat-prod-rebuild.log`. Git-часть (проверка на локальные изменения →
   exit `70`, затем `fetch`/`checkout`/`pull --ff-only`) идёт синхронно, чтобы
   ошибки были видны в ленте, а сам подъём `docker compose up --build -d
   voicechat runner-work runner-personal caddy` уходит в отдельный сеанс
   (`setsid nohup`) с задержкой — шаг возвращает 0 сразу. Иначе шаг убил бы контейнер, в котором работает сам раннер, и ран не
   успел бы закрыться (резюме модели идёт до минуты). Задержка = запас на резюме
   и cleanup; `PROD_DIR` общий с чат-сессиями, поэтому dirty-check обязателен.
   Но dirty-check ловит только **незакоммиченное**: чат-сессия, которая закоммитила
   в `PROD_DIR` и не запушила, проходит его с чистым деревом, а `pull --ff-only`
   потом падает с `fatal: Not possible to fast-forward` (`128`) — ветки разошлись,
   как только ран запушил свой мерж на шаге 6. Лечится это в прод-каталоге (поднять
   локальный коммит в `origin/main`), а не заменой `--ff-only` на merge/rebase:
   прод должен быть линейным продолжением `origin/main`. Правило для сессий —
   [deploy.md](../deploy.md#прод-каталог-заодно-рабочая-копия--коммит-там-пушится-сразу).
9. **Удалить рабочую папку задачи** (`is_cleanup`) — перед ней раннер сам пушит
   ветку задачи (см. «Выполнение»), так что терять уже нечего.

Модели как MCP-инструмент доступен только `npm ci`: тесты, коммит, пуш, мерж и
обновление прода — шаги воркфлоу, не инструменты. Раньше гейт прогонялся дважды
(модель внутри своего хода + шаг 3), что удваивало время рана, а расхождение
между прогонами модель чинила вслепую.

Внутри модельного хода исходники читаются специализированным remote-MCP
инструментом `read` (оконно, с номерами строк), ищутся через `grep`, а точечные
замены выполняются `edit`. Директива рана прямо запрещает использовать `bash`
для чтения файлов и правок heredoc; `bash` остаётся для команд вроде `git`,
`npm` и шагов проверки. Все файловые пути считаются относительно workspace
рана. В plan-фазе `read`/`grep` работают, а `edit` отклоняется.

## Актуализация базы знаний (встроенный шаг)

База знаний не должна устаревать, поэтому запись в неё — шаг воркфлоу, а не
добрая воля модели. `ci_commands.builtin = 'kb_update'` (константы
`CI_KB_UPDATE_COMMAND_ID`/`CI_KB_UPDATE_COMMAND_NAME` в `shared/src/ci.ts`) —
единственный вид команды справочника, чей `script` не исполняется: `runSlot`
видит признак и вместо `executor.run` зовёт серверный хук `kbUpdate`
(`ci/modelHooks.ts`, общий код — `kb/codeUpdate.ts`). Строка справочника нужна
ради настроек: шаг двигается внутри слота и убирается из проекта или задачи тем
же редактором слотов, что и обычные команды. Модели как инструмент он не
предлагается (`available_to_model = 0`). Команда заводится миграцией; при её
первом появлении она встаёт в слот «после модели» всех проектов **перед** шагом
коммита (`isCommitStepLike` по назначению, не по подписи) — правки `docs/kb/*`
должны уехать тем же коммитом, что и код. Убранный руками шаг миграция обратно
не возвращает.

Внутри шага: сервер собирает диф (`KB_DIFF_SCRIPT` — `git diff` **рабочего
дерева** к `origin/$BASE_BRANCH`, потому что шаг идёт до коммита; патч без
`package-lock.json` и сгенерированного индекса, кап 100 000 символов), выбирает
статьи раздела проекта, чьи `areas` пересекаются с путями дифа
(`pickAffectedDocs`), и делает один ход модели с remote-bash в рабочей копии.
Файловые темы `docs/kb/*.md` модель правит сама (там же `kb.mjs touch`,
`kb:log`, `kb:index`), статьи `scope='project'` возвращает JSON'ом — их пишет
сервер через `db.saveKbDocument`, как в «Исследовать проект».

Устойчивость важнее полноты: ошибка сбора дифа, неразборчивый ответ, исключение
хука и таймаут (10 минут, `KB_UPDATE_TIMEOUT_MS`) ран **не валят** — шаг
закрывается как `skipped` с предупреждением в ленте. Работа модели к этому
моменту уже сделана, терять её из-за базы знаний нельзя. Пустой диф — успех с
записью «нечего обновлять», хода модели при этом нет вовсе.

Ручной фолбэк — «Исследовать проект» с телом `{ sinceSha }` (`kb/research.ts`):
тот же промпт (`kbUpdatePrompt`), но диф модель собирает сама и файлы не правит —
рабочая копия проекта общая для чат-сессий.

## Режим запуска и глубина уточнений

`CiLlmConfig` несёт не только `provider`/`model`, но и `mode` (`plan`|`development`),
`clarifyLevel` (`none`|`few`|`medium`|`detailed`) и `clarifyMax` (1..30, только для
`detailed`); бюджет вопросов считает `clarifyBudget()`. Наследование то же, что у
движка: задача → проект → `DEFAULT_CI_LLM_CONFIG` (`resolveTaskLlmConfig`), правится
в `CiTaskSettings` (под выбором модели) и `CiProjectDefaults`. Выбор снимком
фиксируется в `ci_runs.mode/clarify_level/clarify_max`, поэтому повтор рана его
сохраняет; `POST …/ci/run` принимает разовый `{ mode }`.

## Пауза рана: вопросы модели и одобрение плана

Один механизм на оба случая — таблица `ci_interactions` (`kind: clarify|plan_approval`)
и нетерминальный статус рана `awaiting_input`. Работа модели (`modelWork`) —
фазовый цикл ходов CLI в **одной сессии**: `runTurn` захватывает `onSession`, и
следующий ход идёт с `--resume`/`codex resume`. В режиме `plan` первый ход идёт
**не** в CLI-режиме `plan` (он глушит MCP целиком — «Cannot call mcp__remote__bash
while in plan mode», а рабочая копия доступна модели только через remote MCP), а в
`permissionMode: 'default'` с белым списком инструментов: правки файлов CLI отклоняет
сам, remote-bash подключается с `&ro=1` (только чтение, `mcp/planMode.ts`), команды
CI-справочника в план-фазе не публикуются. Затем гейт `askPlanApproval`: `approved`
переводит тот же диалог в `acceptEdits` (слот «после» и резюме идут как обычно), `rework` даёт
модели комментарий и новый план, отсутствие решения (таймаут/отмена) завершает ран
как `cancelled` без слота «после». Уточняющие вопросы разбираются существующим
`parseQuestions` из `@shared/questions` — нового формата нет.

Раны переживают только свой процесс: при старте `buildServer` вызывает
`db.failInterruptedCiRuns()` — раны в `queued`/`running`/`awaiting_input` от прошлого
процесса закрываются как `failed` (незавершённые шаги — `failed`/`skipped`, ожидание
ответа снимается). Иначе после рестарта контейнера карточка задачи навсегда считала
бы CI занятым.

Ожидание **отпускает серверный слот** (`releaseSlot`/`acquireSlot` вокруг await):
одобрение плана может длиться часами, а `maxConcurrentRuns` по умолчанию 2. Слот
привязан к рану (`RunSlot`), а не к вызову: если ран за время паузы закрыли
(в том числе сторожевым таймаутом отмены), зомби-`execute` слот обратно не
берёт — иначе лимит утекал бы по слоту на ран. Лимит ожидания —
`CiGlobalSettings.interactionWaitMs` (30 мин, `0` — без лимита); по таймауту
для `clarify` модель продолжает без уточнений, для гейта плана ран отменяется.

Вопрос дублируется в **связанный чат задачи** обычным AI-сообщением с блоком
```` ```questions ```` и меткой `TurnMeta.ciInteraction` — `ChatColumn` рисует его
готовым `QuestionsForm`, нового UI в чате нет. Ответить можно из ленты или из чата,
побеждает первый (`answerCiInteraction` обновляет строку только пока она `pending`,
повторный ответ — 409). Сервер дописывает ответ репликой в тот же чат.
REST — `POST /api/ci/runs/:runId/interactions/:id`, WS — `ci.interaction`,
`CiRunDetail.interactions` нужен для реплея после reload.

## Резюме рана в связанном чате

Шаг «Резюме модели» не только пишется в лог рана, но и уходит **отдельным
AI-сообщением в связанный чат задачи** (`postSummaryToChat` в `CiRunManagerDeps`,
проводка — в `server.ts`): работу обсуждают в чате, а лента рана служебная и
перекрывается следующим запуском. Текст = шапка `Резюме по задаче <PRJ-N> · <заголовок>`
плюс текст модели; метка `TurnMeta.ciRunSummary = { runId }` отличает его от ответа
хода. Сообщение появляется при любом исходе, где шаг резюме вообще выполнялся
(в том числе при упавшем слоте «после»); отмена рана резюме не даёт. Чат удалён —
`addMessage` бросает, дep возвращает `null`, ран это не роняет.

Кадр `chat.message` (`{ conversationId, message }`) рассылается тем же каналом,
что события рана (`CiRunManager.subscribe` → `session.ts` → сокеты владельца), мост —
`window.ci.onChatMessage`, стор — `applyChatMessage` (дописывает через
`appendPersisted`, только если этот чат открыт; дубли по `id` отбрасываются).
Имя нового связанного чата — «Задача <заголовок>», см. [projects.md](../projects.md).

## Модель в цикле

`createCiModelHooks` (`ci/modelHooks.ts`) на инъектируемом `LlmClient`: работа
модели (remote-bash MCP в рабочей папке, многоходовый цикл с паузами, предел
`MAX_MODEL_TURNS`), резюме, fix-loop (диагноз→правка→повтор
упавшего шага, лимиты `maxFixAttempts`/`fixTimeLimitMs`, предложения по правке
скрипта). URL для `remote-bash`, `ci-commands` и `kb` сервер теперь строит одной
функцией `buildPublicMcpUrl` (`apps/server/src/mcp/publicBase.ts`): с
`VC_MCP_PUBLIC_BASE` исполнитель получает публичный адрес Fastify вроде
`http://voicechat:8787/...`, без env остаётся loopback `http://127.0.0.1:<PORT>`.
Это убирает захардкоженный `127.0.0.1` из кода, но сохраняет старое поведение в
dev и Vitest.

**Роли разведены: модель разрабатывает, проверяет воркфлоу.** Промпт разработки
(и фазы после одобрения плана) содержит запрет `NO_SELF_VERIFICATION`: тесты,
typecheck, линтер и сборку модель сама не запускает, результат отдаёт коммитом в
ветку задачи. Проверочные команды не публикуются ей и инструментом — фильтр в
`modelWork` зовёт `isVerificationCommand` (`shared/src/ci.ts`): флаг
`ci_commands.is_test` (чекбокс «Проверка (тесты) — только для воркфлоу»)
**или** текст команды (`npm test`/`npm run -w … test`/`typecheck`/`lint`/`vitest`
/`jest`). Признак в коде — чтобы отсечение не зависело от того, как кто-то
настроил `available_to_model`; `npm ci` и сборка под правило не попадают.
Миграция добавляет колонку и разом помечает гейт в уже заведённых справочниках.

**Fix-loop идёт тем же диалогом.** `sessionId` работы модели менеджер держит в
`modelSessions` (runId → id сессии CLI) и отдаёт хуку через
`CiFixContext.modelSessionId`; `attemptFix` шлёт ходы с этим `sessionId`
(`--resume`) и обновляет его между попытками — модель помнит и свою работу, и
прошлую неудачную правку (в промпте ещё и «Попытка N из M»). Карта живёт в
памяти менеджера и стирается по завершении рана, поэтому если работы модели в
этом процессе не было (повтор рана с шага слота «после», рестарт сервера),
`modelSessionId` = `null` и правка идёт с чистого диалога — это допустимая
деградация, а не ошибка. Хвост лога упавшего шага — 2000 символов, а для
шага-проверки 20 000 (`CiFixContext.isTestStep`, `tryFix` берёт из лога 400
последних строк вместо 40): по сводке vitest причину не найти.
Ослаблять гейт ради обхода ошибки промпт fix-loop по-прежнему запрещает.

Остальные команды справочника доступны модели как MCP-инструмент
`mcp__ci__run_command` (`ci/ciCommandsMcp.ts`, брокер `ciToolBroker` по токену
рана; лимит `maxModelCommandCalls`, `is_cleanup` и проверки исключены). Каждый
вызов — вложенный шаг ленты. Удалённый workspace передаётся только через
`remote.mcpUrl`; его хостовый путь нельзя задавать как локальный
`LlmRequest.cwd`, потому что CLI запускается внутри server-контейнера.
Ошибка `model_work` останавливает ран до after-слота и сохраняет workspace. В `RunFeed`
можно выбрать Claude/Codex и модель, затем повторить с `model_work`; подготовительные
команды не запускаются повторно, выбранные provider/model сохраняются в ране и аудите.
Меню там — те же `CLAUDE_MODELS`/`CODEX_MODELS`, что в настройках, плюс отдельный
пункт для модели, которой в меню нет: это дефолт CI `DEFAULT_CI_CLAUDE_MODEL`
(`opus`, не пункт меню — см. [../llm.md](../llm.md)) и пустая codex-модель
(«По умолчанию (из codex)», ран уходит без `-m`). Без этого пункта селект показал бы
первый пункт списка, а повтор ушёл бы с моделью, которую никто не выбирал.

## База знаний в работе модели

Модель рана исследует проект по задаче через базу знаний, а не идёт сразу в код.
Режим задаёт настройка ПРОЕКТА `ci_kb_context_mode` (`auto` | `manual` | `off`,
дефолт `auto`) — не режим связанного чата: ран про проект, а не про переписку.
На старте режим снимается в `ci_runs.kb_context_mode`, поэтому смена настройки
действует со следующего рана, а идущий доживает в своём режиме (и лента честно
показывает, в каком он работал).

В `auto` сервер подмешивает в задание блок контекста по заголовку, описанию и
критериям приёмки задачи — тем же `kb/autoContext.ts`, что и ход чата (порог
уверенности и формат разделов общие; см. [kb-usage](kb-usage.md)). Плюс к этому
в задание уходит `kbRunDirective`: «сначала база знаний, потом код». В `manual`
авто-контекста нет, формулировка усиленная — инструменты единственный путь к базе.
`VC_KB_TOOL=off` глушит инструменты и здесь.

Инструменты `mcp__kb__*` подключаются к работе модели, fix-loop и резюме — в том
числе в фазе «план» и в ходе без машины: база read-only и от агента не зависит.
Токен хода выдаёт `kbToolBroker` и снимает `withKbTools` во всех выходах,
включая отмену рана и убийство CLI: живой токен после отмены — это чтение базы
от имени закончившегося рана.

Телеметрия идёт через тот же `createKbUsageTracker` с `conversationId` связанного
чата рана и новыми `ci_run_id` / `ci_step_id`. Нет чата — база работает, метрика
молча пропускается. Ни поиск по базе, ни запись метрики не имеют права уронить
ран: любая беда превращается в обращение со статусом `error`. Отчёты —
`GET /api/ci/runs/:runId/kb-usage` (лента рана) и
`GET /api/projects/:id/tasks/:taskId/kb-usage` (модалка задачи), гейт у обоих —
членство в проекте (чужому 404). Итог рана попадает в резюме строкой
«БЗ: N обращений, M разделов, ≈K токенов».

## Состояние задачи на доске

Карточка колонки подсвечивается по последнему рану — чистые хелперы в
`shared/src/ci.ts`, никакой логики в компоненте:


При финализации рана считается ещё и попадание навигации БЗ в последующее
исследование кода. `relatedFiles` (`areas` документа) сохраняются снимком в
`kb_usage_sections`; открытые моделью файлы извлекаются прежде всего из аргументов
`read`/`grep`/`edit` в `ci_run_logs`, а для старых клиентов — из bash-команд
`cat`/`sed`/`head`/`tail`/`grep`. Для каждого выданного раздела проверяется,
открыт ли хотя бы один связанный файл. В `ci_run_kb_metrics` остаётся только
агрегат: выдано разделов, попало разделов и доля — второй список файлов не
дублируется. Если разделов или логов нет, ран не падает: метрика остаётся пустой.

- `isActiveCiStatus(status)` — `queued`/`running`/`awaiting_input`. Пока активен,
  кнопка «Выполнить» скрыта и на карточке, и в модалке: остаётся «Лента рана» /
  «Ответить модели».
- `canStartCiRun(summary)` — то же правило со стороны кнопки: запуск доступен,
  если рана не было или он завершён (`success`/`failed`/`cancelled`/`timeout`,
  а также `skipped`). Завершённый ран запуску не мешает: «Выполнить» на карточке
  всегда стартует **новый полный** ран (продолжить прошлый — «Повторить с упавшего
  шага» в ленте). Раны, оставшиеся активными после рестарта процесса, закрывает
  `failInterruptedCiRuns()` при старте сервера — иначе карточка навсегда считала
  бы CI занятым (ниже, про переживание процесса).
- Сводка на карточке — всегда про **последний** ран задачи (`latestCiRunSummary`,
  `latestCiRunSummaries`; тай-брейк по `rowid`, потому что повтор сразу после
  отмены попадает в ту же миллисекунду). Поэтому лозенг, фаза и подсветка
  прошлого рана исчезают, как только заведён новый: ни `ci.run`/`ci.done`, ни
  перезагрузка доски терминальный статус не «залипят».
- `ciCardPulse(summary)` → `running` | `fixing` | `awaiting` | `failed` | `done` |
  `null` → класс `jcard--ci-*` и анимация в `app.css`: ран идёт — голубая рамка
  медленно «дышит» (2.6с); модель разбирается с упавшим шагом — медленное красное
  мигание (2.2с) и снова голубое после успешного фикса; ждёт ответа пользователя —
  частое жёлтое (0.9с); свалился окончательно — частое красное (0.7с); успех
  (разработка закончена, ждёт пересборки прода) — статичная зелёная рамка.
  `cancelled`/`skipped` подсветки не дают. При `prefers-reduced-motion` рамка
  остаётся, анимация выключается.

То же состояние видно в списке чатов и в шапке открытого чата задачи — работу
обсуждают в чате, и узнавать «модель ждёт ответа» через открытие доски незачем.
Класс считает та же `ciCardPulse`, кейфреймы в `app.css` переиспользуются, поэтому
цвета совпадают: `.convo--ci-*` на строке списка и `.taskchat--ci-*` на шапке.
Отличие одно: **мигает только активный ран** (`running`/`fixing`/`awaiting`), у
терминального рамка статичная (`failed` — красная, `done` — зелёная) — постоянное
мигание по давно упавшему рану в списке чатов было бы шумом. Принадлежность чата к
задаче видна всегда, независимо от ранов: accent-полоска слева (`.convo--task`) плюс
строка `.ctask` с иконкой типа, ключом `PRJ-42` и лозенгой статуса последнего рана.

Данные для этого: `GET /api/conversations/task-chats` (`db.taskChatBadges(userId)`,
канал `conversations:taskChats`) — по одной `TaskChatBadge` на чат с `task_id`:
ключ, тип и сводка последнего рана (`db.latestCiRunSummary`). Запрос уходит вдогонку
списку бесед (`loadTaskChatBadges`), ответ кладётся в `taskChatBadges` по id беседы,
а раны — в общий `ciSummaries` по `taskId`, **только если ран другой или про задачу
ещё ничего не известно**: состояние известного рана ведут живые кадры `ci.*`, и
медленный ответ не должен откатывать их назад. Дополнительной подписки не нужно —
`ci.*` уже рассылаются на все соединения пользователя (`session.ts`), а не только
подписчикам доски.

Признак «модель чинит ошибку» — флаг `CiSlotProgress.fixing`: `tryFix` поднимает
его на входе в fix-loop (фаза «Модель исправляет ошибку») и снимает на выходе,
доска получает это через `ci.run` и через `latestCiRunSummaries` после перезагрузки.
Флаг транзитный: обычный `progress()` его не проставляет.

## Отчёт по задаче: расход модели

Когда задача выполнена, у неё видно, во что она обошлась: стоимость, токены с
разбивкой по кэшу, число запросов к модели, время рана и суммарное время работы
модели, плюс все шаги CI со статусом, попыткой и длительностью. До этого от рана
оставались только длительности, а расход терялся целиком: `runTurn` в
`ci/modelHooks.ts` выбрасывал и `meta` из `onDone`, и хендлер `onUsage`.

**Один ход CLI = один «запрос к модели».** Расход пишется по каждому выходу
`runTurn` — работа модели (в том числе продолжения одной сессии после вопроса
или одобрения плана), резюме, каждая попытка fix-loop и шаг актуализации базы
знаний: все они идут через него. Строка ложится в `ci_run_usage` с `run_id` и
`step_id` (у fix-loop это упавший шаг — цикл живёт внутри него) и с `kind`
(`model_work` / `summary` / `fix` / `kb_update`). Ход, о котором CLI не сказал
ничего (мгновенная отмена, клиент без usage), строкой не становится, иначе отчёт
считал бы запросы, которых не было. Запись не бросает никогда: расход — метрика,
и ронять ей ран нельзя, как и телеметрии БЗ.

**Стоимость хранится только настоящая.** В `cost_usd` идёт `total_cost_usd` от
CLI, а когда его нет — там `NULL`, и отчёт считает оценку по
`packages/shared/src/pricing.ts` на лету, помечая её «≈» (как `SessionUsage` у
наблюдателей). Хранить оценку нельзя: смена цен переписала бы историю задним
числом. Неизвестная модель (прайса нет) тоже делает итог приблизительным — сумма
заведомо занижена. Внешнего ключа на `ci_run_steps` у таблицы намеренно нет:
шаг бывает синтетическим, а метрика не имеет права уронить ран нарушением FK.

Сама таблица цен держится на этих же строках: прайс opus и fable подобран под
`cost_usd`, которую CLI назвал на реальных ходах, и `scripts/ci-usage-report.mjs`
печатает расхождение оценки с фактом там, где известны обе (см. `shared.md` и
`testing-operations.md`). До 02.08.2026 прайс завышал opus втрое, и заметить это
было неоткуда: у claude в отчёт идёт настоящая цена, оценка достаётся только
codex — а значит, сравнение движков сравнивало факт с кривой оценкой.

`CiRunReport.kbHit` добавляет сохранённое попадание БЗ. Карточка рядом со
стоимостью и токенами показывает «БЗ: выдано N разделов, задето M файлов из них»;
для старого рана и режима `kbContextMode=off` строки нет.

**Агрегаты — чистые функции shared** (`ciUsageTotals`, `sumCiUsageTotals`,
`ciTaskTotals` в `ci.ts`), поэтому сервер и UI складывают одинаково, а тесты
идут на числах без моков. Контракт — `CiRunReport` (сводка рана, агрегаты и все
шаги, у шагов с ходами модели — их расход) и `CiTaskReport` (все раны задачи +
итог: повторы и отмены тоже расход).

REST — `GET /api/ci/runs/:runId/report` и `GET /api/projects/:id/tasks/:taskId/report`
(`db.ciRunReport` / `db.ciTaskReport`), гейт тот же, что у `kb-usage`: чужому
404, а не пустой отчёт. У ранов до фичи строк расхода нет — отчёт открывается,
показывает шаги и время, а деньги и токены рисует прочерками.

UI — `components/ci/CiReport.tsx` в карточке задачи (`TaskModal`), раздел виден
только когда последний ран завершён: пока он идёт, цифры устаревают на глазах, и
смотреть надо ленту. Данные грузит `useRemoteReport` (общий хук врезок-отчётов,
бывший `useKbUsageReport`) через `window.ci.getTaskReport`. По умолчанию открыт
свежий ран со своими шагами; при нескольких ранах переключатель добавляет «Итог
по задаче» с таблицей ранов. Числа форматирует `ci/ciFormat.ts` (нулевое «время работы модели» плитка рисует прочерком: ноль
означает «CLI не сообщил длительность ни по одному ходу», а не «модель работала
0 мс»): `fmtDuration`,
`fmtTokens` (разряды `toLocaleString('ru')` — там неразрывный пробел, DOM-тесты
сравнивают текст только после нормализации) и `fmtUsd`, который сам ставит «≈» у
оценки и пишет «< $0.01» вместо округлённого в ноль «$0.00». Фейк UI
(`test/fakeApi.ts`) отдаёт отчёт из своей же ленты — шаги и длительности есть,
расход пуст (ходов модели фейк не делает), поэтому тестам и сториз есть что
открыть; фикстуры с расходом — `test/fixtures/ci.ts` (`makeRunReport`,
`makeTaskReport`, `makeUsageTotals`, `makeReportStep`).

`runTurn` теперь возвращает `TurnResult` с `meta` (итог из `onDone`) и последним
`onUsage`: счётчики токенов кумулятивны, и у прерванного хода последний `onUsage`
— всё, что о его расходе известно.

**Чего CLI не сообщает — измеряет сервер.** `codex exec --json` не отдаёт ни
`total_cost_usd`, ни длительности, ни `num_turns`, а модель у него бывает пустой
штатно (берётся из его `config.toml`). Поэтому `recordUsage`: длительность — по
замеру хода (`TurnResult.elapsedMs`, часы из `deps.now`), `num_turns` — по числу
событий `onUsage` (одно событие = один ответ модели), модель — `meta.model` →
модель рана → `unknown`. Прайса у `unknown` нет намеренно (`estimateCostUsd`
возвращает `undefined`): итог помечается `costUnderstated` и в UI читается как
«оценка по прайсу, итог занижен», а не как ноль. Замер сервера включает накладные
расходы транспорта и потому НЕ подменяет `meta.durationMs`, а лишь закрывает его
отсутствие.

**Одна семантика входных токенов.** `input_tokens` у claude — вход БЕЗ кэша, у
codex — вместе с прочитанным кэшем; складывать их нельзя, иначе «до/после»
сравнивает разные величины, а оценка по прайсу считает кэш по полной цене входа
(для рана codex это завышало оценку в ~5 раз). `recordUsage` приводит вход к «без
кэша» на записи (у codex вычитает `cache_read_tokens`, с зажимом в ноль) и
помечает строку `input_semantics = 'no_cache'`. Историю задним числом не правим:
у старых строк колонка пустая, и `mapCiRunUsage` считает их `with_cache` для
codex и `no_cache` для claude, а `ciUsageTotals` приводит их на чтении
(`ciUsageInputTokens`) и поднимает `inputNormalized` — в UI это «вход приведён к
„без кэша“».

**Вызовы инструментов за ран** — `ci_run_tool_calls` (`run_id` + вид +
счётчик, UPSERT-инкремент) и `CiRunReport.toolCalls`. Виды —
`bash`/`read`/`grep`/`edit`/`kb`/`other` (`classifyCiToolCall` в `ci.ts`): имя
приходит от CLI в трёх видах (`mcp__remote__read` у claude, `remote:read` у codex,
`Read` у встроенного), а вид должен получаться один, иначе движки несравнимы.
Считается там, где мимо сервера проходит каждый вызов любого движка, — в
`onActivity` хода (`ClaudeLogEntry.tool` — сырое имя рядом с человеческим
`summary`); MCP-эндпоинт для этого не годится: он знает машину и папку, но не ран.
Ход без вызовов строки не пишет: «нет строки» должно означать «счётчика у рана
нет» (ран до фичи), а не «модель ничего не вызвала» — поэтому у старых ранов в
отчёте строки «Инструменты» нет, а не «0». Обе метрики не бросают: любая беда —
пропуск строки, а не упавший ран.

## Замер расхода: методика и вердикт по CHAT-54/55/56

Замер от 02.08.2026 по прод-БД (`ci_run_usage`, `ci_run_logs`, `kb_usage_*`),
повторяется командой `node scripts/ci-usage-report.mjs --since <дата>` (в
контейнере: `--db /data/voicechat.db`). Скрипт даёт на ран: стоимость (настоящую
от CLI либо оценку «≈», у модели без прайса — «занижено»), токены в единой
семантике, время рана и работы модели, попытки fix-loop, вызовы инструментов (из
`ci_run_tool_calls`, а у старых ранов — восстановленные из ленты, тогда «~») и
отдельно то, что было главной гипотезой CHAT-54: сколько раз файл читали
командой внутри `bash` и сколько правок шло heredoc'ом.

Числа (полная таблица — в журнале `docs/kb/log/2026-08-02-*-ci-usage-measurement.md`):

|---|---|---|---|---|---|---|---|---|
| Список чатов | claude/opus | $7.17 | 3 | 7.7M | 75 | 2/0/0 | 49 | 8 |
| Каркас исполнителя | claude/opus | $19.34 | 5 | 17.7M | 112 | 2/0/0 | 89 | 16 |
| RemoteLlmClient | claude/opus | $8.01 | 3 | 4.5M | 41 | 1/0/0 | 30 | 12 |
| RemoteLlmClient (тот же таск) | codex/gpt-5.4 | ≈$1.90 | 5 | 6.4M | 26 | 0/0/0 | 13 | 0 |

| Реестр исполнителей | codex/gpt-5.4 | ≈$1.73 | 3 | 7.0M | 88 | 0/0/0 | 55 | 15 |

**CHAT-54 (remote `read`/`grep`/`edit`) — эффекта нет, потому что инструментов у
модели фактически не было.** Ни в одном ране файловые инструменты не вызваны ни
разу; файлы читались `cat`/`sed` внутри `bash` (5–89 раз за ран) и правились
heredoc'ом (0–16 раз) — как до фичи. Причина не в модели: у claude
`--allowedTools` содержал только `mcp__remote__bash`, и каждый вызов `read`
упирался в неодобренное разрешение (в ране 02.08 — 6 отказов и 54 чтения через
`bash`), а промпт codex про файловые инструменты вообще не говорил. Оба места
исправлены здесь же (см. `llm.md`), так что проверяемым это утверждение станет на
следующих ранах — сама метрика для этого уже есть.

**CHAT-55 (компактный запрос авто-инъекции) — работает численно.** До него запрос
авто-контекста упирался в кап 1200 символов в 6 обращениях из 8 (весь текст
задачи с обрезкой), после — 533–1055 символов там, где в задаче есть бэктики
(1200 остаётся при их отсутствии — это заложенный фолбэк). Выданный объём при
этом не просел: 5 разделов и ~2.4–2.6k символов в обоих случаях, уверенность
`high`. То есть запрос стал вдвое короче при том же результате — но на цену рана
это не влияет: 2.5k символов инъекции против 7.7M токенов кэш-чтения.

**CHAT-56 (полный текст верхних разделов) — не проверено, данных нет.** Код на
месте (`buildKbAutoContext`: первые два раздела целиком, остальные — навигация к
`kb:document`), но после его деплоя в БД ровно один ран (этот), и у него
авто-инъекция вернула `empty` (`no-match`) — сравнивать нечего. Зафиксирован
эталон «до»: 5 разделов по 408–537 символов, всего ~2.4k. Замечание на будущее:
директива БЗ обещает модели «блок контекста ниже» и в случае `no-match`, когда
блока нет.

**Что не удалось развести.** Движок сменился одновременно с оптимизациями
(claude/opus → codex/gpt-5.4), поэтому разница $8.85 → ≈$2.22 за ран — это эффект
СМЕНЫ ДВИЖКА и его прайса, а не оптимизаций: на одном и том же таске
(«RemoteLlmClient») claude дал $8.01 (настоящая цена CLI), codex — ≈$1.90
(оценка), при сопоставимых кэш-чтении (4.5M против 6.4M) и вызовах инструментов.
Ни одного рана с реально доступными файловыми инструментами в выборке нет вовсе,
а телеметрия БЗ существует с 31.07, поэтому по CHAT-56 сравнение осталось
качественным. Отчёта в самой ленте рана нет (там лог и
консоль), но мост `window.ci.getRunReport` для одного рана уже существует.
