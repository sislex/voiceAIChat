# CI-раннер канбана

Выполнение переиспользуемых серверных команд вокруг работы модели обычным действием
«В очередь» на карточке задачи: команды слота **до** → работа модели → команды
слота **после** → резюме модели. Один **ран** с общим статусом, единой лентой,
потоковым логом, метриками длительности, fix-loop и диагностической консолью.
Заменил Feature Run полностью: UI, маршруты, координатор, контракт `features:*` и
таблицы `features`/`feature_events`/`agent_tasks`/`feature_deployments`/`repository_slots`
удалены (миграция сносит их при старте). Корень рабочих копий — `project_machines.repos_root`.

## Модель данных

Таблицы `ci_*` в `db/schema.ts`: `ci_commands` (справочник, soft-delete,
версия текста, `is_test` — команда-проверка), `ci_slot_commands` (привязка к слоту для проекта/задачи с
наследованием), `ci_runs`, `ci_run_steps` (kind: command/model_work/model_command/
model_summary, `parent_step_id` для вложенных вызовов), `ci_run_logs` (монотонный
`seq` для реплея после reconnect; `ci_runs.llm_provider/llm_model` фиксируют выбор модели),
`ci_run_usage` (расход модели по ходам — см. «Отчёт по задаче»), `ci_fix_attempts`, `ci_workspaces`,
`ci_command_suggestions` (группировка по причине), `ci_events` (аудит),
`ci_stage_llm_configs` (переопределения executor/provider/model этапа для проекта или задачи),
`ci_stage_runs` (самостоятельное выполнение этапа со снимком LLM, статусом, длительностью и итогом),
`ci_settings` (единственная строка глобальных настроек; `stage_models` — legacy JSON «модель по стадии
рана», пустая колонка = дефолты кода). CI-поля проекта (`ci_base_branch`,
`ci_branch_template`, `ci_reuse_strategy`, `ci_exec_auth_ref`) добавляются в
`migrate()`. Доступ — по членству проекта; CI-админ = владелец проекта.

## Прогресс активного рана и ETA

`AutomationProgress` в `packages/shared/src/ci.ts` — серверный снимок наблюдаемого
CI-процесса: `runId`, монотонная `version`, этап и текущий шаг, состояние,
времена, фактически завершённые шаги, процент либо `null`, ETA-диапазон,
объяснение отсутствующей оценки, ссылка на журнал и разбивка шагов.
`buildCiAutomationProgress` строит его из сохранённых `ci_runs` и верхнеуровневых
`ci_run_steps`; вложенные команды модели не увеличивают общий процент.

Процент определяется только отношением успешно завершённых/пропущенных шагов к
известному числу шагов рана. Пока активен `model_work`, объём заранее неизвестен:
снимок имеет `percent: null` и `totalSteps: null`, а UI рисует indeterminate bar
без `aria-valuenow`. Успех фиксирует 100%; ошибка, таймаут и отмена используют
сохранённый `finishedAt`, поэтому elapsed и ETA после терминала не тикают.
`awaiting_input` преобразуется в явное «Ожидает действия пользователя».

ETA использует среднюю длительность фактически завершённых шагов текущего рана;
пока таких измерений нет — длительности одноимённых шагов успешных ранов проекта.
Результат показывается как приблизительный диапазон ±25%. Для неизвестной работы
модели и при отсутствии измерений вместо числа сохраняется причина.

`Database.ciRunSummary` собирает прогресс на сервере. Board snapshot включает его
в `CiRunSummary`, поэтому данные восстанавливаются после reload. `RunManager`
инвалидирует snapshot после каждого перехода шага; карточка, открытая задача и
связанный чат используют один `AutomationProgressView`. Клиент локально обновляет
только elapsed. При применении realtime summary стор сравнивает `runId` и
`version`: поздний снимок старого запуска или меньшей версии не откатывает новый.
Компонент передаёт числовые ARIA-атрибуты только determinate-шкале, поддерживает
перенос подписей на mobile и отключает движение indeterminate bar при
`prefers-reduced-motion`.

Во вкладке карточки «Ход выполнения» этап «Работа модели» размещается ровно
один раз: `TaskModal` создаёт keyed-контейнер `${runId}:model-work`, а прежний
отдельный верхний `AutomationProgressView` и дублирующая строка системного
статуса удалены. Компактный заголовок единственного контейнера показывает
локализованный статус, determinate или indeterminate-прогресс, процент при его
наличии, текущую стадию и живую либо зафиксированную продолжительность; сырые
значения статуса пользователю не выводятся. По умолчанию контейнер свёрнут, в том
числе при ошибке, а кнопка с `aria-expanded` и уникальным `aria-controls`,
построенным из run id, раскрывается мышью, Enter или Space.

Раскрытая область остаётся в DOM с атрибутом `hidden` и содержит полный
`AutomationProgressView` (времена, ETA, расширенный прогресс, шаги и «Журнал»),
отчёт рана, расход базы знаний и итоговые факты provider/model, результата,
начала, завершения и длительности. Если данных ещё нет, заглушка находится только
внутри этой области. Ссылка «Журнал» не переключает родительский disclosure.

Состояние раскрытия принадлежит `ModelWorkDisclosure` и не вычисляется из
статуса, прогресса или наличия подробностей. Стабильный key сохраняет сам
DOM-контейнер, фокус и пользовательское раскрытие при realtime-обновлениях,
новых данных отчёта и переходе в терминальный статус. Мобильная раскладка
переносит второстепенные поля компактной строки, а длинный текст и `pre` не
создают горизонтальную прокрутку всей карточки. Источник поведения —
`packages/ui/src/components/kanban/TaskModal.tsx`, подробного прогресса —
`AutomationProgressView.tsx`, адаптивной раскладки — `app.css`; единичность
контейнера, доступность, сохранение DOM/focus и отсутствие автораскрытия
закреплены в `TaskModal.dom.test.tsx`.

## Git-транспорт CI-машины MacBook

Диагностика публикации ветки CHAT-246 зафиксировала разные GitHub-учётные данные
для двух транспортов: HTTPS через macOS Keychain выбирал аккаунт `StimkaT` и
получал HTTP 403, записи `sislex` в Keychain не было. Работоспособным путём для
этой CI-машины оказался SSH deploy key: он аутентифицировался для репозитория
`sislex/voiceAIChat`, а dry-run push прошёл при явном URL
`ssh://git@github.com/sislex/voiceAIChat.git`. Это операционная привязка машины,
а не общий контракт раннера; при повторной диагностике важно проверять явный URL,
поскольку глобальный `url.*.insteadof` может переписать scp-подобный SSH URL.

## Движок и модель: наследование

Конфигурация CI хранится в `ci_llm_configs` отдельно для проекта и задачи.
Эффективная конфигурация `llmEngineId/provider/model` выбирается строго в порядке: переопределение
задачи → настройка проекта → настройки пользователя → системный дефолт. Настройка
задачи снимается `DELETE /api/projects/:id/tasks/:taskId/ci/llm`, после чего она
снова наследует проект. Проектный `GET /api/projects/:id/ci/llm` при отсутствии
собственной строки отдаёт конфигурацию из пользовательских настроек. Выбор и сохранение
на проекте — `CiProjectDefaults`; на задаче — `CiTaskSettings`.

Обычный запуск `CiRunManager.start` фиксирует в `ci_runs` эффективные provider
и model, а не только настройку пользователя. Привязанные к проекту разговоры,
включая приватный канбан-ассистент, хранят `NULL` в полях LLM при наследовании и
резолвят проектную конфигурацию заново на каждом ходе. `ci_llm_configs` хранит
также необязательный `llm_engine_id`; его выбирают в `CiProjectDefaults`, а
`TurnManager` применяет в порядке чат → проект → пользователь. Поэтому смена
проекта сразу влияет на наследующие чаты, а их собственные override не
перезаписываются. Перед созданием рана `CiRunManager.start`
(`apps/server/src/ci/runManager.ts`) читает deny-list запускающего пользователя
и фиксирует в `ci_runs` уже разрешённую пару. Если запрошенный provider запрещён,
он заменяется первым разрешённым provider в порядке Claude, Codex; затем
запрошенная для выбранного provider модель сохраняется либо заменяется первой
разрешённой моделью из общего списка. Если доступной пары или модели нет, ран не
создаётся и возвращается понятная ошибка. Это серверная проверка, поэтому её
нельзя обойти сохранённой CI-конфигурацией или разовым выбором при запуске.

Автоматические этапы имеют отдельную конфигурацию `CiStageLlmSelection`. Поля
`llmEngineId/provider/model` наследуются независимо и строго в порядке: этап
задачи → этап проекта → модель проекта → системный fallback. REST-пути
`…/ci/stages/:stage/llm` читают, сохраняют и сбрасывают override проекта или
задачи; менять их может владелец проекта, читать — участник. Допустимый набор
ключей задан `CI_USAGE_KINDS` в `packages/shared/src/ci.ts`: планирование,
разработка, исправление тестов, анализ ручного QA, подготовка данных, code
review, обновление БЗ, релизный анализ и резюме.

Тем же порядком выбирает движок «Подготовка к разработке»
(`launchTaskPreparation` в `apps/server/src/server.ts`): она резолвит стадию
`planning` через `resolveTaskStageLlmConfig`, а последним уровнем передаёт
`ciLlmDefaultsForUser` НАЖАВШЕГО кнопку — CLI запускается в его профиле. GET и
DELETE стадийного REST-конфига используют тот же пользовательский fallback,
поэтому после сброса проектного override effective-значение показывает Codex,
если он выбран в настройках пользователя, а не системный Claude.

Перед первым ручным запуском и каждым повтором вкладка подготовки показывает
`LlmSettingsEditor`: начальное значение — effective-конфигурация `planning`, а
явно выбранные `llmEngineId/provider/model` передаются только конкретному рану.
Тот же снимок передаёт создание задачи из `task-launch`. Сервер повторно
проверяет персональный deny-list и сохраняет выбранные поля в
`task_preparation_runs`; история и экспорт поэтому не меняются после последующей
перенастройки. При `provider === 'codex'` запрос уходит в codex-клиент. Модель по
умолчанию зависит от движка: пустая модель и claude-`default` дают `sonnet`, у
codex — `DEFAULT_CODEX_MODEL`. Отдельной записи `ci_stage_runs` и строк расхода
у подготовки нет: её история — `task_preparation_runs`.

Системный fallback у этой цепочки заменяем: четвёртый параметр
`db.resolveTaskStageLlmConfig(projectId, taskId, stage, fallback)` подставляет
свою тройку вместо `claude/opus` (и вместо отсутствующей модели проекта).
Для `kb_update` эффективная тройка вычисляется в `VoiceChatDb.startMergeRun`
до создания merge-рана. Последний development-ран задачи служит fallback; если
его нет, используется `ciLlmDefaultsForUser` запустившего merge. Поэтому
приоритет равен: разовый выбор merge-рана → этап задачи → этап проекта → модель
проекта → снимок development-рана → пользовательские и системные значения.
После персонального deny-list фактические `llmEngineId/provider/model` вместе с
исходно запрошенной парой сохраняются в `merge_runs`.

`kbUpdateForMerge` (`apps/server/src/ci/modelHooks.ts`) настройки повторно не
резолвит, а использует неизменяемый LLM-снимок merge-рана. Контекст и CLI-профиль
он по-прежнему строит из последнего development-рана задачи
(`/data/cli-users/<base64url(userId)>`, `run.triggeredBy` development-рана).
Так исторические метаданные совпадают с фактическим запуском, а смена настроек
после постановки merge в очередь не меняет исполнитель. Без резолва в
`startMergeRun` стадийный Codex-override терялся, merge фиксировал глобальный
`claude/opus` и мог завершаться сообщением «Модель не ответила — база знаний не
обновлена» уже после успешного прогона тестов.

На старте модельного этапа `RunManager` один раз резолвит конфигурацию и передаёт
хуку неизменяемый снимок; `modelHooks.ts` больше не перечитывает глобальный
`stageModels` посреди работы. Для разработки, fix-loop, обновления БЗ и резюме
создаётся отдельная запись `ci_stage_runs` со статусом, снимком LLM, временем и
итогом; `CiRunDetail.stageRuns` возвращает эти записи рядом с обычными шагами.
Расход этапа вычисляется из `ci_run_usage` по его виду и временному окну, поэтому
историческая лента не меняется после перенастройки. Fix-loop получает эффективную
конфигурацию этапа `fix`, а безопасный fallback вспомогательного хода берётся из
эффективной модели разработки задачи.

`ci_runs.llm_engine_id/llm_provider/llm_model` — базовый неизменяемый снимок
рана. Он не переписывается стадийными override и показывается с подписью
«Базовая модель рана». Фактический снимок выполнения
`VoiceChatDb.ciExecutionLlm` (`apps/server/src/db/database.ts`) формирует в
`CiRunDetail.executionLlm` и `CiRunSummary.executionLlm` только из сохранённых
`ci_stage_runs`: сначала активная стадия, а после её завершения — последняя
историческая стадия; до создания первой записи источником служит базовый снимок
рана (`source: run`). Контракт снимка находится в `packages/shared/src/ci.ts`;
отдельное поле `base` не даёт UI смешивать базовую и стадийную пары.

При старте и завершении каждой стадии `emitStage` в
`apps/server/src/ci/runManager.ts` заново читает деталь рана, рассылает
`ci.snapshot` подписчикам ленты и вызывает обновление доски. Поэтому
`RunFeed.tsx` получает фактическую модель из детали рана, а `TaskCard.tsx` и
`TaskModal.tsx` — из `CiRunSummary`; переход между `model_work`, `fix`,
`kb_update`, `summary` и другими стадиями виден без перезагрузки. Reconnect и
REST-загрузка восстанавливают те же сохранённые значения. UI подписывает текущий
этап и фактическую пару provider/model, а отличающуюся базовую пару показывает
отдельно. Пустая модель отображается как «Модель не указана» и не заменяется
первым значением селектора.

## Выполнение

`createCiRunManager` (`ci/runManager.ts`) — процесс-глобальный менеджер по образцу
`TurnManager`: прогон слот-за-слотом, общая FIFO-очередь сервера по лимиту
`maxConcurrentRuns` (раны разных задач идут **параллельно**, см. ниже), отмена и
откат Task в `prev_column_id` при ошибке. Development заканчивается единственной
обязательной публикацией task-ветки: после команд `after_model` системный
`pushTaskBranch` фиксирует branch/SHA/машину и `pushed=1` в `ci_workspaces`.
Неуспешный push делает ран failed; успешный переводит карточку к подготовке
ручного QA.

### Диагностика транспорта Git на CI-машине

Ошибка HTTPS push относится к учётным данным самой связанной машины, а не к
проектной роли ChatAI. Проверять её надо в рабочей копии тем же remote и через
`git push --dry-run` с полностью указанным refspec; имя аккаунта можно получить
из настроенного credential helper, не печатая пароль или token. На текущей машине
MacBook `origin` использует `https://github.com/sislex/voiceAIChat.git`, macOS
Keychain отдаёт аккаунт `sislex`, и dry-run в этот репозиторий проходит. SSH сейчас
не является фолбэком: `ssh -T git@github.com` и dry-run на
`ssh://git@github.com/sislex/voiceAIChat.git` отвечают `Permission denied
(publickey)`. Глобальное правило `insteadOf` переписывает форму
`git@github.com:…` в HTTPS, но не явный `ssh://…`; менять origin на явный SSH
имеет смысл только после отдельной успешной проверки ключа и права записи.

Affected-check, встроенный `kb_update`, legacy merge, production deploy и cleanup
удаляются из `after_model` идемпотентной миграцией. Записи справочника и
пользовательские команды сохраняются. Старый снимок слота дополнительно
фильтруется раннером без создания даже skipped-шагов. Workspace остаётся активным
на подготовке QA, ручном QA и ожидании merge; его удаляет общий механизм только
после успешного merge или ручного переноса задачи в Done. Модель может запускать
доступные локальные проверки как инструменты, но они не заменяют обязательный
merge-gate.

Рабочая копия, оставшаяся от **упавшего или отменённого** рана этой же задачи,
чинится сама: системный шаг «Подготовка рабочей директории» нового полного рана
видит `<workspace>/<slug>/.git` и приводит копию в чистое состояние
(`git stash push --include-untracked` → `reset --hard` → `clean -fd`; stash
оставляет работу восстановимой). Без этого следующий запуск падал на шаге
клонирования с exit `66`, и «починили → запустили снова» требовало ручного
«Откатить изменения и повторить», а карточка снова светилась красным. Стратегия
`clean` сносит папку целиком (чинить нечего), стратегия `fail` по-прежнему
защищает от **чужого** содержимого — но своя копия задачи под её запрет не
попадает, иначе повтор после падения был бы невозможен в принципе. Exit code `66`
остаётся страховкой на остальные случаи: ран останавливается, UI требует явного
подтверждения, затем `discardChangesAndRetry` выполняет `git reset --hard` +
`git clean -fdx`, пишет аудит и запускает новый полный ран. Команды выполняются на машине по умолчанию
проекта через `AgentCommandExecutor` (`ci/executor.ts`) поверх нового
`AgentRegistry.execStream` — потоковый форвард `exec.chunk` (агент не пересобирается);
cwd/env собираются с shell-escape (пользовательский ввод — только через env, не
конкатенацией). Секреты маскируются в логе.

## Пустой ход модели не может закончиться успехом

После успешного модельного хода раннер вставляет системный шаг «Проверка
результата модели» (`ensureModelProducedWork`): в клоне ищутся коммиты сверх
`$BASE_BRANCH` и незакоммиченные изменения, пусто — скрипт выходит с кодом `70`.
Саму пустоту за ошибку не считают: «модель не запускалась» отличают от «модель
работала впустую» по счётчику вызовов инструментов рана (`ci_run_tool_calls`).
Есть вызовы и нет изменений — ран останавливается: слот «после» **целиком**
пропускается (значит, и пуш ветки, и cleanup, и мерж, и пересборка прода),
карточка остаётся в рабочей колонке, рабочая копия сохраняется, а в резюме — и в
ленте, и в связанном чате — отдельной строкой сказано «Работа не сдана». Ран
закрывается как `failed`.

Проверка появилась после рана `d2ba80bc` (CHAT-108): модель 604 с читала код, не
смогла записать ни одного файла, прямо написала в ответе «изменений и коммита не
создано» — и ран закрылся успехом, карточка уехала в «Готово», клон удалили.
Так вышло потому, что каждый следующий шаг по отдельности отрабатывает вхолостую
с нулевым кодом: коммит при пустом индексе печатает «Нет незакоммиченных
изменений — коммит не нужен» и выходит с `0`, мерж — `Already up to date`,
пересборка — «прод-репозиторий на том же коммите». Первопричину того рана
(файловые инструменты моста отвергали абсолютные пути) чинит `remotePath`,
см. [llm.md](../llm.md#проброс-bash-на-машину-пользователя).

Сама проверка не отработала (git сломан, машина отвалилась) — ран не рубится: в
ленте остаётся строка «Проверку результата модели выполнить не удалось», а исход
решают следующие шаги.

## Параллельные раны

Раны **разных задач** одного проекта выполняются одновременно в пределах
`maxConcurrentRuns`. Когда лимит исчерпан, ожидающий ран выбирается не по FIFO,
а по **актуальному** порядку карточек его проекта в колонке `development`: выше
стоят `urgent`, затем `high`, `medium` и `low`; одинаковый приоритет сохраняет
ручной порядок (`position`, с устойчивым fallback по времени создания и id).
Поэтому смена приоритета или ручная перестановка карточки, пока её ран ждёт,
влияет на следующий освобождённый слот. У разных проектов общей колонки нет, так
что их относительный порядок остаётся порядком постановки. Порядок доски задаёт
`compareTasksInColumn` в `packages/shared/src/projects.ts`, выбор ожидающего —
`createCiRunManager` в `apps/server/src/ci/runManager.ts`. Работает это
только потому, что раны изолированы по построению: рабочая директория —
`{repos_root}/{project}/{issue_key}`, ветка — по шаблону
`{task_number}`, где `{task_number}` — полный ключ вида `CHAT-172`; npm-кэш —
`{repos_root}/.npm-cache/{project}-{task_seq}`. Заголовок задачи не участвует в
идентичности новой ветки или workspace. Два прежних стандартных шаблона
`feature/{task_number}` и `feature/{task_number}-{slug}` при старте мигрируются
на новый; явно сохранённые нестандартные шаблоны с `{slug}` продолжают работать.
Инвариант закреплён проверкой на старте `execute`: если папку или ветку уже занял
другой активный ран (сломанный шаблон ветки, совпавший номер задачи), ран не
начинает работу — в ленте появляется шаг «Проверка изоляции рабочей директории»
со статусом `failed`, в аудите — `run.isolation_conflict`.

**Один активный ран на задачу.** `start`, `retryFromFailed` и
`discardChangesAndRetry` отказывают, пока у задачи есть незавершённый ран
(REST отвечает 409): два рана одной задачи неизбежно делили бы папку и ветку.

**Параллельный запуск мимо очереди.** Помимо обычного запуска в общую
FIFO-очередь есть `launch: 'parallel'` (`CiRunStartOptions`, кнопка
«Параллельно» на карточке и в модалке задачи): ран уходит в работу сразу, не
занимая серверный слот и не считаясь в `maxConcurrentRuns`. Способ запуска не
персистится — повтор упавшего рана идёт через очередь. Машину параллельный ран
выбирает сам (`pickCiRunAgent` в `packages/shared/src/ci.ts`): машина проекта
по умолчанию, если на ней нет активных ранов; иначе машина проекта без активных
ранов; иначе машина с минимальным их числом (при равенстве — машина по
умолчанию, затем порядок списка). Загрузку считает
`countActiveCiRunsByAgent()`: незавершённые раны (`queued/running/awaiting_input`)
по всем проектам, причём ран с пустым `agent_id` учитывается за машиной по
умолчанию его проекта — иначе она выглядела бы свободной. Карточка с явно
закреплённой машиной (`Task.agentId`) и при параллельном запуске идёт на неё,
автоподбор — только для «наследующих» карточек.

**Принудительный запуск на указанной машине.** Из настроек CI задачи (выбрана
конкретная машина → кнопка «Запустить на этой машине сейчас») уходит
`POST …/ci/run-on-machine` (`REST.ciRunForceStart`) →
`CiRunManager.forceStartOnMachine`. Простаивающая задача стартует сразу, мимо
очереди, на указанной машине. Ран задачи, ещё стоящий в очереди, **не
отменяется, а продвигается** (`promoteQueuedRun`): тот же ран получает машину
(`updateCiRun({agentId})`), выдёргивается из очереди ожидания и уходит в работу,
не трогая счётчик слотов; в аудите — `run.forced_to_machine`. Проверка «ран ещё
queued» и продвижение выполняются синхронно в одном ходе event loop (как в
`dequeue`), поэтому гонка со стартом честно отвечает «Для этой задачи уже
выполняется ран» — уже выполняющийся ран не перезапускается. Машина должна быть
доступна запускающему лично либо через проект задачи, иначе сервер отвечает 409.

**Машина рана.** `execute` берёт только зафиксированный `runRow.agentId` и повторно проверяет доступ инициатора и online-статус. Изменение default или предоставления не переписывает историю и не вызывает автоматического переключения; legacy NULL не подменяется текущим `project.defaultAgentId`.

**Общие ресурсы вынесены из разработки.** Настроенные в слоте
`after_model` команды merge в базовую ветку и production rebuild/deploy не
доходят до `runCommandStep`: раннер создаёт для них шаг `skipped` и пишет в
лог, что операция отложена до самостоятельной стадии workflow. Поэтому ран
разработки не захватывает mutex merge/deploy и не дренирует очередь перед
пересборкой production; эти механизмы относятся к legacy-пути выполнения таких
команд внутри разработки.

## Вкладки карточки задачи

`TaskModal` держит выбранную вкладку локально и не размонтирует панели при
переключении, поэтому введённые черновики сохраняются. Вкладки следуют порядку
workflow: «Общее» → условная «Подготовка к разработке» → «Настройки» → «Ход
выполнения» → условные «Component QA», «Интеграционные тесты», «Automated QA» →
«Ручное QA» → «Merge» → «Лента рана».
«Подготовка к разработке» видима только у обычной задачи в `backlog`,
`preparation` или `ready`, когда существует `taskPreparationRunId` либо активный
preparation-run. QA-вкладка видима на своей или более поздней workflow-стадии
либо при сохранённой истории ранов этого этапа. Первоначальный выбор вкладки
идёт по приоритетам: активный preparation-run (`taskPreparationStatus ===
'running'`) открывает «Подготовку к разработке» при любом способе открытия
карточки, следом её же открывает deep-link `initialTab === 'preparation'` (но
только если вкладка видима), затем колонка QA-стадии выбирает свою вкладку,
затем активный development-/merge-ран выбирает «Ленту рана», а без активного
процесса открывается «Общее». `defaultTab()` пересчитывается только при
монтировании и смене `task.id`, поэтому обновление той же карточки не сбрасывает
вкладку, выбранную пользователем вручную. Эффект загрузки QA-истории зависит только от `task.id`,
поэтому обновление того же task не сбрасывает ручной выбор. На узком экране
строка вкладок прокручивается горизонтально.

Эти три вкладки обслуживает отдельная сущность ранов `qa_stage_runs` со своей
таблицей, REST-набором `…/qa/runs/:stage` и панелью `QaStageRunPanel`: она не
пересекается с `ci_runs`, `component_qa_runs`, ручным QA и merge-раном.
Открытие вкладки делает только GET и ран не запускает; исполнителя у этих ранов
пока нет. Модель данных, идемпотентный старт, гейты перехода по колонкам,
восстановление после рестарта и границы реализации — в
[qa-stage-runs.md](qa-stage-runs.md). Вкладка «Component QA» при этом
по-прежнему показывает старую `ComponentQaPanel` поверх `component_qa_runs`
([manual-qa.md](manual-qa.md)).

В шапке карточки отдельной строкой показаны ключ задачи и полный заголовок,
текущая колонка, активная фаза development/merge и визуально отдельный результат
последнего завершённого запуска. Связанный чат открывается компактным действием
шапки и отдельной вкладки не имеет. Заголовок — многострочное поле с переносом,
а описание и критерии находятся в одном вертикальном scroll-контейнере и в
просмотре используют один компонент Markdown.

«Настройки» вертикально монтируют машину, движок/модель и команды без внутренних
табов. Блок «Тестовое окружение» (`FeaturePreviewSection`) находится первым во
вкладке «Ручное QA», перед `ManualQaPanel` с тест-кейсами и QA-сессией.
`CiTaskSettings` сохраняет прежние серверно проверяемые режимы
`commands`, `machine` и `model`: сохранение настройки само ран не запускает.
Каталог машины объединяет личные и проектные машины с дедупликацией по `agentId`,
показывает online/offline, наследование default и утраченный выбор; `Task.agentId
= null` означает наследование машины проекта. «Ход выполнения» имеет подтабы
«Обзор», «Работа модели», «Проверки», «Изменения», «База знаний», «Результат и
доставка», «Ресурсы» и использует серверные progress/report/KB данные.

«Подготовка к разработке» использует только историю `task_preparation_runs` и не
смешивает её с development/merge ни визуально, ни по данным: её панель
(`packages/ui/src/components/kanban/TaskPreparationTab.tsx`) не знает про
`ci_runs`, `merge_runs` и `getTaskReport`, а «Лента рана» — про подготовку.
Прежний inline-блок `task-modal-preparation` на вкладке «Общее» удалён целиком,
поэтому «Начать подготовку задачи» осталось только на карточке в TODO; из
модалки первый запуск не делается, а из вкладки доступен лишь повтор.

Навигация — hash-deep-link `#/projects/:projectId/task/:taskId/preparation`.
Кнопка «Лента подготовки» на карточке вызывает `onOpen(task.id, 'preparation')`,
`KanbanBoard` передаёт таб вверх через `onOpenTaskChange(taskId, tab)`,
`ProjectBoard` хранит его в состоянии и дублирует в адрес через
`onOpenTaskRouteChange`, а `App.tsx` разбирает `segments[4] === 'preparation'`
(соседний сегмент того же уровня, что и `/chat/:chatId`) и возвращает его в
`initialOpenTaskTab` → `TaskModal.initialTab`. Побочный эффект той же проводки:
теперь любое открытие карточки с доски пишет `#/projects/:id/task/:taskId`, а
закрытие возвращает `#/projects/:id`. Дальнейшее ручное переключение вкладок
внутри модалки адрес не меняет.

`TaskPreparationTab` грузит все попытки задачи одним `loadRuns` (свежие первыми),
выбирает активную (`task.taskPreparationRunId`) либо первую в списке и даёт
открыть ленту любой прошлой попытки кнопками списка «Предыдущие попытки»
(`data-testid="task-preparation-history"`, подпись «Попытка N · дата · статус»).
Показывает `Статус: выполняется|успешно|ошибка|отменён`, «Причина ошибки» в
`role="alert"` для failed, список `gateReasons`
(`task-preparation-gate-reasons`), потоковый `log` в `aria-live="polite"` и
пустое состояние `task-preparation-empty` («Подготовка к разработке ещё не
запускалась»), когда истории нет. Реальное время сделано поллингом: пока
`task.taskPreparationStatus === 'running'`, история перечитывается раз в 1,5 с,
поэтому лог растёт без перезагрузки страницы; отдельного SSE/WS у подготовки нет.

Действия ограничены статусом самого рана, а не UI: «Отменить» рисуется только
при `status === 'running' && canCancel`, «Повторить подготовку» — только при
терминальном статусе с `canRetry`, а `canRetry` в
`mapTaskPreparationRun` истинен лишь для `failed` и `cancelled`. То есть
успешную подготовку повторить из вкладки нельзя (опциональный пункт требования
не реализован); повторный проход по успешной задаче — это обычный перенос
карточки обратно в `preparation`. Development-действия «В очередь» и
«Параллельно» на стадиях `backlog`/`preparation` не рисуются ни на карточке, ни
в модалке.

Контракт: `GET /api/projects/:id/tasks/:taskId/preparation/runs` (история),
`DELETE /api/task-preparation/runs/:runId` (отмена),
`POST /api/task-preparation/runs/:runId/retry` (повтор; 404 на чужой/неизвестный
ран, 409 если `canRetry` ложен). Retry не переиспользует запись, а зовёт тот же
`launchTaskPreparation`, то есть `startTaskPreparationRun` вставляет НОВУЮ строку
с `attempt = MAX(attempt)+1` по задаче — предыдущие попытки остаются нетронутыми.
Не путать два счётчика: `attempt` — порядковый номер пользовательской попытки
подготовки, а `maxAttempts: 2` в маппинге — константа внутренних повторов вызова
модели внутри одной записи (`sendAttempt` с коррекцией промпта). Рендерер ходит
через мост, каналы `tasks:listPreparationRuns`, `tasks:cancelPreparationRun`,
`tasks:retryPreparationRun` (`packages/shared/src/ipc.ts`,
`packages/ui/src/remote/httpApi.ts`).

Отмена жива и на сервере, а не только в БД. `server.ts` держит
`taskPreparationHandles: Map<runId, {cancel()}>` с handle CLI-вызова: DELETE
переводит запись в `cancelled` и глушит процесс, а `onDone`/`onError` перед
работой перечитывают ран и выходят, если он уже не `running`, — иначе поздний
`onError` запускал бы внутренний повтор у отменённой подготовки. Хук
`app.onClose` отменяет все живые handle, чтобы CLI-дети не пережили закрытие
приложения и не постучались в закрытую БД.

«Лента рана» сразу монтирует `TaskRunFeed` внутри карточки: промежуточной кнопки и
отдельного окна нет. При первом открытии он параллельно читает development-историю
из `getTaskReport` и merge-историю из `listMergeRuns`, показывает
«Загрузка технической ленты…», затем выбирает активный development/merge-ран,
иначе самый свежий завершённый. Селектор группирует типы в отдельные
`optgroup` и рядом показывает чип `Development`/`Merge`; отсутствие запусков и
ошибка списка имеют отдельные состояния, ошибка допускает повтор без закрытия
карточки. Панель создаётся только у открытой вкладки, поэтому история выбранного
development-рана запрашивается сразу при входе в неё.

Development-вариант использует штатный `RunFeed` непосредственно в панели:
шаги, модельные команды, stdout/stderr, вопросы и действия остаются теми же, что
в полной технической ленте. Компонент подписывается только на выбранный `runId`,
отбрасывает кадры других запусков и при переключении отписывается от прежнего.
REST-история, snapshot и live-кадры объединяются без очистки уже показанного:
шаги — по `step.id`, лог — по монотонному `CiLogLine.seq`, интеракции и fix-попытки
— по `id`. То же объединение истории и realtime применяется в `projectsStore`, так
что повторный кадр и reload/reconnect не создают дубль и поздний REST-ответ не
стирает свежую запись.

`RunFeed` сам является вертикальным scroll-контейнером. Пока пользователь у
нижней границы, новые события прокручивают его к концу; ручная прокрутка вверх
выключает автопрокрутку и показывает липкую кнопку «К новым событиям». Нажатие
возвращает к концу и снова включает следование. Merge-лог соблюдает то же правило
и при ошибке своей первоначальной загрузки показывает «Повторить».

Панель «Лента рана» — единственная вкладка `TaskModal` с классом
`.task-run-feed-tab`: её flex-basis и ширина равны `100%`, а `min-width: 0`,
`max-width: 100%`, `box-sizing: border-box` и скрытое внешнее переполнение не дают
содержимому расширить модалку. `TaskRunFeed` оборачивает тем же полноширинным
`.task-run-feed` не только development- и merge-ленты с селектором попыток, но и
загрузку, ошибку и пустое состояние. Вложенные шаги, статусы, детали и служебные
блоки ограничены `min-width: 0`/`max-width: 100%`; длинные маршруты и сообщения
переносятся, а строки терминалов прокручиваются по горизонтали только внутри
`.ci-log` и `.merge-terminal`. Инвариант одинаков для desktop/mobile и тем, при
этом CSS остальных вкладок не меняется. Источники —
`packages/ui/src/components/kanban/TaskModal.tsx`,
`packages/ui/src/components/ci/TaskRunFeed.tsx` и `packages/ui/src/styles/app.css`.

## Ручное исключение ожидающего рана

На карточке с `queued`-раном есть опасная кнопка «Убрать из очереди» с подтверждением; после подтверждения она вызывает `POST /api/ci/runs/:runId/dequeue` (`REST.ciRunDequeue`). `CiRunManager.dequeue` без `await` в одном ходе event loop проверяет статус, отменяет ещё активный ожидающий ран и переносит его задачу в колонку с semantic type `backlog` (TODO); ран финализируется как `cancelled`, а аудит получает `run.dequeued`. Повтор для уже отменённого рана идемпотентно возвращает `removed`; отсутствие активного локального исполнителя, например после рестарта, даёт `not_queued` и не меняет доску.

Этот запрос не является общей отменой рана: его типизированный результат (`CiQueueRemovalResult` в `packages/shared/src/ci.ts`) различает `removed`, `running`, `not_queued` и `not_found`. Если к обработке запроса `execute` уже успел перевести ран в `running` или `awaiting_input`, сервер не отменяет его и возвращает `running`; store сразу применяет полученный актуальный ран и показывает подсказку открыть ленту и остановить выполнение, если задачу всё ещё надо вернуть в TODO. Поэтому интерфейс не сообщает ложный успех в гонке старта. Кнопка видна только пока сводка рана `queued` (`packages/ui/src/components/kanban/TaskCard.tsx`).

## Перенос из разработки в TODO

`POST /api/projects/:id/tasks/:taskId/move` (`apps/server/src/routes/projects.ts`) отдельно обрабатывает перенос карточки из колонки `development` в `backlog` (TODO). Он берёт последнюю сводку CI-рана задачи до переноса. Для `queued` синхронно вызывает `CiRunManager.dequeue`: ран финализируется как `cancelled`, поэтому успешный перенос не оставляет его в очереди для последующего запуска. Вызов не содержит `await`, так что исполнитель не может начать этот ран между проверкой и исключением.

Если последний ран уже `running` или `awaiting_input`, `dequeue` не маскирует выполнение: маршрут отвечает `409` с требованием сначала остановить ран в его ленте, а карточка остаётся в исходной колонке. Карточка без активного рана переносится обычным образом. Это правило действует только для направления `development` → `backlog`; остальные перемещения не меняют очередь.

## Автозапуск при переносе Ready for Development → Development

Перенос карточки из системной `ready` в системную `development` — единственный
drag&drop-переход, который сам ставит обычный development-run в общую
FIFO-очередь. Триггер сужен намеренно: маршрут `tasks/:taskId/move` требует
одновременно `semanticType` цели `development`, семантику `ready` у колонки
источника и чтобы сервер видел карточку либо ещё в `ready`, либо уже в
`development`. Колонку источника присылает клиент полем `fromColumnId`
(`tasks:move` в `packages/shared/src/ipc.ts`, снимок `columnId` до
оптимистичного переноса в `moveTask`, `packages/ui/src/store/domains/projectsStore.ts`) —
без него повторный или конкурирующий запрос уже не смог бы отличить настоящий
переход от сортировки, потому что карточка к тому моменту лежит в
`development`. Переход из `backlog`, `component_qa`, `done` и любой другой
стадии, как и перетаскивание внутри `development`, остаётся обычным `move` без
побочных эффектов.

Порядок операций обратный привычному: сначала ран, потом колонка.
`CiRunManager.startForDevelopmentTransition` идемпотентно возвращает
`{ run, existing }`: сперва ищет активный ран задачи запросом
`VoiceChatDb.activeCiRunForTask` (`queued`/`running`/`awaiting_input`), при
находке переиспользует его, иначе выполняет обычный `start()` со стандартными
настройками задачи и проекта — без параметров, доступных явному запуску.
Проверка-и-создание идёт синхронно, в одном ходе event loop, поэтому два почти
одновременных переноса одной карточки дают ровно один ран; на всякий случай
после отказа и после исключения из `start()` проверка активного рана
повторяется, и найденный ран возвращается как существующий. Запрос, у которого
`fromColumnId` указывает на `ready`, а карточка уже фактически в `development`
(проигравший гонку второй запрос), вызывает менеджер с `createIfMissing = false`
— он только переиспользует активный ран и отвечает 409, если такого нет.
Только после успеха маршрут двигает карточку `db.moveTask` с запрошенными
`afterId`/`beforeId`, шлёт `boardHub.emit` и возвращает задачу; id связанного
рана уходит заголовком `x-ci-run-id` для диагностики и тестов — UI его не
читает, ран приезжает на доску следующим снимком.

Ошибка постановки в очередь оставляет карточку в `ready`: маршрут отвечает 409 с
человекочитаемым `error` от `start()` (машина проекта не задана, выбранная
машина offline или больше недоступна, нет доступных движков и моделей, для
задачи уже выполняется ран), а отсутствие CI-менеджера — 503 «Сервис запуска
development-run временно недоступен». Оптимистичный UI по отказу восстанавливает
предыдущий снимок доски и показывает текст ошибки тостом с «Повторить»
(`moveTask` → `fail`). Диагностика — структурные записи `pino`:
`development transition linked to run` с `runId` и флагом `existing` на успехе и
`development transition rejected` с причиной на отказе.

Автозапуск не подменяет и не блокирует явное действие «Параллельно»: оно
остаётся отдельным пользовательским запуском (`launch: 'parallel'`, мимо FIFO и
лимита общей очереди, с автоподбором машины), а drag&drop всегда создаёт
обычный queued-run. Общий инвариант «один активный ран на задачу» никуда не
делся, но у двух проверок разная память: `start()` смотрит in-memory карту
активных исполнителей, а переход — таблицу `ci_runs`, поэтому после рестарта
сервера перенос переиспользует уцелевший `queued`-ран, а не создаёт второй.
Сценарии закрыты тестами `apps/server/src/ci/runManager.test.ts` (гонка двух
переносов, отказ без машины, отсутствие рана при прочих переходах и при
сортировке) и `packages/ui/src/App.projects.dom.test.tsx` (тост с причиной и
откат карточки в `ready`).

## Куда уезжает карточка после рана разработки

`settleTaskColumn` завершает ран одним переносом. Успешная разработка без
legacy merge-шага всегда переходит в колонку с semantic type `component_qa`;
интеграционные и ручные проверки больше не подменяются development-run.
Development-run нельзя запустить из `backlog` или `preparation`. Наличие
успешного legacy merge-шага по-прежнему переводит старый workflow в `done`.
Ошибка, отмена или таймаут могут вернуть карточку в `prev_column_id`
через `rollbackTask`, только пока она остаётся в `run_column_id` этого рана и
нет более нового активного рана. Ручной перенос после запуска имеет приоритет;
если нужной колонки нет, карточка также остаётся на месте.

Повтор полного рана и `retryFromFailed` на время исполнения возвращают карточку
в `development`, а после успеха снова отправляют её в `component_qa`.
Неудачный push ветки по-прежнему закрывает ран как `failed`, поэтому до
успешного перехода дело не доходит. Завершение merge, production deploy и
перевод в `done` должны происходить самостоятельными стадиями workflow, а не
финализацией разработки.

## Отмена рана

`POST /api/ci/runs/:runId/cancel` → `CiRunManager.cancel`: строка в ленте
(«Отмена рана: останавливаю шаг…»), аудит `run.cancel_requested`, `abort()` у
`AbortController` рана и снятие возможной паузы. Дальше сигнал доходит до всех
уровней исполнения, и это главное отличие от прежнего поведения:

- **Команды шага** — `signal` уже был у `executor.run` → `AgentRegistry.execStream`
  шлёт агенту `exec.cancel`.
- **Работа модели** — `runTurn` (`ci/modelHooks.ts`) слушает `ctx.signal`
  (`CiRunPrimitives.signal`), вызывает `LlmHandle.cancel()` и **сам** закрывает
  промис хода: `cancel()` в клиенте глушит `onDone/onError`, поэтому раньше
  `execute` навсегда висел на этом `await`, ран оставался `running`, а очередь
  проекта (`projectChains`) стояла до перезапуска сервера. `modelWork` возвращает
  `{ ok: false, cancelled: true }`, `attemptFix` выходит из fix-loop.
- **Процесс CLI** — `killCliChild` (`apps/llm-runner/src/cli/childKill.ts`, общий для claude и
  codex): SIGTERM, через 5 с SIGKILL. Заодно обрывается MCP-запрос remote-bash,
  и его команда на машине отменяется по `close` ответа.
- **Дерево процессов на машине** — `exec.cancel` у агента снимает **группу**
  процессов (`killProcessTree`, `apps/agent/src/exec.ts`: команда запускается
  `detached`, сигнал уходит на `-pid`; Windows — `taskkill /T`). Раньше SIGTERM
  получал только shell, а `npm ci`/тесты продолжали работать сиротами. Правка
  живёт в бандле агента — на машинах она появляется после переустановки/рестарта
  компаньона.

Ран закрывается как `cancelled` (не `failed`) на любой стадии: в очереди (шагов
не появляется вовсе), в слоте команд, в фазе модели; карточка возвращается в
`prev_column_id`. Ран **из очереди** закрывается прямо в `cancel`, не дожидаясь
своего слота: иначе он висел бы `queued` до конца чужого рана, а карточка после
«Отменить» показывала «в очереди».

Задачу отменённый ран отпускает сразу: `hasActiveRunForTask` пропускает
закрывающиеся раны (`isClosingRun` — поднятый `abort` или терминальный статус в
БД), поэтому «В очередь» сразу после «Отменить» стартует новый ран, а не отвечает
«Для этой задачи уже выполняется ран». Папку и ветку подвисший исполнитель может
держать ещё несколько секунд — новый ран не валится конфликтом изоляции, а ждёт
их освобождения (фаза «Жду освобождения рабочей директории», не дольше
`cancelGraceMs` + 1 с) и только потом сдаётся.

Сторож `guardCancel`: если `execute` не завершился за
`cancelGraceMs` (15 с, в тестах короче) после `abort`, `hardCancel` закрывает
незавершённые шаги и ран (`run.cancel_forced`), отпускает серверный слот и
**звено `projectChains`** — очередь проекта едет дальше даже с подвисшим
исполнителем. Подвисший `execute`, догребший до конца позже, ран уже не
перепишет: `finalize` не меняет статус `cancelled` ни на что другое.

## Изоляция кэша npm

Все раны идут на одной машине под одним пользователем, поэтому общий `~/.npm`
ломался, когда два `npm ci` работали одновременно: `EEXIST` при `rename` в
`_cacache/content-v2`, затем `ENOENT` на `stat` — шаг падал с кодом **254**, и
ретраи не помогали, пока кэш не чистили руками. Раннер даёт каждой задаче свой
кэш: в env шага уходят `NPM_CACHE_DIR` и `npm_config_cache` =
`$REPO_ROOT/.npm-cache/$TASK_KEY`. Каталог создаётся системным шагом «Подготовка
рабочей директории», там же `touch` (отметка «использован») и удаление кэшей, к
которым не ходили две недели. Кэш лежит **рядом** с рабочими копиями, а не внутри
рабочей директории: её сносит `is_cleanup` в конце рана, и каждый повтор качал бы
пакеты заново.

## Инфраструктурные ошибки шага

`classifyCiInfraFailure` (`ci/infraErrors.ts`) смотрит хвост вывода упавшего шага
и отличает сбой машины от ошибки задачи: повреждённый кэш npm (`EEXIST`/`ENOENT`/
`EINTEGRITY` в `_cacache`), `ENOSPC` и потерю связи с машиной. Такой шаг **не идёт
в fix-loop** — в рабочей копии он не лечится, а модель уводит диагностику в проект
(реальный случай: три хода opus на `TAR_ENTRY_ERROR` от битого кэша). Вместо этого
в лог шага пишется диагноз с подсказкой («почистить кэш», «кэш изолирован не был»),
в аудит — `run.infra_error` с `kind`, фаза рана называет причину ярлыком из
`CI_INFRA_LABEL`, и ран падает сразу.

Сбой исполнителя приходит **исключением**, а не строкой stdout: реестр машин
отклоняет вызов с «Машина отключилась во время выполнения команды» или «Машина не
в сети», код выхода шага остаётся пустым. `runCommandStep` кладёт такое сообщение
и в `output` шага — иначе классификатор его не увидит. Признак `agent_offline`
поэтому требует обоих условий: пустой код выхода **и** сообщение в самом хвосте
вывода; тот же текст с кодом выхода или в середине лога (свои же тесты печатают
его как название кейса) остаётся ошибкой задачи. Реальный случай — ран CHAT-115:
отложенная пересборка прода пересоздала контейнер сервера посреди рана, шаг
«Удалить рабочую папку задачи» получил отключение машины, и три попытки fix-loop
ушли в исчезнувший `runner-work`.

## Стандартный пайплайн проекта

Справочник команд — это **данные** (`ci_commands` + `ci_slot_commands`), набор
и порядок задаются в UI проекта. Стандартный development pipeline ограничен
подготовкой и публикацией ветки задачи:

**Слот «до модели»**

1. **Клонировать репозиторий задачи** — `git clone --branch $BASE_BRANCH
   --single-branch`; существующая копия с локальными правками → exit `66`
   (dirty workspace, дальше решает пользователь).
2. **Установить зависимости (npm ci)**.

На MacBook, где SSH-ключ не авторизован в GitHub, сама команда клонирования не
меняется: глобальный Git rewrite `url.https://github.com/.insteadOf git@github.com:`
преобразует GitHub SSH URL в HTTPS. Конфигурация проверена клонированием ветки
`main` репозитория `sislex/voiceAIChat`; это настройка машины, а не логика
CI-раннера.

MacBook-agent запускает команды через неинтерактивный `zsh` с системным `PATH`.
Node/npm установлены в `/usr/local/bin`, поэтому путь закреплён одновременно в
`~/.zshenv` и окружении `launchctl`. Проверка из исходного урезанного PATH
`/usr/bin:/bin:/usr/sbin:/sbin` получает `/usr/local/bin/node` v22.19.0 и
`/usr/local/bin/npm` 10.9.3; без машинной настройки шаг `npm ci` не должен
полагаться на интерактивный shell profile.

**Слот «после модели»**

3. **Закоммитить оставшиеся изменения в ветку задачи** — `checkout -B $BRANCH`,
   `add -A`, коммит `«$TASK_KEY: работа CI-рана»`. Чистое дерево допустимо:
   модель могла закоммитить работу сама.
4. **Системно отправить ветку задачи в origin** — единственный обязательный push
   development-рана. Он использует `--force-with-lease` при расхождении и только
   после подтверждения сохраняет branch, SHA, машину и `pushed=1`.

До слота выполняются работа модели и системная проверка результата модели.
Affected-check и актуализация БЗ перенесены в merge-workflow; merge и production
deploy принадлежат merge/release workflow. Cleanup в development отсутствует,
поэтому workspace сохраняется для QA, диагностики и повторной разработки.

Проверенный профиль ChatAI: проект использует `main`, шаблон ветки
`feature/{task_number}-{slug}`, машину `45.135.182.251` с репозиториями в
`/root/VoiceAIChatRepos`. Гейт `npm run affected-check` имеет таймаут 30 минут,
флаг `is_test` и `available_to_model = 1`; он не входит в слот «после модели».
Точка входа `scripts/affected-check.mjs` сравнивает свой URL с
`pathToFileURL(process.argv[1]).href`: это сохраняет запуск гейта из рабочей
папки с не-ASCII символами в пути. Сравнение с шаблоном `` `file://${process.argv[1]}` ``
было ложным всегда, потому что слаг рабочей папки берётся из русского заголовка
задачи: `main()` не вызывался, `npm run affected-check` выходил с кодом 0 и пустым
выводом, и гейт рана не проверял ничего. Так в `main` попали пять красных тестов
(раны CHAT-112, CHAT-114, CHAT-115) и зависание `UsersAdmin.dom.test.tsx`, из-за
которого ui-набор не доходил до конца (см. [ui.md](../ui.md), про пустые пропсы по
умолчанию). Замер после починки: полный гейт монорепо (typecheck + все тесты, 2679
тестов) — **около 9 минут** на этой машине, так что таймаут 30 минут — это запас
втрое, а не предел.

При двух параллельных пакетных гейтах `affected-check` ограничивает внутренний
пул каждого Vitest. Для Vitest 2.x обязательно передавать согласованную пару
`--minWorkers=1 --maxWorkers=1`: один `--maxWorkers=1` при вычисленном по CPU
минимуме может дать JSON с `success:true`, но нулём suites и кодом выхода 1.
Аргументы формирует `packageArgs`, их инвариант покрыт
`scripts/affected-check.test.mjs`.

Коммит и единственный системный push development-ветки недоступны модели и
обязательны. Интеграционные операции не создают шагов development-ленты.

Команды справочника, включая гейт, модель получает MCP-инструментом только при
`available_to_model = 1`; `is_cleanup` и встроенная БЗ всегда исключены.
Вызов команды создаёт вложенный шаг ленты и учитывается в общем лимите
`maxModelCommandCalls` (дефолт 20), поэтому лимит оставляет место для `npm ci` и
самопроверки.

Внутри модельного хода исходники читаются специализированным remote-MCP
инструментом `read` (оконно, с номерами строк), ищутся через `grep`, а точечные
замены выполняются `edit`. Директива рана прямо запрещает использовать `bash`
для чтения файлов и правок heredoc; `bash` остаётся для команд вроде `git`,
`npm` и шагов проверки. Все файловые пути считаются относительно workspace
рана. В plan-фазе `read`/`grep` работают, а `edit` отклоняется.

## Актуализация базы знаний (общий код merge-workflow)

Строка справочника `ci_commands.builtin = 'kb_update'` сохраняется для истории,
но миграция удаляет её из development-слотов. Проверенная реализация
`ci/modelHooks.ts` + `kb/codeUpdate.ts` переиспользуется обязательной стадией
`MergeRunManager.kb_update`; модель как CI-инструмент её не видит.

Сервер проверяет корень постоянного merge-клона, а `KB_DIFF_SCRIPT` получает
`KB_BASE_REF` зафиксированного target SHA. Поэтому контекст — итоговый merged
tree относительно target, а не незакоммиченный development workspace.
Файловые темы `docs/kb/*.md` модель правит сама (там же `kb.mjs touch`,
`kb:log`, `kb:index`), статьи `scope='project'` возвращает JSON'ом — их пишет
сервер через `db.saveKbDocument`, как в «Исследовать проект».

Финальный контракт `kb_update` — один объект с обязательными полями `note:
string`, `nothingToUpdate: boolean`, `topics: string[]` и `documents: array`;
каждый документ целиком задаёт `id` (строка, пустая для новой статьи), `title`,
допустимый `kind`, `tags`, `areas` и `body`. Необязательных полей у контракта
нет, и лишние поля не игнорируются: неизвестный ключ в корне или в документе —
такая же ошибка, как отсутствующий обязательный. Капы прежние (`MAX_DOCUMENTS`
= 12 статей, `MAX_BODY_CHARS` = 24 000 символов тела): превышение числа статей
отклоняет ответ целиком, слишком длинное тело сервер обрезает с пометкой.

Разбор (`parseKbUpdateOutput`) — это два независимых этапа, и это главное
отличие от прежней реализации. Транспортный `extractKbUpdateJson` сначала
пробует разобрать весь ответ как чистый JSON и только при неудаче ищет
fenced-блоки: принимается единственный блок с меткой `json` либо единственный
блок без метки, содержимое которого начинается с `{` и содержит ключ контракта.
Поиск «от первой до последней фигурной скобки» не применяется намеренно — это он
раньше подбирал JSON из отчёта модели. Несколько подходящих блоков — отказ по
неоднозначности, а не догадка о том, какой из них финальный. Практический смысл:
обычный текстовый отчёт перед единственным ```` ```json ````-блоком и хвост после
него — валидный ответ, а не «ответ неразборчив».

Структурная валидация (`validateKbUpdateJson`) проверяет уже извлечённое
значение и целиком проходит до первой записи в БД. Проверяются корень-объект,
типы всех обязательных полей, `topics` как массив непустых строк, каждый
документ по всем полям и согласованность флага: `nothingToUpdate=true` допустим
только при пустых `topics` и `documents`, а `false` требует хотя бы один
документ. Молчаливого отбрасывания плохих документов больше нет — невалидность
одного отменяет сохранение всего набора, так что повторный merge начинает с
чистого состояния.

Диагностика различает четыре причины отказа через `KbUpdateParseError.code`:
`json_not_found`, `ambiguous_json`, `invalid_json`, `invalid_contract`. Хук
пишет полную причину с путём поля (например, `documents[1].title`) в
технический лог стадии через `log()`, а наружу возвращает короткое сообщение
своей категории — текст ответа модели в UI не попадает.

Для `json_not_found`, `invalid_json` и `invalid_contract` хук делает ровно один
короткий repair-ход через `sessionId` основного хода. Он использует тот же
`stageRunner` и общий `AbortSignal` стадии, поэтому расход агрегируется как второй
ход `kb_update`, а таймер не перезапускается. Repair получает буквальную схему
контракта и правила согласованности, выполняется с `executionDisabled` без remote,
KB и CI MCP и не может читать или менять проект. `ambiguous_json` остаётся
fail-closed; без `sessionId` независимый ход не создаётся. Ответы двух ходов не
объединяются: только полностью валидный repair-объект допускает последующую
запись всех документов. Таймаут и отмена гасят открытый repair тем же способом,
что основной ход; существующая политика сохранения уже сделанных файловых тем
`docs/kb` при таймауте не меняется.

Третьего хода не бывает ни при каком исходе. Repair вызывает `stageRunner` с
выключенным фолбэком на модель рана (`allowModelFallback = false`): пустой ответ
стадийной модели здесь не повторяется на модели разработки, иначе повтор ушёл бы
в новую сессию без контекста исследования. Невалидный или оборванный repair —
конец стадии. Stdout repair-хода в ленту не транслируется вовсе (в `ctx.log`
уходит только поток `system`), поэтому сырой текст второй попытки не может
просочиться в UI даже при провале разбора. Наружу стадия отдаёт фиксированные
строки: успех получает префикс «Финальный JSON восстановлен дополнительным
запросом» перед обычным резюме, отказы — «Модель повторно не вернула корректный
JSON…», «Repair финального ответа не выполнен: сессия модели недоступна» и
«Repair финального ответа не завершён до таймаута». Технический лог, наоборот,
подробен: код и текст исходной ошибки, факт запуска и наличие `sessionId`,
длительность хода в миллисекундах, код ошибки repair и итог. Отдельной
development-операции repair не создаёт — оба хода идут через тот же
`stageRunner`, поэтому токены, стоимость и длительность ложатся двумя строками
расхода в метрику стадии `kb_update`.

Второй вход шага, наравне с дифом, — **пробелы базы знаний за ран**
(`collectKbGaps`): вопросы, на которые база не ответила или ответила неполно.
Источников два, и они закрывают разные дыры. Названные самой моделью приходят
блоком `kb-gaps` из её ответа (`parseKbGaps`, `db.addCiRunKbGaps`) и несут уже
найденный по коду ответ. Обращения со статусом `empty`/`error` берутся из
телеметрии (`db.kbUsageRunGaps`) — они видны, даже если модель про блок забыла;
ответа у них нет, и шаг ищет его в коде рабочей копии. Вопрос, который позже
ВСЁ ЖЕ был отвечен тем же текстом, из списка выпадает: там была неудачная
попытка, а не пробел. Дубли снимаются дважды — ключом `(ран, вопрос)` в
`ci_run_kb_gaps` (повтор берёт более полный ответ, сохраняя порядок первого появления) и отбрасыванием уже названных
вопросов при сборке списка. В промпте (`gapsBlock`) каждый пункт обязан стать
правкой того раздела, где эти сведения искали: сначала сверка с кодом, потом
дополнение существующего раздела, а неподтверждённое не пишется вовсе —
незакрытый пробел дешевле записанной догадки.

Ход шага идёт на модели стадии `kb_update` (дефолт — `sonnet`, см. «Модель в
цикле»): сверять диф с текстом статей на модели разработки — 14% цены рана за
работу другого класса. Замер opus против sonnet на одном дифе — ниже, в «Замере
расхода».

Стадия обязательна для merge: ошибка корня, дифа, модели, разбора или сохранения
останавливает ран до push. При таймауте валидные файловые темы разрешают
продолжение, но проектные статьи без структурированного ответа не сохраняются;
без файловых изменений таймаут остаётся ошибкой.

Лента CI-рана — служебные данные сервера и UI, а не MCP-инструмент модели: ей
доступны `remote-bash` для рабочей копии и опубликованные команды CI, но отдельного
API для чтения ленты задачи или CI-рана нет. Разбирать историю конкретного рана
можно через UI либо серверные REST-эндпоинты (например, `kb-usage` ниже), а не
ожидать её среди инструментов модели. Пустой диф И отсутствие
пробелов — успех с записью «нечего обновлять», хода модели при этом нет вовсе;
пустой диф с пробелами ход делает (ран мог быть исследованием, у которого база не
ответила) и в промпте честно говорит, что изменений кода нет.

Ручной фолбэк — «Исследовать проект» с телом `{ sinceSha }` (`kb/research.ts`):
тот же промпт (`kbUpdatePrompt`), но диф модель собирает сама и файлы не правит —
рабочая копия проекта общая для чат-сессий. Разбор ответа у него другой:
research остался на прежнем терпимом `parseResearchOutput`/`parseModelDocuments`
(`kb/modelDocs.ts`) — тот подставляет `kind: 'subsystem'` по умолчанию, молча
отбрасывает статьи без заголовка или тела и всё ещё ищет JSON регуляркой по
скобкам. Строгий контракт с атомарным сохранением действует только на стадии
`kb_update`; при правке `modelDocs.ts` нужно помнить, что у двух путей теперь
разная политика ошибок при одном формате ответа.

## Режим запуска и глубина уточнений

`CiLlmConfig` несёт не только `provider`/`model`, но и `mode` (`plan`|`development`),
`clarifyLevel` (`none`|`few`|`medium`|`detailed`) и `clarifyMax` (1..30, только для
`detailed`); бюджет вопросов считает `clarifyBudget()`. Конфигурация задачи
наследуется от проекта и `DEFAULT_CI_LLM_CONFIG` (`resolveTaskLlmConfig`), правится
в `CiTaskSettings` и `CiProjectDefaults`; при обычном запуске раннер берёт
`provider`/`model` из пользовательских настроек, а из CI-конфига — режим и
уточнения. Окно запуска новой задачи по умолчанию показывает пару из этих настроек
и отправляет выбранные `provider`/`model` разовым параметром `POST …/ci/run`; эта
пара фиксируется в `ci_runs.llm_provider/llm_model`, не меняя настройку карточки.
Тот же запрос принимает разовый `{ mode }`.

## Пауза рана: вопросы модели и одобрение плана

Один механизм на оба случая — таблица `ci_interactions` (`kind: clarify|plan_approval`)
и нетерминальный статус рана `awaiting_input`. Работа модели (`modelWork`) —
фазовый цикл ходов CLI в **одной сессии**: `runTurn` захватывает `onSession`, и
следующий ход идёт с `--resume`/`codex resume`. В режиме `plan` первый ход идёт
**не** в CLI-режиме `plan` (он глушит MCP целиком — «Cannot call mcp__remote__bash
while in plan mode», а рабочая копия доступна модели только через remote MCP), а в
`permissionMode: 'default'` с белым списком инструментов: правки файлов CLI отклоняет
сам, remote-bash подключается с `&ro=1` (только чтение, `mcp/planMode.ts`), команды
CI-справочника в план-фазе не публикуются. Ветка план-фазы в `modelHooks.ts`
пересобирает `remote` вручную, поле за полем (`mcpUrl` с `&ro=1`, `agentName`,
`projectMachines`), а не берёт готовый `base.remote` целиком — это единственный
способ снять `ciMcpUrl`. Поэтому любое новое поле `LlmRequest['remote']`
(`packages/shared/src/llm.ts`) без явного переноса в эту ветку молча пропадает
именно в фазе плана, а не в развитии. Затем гейт `askPlanApproval`: `approved`
переводит тот же диалог в `acceptEdits` (слот «после» и резюме идут как обычно), `rework` даёт
модели комментарий и новый план, отсутствие решения (таймаут/отмена) завершает ран
как `cancelled` без слота «после». Уточняющие вопросы разбираются существующим
`parseQuestions` из `@shared/questions` — нового формата нет.

Раны переживают только свой процесс: при старте `buildServer` вызывает
`db.failInterruptedCiRuns()` — раны в `queued`/`running`/`awaiting_input` от прошлого
процесса закрываются как `failed` (незавершённые шаги — `failed`/`skipped`, ожидание
ответа снимается). Иначе после рестарта контейнера карточка задачи навсегда считала
бы CI занятым.

Ожидание **отпускает серверный слот** (`releaseSlot`/`acquireSlot` вокруг await):
одобрение плана может длиться часами, а `maxConcurrentRuns` по умолчанию 2. Слот
привязан к рану (`RunSlot`), а не к вызову: если ран за время паузы закрыли
(в том числе сторожевым таймаутом отмены), зомби-`execute` слот обратно не
берёт — иначе лимит утекал бы по слоту на ран. Лимит ожидания —
`CiGlobalSettings.interactionWaitMs` (30 мин, `0` — без лимита); по таймауту
для `clarify` модель продолжает без уточнений, для гейта плана ран отменяется.

Вопрос дублируется в **связанный чат задачи** обычным AI-сообщением с блоком
```` ```questions ```` и меткой `TurnMeta.ciInteraction` — `ChatColumn` рисует его
готовым `QuestionsForm`, нового UI в чате нет. Ответить можно из ленты или из чата,
побеждает первый (`answerCiInteraction` обновляет строку только пока она `pending`,
повторный ответ — 409). Сервер дописывает ответ репликой в тот же чат.
REST — `POST /api/ci/runs/:runId/interactions/:id`, WS — `ci.interaction`,
`CiRunDetail.interactions` нужен для реплея после reload.

## Резюме рана в связанном чате

Шаг «Резюме модели» не только пишется в лог рана, но и уходит **отдельным
AI-сообщением в связанный чат задачи** (`postSummaryToChat` в `CiRunManagerDeps`,
проводка — в `server.ts`): работу обсуждают в чате, а лента рана служебная и
перекрывается следующим запуском. Текст = шапка `Резюме по задаче <PRJ-N> · <заголовок>`
плюс текст модели; метка `TurnMeta.ciRunSummary = { runId }` отличает его от ответа
хода. Сообщение появляется при любом исходе, где шаг резюме вообще выполнялся
(в том числе при упавшем слоте «после»); отмена рана резюме не даёт. Чат удалён —
`addMessage` бросает, дep возвращает `null`, ран это не роняет.

Кадр `chat.message` (`{ conversationId, message }`) рассылается тем же каналом,
что события рана (`CiRunManager.subscribe` → `session.ts` → сокеты владельца), мост —
`window.ci.onChatMessage`, стор — `applyChatMessage` (дописывает через
`appendPersisted`, только если этот чат открыт; дубли по `id` отбрасываются).
Имя нового связанного чата — «Задача <заголовок>», см. [projects.md](../projects.md).

## Модель в цикле

`createCiModelHooks` (`ci/modelHooks.ts`) на инъектируемом `LlmClient`: работа
модели (remote-bash MCP строго в корне клонированного репозитория
`{repos_root}/{project}/{task_number}`, а не в родительском каталоге проекта,
многоходовый цикл с паузами, предел `MAX_MODEL_TURNS`), резюме, fix-loop (диагноз→правка→повтор
упавшего шага, лимиты `maxFixAttempts`/`fixTimeLimitMs`, предложения по правке
скрипта). URL для `remote-bash`, `ci-commands` и `kb` сервер теперь строит одной
функцией `buildPublicMcpUrl` (`apps/server/src/mcp/publicBase.ts`): с
`VC_MCP_PUBLIC_BASE` исполнитель получает публичный адрес Fastify вроде
`http://voicechat:8787/...`, без env остаётся loopback `http://127.0.0.1:<PORT>`.
Это убирает захардкоженный `127.0.0.1` из кода, но сохраняет старое поведение в
dev и Vitest.

**Базовая модель и исполнитель рана — пользовательские.** При старте
`CiRunManager` фиксирует в `ci_runs` provider, model и разрешённый для роли
`llmEngineId` из `Settings` пользователя, который запустил задачу. Сохранённые
CI-конфиги проекта/карточки задают только режим и параметры уточнений; они не
переопределяют пользовательский выбор LLM. **Модель назначается на стадию, а не
на ран.** `modelFor(ctx, stage)` спрашивает
`resolveCiStageModel` (`shared/src/ci.ts`) с настройкой `ci_settings.stage_models`
(JSON `CiStageModels`, ключи — те же `CiUsageKind`, что у строк расхода:
`model_work`/`fix`/`kb_update`/`summary`). Пустое значение стадии — модель рана,
и разработка с fix-loop по умолчанию именно на ней: экономия там означает худший
код, а он дороже сэкономленного. Дефолт `DEFAULT_CI_STAGE_MODELS` — `kb_update`
на `sonnet`, `summary` на `haiku`: по замеру CHAT-70 актуализация базы знаний
стоила $2.75 и 6.9 минуты (14% цены рана), резюме — ещё $0.11, а сверка дифа с
текстом статей и пересказ шагов — работа не того класса, что разработка. Старая
строка настроек читается как дефолт кода (колонка пустая), поэтому обновление
включает экономию само. Правится настройка в «Глобальных настройках CI» селектом
на стадию («Модель рана» = пусто, список общий для обоих движков); тело
`PUT /api/ci/settings` сливается с текущими стадиями и чистится
`normCiStageModels` — патч на одну стадию не сбрасывает соседние, а чужие ключи и
не-строки в БД не попадают.

**Недоступная модель стадии ран не роняет.** Проверок две. Статическая —
`ciModelKnown`: реестр исполнителей моделей не перечисляет, поэтому единственное,
что можно проверить, — знает ли алиас сам CLI (`default`/`opus`/`fable`/`sonnet`
/`haiku` с необязательными `claude-` и `[1m]`, у codex — `CODEX_MODELS`);
claude-алиас в codex-ране и опечатка молча превращаются в модель рана.
Динамическая — `stageRunner`: если ход упал ПУСТЫМ (ни текста, ни расхода — так
выглядит CLI, который не смог начать), стадия повторяется на модели рана ровно
один раз, с записью в ленту. Откат помнится до конца вызова хука, поэтому
следующий ход диалога и следующая попытка fix-loop к сломанной модели уже не
ходят. Настоящую ошибку работы модели повторять на другой незачем — её признак
как раз в том, что ход что-то сказал.

**Модель сама проверяет результат перед завершением.** Промпт разработки
(и фазы после одобрения плана) требует прогнать штатный `npm run affected-check`,
а не сырой `npm test`, и не отдавать работу с падающими тестами или ошибками типов.
Vitest-скрипты пакетов запускаются с `--silent`: прямой прогон остаётся пригоден
для диагностики (падения видны), но штатные React-предупреждения не засоряют вывод. Команды справочника
публикуются инструментом `mcp__ci__run_command` по `available_to_model`;
проверочный признак `is_test` и текст команды их больше не отсекают. Поэтому
вызов гейта создаёт вложенный `model_command` с логом в ленте рана. Миграция
для прежнего штатного гейта `npm run typecheck && npm test` меняет скрипт на
`npm run affected-check`, сохраняет `is_test = 1` и включает
`available_to_model = 1`.

Быстрый этап гейта (`startRelatedTest` в `scripts/affected-check.mjs`) зовёт
`npx vitest related <файлы> --run` **в папке пакета**, а не через его npm-скрипт.
Причина в CLI vitest 2.x: `related` там — подкоманда
(`cli.command("related [...filters]")`), а скрипт `test` каждого пакета — это
`vitest run`, поэтому прежний `npm test -- --related …` разворачивался в
`vitest run --related` и падал с «Unknown option `--related`». Быстрый этап валил
`npm run affected-check` на любой правке кода, и заметно это было только вне
рана: в ленте шага «Запустить проверки затронутых пакетов» от `affected-check.mjs`
остаётся один заголовок npm — его собственный stdout туда не попадает.

**Fix-loop идёт тем же диалогом и получает свежую диагностику.**
`sessionId` работы модели менеджер держит в `modelSessions` (runId → id
сессии CLI), а также сохраняет в `ci_runs.model_session_id`. Поэтому
`attemptFix` продолжает тот же CLI-диалог через `--resume` не только между
попытками, но и после повторного входа менеджера в сохранённый ран. Последний
контекст падения хранится в `ci_runs.fix_context_json`: id шага, свежий хвост
лога и разобранные `CiTestFailure`. После каждого полного повтора упавшей
команды контекст заменяется его новым выводом; следующая попытка больше не видит
первоначальный устаревший лог. Успешный повтор очищает контекст.

Хвост обычного упавшего шага — 2000 символов, шага-проверки — 20 000
(`CiFixContext.isTestStep`, `tryFix` берёт 400 последних строк вместо 40).
`parseCiTestFailures` извлекает из вывода Vitest/Jest/npm пакет, файл, имя теста,
команду и сообщение; исходный хвост остаётся рядом как страховка для незнакомого
формата.

Во время каждой попытки fix-loop модель получает отдельный MCP-инструмент
`mcp__ci__run_targeted_tests`. Он принимает только конкретную точечную команду
с путём `*.test.*`/`*.spec.*` или фильтром имени теста, запрещает shell-
операторы и полный gate/typecheck/lint/build и допускает не более трёх запусков
за попытку. Точечные проверки создают вложенные шаги `model_command`, но не
расходуют `maxFixAttempts`: попытка считается только после обязательного полного
повтора исходного упавшего шага. Для каждой `CiFixAttempt` база и API сохраняют
диагноз, действие, изменённые файлы, структурированные падения, точечные прогоны
и исход полного повтора; `RunFeed` показывает эти данные в ленте.
Ослаблять гейт ради обхода ошибки промпт fix-loop по-прежнему запрещает.

Остальные команды справочника доступны модели как MCP-инструмент
`mcp__ci__run_command` (`ci/ciCommandsMcp.ts`, брокер `ciToolBroker` по токену
рана; лимит `maxModelCommandCalls` и `is_cleanup` исключены). Каждый
вызов — вложенный шаг ленты. Удалённый workspace передаётся только через
`remote.mcpUrl`; его хостовый путь нельзя задавать как локальный
`LlmRequest.cwd`, потому что CLI запускается внутри server-контейнера. Командные
шаги стартуют из каталога проекта и сами делают `cd $SLUG`, где для новых задач
`SLUG` равен стабильному номеру задачи. Поэтому раннер держит два пути: родитель
для скриптов и корень клона `{repos_root}/{project}/{task_number}` для модели,
fix-loop и KB-update. После слота «до» системный шаг выполняет
`git rev-parse --show-toplevel` именно в корне клона; если clone-скрипт положил
репозиторий не туда или ничего не создал, модель не стартует, ран становится
`failed`, а карточка возвращается в исходную колонку — пустой ответ модели больше
не может доехать до ложного merge/success.
Ошибка `model_work` останавливает ран до after-слота и сохраняет workspace. В `RunFeed`
можно выбрать Claude/Codex и модель, затем повторить с `model_work`; подготовительные
команды не запускаются повторно, выбранные provider/model сохраняются в ране и аудите.
Меню там — те же `CLAUDE_MODELS`/`CODEX_MODELS`, что в настройках, плюс отдельный
пункт для сохранённой модели, которой в меню нет, включая пустую codex-модель
(«По умолчанию (из codex)», ран уходит без `-m`). Без этого пункта селект показал бы
первый пункт списка, а повтор ушёл бы с моделью, которую никто не выбирал.

## База знаний в работе модели

Модель рана исследует проект по задаче через базу знаний, а не идёт сразу в код.
Режим задаёт настройка ПРОЕКТА `ci_kb_context_mode` (`auto` | `manual` | `off`,
дефолт `auto`) — не режим связанного чата: ран про проект, а не про переписку.
На старте режим снимается в `ci_runs.kb_context_mode`, поэтому смена настройки
действует со следующего рана, а идущий доживает в своём режиме (и лента честно
показывает, в каком он работал).

В `auto` сервер подмешивает в задание блок контекста по заголовку, описанию и
критериям приёмки задачи — тем же `kb/autoContext.ts`, что и ход чата (порог
уверенности и формат разделов общие; см. [kb-usage](kb-usage.md)). Плюс к этому
в задание уходит `kbRunDirective`: «сначала база знаний, потом код». В `manual`
авто-контекста нет, формулировка усиленная — инструменты единственный путь к базе.
`VC_KB_TOOL=off` глушит инструменты и здесь.

Инструменты `mcp__kb__*` подключаются к работе модели, fix-loop и резюме — в том
числе в фазе «план» и в ходе без машины: база read-only и от агента не зависит.
Токен хода выдаёт `kbToolBroker` и снимает `withKbTools` во всех выходах,
включая отмену рана и убийство CLI: живой токен после отмены — это чтение базы
от имени закончившегося рана.

Обратная половина требования — **пробел базы знаний обязан стать записью**. К
`kbRunDirective` пришиты `KB_GAP_RULE` (общее правило, оно же в системном хинте
`kbToolHint`, см. [llm.md](../llm.md)) и `KB_GAPS_HINT` — формат блока
`kb-gaps`: в ране модель в базу не пишет сама, поэтому закрытый пробел она
обязана НАЗВАТЬ. Блок снимается с КАЖДОГО хода работы модели (`recordKbGaps`:
пробел закрывается и в исследовании, и в ответе на уточнение, и в плане) и с
каждой попытки fix-loop — правка чужого падения такое же исследование проекта,
поэтому её промпт тоже несёт формат блока. Дальше пробелы уезжают в шаг
«Актуализировать базу знаний» (выше). Потеря пробела ран не валит: запись
обёрнута в try/catch, как метрика.

Телеметрия идёт через тот же `createKbUsageTracker` с `conversationId` связанного
чата рана и новыми `ci_run_id` / `ci_step_id`. Нет чата — база работает, метрика
молча пропускается. Ни поиск по базе, ни запись метрики не имеют права уронить
ран: любая беда превращается в обращение со статусом `error`. Отчёты —
`GET /api/ci/runs/:runId/kb-usage` (лента рана) и
`GET /api/projects/:id/tasks/:taskId/kb-usage` (модалка задачи), гейт у обоих —
членство в проекте (чужому 404). Итог рана попадает в резюме строкой
«БЗ: N обращений, M разделов, ≈K токенов; пригодились H из D (P%)» — долю
`kbSummaryLine` считает сам, прямо перед отправкой резюме: `finalize` со своим
пересчётом случится позже, а счётчик разделов без доли не сообщает главного.
Рядом отдельной строкой `База знаний:` уходит исход встроенного шага
«Актуализировать базу знаний»: на успехе — темы и статьи из
`formatKbUpdateSummary`, на ошибке — её причина. Исход сохраняется до резюме,
поэтому доезжает и когда следующий after-слот упал.

## Состояние задачи на доске

### Подписи и действия запуска

Перетаскивание карточки из `ready` в `development` само ставит ран в очередь —
см. «Автозапуск при переносе Ready for Development → Development» выше; кнопки
ниже остаются явным запуском из карточки.

На карточке канбана и в открытой карточке обычный запуск подписан «В очередь», а
пока `startCiRun` не завершил запрос — «Добавляем в очередь…». Его подсказка:
«Добавить задачу в очередь выполнения. Если свободный слот есть, выполнение
начнётся сразу». Соседнее действие «Параллельно» сохраняет подпись и поясняет:
«Запустить задачу сразу, минуя общую очередь. Машина будет выбрана автоматически
с учётом загрузки». Обе реализации находятся в
`packages/ui/src/components/kanban/TaskCard.tsx` и `TaskModal.tsx`.

Локальное состояние `launching` допускает только один запрос запуска с каждой
поверхности: во время обычного или параллельного запроса обе кнопки заблокированы,
после завершения Promise блокировка снимается. Серверная защита «один активный
ран на задачу» остаётся окончательной защитой от повторного или сетевого запроса.
После создания обычного рана `ciStatusLabel` показывает «в очереди», при работе —
«выполняется», при паузе модели — «ждёт ответа»; после отмены или другого
терминального результата действие «В очередь» снова доступно по правилам ниже.
Строки действий карточки и модалки переносятся (`flex-wrap`), а на мобильной
ширине кнопки модалки занимают доступное место без горизонтального скролла
(`packages/ui/src/styles/app.css`, `packages/ui/src/components/ci/ciFormat.ts`).

В настройках выбранной машины отдельная кнопка сохраняет подпись «Запустить на
этой машине сейчас» и подсказку «Запустить или продвинуть ожидающий ран на
выбранной машине» (`packages/ui/src/components/ci/CiTaskSettings.tsx`). Семантика
продвижения существующего queued-рана описана выше в «Параллельных ранах».

Снапшот доски несёт на каждой задаче серверный `latestRunResult`.
`VoiceChatDb.latestTaskRunResult` выбирает последний актуальный процесс среди
подготовки задачи, development, QA-этапов, Component QA, integration tests,
подготовки ручного QA, manual QA и merge. Нормализованный контракт и единственная
таблица соответствия исходов находятся в `packages/shared/src/projects.ts`: UI
принимает решение по `outcome`, а не по тексту лога или названию стадии.
`failed`, `blocked`, `timeout` и неизвестные терминальные статусы fail-closed
относятся к `failure`; `cancelled` нейтрален, а `skipped` и `stale` относятся
к пропущенному результату. Отсутствие результата означает отсутствие ошибки.

Новый подтверждённый старт сразу становится актуальным и вытесняет старую
ошибку; при одинаковом времени создания активный процесс имеет приоритет. Если
старт не создал запись, прежний результат не меняется. Сервер публикует
`board.update` при старте и терминальном исходе подключённых workflow-ранов,
поэтому тот же признак восстанавливается при загрузке и обновляется после
переподключения. Точки публикации для QA находятся в
`apps/server/src/routes/qa.ts`, `apps/server/src/ci/componentQa.ts` и
`apps/server/src/ci/integrationTests.ts`.

`TaskCard` при `outcome=failure` получает статичную красную рамку через
`box-shadow`, которая не влияет на геометрию и порядок доски, и доступную кнопку
«Последний этап завершился с ошибкой». Кнопка открывает вкладку ленты,
соответствующую `kind` результата; маршрутизация вкладок типизирована
`TaskModalTab` в `packages/ui/src/components/kanban/TaskModal.tsx`. Для active,
success, cancelled, skipped и отсутствующего результата общей красной рамки нет.
Legacy-пульс только development CI по-прежнему вычисляют хелперы
`packages/shared/src/ci.ts`; общий признак последней ошибки от него не зависит.

При финализации рана считается ещё и попадание навигации БЗ в последующее
исследование кода. `relatedFiles` (`areas` документа) сохраняются снимком в
`kb_usage_sections`; открытые моделью файлы извлекаются прежде всего из аргументов
`read`/`grep`/`edit` в `ci_run_logs`, а для старых клиентов — из bash-команд
`cat`/`sed`/`head`/`tail`/`grep`. Для каждого выданного раздела проверяется,
открыт ли хотя бы один связанный файл. В `ci_run_kb_metrics` остаётся только
агрегат: выдано разделов, попало разделов и доля — второй список файлов не
дублируется. Если разделов или логов нет, ран не падает: метрика остаётся пустой.

- `isActiveCiStatus(status)` — `queued`/`running`/`awaiting_input`. Пока активен,
  кнопка «В очередь» скрыта и на карточке, и в модалке: остаётся «Лента рана» /
  «Ответить модели».
- `canStartCiRun(summary)` — то же правило со стороны кнопки: запуск доступен,
  если рана не было или он завершён (`success`/`failed`/`cancelled`/`timeout`,
  а также `skipped`). Но карточка в колонке с semantic type `done` не предлагает
  «В очередь» ни на доске, ни в модалке: это завершённый результат, а не точка
  повторного запуска. В остальных колонках завершённый ран запуску не мешает:
  «В очередь» стартует **новый полный** ран (продолжить прошлый — «Повторить с
  упавшего шага» в ленте). Раны, оставшиеся активными после рестарта процесса, закрывает
  `failInterruptedCiRuns()` при старте сервера — иначе карточка навсегда считала
  бы CI занятым (ниже, про переживание процесса).
- Сводка на карточке выбирается единым серверным селектором
  `taskCiDisplaySummary`, который используют доска, модалка, Sidebar и связанный
  чат. Активный ран всегда главный независимо от колонки. При финализации в
  `terminal_column_id` сохраняется текущий этап, а `run_column_id` хранит
  колонку, занятую раннером. Ошибка, таймаут или отмена релевантны только пока
  текущая колонка совпадает со снимком завершения; ручной перенос скрывает их с
  поверхностей, не меняя историю.
- Отменённая или пропущенная повторная попытка не вытесняет предыдущий успех:
  `CiRunSummary` передаёт основной результат и `latestAttempt` отдельно.
  Поэтому для `success → cancelled` основной лозенг остаётся успешным, рядом
  показывается «Последняя попытка отменена» со ссылкой на её ленту. Все раны
  остаются в неизменяемой истории. Тай-брейк порядка — `created_at, rowid`.
- Rollback в `prev_column_id` выполняется только если карточка всё ещё находится
  в `run_column_id` этого рана и её не занял более новый активный ран. Ручной
  перенос во время выполнения имеет приоритет и отменой не перезаписывается.
  `ciSummaryForTask` остаётся защитой для старых/stale payload в UI.
- `ciCardPulse(summary)` → `running` | `fixing` | `awaiting` | `failed` | `done` |
  `null` → класс `jcard--ci-*` и анимация в `app.css`: ран идёт — голубая рамка
  медленно «дышит» (2.6с); модель разбирается с упавшим шагом — медленное красное
  мигание (2.2с) и снова голубое после успешного фикса; ждёт ответа пользователя —
  частое жёлтое (0.9с); свалился окончательно — частое красное (0.7с); успех
  (разработка закончена, ждёт пересборки прода) — статичная зелёная рамка.
  `cancelled`/`skipped` подсветки не дают. При `prefers-reduced-motion` рамка
  остаётся, анимация выключается.

То же отображаемое состояние видно в списке чатов и в шапке открытого чата
задачи — работу обсуждают в чате, и узнавать «модель ждёт ответа» через открытие
доски незачем. Класс считает та же `ciCardPulse`, кейфреймы в `app.css`
переиспользуются, поэтому цвета совпадают: `.convo--ci-*` на строке списка и
`.taskchat--ci-*` на шапке. Отличие одно: **мигает только активный ран**
(`running`/`fixing`/`awaiting`), у терминального рамка статичная (`failed` —
красная, `done` — зелёная) — постоянное мигание по давно упавшему рану в списке
чатов было бы шумом. Принадлежность чата к задаче видна всегда, независимо от
ранов: accent-полоска слева (`.convo--task`) плюс строка `.ctask` с иконкой типа,
ключом `PRJ-42` и лозенгой основного результата. Если `latestAttempt` сообщает
об отменённом повторе, Sidebar и шапка дополнительно показывают «Последняя попытка
отменена», не заменяя успешную лозенгу.

Данные для этого: `GET /api/conversations/task-chats` (`db.taskChatBadges(userId)`,
канал `conversations:taskChats`) — по одной `TaskChatBadge` на чат с `task_id`:
ключ, тип, семантика текущей колонки и выбранная сервером сводка
(`db.latestCiRunSummary`). Семантика нужна сайдбару без открытой доски: ручной
перенос должен сразу убрать нерелевантный терминальный результат. Запрос уходит
вдогонку списку бесед (`loadTaskChatBadges`), ответ кладётся в `taskChatBadges`
по id беседы, а сводки — в общий `ciSummaries` по `taskId`, **только если основной
ран другой или про задачу ещё ничего не известно**: состояние известного рана ведут
живые кадры `ci.*`, а `applyCiDone` при `success → cancelled/skipped` сохраняет
успех основным и добавляет терминальную попытку в `latestAttempt`. Поэтому
медленный REST-ответ не откатывает живое состояние, а после перезагрузки тот же
выбор восстанавливает сервер. Дополнительной подписки не нужно — `ci.*` уже
рассылаются на все соединения пользователя (`session.ts`), а не только
подписчикам доски.

Признак «модель чинит ошибку» — флаг `CiSlotProgress.fixing`: `tryFix` поднимает
его на входе в fix-loop (фаза «Модель исправляет ошибку») и снимает на выходе,
доска получает это через `ci.run` и через `latestCiRunSummaries` после перезагрузки.
Флаг транзитный: обычный `progress()` его не проставляет.

## Отчёт по задаче: расход модели

Когда задача выполнена, у неё видно, во что она обошлась: стоимость, токены с
разбивкой по кэшу, число запросов к модели, **контекст на запрос (средний и
максимальный)**, время рана и суммарное время работы модели, плюс все шаги CI со
статусом, попыткой и длительностью, объём ответов инструментов и три самых
тяжёлых ответа. До этого от рана оставались только длительности, а расход терялся
целиком: `runTurn` в `ci/modelHooks.ts` выбрасывал и `meta` из `onDone`, и хендлер
`onUsage`. Про контекст на запрос и его сжатие — отдельный раздел ниже.

**Один ход CLI = один «запрос к модели».** Расход пишется по каждому выходу
`runTurn` — работа модели (в том числе продолжения одной сессии после вопроса
или одобрения плана), резюме, каждая попытка fix-loop и шаг актуализации базы
знаний: все они идут через него. Строка ложится в `ci_run_usage` с `run_id` и
`step_id` (у fix-loop это упавший шаг — цикл живёт внутри него) и с `kind`
(`model_work` / `summary` / `fix` / `kb_update`). Ход, о котором CLI не сказал
ничего (мгновенная отмена, клиент без usage), строкой не становится, иначе отчёт
считал бы запросы, которых не было. Запись не бросает никогда: расход — метрика,
и ронять ей ран нельзя, как и телеметрии БЗ.

**Стоимость хранится только настоящая.** В `cost_usd` идёт `total_cost_usd` от
CLI, а когда его нет — там `NULL`, и отчёт считает оценку по
`packages/shared/src/pricing.ts` на лету, помечая её «≈» (как `SessionUsage` у
наблюдателей). Хранить оценку нельзя: смена цен переписала бы историю задним
числом. Неизвестная модель (прайса нет) тоже делает итог приблизительным — сумма
заведомо занижена. Внешнего ключа на `ci_run_steps` у таблицы намеренно нет:
шаг бывает синтетическим, а метрика не имеет права уронить ран нарушением FK.

Сама таблица цен держится на этих же строках: прайс opus и fable подобран под
`cost_usd`, которую CLI назвал на реальных ходах, и `scripts/ci-usage-report.mjs`
печатает расхождение оценки с фактом там, где известны обе (см. `shared.md` и
`testing-operations.md`). До 02.08.2026 прайс завышал opus втрое, и заметить это
было неоткуда: у claude в отчёт идёт настоящая цена, оценка достаётся только
codex — а значит, сравнение движков сравнивало факт с кривой оценкой.

`CiRunReport.kbHit` добавляет сохранённое попадание БЗ. Карточка рядом со
стоимостью и токенами показывает «БЗ: выдано N разделов, пригодились M (P% —
модель открыла файлы из них)»; для старого рана, режима `kbContextMode=off` и
рана с нулём выданных разделов строки нет. Доля важнее счётчика: «выдано 5
разделов» само по себе не говорит, пригодился ли хоть один, — поэтому ту же
долю печатает и строка резюме рана (`formatKbUsageSummaryLine`, см.
`features/kb-usage.md`), а не только этот врез.

**Модель хода — та, которой его РЕАЛЬНО запускали.** В `model` идёт `meta.model`
от CLI, а когда он молчит (codex так всегда) — модель стадии, а не модель рана:
после «модели по стадии» это разные вещи, и подстановка модели рана врала бы про
дешёвые стадии.

**Разбивка по стадиям — `CiRunReport.stages`** (`ciUsageStages`): группа на пару
(стадия, модель) с обычными `CiUsageTotals`, порядок — как в `CI_USAGE_KINDS`.
Пара, а не одна стадия: после смены настройки и в повторном ране одна и та же
стадия идёт на разных моделях, и складывать их цену в одну строку нельзя. Отсюда
и видно, чем каждая стадия посчитана и во что обошлась, — по одной сумме за ран
это не читается. Подписи стадий общие с настройками — `CI_USAGE_KIND_LABELS`.

**Агрегаты — чистые функции shared** (`ciUsageTotals`, `ciUsageStages`,
`sumCiUsageTotals`, `ciTaskTotals` в `ci.ts`), поэтому сервер и UI складывают
одинаково, а тесты идут на числах без моков. Контракт — `CiRunReport` (сводка
рана, агрегаты, стадии и все шаги, у шагов с ходами модели — их расход) и
`CiTaskReport` (все раны задачи + итог: повторы и отмены тоже расход).

REST — `GET /api/ci/runs/:runId/report` и `GET /api/projects/:id/tasks/:taskId/report`
(`db.ciRunReport` / `db.ciTaskReport`), гейт тот же, что у `kb-usage`: чужому
404, а не пустой отчёт. У ранов до фичи строк расхода нет — отчёт открывается,
показывает шаги и время, а деньги и токены рисует прочерками.

UI — `components/ci/CiReport.tsx` в карточке задачи (`TaskModal`), раздел виден
только когда последний ран завершён: пока он идёт, цифры устаревают на глазах, и
смотреть надо ленту. Данные грузит `useRemoteReport` (общий хук врезок-отчётов,
бывший `useKbUsageReport`) через `window.ci.getTaskReport`. По умолчанию открыт
свежий ран со своими шагами; при нескольких ранах переключатель добавляет «Итог
по задаче» с таблицей ранов. Над шагами — таблица «Стадии рана» (стадия, модель,
запросов, время модели, расход); у рана без строк расхода её нет вовсе. Числа форматирует `ci/ciFormat.ts` (нулевое «время работы модели» плитка рисует прочерком: ноль
означает «CLI не сообщил длительность ни по одному ходу», а не «модель работала
0 мс»): `fmtDuration`,
`fmtTokens` (разряды `toLocaleString('ru')` — там неразрывный пробел, DOM-тесты
сравнивают текст только после нормализации) и `fmtUsd`, который сам ставит «≈» у
оценки и пишет «< $0.01» вместо округлённого в ноль «$0.00». Фейк UI
(`test/fakeApi.ts`) отдаёт отчёт из своей же ленты — шаги и длительности есть,
расход пуст (ходов модели фейк не делает), поэтому тестам и сториз есть что
открыть; фикстуры с расходом — `test/fixtures/ci.ts` (`makeRunReport`,
`makeTaskReport`, `makeUsageTotals`, `makeReportStep`).

`runTurn` теперь возвращает `TurnResult` с `meta` (итог из `onDone`) и последним
`onUsage`: счётчики токенов кумулятивны, и у прерванного хода последний `onUsage`
— всё, что о его расходе известно.

**Чего CLI не сообщает — измеряет сервер.** `codex exec --json` не отдаёт ни
`total_cost_usd`, ни длительности, ни `num_turns`, а модель у него бывает пустой
штатно (берётся из его `config.toml`). Поэтому `recordUsage`: длительность — по
замеру хода (`TurnResult.elapsedMs`, часы из `deps.now`), `num_turns` — по числу
событий `onUsage` (одно событие = один ответ модели), модель — `meta.model` →
модель рана → `unknown`. Прайса у `unknown` нет намеренно (`estimateCostUsd`
возвращает `undefined`): итог помечается `costUnderstated` и в UI читается как
«оценка по прайсу, итог занижен», а не как ноль. Замер сервера включает накладные
расходы транспорта и потому НЕ подменяет `meta.durationMs`, а лишь закрывает его
отсутствие.

**Одна семантика входных токенов.** `input_tokens` у claude — вход БЕЗ кэша, у
codex — вместе с прочитанным кэшем; складывать их нельзя, иначе «до/после»
сравнивает разные величины, а оценка по прайсу считает кэш по полной цене входа
(для рана codex это завышало оценку в ~5 раз). `recordUsage` приводит вход к «без
кэша» на записи (у codex вычитает `cache_read_tokens`, с зажимом в ноль) и
помечает строку `input_semantics = 'no_cache'`. Историю задним числом не правим:
у старых строк колонка пустая, и `mapCiRunUsage` считает их `with_cache` для
codex и `no_cache` для claude, а `ciUsageTotals` приводит их на чтении
(`ciUsageInputTokens`) и поднимает `inputNormalized` — в UI это «вход приведён к
„без кэша“».

**Вызовы инструментов за ран** — `ci_run_tool_calls` (`run_id` + вид +
счётчик, UPSERT-инкремент) и `CiRunReport.toolCalls`. Виды —
`bash`/`read`/`grep`/`edit`/`kb`/`other` (`classifyCiToolCall` в `ci.ts`): имя
приходит от CLI в трёх видах (`mcp__remote__read` у claude, `remote:read` у codex,
`Read` у встроенного), а вид должен получаться один, иначе движки несравнимы.
Считается там, где мимо сервера проходит каждый вызов любого движка, — в
`onActivity` хода (`ClaudeLogEntry.tool` — сырое имя рядом с человеческим
`summary`); MCP-эндпоинт для этого не годится: он знает машину и папку, но не ран.
Ход без вызовов строки не пишет: «нет строки» должно означать «счётчика у рана
нет» (ран до фичи), а не «модель ничего не вызвала» — поэтому у старых ранов в
отчёте строки «Инструменты» нет, а не «0». Обе метрики не бросают: любая беда —
пропуск строки, а не упавший ран.

Седьмой вид — `denied`, и это **исход вызова, а не инструмент**: отказ CLI по
неодобренному разрешению («Claude requested permissions … you haven't granted it
yet») либо отказ remote-моста (текст начинается с «Отклонено:»). Раньше отказы
были видны только в сырой ленте — в CHAT-70 их было шесть, и никто их не считал.
Узнаются по тексту результата (`isCiToolDenial` в `ci.ts`): в `tool_result`
имени инструмента уже нет, поэтому в `onActivity` отказ считается отдельной
веткой. В «всего вызовов» (`ciToolCallsTotal`, список `CI_TOOL_CALL_KINDS`)
отказ не входит — сам вызов уже посчитан своим видом, иначе он считался бы
дважды; в отчёте это приписка «· отказов N», которой нет, когда отказов нет. Ход
из одних отказов счётчик всё-таки пишет (`ciToolCallsAny`) — иначе отказы снова
некому показать. Маркеры узкие намеренно: упавший `npm test` и `ENOENT` — не
отказ, и недосчитать честнее, чем записать в отказы ошибку команды.

## Контекст хода: второй множитель цены и его сжатие

Цена хода — это **размер контекста, умноженный на число запросов к API**, и до
CHAT-73 не измерялся ни один множитель. Разбор CHAT-70 по фактическим ценам:
чтение кэша $12.05 из $16.13 за ход модели (75%), 24.1M токенов чтения на ~190
запросов — около 125–130k контекста в среднем на запрос. Каждый вызов инструмента
идёт новым запросом ко ВСЕМУ накопленному контексту, поэтому один толстый ответ
оплачивается столько раз, сколько запросов осталось до конца хода. Измеренный
состав контекста того же рана (скриптом замера, см. `testing-operations.md`):

| часть контекста хода | измерено (ран CHAT-70, `e14f3868`) |
|---|---|
| директива задачи (`taskPrompt` + инструкции моста) | ~4k символов |
| инъекция БЗ (`kb_usage_queries.injected`) | 23k символов (8 обращений, 31 раздел) |
| системный промпт CLI + схемы инструментов + директива | ≤34k токенов (по самому скромному ходу рана) |
| **ответы инструментов** | **~786k символов**: bash 497k · read 184k · grep 58k · edit 24k · БЗ 21k |
| самый тяжёлый ответ | один `bash` на 425k символов (≈106k токенов) |
| выход модели (накапливается и перечитывается) | 92k токенов за ход работы модели |

Считать надо не байты, а «байты × число оставшихся запросов»: тот самый ответ на
425k пришёл 155-м из 187, поэтому его обрезка снимает меньше, чем кажется. По
симуляции на ленте CHAT-68/70 (каждый ответ перечитывается на всех последующих
запросах) лимиты дают **−15…17% среднего контекста на запрос**, а не −25%: ответы
инструментов — это 55–56% чтения кэша, остальное — базовый промпт, перечитываемый
на КАЖДОМ запросе, и накопленный выход самой модели. Отсюда следующий рычаг: не
объём ответов, а число запросов и размер базового промпта (системный промпт CLI со
схемами инструментов — десятки тысяч токенов на каждом запросе). Поэтому лимиты и
сделаны настройкой: их подкручивают по измеренному отчёту, а не по вере. Решение по
зазору до −25% (02.08.2026): дефолты оставлены тесными и с перекосом в хвост, потому
что срезанный токен экономится на ВСЕХ оставшихся запросах, а один лишний вызов из-за
тесного лимита стоит один контекст — обрезка на 10k окупает до семи повторных вызовов.
Проверять на живом ране, а не подкручивать вслепую. Второй множитель — базовый промпт
CLI и число запросов — измеряется в CHAT-78: `ci-usage-report --context` показывает
токеновую оценку директивы и БЗ, верхнюю оценку всего базового промпта и разницу
между минимальным и средним живым контекстом (накопленный хвост). Дублирующая
директива remote-инструментов из `taskPrompt` удалена: правила остаются в системном
хинте CLI; тот же хинт просит объединять независимые чтения и поиски.

**Что измеряется.** `CiUsageTotals` считает `apiRequests` (сумма `num_turns` —
запросы к API, а не ходы CLI) и `maxContextPerRequest`, средний даёт
`ciAvgContextPerRequest` (вход + чтение кэша + запись кэша, делённые на запросы;
выход не входит — он не перечитывается). Ноль запросов — это `null`, а не нуль: у
codex CLI числа не сообщает, и «контекста не было» здесь читалось бы как ложь.
Объём ответов инструментов лежит рядом с их числом — колонка `chars` в
`ci_run_tool_calls` (`CiToolChars`, `ciRunToolChars`), а «кто именно раздул
контекст» — в `ci_run_tool_responses`: вид, подпись вызова, символы и, если ответ
обрезали, исходный объём. Хранится верхушка по объёму (`CI_TOOL_RESPONSES_KEEP`,
лишние удаляются на записи) — это метрика, а лента вызовов и так в `ci_run_logs`.
Объём считается в `onActivity`: в `tool_result` имени инструмента нет, поэтому
ответ сшивается со своим вызовом по `tool_use_id` (`ClaudeLogEntry.toolUseId`,
claude), а без него — по порядку (codex). В отчёте это плитка «Контекст на запрос»
(средний, максимум, число запросов), приписка «ответами N символов» к строке
инструментов и строка «Самые тяжёлые ответы» с тремя виновниками
(`CI_TOOL_RESPONSES_SHOWN`).

**Что режется.** Лимиты ответов моста — в `machines.md`; здесь важно, что они
настройки `ci_settings`, а не константы, и что тем же лимитом режется вывод
команд справочника внутри хода модели. Авто-инъекция БЗ в CI-ране имеет отдельный стабильный
бюджет 1600 символов (обычный чат сохраняет общий бюджет 3500): это навигация,
а полный раздел модель берёт точечно через `kb:document`. Обрезка не ломает fix-loop: тесты гоняет шаг воркфлоу, а его хвост
лога приходит модели отдельным путём (`ctx.logTail`, 20k для шагов-гейтов), плюс
сама обрезка оставляет хвост, а не голову. Директивы remote остаются в промпте,
но описания MCP-инструментов и системный хинт сокращены до операционных правил:
команды через bash, файлы через read/grep/edit, запрет cat/heredoc и явный
`timeout_ms`. Это сохраняет стабильность промпта между запросами и не меняет
ключ кэша внутри хода. Отчёт рана и `ci-usage-report.mjs` показывают среднее
число API-запросов на вызов инструмента; метрика нужна, чтобы проверять пользу
батчинга, а не путать ходы CLI с обращениями к API.

## Замер расхода: методика и вердикт по CHAT-54/55/56

Замер от 02.08.2026 по прод-БД (`ci_run_usage`, `ci_run_logs`, `kb_usage_*`),
повторяется командой `node scripts/ci-usage-report.mjs --since <дата>` (в
контейнере: `--db /data/voicechat.db`). Скрипт даёт на ран: стоимость (настоящую
от CLI либо оценку «≈», у модели без прайса — «занижено»), токены в единой
семантике, время рана и работы модели, попытки fix-loop, вызовы инструментов (из
`ci_run_tool_calls`, а у старых ранов — восстановленные из ленты, тогда «~») и
отдельно то, что было главной гипотезой CHAT-54: сколько раз файл читали
командой внутри `bash` и сколько правок шло heredoc'ом.

**CHAT-54 (remote `read`/`grep`/`edit`) — эффекта нет, потому что инструментов у

heredoc'ом (0–16 раз) — как до фичи. Причина не в модели: у claude
`--allowedTools` содержал только `mcp__remote__bash`, и каждый вызов `read`

## Контракт и UI

Типы — `packages/shared/src/ci.ts`; REST-пути и WS-сообщения `ci.*` — в
`protocol.ts` (union'ы + `*_MESSAGE_TYPES`). Роуты — `routes/ci.ts`. Мост
`window.ci` (`remote/ciBridge.ts`), стор `ci*` + подписки. UI (`components/ci/`):
`CiCommands` (виджет-справочник + глобальные настройки + предложения + отчёт по
месту), `RunFeed` (лента рана + консоль), `CiReport` (отчёт по расходу в карточке
задачи), `CiTaskSettings`/`CiSlotEditor` (настройки
задачи), `CiProjectDefaults`, `CiConsole` (US-6, read-only/edit). Стиль — токены
`var(--…)` в `app.css`, без хардкода.

Счётчик `N/M` в шапке `RunFeed` дополнен кнопкой «Показать шаги рана».
Доступный popover строит нумерованный список из фактических корневых
`CiRunDetail.steps`, отсортированных по `position`: вложенные
`model_command` не входят в прогресс слотов и потому остаются только внутри
`model_work`. Каждый пункт показывает текстовую подпись статуса и отдельный
знак; активный шаг имеет `aria-current="step"` и визуальный маркер. Popover
открывается наведением, фокусом или нажатием, закрывается с небольшой задержкой,
повторным нажатием, Esc и нажатием снаружи. Он рендерится порталом,
переставляется выше/ниже кнопки по свободному месту, ограничивается viewport и
вертикально прокручивается; длинные названия переносятся.

Контракт каталога машины задачи — `CiTaskMachines` в
`packages/shared/src/ci.ts`, REST — `GET …/tasks/:taskId/ci/machines` в
`apps/server/src/routes/ci.ts`. Он содержит все собственные машины и только явно
предоставленные этому проекту чужие машины, без дублей. Для варианта возвращаются
owner/ownership, online, sharedWithProject, isMyDefault, canUse,
unavailableReason и load; путь чужой машины не раскрывается.

Запуск задачи разрешает машину единообразно: явный `agentId` запуска →
явный `Task.agentId` → текущий `Project.defaultAgentId`. Значение `null` у
задачи остаётся наследованием и не заполняется после запуска, поэтому смена
project default действует на следующий ран существующей задачи. Персональный
default инициатора и load-aware fallback в цепочку задач не входят. Перед
фактическим стартом queued-рана `execute` повторяет членство, предоставление,
существование и online-статус; автоматического переноса нет. В `ci_runs`
фиксируются `agent_id`, исторический owner id/name и источник `explicit`,
`task_pinned` или `project_default`; legacy-источники остаются читаемыми.

Корректный структурированный `taskLaunch` из чата проекта сразу открывает в
`App.tsx` стандартную карточку задачи (`TaskModal`) в режиме несохранённого
черновика. В ней доступны обычные поля карточки, а также движок и модель;
начальная пара берётся из пользовательских Settings, список моделей зависит от
выбранного движка. «Работать в текущем чате» закрывает карточку без создания
задачи, а выбор отправляется модели отдельным следующим ходом. «Создать в
InProgress» передаёт выбранные движок и модель как разовый override в `POST
.../ci/run`: они фиксируются в новом ране, но не меняют конфигурацию CI задачи
или проекта.

## Временная шкала задачи

Карточка задачи содержит отдельную вкладку «Временная шкала». Её единственный
источник — версионированный ответ `GET
/api/projects/:id/tasks/:taskId/timeline`: типы находятся в
`packages/shared/src/timeline.ts`, агрегация — в
`VoiceChatDb.taskTimeline`, отображение — в
`packages/ui/src/components/kanban/TaskTimeline.tsx`. Абсолютные отметки сервер
отдаёт как UTC ISO 8601, а UI форматирует их в локальном часовом поясе. Числовые
длительности уже рассчитаны сервером; UI добавляет текущее время только к
незакрытому активному интервалу и к возрасту незавершённой задачи, ничего не
сохраняя и не перечитывая шкалу.

Агрегатор читает фактические `tasks.created_at/updated_at/done_at`, development
`ci_runs` и `ci_run_steps`, `ci_interactions`, task preparation,
специализированные Component QA / integration-test / QA-stage раны,
QA preparation, ручные `qa_sessions` и merge-раны. Статусы приводятся к
`queued|running|awaiting_input|succeeded|failed|cancelled|skipped`; исходные id
и kind сохраняются в связях с ранами. Фактически подтверждённая модель берётся
из `ci_run_usage.model`; снимок запрошенной модели не выдаётся за использованную.
Машина берётся из сохранённого `agent_id` и справочника agents.

Каждая исходная запись становится неизменяемой попыткой со стабильной связью на
ран, затем попытки группируются в этапы по нормализованному типу. Внутри этапа
они упорядочены по номеру попытки и id; сами этапы — по позиции workflow, затем
по фактическому времени и стабильному id. Поэтому повторные и параллельные раны
не перезаписывают историю и сохраняют детерминированный порядок.

Очередь известна только при наличии обеих границ `created_at` и `started_at`.
Awaiting-input строится из `ci_interactions.created_at/answered_at` и вычитается
из активного интервала CI. Для старых preparation-записей без `started_at`
активное время остаётся `null`, даже когда можно вычислить календарный интервал.
Незакрытые интервалы имеют `finishedAt: null` и `durationMs: null`.
Суммы задачи для active, queue и awaiting_input считаются как длина объединения
пересекающихся интервалов каждой категории отдельно, поэтому параллельные раны
не удваивают время. Полный цикл завершённой задачи — строго
`tasks.created_at → tasks.done_at`, а последнее изменение — максимум только
фактических отметок задачи, ранов и интеракций; `generatedAt` и живой тик в него
не входят.

Нативные `details/summary` сохраняют клавиатурное управление и
`expanded/collapsed`. Таймер меняет состояние времени внутри уже смонтированных
строк раз в секунду: запрос выполняется один раз при открытии вкладки, поэтому
раскрытие, прокрутка и фокус не сбрасываются. Отсутствующие исторические поля UI
показывает как «Нет данных».

## Группированный fail-fast test pipeline

До этой задачи CI использовал общий `CiRun` с потоковыми шагами, fix-loop и
частичным разбором тестов; отдельной модели полного группированного прогона не
было. Теперь полный `TestRun` отделён от development-run и фиксирует проект,
задачу, feature-ветку, точный commit SHA, workspace/машину, preview, модель
анализа, инициатора, номер попытки и ссылку на предыдущую попытку. Контракты
находятся в `packages/shared/src/ci.ts` (`TestRun`, `TestGroupRun`,
`TestGroupConfig`). Проектный порядок хранится в конфигурации, а
`BASE_TEST_PIPELINE` задаёт поставляемый профиль: typecheck, shared/contract,
server, UI unit/DOM, build, Storybook build/smoke, Playwright smoke и Playwright
regression.

Статусы полного рана и группы определены отдельно в shared-контракте. Группа
проходит `queued → running → passed|failed|cancelled` либо до старта
`queued → skipped|not_applicable`. `createTestPipelineCoordinator` в
`apps/server/src/ci/types.ts` запускает группы по `position` строго по одной
и перед каждым сохранением проверяет этот инвариант. После первого обязательного
падения `blockedGroupsAfterFailure` помечает оставшийся queued-хвост
`skipped/blocked_by_failure`; завершённые и N/A группы не меняются.
Необязательное падение не обрывает цикл, но итоговый run всё равно становится
`failed`. Команда, её версия, SHA, времена, exit code, counters, текущие
suite/test, процент, raw log, распознанные failures и artifacts входят в снимок
группы. Ошибка parser добавляется рядом с исходным логом, а не подменяет
результат команды.

Перед Playwright preview-guard сверяет preview SHA с SHA рана, выполняя
подготовку/health-check в своём адаптере. Ошибка guard классифицируется как
`infrastructure`; product failure хранится отдельно. HTML report, trace,
screenshots/video передаются как `TestArtifact` и связываются с группой.
Ручной Playwright N/A сервер разрешает только ролям owner/tester и требует
причину и альтернативный способ проверки; решение фиксирует пользователя,
время и SHA. Обязательные группы нельзя сделать N/A.

Повторы разделены контрактом coordinator. Точечный повтор выполняется отдельным
`executeTargeted`, записывает аудит с командой, exit code и SHA и не мутирует
статус полного pipeline и не запускает следующие группы. Полный повтор — новый
`TestRun` с новым SHA и `previousRunId`; `sameTestRunRevision` не позволяет
считать результаты разных SHA одним прогоном. Отмена посылает AbortSignal
активному исполнителю, текущую группу закрывает `cancelled`, queued-хвост —
`skipped/cancelled`, сохраняя завершённые результаты.

В `apps/server/src/db/schema.ts` подготовлена персистентная схема grouped pipeline:
`ci_test_group_configs`, `ci_test_runs`, `ci_test_group_runs`,
`ci_test_events`, `ci_test_targeted_runs`. Сам coordinator пока хранит
активные раны в памяти и делегирует сохранение/аудит интерфейсу
`TestPipelineStore`, исполнение — `TestPipelineExecutor`, preview —
`TestPreviewGuard`; конкретные DB, HTTP/WS, UI и runner-адаптеры grouped pipeline
в код не подключены. `subscribe` отдаёт полный снимок при каждом publish, а
потоковый и сохранённый лог проходит инъектируемую redaction-функцию. Чистые
переходы и права покрыты в `packages/shared/src/ci.test.ts`; серверные сценарии
success, fail-fast, preview infrastructure failure, N/A и targeted retry — в
`apps/server/src/ci/infraErrors.test.ts`.

## Межстадийный fix cycle автотестов

Shared-домен в `packages/shared/src/ci.ts` описывает состояние задачи, цикл,
структурированную диагностику и дочерние точечные запуски. Там же находятся
консервативная классификация падения, стабильный fingerprint с нормализацией
динамических частей сообщения, сравнение повторной и новой ошибки, нормализация
лимита и серверная проверка узкой test-команды. Только `product_failure` допускает
автоматическое исправление; infrastructure/configuration/cancelled/unknown не
расходуют попытку. Полный перечень полей и статусов следует читать из shared-
контракта, а не восстанавливать из текста лога.

`createTestFixCycleCoordinator` в `apps/server/src/ci/types.ts` атомарно работает
через инъектируемый `TestFixCycleStore`. Идемпотентный ключ — пара test run и
failed group. Для продуктового падения coordinator проверяет effective limit,
фиксирует снимок выбранной fix-модели и исходный commit SHA, создаёт queued-цикл,
ровно один раз увеличивает `usedAttempts`, переносит карточку в `development` и
пишет аудит. При исчерпанном лимите цикл не создаётся, карточка переносится в
`decision_required`; наличие активного цикла запрещает второй старт.

Персистентная форма подготовлена таблицами `ci_test_fix_task_state`,
`ci_test_fix_cycles`, `ci_test_fix_targeted_runs` и `ci_test_fix_decisions` в
`apps/server/src/db/schema.ts`. Проектный `ciTestFixCycleLimit` имеет дефолт 10,
принимает только целое число не меньше нуля, возвращается в `ProjectSummary` и
меняется владельцем через общий `PATCH /api/projects/:id`; миграция добавляет
колонку существующим проектам. Task override представлен в домене и схеме, но
отдельного API для него пока нет.

Граница текущей реализации принципиальна: таблицы fix-cycle ещё не имеют методов
чтения/записи в `VoiceChatDb`, а coordinator не собран с DB-store и не вызван из
завершения grouped pipeline. Запуск fix-модели, построение её исторического
контекста, выполнение и сохранение точечных проверок, повтор полного pipeline,
восстановление после рестарта, HTTP/WS-события и UI истории/решений пока не
подключены. Поэтому наличие контрактов и схемы само по себе не меняет фактический
runtime-поток карточки.

## Переход в QA-workflow

Успешный development-ран без выполненного legacy-шага мержа переносит карточку в
системную колонку `component_qa` и пишет событие `run.component_qa`. Legacy
`qa_preparation` больше не является визуальной стадией доски: при миграции её
карточки безопасно объединяются с `component_qa`, а сама колонка удаляется.
Следующие `integration_tests`, `automated_qa` и `manual_qa` остаются отдельными
quality gates; допуск из ручной проверки переносит карточку в `awaiting_merge`.
У первых трёх пост-development стадий есть собственные раны и вкладки карточки —
[qa-stage-runs.md](qa-stage-runs.md).
Домен критериев, sessions, результатов и скриншотов описан в
[manual-qa.md](manual-qa.md).

Стадия `component_qa` больше не проходится вручную: она ведёт собственные раны
`component_qa_runs`, привязанные к workspace и SHA завершившегося
development-рана, и сама переводит карточку в `integration_tests` при
выполненном gate. Возврат на доработку из неё запускает обычный development-ран
через `CiRunManager.start` (карточка уезжает в `development`) и передаёт модели
`fixContext` со `stepId` `component_qa:<runId>`, логом команд и списком упавших
сценариев. Подробности — в [manual-qa.md](manual-qa.md).
