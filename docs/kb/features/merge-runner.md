# Merge-ран задачи: безопасное слияние в main

## Граница подсистемы

Merge выполняет отдельный `MergeRunManager` из
`apps/server/src/merge/runManager.ts`; development CI заканчивается подготовкой и
push ветки задачи в `origin`, после чего карточка находится в
`awaiting_merge`. Успешное транзакционное создание merge-рана сразу переводит
её в системную колонку `merge`: там она остаётся во время слияния, актуализации
БЗ и обязательных проверок. Успех переводит карточку в `done`; обычная ошибка,
отмена и неуспешное автоматическое исправление конфликтов оставляют в `merge`
для безопасного повтора. В `decision_required` переходят stale source и
неопределённый push; явный пользовательский retry возвращает карточку в `merge`. Отклонённый до создания рана запрос положение
карточки не меняет. Merge-ран не запускает production deploy и не смешивает своё
состояние или ленту с CI-раном разработки. В `TaskModal` Merge остаётся отдельной
верхней вкладкой между «Ходом выполнения» и «Лентой рана»; при активном merge
карточка впервые открывается на технической ленте, где рендерится
`MergeRunFeed`, а development-сводка не выдаётся за результат merge.

Клиент запускает процесс через
`POST /api/projects/:id/tasks/:taskId/merge`, не передавая ветку, target, Git URL,
checkout или машину. `VoiceChatDb.startMergeRun` определяет их из задачи,
проекта и последнего успешно отправленного `ci_workspaces`, требует owner-доступ,
target `main`, сохранённый source SHA и привязанную машину. Машина merge-рана
всегда берётся из этой записи workspace, а не из текущей default-машины проекта
или настройки карточки: именно на ней гарантированно существует родительский
каталог для временного merge-клона. Создание идемпотентно:
partial unique index и транзакционная проверка оставляют не больше одного активного
merge-рана задачи, а повторное нажатие возвращает его.

## Исполнение и защита main

Менеджер использует один процесс-глобальный слот. До мутаций он проверяет
права и статус задачи в БД, доступность машины и workspace, отсутствие другого
активного рана, а затем read-only командой `ls-remote` — доступ к origin и
существование `main` и feature-ветки. Fetch сохраняет оба актуальных SHA в refs
`refs/merge-runs/<runId>/source|target`; это неизменяемые ссылки одного цикла,
не зависящие от общего `FETCH_HEAD`. Изменившаяся после development CI feature
завершается как stale source до checkout target.

Источник правды — **последний отправленный** workspace
(`findLatestPushedCiWorkspace`, `pushed=1`): более новая неотправленная запись
(начатый dev-ран) его не заслоняет — иначе merge падал бы «workspace недоступен»
сразу после старта нового dev-рана.

Development-workspace сохраняется во время подготовки QA, ручного QA и ожидания
merge, но технической зависимостью merge не является. Менеджер использует из его
записи только сохранённые ветку, SHA, машину и путь, а Git-операции выполняет в
**постоянном merge-клоне проекта**. Для машины с MachineStorage общий helper
`managedMergeClonePaths` строит канонический путь
`<storageRoot>/projects/<projectId>/merge-clones/repository`; legacy
`{repos_root}/{project}/.merge` допускается только при полном отсутствии storage.
Подробные проверки storage и правило fallback описаны в
[machines.md](../machines.md#каталоги-проектной-машины).

Клон создаётся идемпотентно напрямую из проектного Git URL либо безопасно
переиспользуется после проверки origin. Перед каждым merge дерево вычищается
(`merge --abort`, `checkout -f --detach <source>`, `reset --hard`, `clean -fd`).
Изоляцию обеспечивает глобальный слот менеджера — активный merge-ран всегда один.
**Работа в колонке merge начинается с вливания `main` в ветку задачи**
(2026-09-04): checkout встаёт на pinned feature, а pinned `main` вливается в неё
вторым родителем (`Merge main into <branch> (task …)`). Так merge-коммит
принадлежит ветке — её история продолжается линейно (first parent — feature),
конфликты и обязательные проверки решаются в контексте задачи, а `main` затем
догоняет ветку fast-forward тем же SHA. Прежде направление было обратным
(checkout `main`, feature вторым родителем); при смене изменился смысл `--ours`:
теперь это версия ветки, и `git checkout --ours -- docs/kb/README.md` берёт
feature-вариант производного индекса, который всё равно перегенерируется в
`kb_update`. Полученный merge-коммит становится неизменяемым проверяемым SHA. Из него создаются два непересекающихся detached
worktree: один для обязательного гейта, второй для актуализации БЗ. Обе ветви
запускаются через `Promise.allSettled` одновременно; ошибка любой запрещает
публикацию, отмена прерывает модель, а оба worktree удаляются в `finally`.

После успешной пары индекс БЗ проверяется в KB-worktree. Если файлы изменились,
создаётся отдельный дочерний `docs(kb)`-коммит в feature; пустой коммит не
создаётся. Для одних только документов выполняется сокращённый `kb.mjs check`,
для прочих путей — полный проектный гейт заново. Перед публикацией origin/main
и origin/feature повторно сверяются с pinned SHA. Новый main запускает весь цикл
с новым снимком и новыми проверками; старый результат не переиспользуется.
Публикация строго двухфазная: сначала итоговый SHA отправляется в feature с lease,
затем **тот же SHA** — в `main` с lease. Push main является последней
мутирующей Git-операцией; промежуточный merge SHA в main не отправляется.

Сразу после fetch — до stale-сверки — менеджер проверяет
`git merge-base --is-ancestor source target`: уже влитая в main ветка завершает
ран мгновенным успехом «Ветка уже вмержена в main» (mergeSha = target) без
установки зависимостей, гейта и push; карточка уходит в `done`, копии
репозиториев задачи чистятся как при обычном успехе.

Повторный merge после возврата задачи из Done определяется не наличием любого
старого успешного рана, а парой SHA. Снапшот доски отдаёт текущий
`mergeSourceSha`, `mergedSha` последнего успешного merge и его
`mergedSourceSha`. UI блокирует кнопку только когда текущий source SHA совпадает
с `mergedSourceSha`; новый pushed workspace с другим SHA снова делает merge
доступным в `awaiting_merge`. Для старых успешных ранов без сохранённого source
SHA применяется безопасная миграционная семантика: они сами по себе не скрывают
кнопку для подготовленной ветки, а сервер заново проверяет ветку при старте.

При конфликте пути из `git diff --name-only --diff-filter=U` сохраняются в
снимке. `docs/kb/README.md` считается производным индексом: менеджер всегда
снимает его конфликт, временно оставляя target-версию. Остальные конфликты
оцениваются независимо; смешанный конфликт индекса и исходного кода передаёт
дополнительному шагу только реально неразрешённые пути.

Для конфликтов тем `docs/kb/*.md` строки `updated:`/`checked:` во всех трёх
git-стадиях нормализуются плейсхолдером, затем выполняется честный трёхсторонний
`git merge-file`: чистый результат означает, что конфликтовали только метаданные
и неконфликтующие правки тела обеих сторон сохранены. После этого
`node scripts/kb.mjs touch` ставит свежие значения. Нормализация построчная
(`sed -E 's/^(updated:).*/…@@KB@@/'`) и не знает про границы фронтматтера:
строка `updated:`/`checked:` внутри примера в ```-блоке темы тоже станет
`@@KB@@`, а `touch` вернёт настоящие значения только фронтматтеру. Тема с
примером фронтматтера (`docs/kb/kb-workflow.md`) после такого конфликта требует
ручной сверки примера.

Остальные unmerged-пути проходят консервативный детерминированный анализ
`textConflictResolver.ts` без LLM и языковых эвристик. Менеджер читает стадии
1/2/3 из индекса и допускает только обычные текстовые blob с одинаковым mode;
отсутствующая стадия, бинарный файл, symlink, submodule, delete/modify либо
изменение типа/mode остаются конфликтом. Чистый модуль сопоставляет строки base
с ours/theirs и строит диапазоны base плюс добавленный текст. Он объединяет
непересекающиеся диапазоны и вставки у разных якорей. Разные непустые вставки в
одну неизменённую границу идут стабильно `ours → theirs`, одинаковые вставки
дедуплицируются. Пересекающиеся замены/удаления, вставка внутри или у границы
заменяемого диапазона, неоднозначное сопоставление строк и маркеры конфликта
fail-closed.

Доказанный результат сначала пишется во временный файл, проверяется на
`<<<<<<<`/`=======`/`>>>>>>>`, затем атомарно заменяет рабочий файл и
индексируется. Ошибка анализа/чтения/записи оставляет путь unmerged. После всех
детерминированных правил менеджер заново читает
`git diff --name-only --diff-filter=U`. Если неоднозначные пути остались,
автоматически запускается ровно один дополнительный модельный шаг исправления
конфликтов (`conflictFixForMerge`) в текущем merge-клоне. Модель получает задачу
и точный список путей, не может делать abort/commit/push/reset и должна снять
конфликты и выполнить `git add`.

Результату модели не доверяют: сервер повторно требует пустой
`git diff --name-only --diff-filter=U`, отсутствие конфликтных маркеров во всём
дереве и только затем сам создаёт merge-коммит. Успех продолжает `kb_update`,
установку зависимостей, tests и защищённый push. Модель не стартовала, вернула
ошибку либо не прошла серверную проверку — ран завершается как `failed`, остаётся
в колонке `merge`, рабочая копия сохраняется и push не выполняется. Внутри
одного merge-рана второй модельный повтор не запускается. Лог каждого
детерминированно разобранного пути содержит classification, applied, правило и
количества изменений либо конкретную причину отказа.

Упавшие обязательные проверки тоже лечатся автоматически (2026-09-04). При
`status: failed` первого гейта менеджер один раз за ран вызывает
`testFixForMerge`: модель работает **в проверочном worktree**, где зависимости
уже установлены, получает команду, код возврата и последние 120 строк вывода, и
обязана править причину, а не ослаблять проверки. Ей запрещены commit, push,
reset, checkout и stash. Результату не доверяют: сервер сам убеждается, что
HEAD worktree не сменился, что-то действительно изменилось и конфликтных
маркеров нет (`git rev-parse HEAD`, `git status --porcelain`, `git grep`), сам
делает коммит `fix(merge): автоисправление упавших проверок <task>` и повторяет
**и проверки, и актуализацию БЗ** уже от нового SHA — дальше ран идёт обычным
путём, включая KB-коммит и защищённый push. Тот же бюджет распространяется на повторный гейт после KB-коммита: он падает
так же обидно, и его лечит та же одна попытка (модель работает уже в
KB-worktree, сервер коммитит поверх KB-коммита, в main уходит починенный SHA).
Внутри одного рана вторая попытка не запускается — суммарно одна на ран,
независимо от того, какой из гейтов упал (иначе ран крутился бы на одной
ошибке). Любой отказ проверки результата оставляет карточку в `merge` с текстом
`…; автоисправление не помогло`, а без подключённого хука поведение прежнее:
ран сразу падает.

Что моделью **не** лечится и по-прежнему требует человека: провал обязательного
`kb_update` (это сам модельный шаг, повтор без изменения условий бессмысленен),
stale source и разъехавшийся `origin/main` (нужно обновить ветку — ран уходит в
`decision_required`), отклонённый или неопределённый push (`reconcile`), а также
инфраструктура: офлайн-машина, недоступный origin, не созданный worktree,
упавший `npm ci`. Конфликты слияния лечит отдельный шаг `conflictFixForMerge`,
и у него свой бюджет — одна попытка.
Причины отказа пишутся в лог этапа `testing` — новых этапов и полей контракта
шаг не добавляет.

Исполнитель merge-рана работает из уже развёрнутого серверного кода целевой
ветки. Поэтому ветка, которая впервые добавляет `conflictFixForMerge`, не может
использовать этот же хук для собственного конфликтного вливания: до попадания
изменения в `main` сервер исполняет прежнюю логику. Такой bootstrap-конфликт
разрешается один раз в feature-ветке; следующие merge-раны после обновления
сервера получают дополнительный шаг автоматически.

Машину рана можно выбрать. `MergePanel` объединяет обычный каталог
`GET …/tasks/:taskId/ci/machines` с отдельным server readiness
`GET …/tasks/:taskId/merge/machines`: ответ содержит точную причину, режим
`managed|legacy`, selectable и машину pushed workspace по умолчанию. Непроверенные
и неготовые варианты отключены, кнопка старта активна только для selectable-машины.
Это лишь ранняя обратная связь: `POST …/merge`, `…/retry` и исполнитель повторяют
тот же `MergeRunManager.checkReadiness` до создания рана и до операций с клоном.

`MergePanel` получает каталог и readiness согласованно через `Promise.all` для
`getTaskMachines` и `getMergeMachines` и публикует результат только после успеха
обоих запросов. `loadView` различает первую загрузку (`Skeleton` и `aria-busy`),
успешный пустой ответ (`EmptyState`) и ошибку (`ErrorState` с повтором); при
обновлении уже показанные данные остаются на экране с `RefreshIndicator` либо
компактной ошибкой. Данные дополнительно привязаны к ключу `projectId:taskId`,
поэтому ответ или сохранённый список другой задачи не открывает селектор текущей.

`POST …/merge` и `…/retry` принимают `agentId`; retry без нового id наследует машину
предыдущей попытки. Когда ответ рана разрешает retry (`canRetry`), лента показывает
селектор, изначально выбирает `agentId` этой попытки и передаёт текущий выбор в
`POST …/retry`. Если прежней машины уже нет в каталоге, она остаётся выбранным
офлайн-вариантом, чтобы наследование было явным. У активного рана `canRetry=false`,
поэтому селектора нет и машину сменить нельзя. После retry лента принимает новый
`MergeRun` и синхронизирует выбор с его `agentId`; имя машины конкретной попытки
видно в текущей ленте и истории, полный `agentId` остаётся в tooltip.

Для merge нужна запись `project_machines` выбранной машины. `getProjectMachine`
одним join возвращает назначенный storage только когда он принадлежит этой машине;
наличие `storage_id` включает строгий managed-режим без fallback на `repos_root`.
Origin существующего клона сверяется канонично (`canonicalGitUrl`: host/owner/repo
без протокола, `git@`, `.git`), поэтому машинный rewrite SSH→HTTPS (`insteadOf`,
MacBook) не валит проверку, а посторонний репозиторий отклоняется.

Копии репозиториев задачи учитываются в `task_repositories` (машина, путь,
`dev-workspace` | `merge-clone`, `active` | `deleted`): workspace разработки
регистрируется при merge-ране, запись помечается `deleted` только после
подтверждённого `rm -rf`. Постоянный merge-клон — project-scoped, в учёте задач
не значится и при их закрытии не удаляется. Успешный merge и **ручной перенос
карточки в Done** (хук в маршруте `…/move`) удаляют все активные копии задачи
на доступных машинах (`releaseTaskRepositories` — публичный метод менеджера);
запись недоступной машины остаётся до следующей очистки. Список отдаёт
`GET …/tasks/:taskId/repositories`, в UI он виден во вкладке «Merge» задачи.

Обязательная стадия `kb_update` переиспользует `ci/modelHooks.ts`
(`kbUpdateForMerge`) и `kb/codeUpdate.ts`. Хук получает путь **KB-worktree** как
`workspacePath` плюс `BASE_BRANCH=main` и `KB_BASE_REF=<targetRef>`, поэтому
строит диф проверяемого дерева относительно зафиксированного target ref,
пропускает модель при пустом дифе без подтверждённых пробелов и сохраняет
проектные статьи только из валидного структурированного ответа. Отмена идёт
через отдельный `branchCtl`: он срабатывает и при отмене рана пользователем, и
как только упал параллельный гейт или сам хук, — то есть неуспешная ветвь
отменяет соседнюю, а не ждёт её. Ошибка останавливает ран без push; безопасная
семантика таймаута разрешает продолжить только если файловые темы уже валидно
изменены.

После успешного хука менеджер в том же KB-worktree выполняет `kb.mjs index`,
`kb.mjs check`, `git add -- docs/kb` и — только если индекс непуст — **отдельный
коммит** `docs(kb): update after merge <taskId>` (не amend; пустой коммит не
создаётся). Из вывода он читает `FINAL=<sha>` и список
`git diff --name-only <проверяемый SHA> HEAD`. Совпадение FINAL с проверяемым SHA
означает «БЗ ничего не изменила», и повторный гейт не нужен. Иначе список путей
классифицируется: только `docs/**` без `generated|dist|build`, `.github/**` и
корневые `*.md` считаются документальными — тогда выполняется сокращённый гейт
`node scripts/kb.mjs check` (проверка «Документальный гейт после БЗ»); любой
другой путь означает полный проектный набор заново («Полный повторный гейт после
БЗ»). Повторный гейт всегда идёт в KB-worktree, его результат добавляется вторым
элементом `run.checks`, и его провал останавливает ран без push.

Зависимости ставятся **внутри каждого worktree** через
`npm ci --no-audit --no-fund` с лимитом 15 минут. В managed-режиме npm-кэш —
`<storageRoot>/projects/<projectId>/merge-clones/npm-cache`, в legacy — соседний с
клоном `.merge-npm-cache`. Кэш переживает раны,
поэтому две установки в свежих каталогах остаются дешёвыми; прежней оптимизации
с маркером `node_modules/.merge-lock-sha` в постоянном клоне больше нет —
worktree создаётся пустым и удаляется после рана. Повторный гейт ставит
зависимости в KB-worktree отдельно. Неуспешная установка сразу делает свою
проверку `failed`, команды гейта после неё не запускаются.

Настроенная `project.testCommand` либо fallback `npm run affected-check`
выполняется в tests-worktree проверяемого SHA до push. Разбор настройки — общий модуль
`apps/server/src/ci/testStages.ts` (его же использует Component QA со своим
дефолтом `npm run test:storybook`): обычная строка запускается как одна
команда; JSON-массив непустых строк исполняется последовательно с fail-fast — в том
же формате, который использует release-gate проекта; каждой команде отводится до
30 минут (полный UI-набор не укладывался в прежние 5). Результат проверки хранит времена,
длительность, exit code, timeout и полный вывод. Потоковый executor сразу добавляет
в merge-ленту heartbeat `affected-check` с активным пакетом и длительностью, а при
остановке — диагностический хвост, поэтому длинный тест не выглядит тишиной до
финального `exit`. Любая неуспешная обязательная проверка оставляет
`origin/main` неизменным и возвращает карточку в `awaiting_merge`.

Перед публикацией менеджер заново fetch-ит main и source в те же refs рана.
Изменившийся source — `stale source` → `decision_required`. Изменившийся main
ошибкой **не** считается: менеджер пишет в лог старый и новый SHA, удаляет
worktree и рекурсивно перезапускает весь `execute` — новый fetch, новый
merge-коммит, новые проверки и новая актуализация БЗ; результаты, полученные для
прежнего main, для нового снимка не переиспользуются. Публикация двухфазная:
сначала итоговый SHA идёт в feature
(`git push --porcelain --force-with-lease=refs/heads/<feature>:<sourceSha> origin <finalSha>:refs/heads/<feature>`),
затем **тот же** `finalSha` — в main с `--force-with-lease=refs/heads/main:<targetSha>`;
безусловного force нет. Отказ первого push оставляет main нетронутым и
завершает ран без публикации. Успех фиксируется лишь после того, как
`git ls-remote origin refs/heads/main` подтверждает `finalSha`, затем задача
переходит в `done`. Неопределённый результат push переводит процесс в
`decision_required` с рекомендуемым действием.

Наблюдаемость собрана в сообщениях стадий и логе рана: `fetching` печатает SHA
source и main, `merging` — проверяемый SHA («main + feature»), обе параллельные
стадии — этот же SHA и свои роли, `testing` — статус, длительность гейта и
длительность параллельного участка, `kb_update` — сообщение модели, SHA
отдельного KB-коммита либо «дерево не изменилось, пустой коммит не создан» и ту
же длительность участка, повторный гейт — своё имя, статус и длительность,
`pushing` — итоговый SHA, отправленный в main. Любая остановка пишет
`Остановка merge: <причина>`, а `finally` — общую длительность рана.

Очистка изолированных каталогов идёт через `cleanupWorktrees`: после успеха,
перед рекурсивным перезапуском из-за нового main и в `finally` (то есть и при
ошибке, и при отмене пользователем). Каталоги снимаются в обратном порядке
`git worktree remove --force`, затем `git worktree prune` убирает служебные
записи. Ошибки самой очистки проглатываются: отключившаяся машина не должна
подменять настоящую причину остановки рана.

Managed workspace обычного разговора не является частью этого cleanup. Его запись
живёт в отдельной таблице `conversation_workspaces`, а канонический chat-путь и
`ProjectWorkspaceManifest` определены в `packages/shared/src/projects.ts`.
`MergeRunManager` сейчас не читает эту запись, не проверяет `origin/main` или
`workspace.json` такого workspace и не выполняет manifest-guarded удаление либо
очистку chat workspace после merge. Текущий merge cleanup охватывает только два
временных detached worktree рана и отдельно учтённые task repositories; связывать
с ним lifecycle workspace разговора пока нельзя.

Оркестрация целиком покрыта `apps/server/src/merge/runManager.test.ts` без
единого реального CLI, git-репозитория и сети. `CommandExecutor` — `vi.fn`,
который распознаёт скрипты по подстрокам (`git ls-remote --exit-code`,
`git worktree add --detach`, `git add -- docs/kb`, `git push --porcelain`) и
отдаёт заранее заданный stdout; остальные команды разбирают очередь `outputs`.
БД — литерал с нужными методами, `kbUpdate` — стаб с `{ok,message}` и
LLM-полями, `isOnline` — предикат, `now` — монотонный счётчик, поэтому
длительности детерминированы. Тесты фиксируют именно направление истории и
порядок, а не только исход: отдельный `docs(kb)`-коммит без `--amend`, один и
тот же итоговый SHA в feature и затем в main, push feature раньше push main,
два непересекающихся worktree `.merge-run-<runId>-tests` и `-kb`, единственный
`npm ci` на обычном успехе, сокращённый гейт против полного по составу путей
KB-коммита и отсутствие push при упавшем `kb_update` — при том, что проверки к
этому моменту уже стартовали.

## Состояние, восстановление и управление

Контракт снимка находится в `packages/shared/src/merge.ts`: он отделяет общий
статус от записей стадий, проверок и конфликтов и содержит SHA, времена, журнал,
рекомендованное действие, `canCancel`, `canRetry` и `pushStartedAt`. SQLite
хранит эти данные в `merge_runs`; snapshot доски дополнительно отдаёт
`activeMergeRunId` и `latestMergeRunId`, поэтому активная или последняя лента
восстанавливается после reload.

`DELETE /api/merge/runs/:runId` отменяет дочернюю команду и возвращает карточку
в `awaiting_merge`, но только пока push не отмечен начатым.
`POST /api/merge/runs/:runId/retry` создаёт новую попытку через повторные
серверные проверки. Обычный retry сохраняет строгую сверку с SHA development-рана.
Если предыдущая попытка обнаружила Git-конфликты, владелец разрешает их в task-ветке;
у такой новой попытки source SHA намеренно остаётся пустым до fetch, после чего
менеджер сразу фиксирует актуальный remote SHA и продолжает merge. Иначе ручное
разрешение неизбежно считалось бы stale source. Тем же образом снимается закрепление
при retry попытки, которая сама завершилась ошибкой stale source (`retryMergeRun`
распознаёт её по тексту ошибки), и при явном `{"unpin":true}` в теле retry —
кнопка «Мержить текущий head ветки» в ленте stale-рана. Обычный retry (упавшие
проверки и прочие сбои) по-прежнему сохраняет строгую сверку с SHA
development-рана. Постоянный merge-клон после рана не удаляется.

История попыток задачи — `GET …/tasks/:taskId/merge/runs` (`listMergeRuns`,
свежие первыми), в UI это список «Попытки» во вкладке Merge. Из успешного рана
доступен production-деплой: `POST /api/merge/runs/:runId/deploy` запускает
штатный `ReleaseManager.start` по ветке main и пишет `deployId`,
`deployVersion` и `productionStatus` в снимок рана (кнопка «Выпустить на прод»
в ленте). Терминальный исход merge-рана показывается тостом через
store-подписку на `merge.snapshot` (дедуп по ран+статус).

При старте сервера `reconcile()` подбирает незавершённые записи. Для рана с
`pushStartedAt` и `mergeSha` он не повторяет merge или push: только читает
remote main, завершает success при совпадении и запускает обычную очистку
task-specific копий либо требует ручного решения при расхождении. Очистка
начинается только после подтверждения SHA через `ls-remote`; ошибка или
неопределённый исход push рабочие копии не удаляют. Остальные активные записи
безопасно запускаются через обычный исполнитель.

## Realtime-лента

Сервер публикует отдельное WS-сообщение `merge.snapshot` через подписчиков
CI-транспорта; контракт сообщения зарегистрирован в
`packages/shared/src/protocol.ts`. При монтировании активный `MergePanel` по одному
разу загружает списки репозиториев и merge-ранов. Дальше `merge.snapshot` общей
upsert-операцией обновляет и историю, и выбранный ран; `MergeRunFeed` использует
переданный снимок и не запускает периодический `getMerge`. После reconnect
смонтированная панель делает одну контрольную синхронизацию списков. GET каждого
ресурса сериализован: частые сигналы во время запроса оставляют максимум один
trailing-запрос, а поздний ответ уже скрытой или сменившей задачу панели
игнорируется. В карточке показываются статус, отдельная стадия БЗ между merge и tests, SHA,
машина, выбранные engine/provider/model, инициатор, длительность, outcome,
ошибка, конфликты, проверки и сохранённые общий и постадийные логи; доступны копирование, скачивание
`.txt`, управление автоскроллом, отмена и повтор.

LLM для нового merge-рана разрешается до вставки `merge_runs`: разовый
`provider/model` из запроса запуска имеет приоритет над глобальными настройками
пользователя, затем используются системные значения. Пустая модель нормализуется
до фактической модели выбранного provider (`codexModel`/Codex default либо
Claude model/default), после чего deny-list пользователя может заменить
недоступный provider или модель. Запись хранит фактические
`llm_provider/llm_model`, исходные `requested_llm_provider/requested_llm_model`
и машиночитаемый `llm_fallback_reason` (`provider_unavailable` или
`model_unavailable`). `kbUpdateForMerge` запускает сохранённый фактический
снимок и не перечитывает настройки после старта. Лента показывает предупреждение
только при сохранённой причине fallback; старые записи без новых полей читаются
без попытки вывести неподтверждённую подмену.
