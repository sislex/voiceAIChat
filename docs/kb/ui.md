# Интерфейс: React, store, remote-мосты и голосовой UX

`packages/ui` остаётся React-host для браузера и Electron, а Chat начал выделяться в workspace-пакет `@voicechat/chat-app`. `apps/web` вычисляет URL сервера, вызывает `installRemoteBridges()` до первого импорта состояния приложения, монтирует `<App/>` и подключает стили обоих пакетов. Большая часть продуктовых Chat-компонентов пока всё ещё меняется в `packages/ui`; независимая граница нового пакета описана ниже.

## Слои

```text
App/components → useChat/useVoice/useSettings/… (store/react.tsx)
                     ↓ actions владельца данных
                 доменные stores (store/domains/*)
                     ↓ доменные клиенты (clients/types.ts)
                 адаптеры мостов (clients/browser.ts, clients/realtime.ts) → window.*
AppRuntime (runtime/appRuntime.ts): bootstrap, routing WS-кадров, logout, dispose
web/desktop host → installRemoteBridges → HTTP + WebSocket → server
```

Каждое хранилище — обычное замыкание с `getState`, `subscribe`, `actions`, `dispose`
(общая основа — `store/createStore.ts`); React в них отсутствует, поэтому сложные
сценарии тестируются без DOM, а компоненты — через Testing Library и fake bridges.

**Глобального `voiceStore`/`useVoiceStore` больше нет** (CHAT-236): состояние
разобрано на независимые домены, а `voiceStore` теперь отвечает только за голос.

### Фактическая граница `@voicechat/chat-app`

Пакет владеет React-независимым `chatStore` и его ядром с `dispose`, чистыми read-model helpers телеметрии БЗ и загрузки, публичным `ChatClient` и интеграционными портами, parser/builder маршрутов Chat, собственными стилями и каркасными React-поверхностями `ChatProvider`, `ChatApp`, `ChatPage`, `EmbeddedChat`, `SplitChatWorkspace` и `ChatNavigation`. Полный публичный контракт собран в `packages/chat-app/src/index.ts`; `AppRuntime` создаёт store только через этот вход и внедряет существующие host-клиенты и порты. Старый `packages/ui/src/store/domains/chatStore.ts` оставлен как совместимый реэкспорт, реализации состояния в нём больше нет.

Граница пока частичная: основной layout и маршрутизация остаются в `packages/ui/src/App.tsx`, а полноценные `ChatColumn`, timeline/renderers, `VoiceBar`, настройки разговора и остальные продуктовые Chat-компоненты физически ещё находятся в `packages/ui/src/components`. Публичные поверхности нового пакета сейчас являются контейнерами для переданных `children`, а не самостоятельной сборкой полного чата. Канбан использует публичный `EmbeddedChat`, но внутрь него по-прежнему передаёт host-компоненты `ChatColumn` и `VoiceBar`. Поэтому наличие экспорта в `@voicechat/chat-app` нельзя трактовать как завершённый перенос всего Chat UI.

| Домен | Что внутри |
|---|---|
| `shellStore` | окна верхнего уровня, выдвижной/свёрнутый сайдбар, палитра, шпаргалка, очередь тостов `notices`, баннер `error` |
| `sessionStore` | `authRequired`, `currentUser`, `authError`, login/logout, события `session.*` |
| `settingsStore` | настройки, движки и права моделей, capabilities, MCP, статус входа CLI, микрофоны, каталоги Whisper/Piper, загрузки |
| `chatStore` | разговоры (обычные, reader, playwright-reader), сообщения, поиск, черновик и вложения, стрим, активные ходы и очередь, `taskChatContext`, телеметрия БЗ |
| `voiceStore` | голосовой автомат, live STT-сегменты, захват микрофона, VAD, hands-free, barge-in, очередь TTS |
| `operationsStore` | машины, утилиты (консоль/проводник), история команд, наблюдатели Claude Code и Codex |
| `adminStore` | пользователи, расход, прайсы моделей, реестр LLM-исполнителей, права выбранного пользователя |
| `projectsStore` | проекты, доска, CI-раннер, сводки ранов, паузы ленты |

**Хранилища не импортируют друг друга.** Когда домену нужен сосед, он получает
порт от `AppRuntime`: `chatStore` спрашивает у голосового автомата состояние и
переходы (`ChatVoicePort`), `projectsStore` просит Chat перечитать список
(`ProjectsChatPort`), `operationsStore` берёт эффективную машину активного чата.
Общие ключи localStorage и форма голосового среза настроек лежат в нейтральном
`store/contracts.ts` — так домены не связаны даже типом. Правила сторожит
`src/architecture.test.ts` (обычный vitest-тест): импорты между доменами, React,
`window.*`, `fetch`, `WebSocket`, `localStorage`, `document` в сторах, импорт
внутренностей стора из компонентов, доменные данные в runtime и наличие старого
`useVoiceStore`.

**Домен проектов пока остаётся в `packages/ui`.** Пакет `@voicechat/projects-app`
уже существует, но экраны проектов и их состояние не переехали туда — это
следующий шаг; до него `projectsStore` живёт рядом с остальными доменами и
подчиняется тем же правилам границ.

`store/react.tsx` — единственный React-слой состояния: `AppRuntimeProvider`,
`useShell/useSession/useSettings/useChat/useVoice/useOperations/useAdmin/useProjects`
(каждый принимает селектор и стабилен по `Object.is`) и парные `use*Actions`.
Универсального хука со всеми доменами сразу нет и заводить его нельзя — ради
этого стор и разбирали. `useCreateAppRuntime` создаёт runtime один раз на
монтирование, запускает bootstrap и освобождает ресурсы при размонтировании.

`clients/types.ts` описывает доменные клиенты: наборы методов собраны `Pick` из
`RendererApi`, плюс собственные порты (`ChatTurnPort`, `SttPort`, `TtsPort`,
`AudioPlaybackPort`, `PreferencesPort`, `DownloadPort`). Клиент собирается
хелпером `withApi(api, ports)` — это Proxy с **живой** ссылкой на `RendererApi`:
копировать методы в новый объект нельзя, иначе подменённый позже мост (в тестах —
`vi.spyOn`) до стора не доедет.

## Состояние приложения

Админская карточка пользователя получает персональные запреты моделей через
`GET/PUT /api/admin/users/:name/llm-access`; пустой список означает полный доступ.
В `UsersAdmin` секция «Доступ к моделям» группирует чекбоксы по Claude и Codex:
чекбокс движка записывает запрет `{ provider, modelId: '*' }`, а снятая модель —
`{ provider, modelId }`; сохранение заменяет deny-list атомарно.
Права текущего пользователя загружаются стором через `llm:access` при bootstrap.
`SettingsModal` и `ConversationSettings` фильтруют движки и модели через
`isProviderAllowed`/`allowedModels`; при запрете всех движков показывается пункт
«Нет доступных движков». Тот же список прав передаётся из App в админку и настройки
разговора, поэтому пустой список прав не требует отдельной инициализации.
Роль на набор моделей больше не влияет: у `user` без запретов меню то же, что у
админа, — сужают его только записи `llmAccess`. Раньше фильтр был по роли, и
`ConversationSettings.dom.test.tsx` с `SettingsModal.dom.test.tsx` продолжали
требовать старое поведение.

**Пустой список прав по умолчанию — модульная константа, а не литерал в
параметрах.** `llmAccess = []` в деструктуризации пропсов создаёт новый массив на
каждый рендер, а в `UsersAdmin` этот пропс стоит в зависимостях эффекта, который
синхронизирует черновик доступа: эффект срабатывал каждый рендер, звал
`setAccessDraft` и зацикливал компонент. Цикл синхронный, поэтому Vitest не мог
прервать его таймаутом теста — `UsersAdmin.dom.test.tsx` вис навсегда и вешал весь
ui-набор (а с ним и `stories.a11y.dom.test.tsx`, который рендерит сториз
`UsersAdmin`). Гейт рана этого не показывал, потому что сам не запускался. После
правки набор проходит целиком за ~4,5 минуты.
Карточка задачи, `CiCommands`, `CiTaskSettings`, `CiProjectDefaults` и `RunFeed`
получают тот же deny-list и скрывают запрещённые модели/движки, включая повтор
CI-рана; при отсутствии вариантов оставляют объясняющее пустое состояние.
`ProjectSettings` передаёт текущий deny-list в `CiProjectDefaults`, поэтому тот же
фильтр действует и для проектной пары движок/модель.

### Инспектор контекста разговора

`ConversationSettings` содержит третью вкладку «Контекст и инструкции».
`ContextInspector` строит клиентское представление конфигурации следующего хода
из текущего черновика настроек: провайдера и модели, эффективного permission mode,
выбранных машины, рабочего каталога и проекта, режима БЗ, а также списка навыков
из политики машины и выбранных в разговоре имён. Сводка показывает число
действующих карточек инструкций, выбранных навыков и доступных инструментов.
Группы расположены от системных правил до истории и текущего сообщения; MCP
вынесены в отдельную группу возможностей и явно не считаются уровнем команд.

Это представление не является снимком реально собранного сервером prompt.
Системные и прикладные правила, перечень remote/kb-инструментов и блок
неустановленных плагинов заданы в компоненте безопасными карточками. Применимость
AGENTS.md выводится из наличия `workdir`, но компонент не обходит и не читает
иерархию файлов. Статус remote-инструментов зависит от online-состояния выбранной
машины, а статус kb-инструментов — от режима БЗ. Для навыков различаются
доступность на машине и выбор в разговоре; выбор не выдаётся за фактическую
активацию навыка в отдельном ходе. Автоматически внедрённые документы, ручные
обращения к БЗ и исторические снимки ходов экран пока не получает от сервера.

Карточка открывает подробности по hash-URL
`#/conversations/:conversationId/context/:itemId`. Детали показывают источник,
область, приоритет, причину, ограничения, а для инструмента — техническое имя,
верхнеуровневые параметры и признак изменения данных. Закрытые системные правила
показываются только безопасным описанием с отметкой о недоступности полного
текста; секреты и содержимое AGENTS.md компонент не читает. Секция «Можно
подключить» визуально отделяет фиксированный каталог неустановленных плагинов от
доступных инструментов. Разметка в `app.css` перестраивает сводку, карточки и
метаданные в одну колонку на узких экранах.

Состояние разложено по доменным хранилищам (таблица выше); ниже — что в каких
областях лежит:

- сессия: `authRequired`, `currentUser`, `authError`;
- голос: текущее состояние автомата, live STT segments, микрофоны, настройки, модель и capabilities;
- разговор: список, активный id, сообщения, draft, attachments, поиск, streaming reply, active turns/activity/usage;
- TTS: голоса, каталог, загрузки, активное сообщение и очередь воспроизведения;
- LLM/диагностика: MCP servers, login status, console log;
- уведомления: очередь `notices` для тостов (ошибки мостов, успех операций);
- машины: агенты, окно управления, utility console/explorer;
- наблюдатели: Claude Code и Codex projects/sessions/transcripts;
- администрирование: пользователи, usage с отдельными «по данным CLI» и «по прайсу», разговоры и сообщения выбранного пользователя, отдельный список LLM-исполнителей и редактируемая таблица model_prices;
- проекты: список, sidebar filter, detail, board и loading;

## Админка пользователей и стоимости моделей

Маршрут `#/users` рендерит `UsersAdmin` из
`packages/ui/src/components/UsersAdmin.tsx`. Выбранный пользователь открывает
табы доступа, машин, «Использование моделей» и истории; таб расхода показывает
токены, число ответов и две независимые стоимости — «По данным CLI» и «По
прайсу» — в итогах, разбивке по моделям и временным бакетам. Если для ответа нет
ни цены CLI, ни строки тарифа, компонент показывает «—» для отсутствующей суммы
и объясняет неполноту в tooltip, а не выдаёт ноль за известную цену.

Только администратор видит ниже пользовательской карточки реестр LLM-исполнителей
и «Стоимость моделей». Последний виджет выводит провайдера, модель, четыре цены
USD за 1M токенов, источник и дату тарифа; форма позволяет добавить строку или
перенести её в черновик для правки, удаление передаёт пару provider/model. Стор
загружает прайсы при открытии админки и после сохранения либо удаления перечитывает
их через IPC-мосты `admin:modelPrices`, `admin:saveModelPrice` и
`admin:deleteModelPrice`; HTTP-реализация этих мостов использует общий REST-контракт
из `packages/shared/src/protocol.ts`.
- поверхности UI: settings/users/machines/projects/board/utility open flags.

Начальное состояние не считается серверной истиной. Загрузкой руководит
`AppRuntime.start()`: сначала `sessionStore.check()` (наличие моста сессии → `/me`),
и **без авторизации защищённый bootstrap не запускается вовсе** — показывается
`LoginScreen`. После входа граф такой: параллельно `settings.load()` (настройки,
движки, права — раньше любой фильтрации моделей) и `chat.loadConversationIndex()`,
затем параллельно необязательные `projects.loadNavigation()`,
`operations.refreshAgents()` и `settings.loadCatalogs()` (микрофоны, статус модели,
голоса, capabilities, MCP, статус входа CLI), после чего запускается опрос статуса
входа и открывается чат из адреса либо самый свежий. Bootstrap идемпотентен:
повторный вход в той же вкладке не запускает второй граф. **Ошибка необязательного
домена не превращает приложение в `LoginScreen` и не стирает уже загруженный чат** —
она видна на своём экране (`agentsStatus: 'error'`, тост) и всё. Админские данные
грузятся только при открытии админки (`AppRuntime.openAdmin()`).

`logout` и вход другим пользователем в той же вкладке проходят через события
`sessionStore` и приводят к полной очистке пользовательских и административных
доменов: чужих разговоров, настроек, машин и админских таблиц после смены
пользователя не остаётся.

## Маршруты (hash-роутер)

Навигация — собственный `lib/useHashRoute.ts` без зависимостей: hash выбран потому,
что desktop грузит рендерер по `file://`, где path-роутинг не работает. Маршруты:
`#/chat/:id` (открытый разговор),
`#/projects/:id[/settings|/releases|/assistant|/task/:taskId[/preparation|/chat/:chatId]]` и
страницы-утилиты `#/claude-code`, `#/codex`, `#/machines`, `#/kb`, `#/users`, `#/ci`. Мост `usage:report` уже запрашивает личный `GET /api/usage`, но отдельный экран и пункт меню для него в текущем `packages/ui` ещё не подключены; отчёт по-прежнему показывает только админская страница пользователей.
Все три адреса проекта — одна и та же страница с общей шапкой (`ProjectPage`),
меняется только содержимое; `#/projects` без id страницей-списком больше не
является — с него сразу уводим на первый проект (`replace`), а если проектов нет,
показываем пустое состояние с подсказкой создать проект в сайдбаре. Правило
«первый в списке» единое и для клика «Проекты» в переключателе сайдбара, поэтому
персиста последнего проекта (`vc.lastProject`) нет.
`navigate(to, { replace: true })` меняет адрес через `history.replaceState` без новой
записи в истории — так пишутся адреса, на которые приложение перекидывает само
(иначе «Назад» упирается в редирект); подписчиков `useSyncExternalStore` при этом
будит сам роутер, потому что `replaceState` не порождает `hashchange`.

Карточка задачи тоже адресуема: `ProjectBoard` не только принимает
`initialOpenTaskId`/`initialOpenTaskTab` из адреса, но и сообщает наружу каждое
открытие и закрытие (`onOpenTaskRouteChange`), поэтому `App.tsx` пишет
`#/projects/:id/task/:taskId` при открытии и возвращает `#/projects/:id` при
закрытии. Необязательный четвёртый сегмент выбирает вкладку модалки:
`/preparation` открывает «Подготовку к разработке» (кнопка «Лента подготовки» на
карточке), `/chat/:chatId` — связанный чат задачи. Ручное переключение вкладок
внутри уже открытой модалки в адрес не пишется.

**У открытого чата всегда есть адрес.** `App.tsx` держит одну точку синхронизации
`syncedChatId` (последний согласованный id): изменился адрес — грузим чат из адреса
(`selectConversation`), изменился `activeId` в сторе (создание, удаление, resume
сессии CLI, автосоздание чата первой репликой) — переписываем адрес `replace`-ом.
Поэтому «#/» сразу превращается в `#/chat/:id`, а ссылку на чат можно скопировать
и открыть заново — в том числе в другом браузере.

Ссылка ведёт в чат и мимо обычного пути: `init(preferredChatId)` передаёт id из
адреса в `bootstrap()`, и тот открывает именно его, а не самый свежий разговор —
лишней загрузки «свежего» не происходит. Если чат из адреса лежит в другом проекте,
`selectConversation` сам переключает фильтр сайдбара (`setSidebarProject`), иначе
активного разговора не видно в списке. Битая ссылка (чат удалён или чужой) даёт
`selectConversation → false`, баннер «Разговор не найден» и возврат на прежний
(при загрузке страницы — на самый свежий) чат с починкой адреса.

## Общий переключатель Sidebar

Состояние общей боковой панели принадлежит `App` (`packages/ui/src/App.tsx`), а не чату или канбану. На десктопе `collapsed` сворачивает колонку Sidebar и сохраняется в `localStorage` под ключом `vc:sidebarCollapsed`; на мобильной ширине независимый `sidebarOpen` управляет выдвижной панелью. Вычисленное `sidebarExpanded` и один обработчик `toggleSidebar` передаются и в `ChatColumn`, и в `ProjectPage`, поэтому переходы между чатом, проектом и карточкой задачи используют одну панель и одну механику. Любая смена маршрута закрывает только мобильный drawer; десктопное предпочтение сохраняется.

Обе шапки рендерят `SidebarToggle` из `packages/ui/src/components/ui/IconButton.tsx`. Компонент использует один значок, меняет `aria-label` и `title` между «Открыть боковую панель» и «Закрыть боковую панель» и отражает состояние через `aria-expanded`; базовый `IconButton` даёт клавиатурную кнопку и общий видимый focus. В `ProjectPage` переключатель передаётся в слот `leading` общей рамки `ToolFrame`, то есть стоит перед заголовком проекта и доступен также при прямом переходе на URL канбана.

На мобильной ширине открытый Sidebar получает `side--open` и показывается вместе с `.side-backdrop`; существующая адаптивная раскладка выводит его поверх содержимого и блокирует прокрутку фона. Клик по backdrop или Esc вызывает `closeMobileSidebar`, после чего фокус возвращается к `.sidebar-toggle`. `ProjectPage` передаёт открытой панели Esc через `ToolFrame.onEscape`, чтобы общий стек окон не обработал это нажатие как действие страницы. На десктопе переключение меняет только класс раскладки `app--sidebar-collapsed`, а канбан остаётся смонтированным, поэтому его `scrollLeft` и `scrollTop` не сбрасываются. Эти сценарии закреплены в `packages/ui/src/App.projects.dom.test.tsx`.

## Прокрутка канбан-доски

Рабочая область `KanbanBoard` заполняет остаток полностраничного `ToolFrame`: `.toolpage` имеет `height: 100%` и `overflow: hidden`, а цепочка `.toolpage > .jboard-wrap` → `.jboard` использует `flex: 1`, `min-height: 0` и `min-width: 0`. `.jboard-wrap` обрезает выход за границы, поэтому переносимая по строкам шапка проекта и соседняя `.jboard-filters` остаются вне прокрутки доски и автоматически отнимают свою фактическую высоту без пиксельных offsets. На мобильной ширине корневая `.app` использует `100dvh`, поэтому изменение браузерных панелей и ориентации пересчитывает доступную высоту.

`.jboard` растягивается на остаток области и владеет только горизонтальной прокруткой (`overflow-x: auto; overflow-y: hidden`). Обычная `.jcol` занимает `height: 100%`, ограничена высотой поверхности и состоит из неподвижных siblings `.jcol-head`, `.jcol-body`, `.jcompose`/`.jcompose-open`. Только `.jcol-body` получает остаток (`flex: 1; min-height: 0`) и `overflow-y: auto`; поэтому длинная колонка не растягивает страницу, её header и композер остаются видимыми, а соседние списки сохраняют независимые `scrollTop`. `overscroll-behavior: contain` не передаёт вертикальный жест наружу. Режим свимлейнов сохраняет собственную общую вертикальную прокрутку `.jboard--lanes`, поскольку его DOM организован дорожками, а не цельными вертикальными колонками.

Во время pointer-переноса карточки `KanbanBoard.tsx` направляет горизонтальный автоскролл на `.jboard`, а вертикальный — на фактический `[data-drop-body]` активной/ближайшей колонки. Для переноса колонок используется только горизонтальная ось `.jboard`. Стабильные React-ключи сохраняют сами DOM scroll-контейнеры и их позиции при drop, открытии карточки и обычном обновлении данных. Источник инвариантов высоты и overflow — `packages/ui/src/styles/app.css`; регрессии цепочки, независимой прокрутки, сохранения позиций и обеих осей DnD закреплены в `packages/ui/src/styles/boardScroll.test.ts` и `packages/ui/src/components/kanban/KanbanBoard.dom.test.tsx`.

## Отдельный режим Web Reader

Маршрут `#/web-reader[/<conversationId>]` использует общий `App`, но работает как полноэкранный workspace, а не как разновидность обычной страницы чата. В `packages/ui/src/App.tsx` признак `inReader` добавляет корню класс `app--web-reader`, полностью исключает из DOM общий `Sidebar` вместе с мобильным backdrop и не передаёт в `ChatColumn` обработчик открытия сайдбара. Переключение Reader-разговоров остаётся в собственной шапке `web-recorder-selector`, поэтому список обычных чатов в этом режиме не нужен.

Список чатов Web Reader — отдельное состояние стора `readerConversations` (`packages/ui/src/store/domains/chatStore.ts`): оно строится из полного ответа `conversations:list` до фильтра сайдбара, поэтому persisted-фильтр проекта обычного чата (`sidebarProjectId`) на него не влияет. Reader-чатом считается разговор с `assistantKind === 'web-recorder'` либо разговор **без** `assistantKind`, но с сохранённым `previewUrl` (старые чаты до введения `assistantKind`) — предикат `isReaderConversation` экспортирован из `chatStore`. Легаси-ветка намеренно ограничена пустым `assistantKind`: иначе разговор другого вида (Playwright Reader), которому кто-то сохранил `previewUrl`, попал бы и в селектор Web Reader. Активный поисковый запрос сайдбара (`conversations:search`) список Web Reader не трогает; удаление чата и смена `previewUrl` синхронизируют его напрямую.

Селектор `web-recorder-selector` перечисляет все reader-чаты из `state.readerConversations` и подсвечивает текущий `activeId`; если активный чат в списке отсутствует (ещё грузится или это не reader-чат), селектор показывает недоступный плейсхолдер «Чат не выбран», а не молча первый пункт. «+ Новый» и авто-создание из эффекта Reader идут через общий `createReaderChat` с in-flight флагом: пока создание в полёте, эффект авто-выбора не переключает `activeId` и не создаёт второй чат; так как список полный, только что созданный чат не может «выпасть» из него из-за фильтра проекта, и цикла повторного создания нет. Новый reader-чат получает различимое имя «Web Reader N» (N — следующий порядковый номер по существующим именам этого вида). Гонка «клик по старому чату → сразу „+ Новый“» закрыта токеном актуальности в `selectConversation`: каждый выбор и `newConversation` инкрементируют счётчик, и ответ `conversations:get` применяется к стору только с актуальным токеном, устаревший отбрасывается молча. Устаревший вызов возвращает `false` (без `error` и без «разговор не найден»), лентой он больше не владеет: `loadingMessages` снимает только актуальный вызов, а `newConversation` сбрасывает флаг сам, чтобы после отброшенного выбора чат не остался в скелетоне. Регрессии закреплены в `packages/ui/src/store/appRuntime.sidebar.test.ts` и `packages/ui/src/App.chat.dom.test.tsx`.

Цепочка высоты описана в `packages/ui/src/styles/app.css`: корень Web Reader становится одноколоночным, `chat-split` занимает первую колонку и наследует `height: 100%`, а `section.webpreview[aria-label="Web Reader"]` также имеет `height: 100%`. Обычная `chat-page` использует ту же наследуемую высоту вместо отдельного `100vh`; на узком экране действуют существующие правила `100dvh` и переключение табов «Чат»/«Сайт». DOM-регрессия закреплена сценарием отдельной страницы в `packages/ui/src/App.chat.dom.test.tsx`: тест требует отсутствие `aside.side`, класс `app--web-reader` и наличие семантической секции Web Reader.

## Отдельный режим Playwright Reader

Рядом с Web Reader живёт второй полноэкранный режим — Playwright Reader (маршруты `#/playwright-reader` и `#/playwright-reader/<conversationId>`). Он устроен по той же схеме: признак `inPlaywrightReader` в `App.tsx` даёт корню класс `app--playwright-reader`, исключает `Sidebar` из DOM тем же условием, что и Reader, не передаёт в `ChatColumn` обработчик сайдбара и рендерит ту же `chat-split` с левой колонкой обычного чата. Пункт меню «Playwright Reader» (иконка `▣`) стоит в `Sidebar` сразу после «Web Reader» и в компактном наборе иконок, но, в отличие от него, открывается в текущей вкладке обычным `navigate('/playwright-reader')`, а не `window.open`. Смысл, состав контрактов и состояние backend-части — в [features/playwright-reader.md](features/playwright-reader.md).

Список этого режима — отдельное состояние `playwrightReaderConversations` в `chatStore`, которое строится из того же полного ответа `conversations:list` и по тем же правилам, что `readerConversations`: фильтр проекта и активный поиск сайдбара на него не влияют, удаление чата вычищает оба списка. Предикат `isPlaywrightReaderConversation` в `chatStore` смотрит только на `assistantKind === 'playwright-reader'` и не принимает легаси-чаты с `previewUrl`, поэтому два reader-списка не пересекаются. Эффект маршрута повторяет reader-логику: найденный по ID чат выбирается через `selectConversation`, иначе адрес заменяется первым чатом из списка, и только при пустом списке создаётся новый — под in-flight флагом `playwrightReaderCreating`, который проверяется и в самом эффекте, чтобы React не создал второй разговор. Имя нового чата — «Playwright Reader N»; общая для обоих видов нумерация теперь ищет **первый свободный** номер по существующим именам (прежний `nextReaderNumber` с максимумом удалён), поэтому после удаления «Web Reader 1» следующий чат снова получит номер 1.

Правая панель монтирует общий `WebReaderHost`, поэтому уже поддерживает рабочий iframe-превью и действия модели `mcp__browser__*`; интеграции этой панели с изолированным Chromium из `apps/browser-runner` пока нет. Регистрация исполнителя хранится вместе с `conversationId` активного чата, URL сохраняется в разговоре и восстанавливается после refresh, а при переключении чатов команды прежнего разговора отклоняются. Два следствия общего host-а стоит помнить: в этом режиме ему передаётся только `conversationUrl` (`projectUrl` жёстко `null` — проектный адрес сюда не подставляется, у Playwright-чатов проекта и не бывает), а секция и iframe остаются с подписью «Web Reader», то есть DOM-селекторы и тесты ищут панель по этому имени и на маршруте Playwright Reader. Прежняя статичная заглушка (шапка «Браузер остановлен», отключённая адресная строка Chromium, «Подключение к изолированному Chromium…») из разметки удалена, но её правила `.playwright-browser-pane` и `.playwright-reader-header` остались в `app.css` неиспользованными; живёт из старых стилей только `.playwright-reader-selector`. Восстановление после refresh держится на `initialChatId`: `useVoiceStore` получает `routeChatId ?? routeReaderChatId ?? routePlaywrightReaderChatId`, поэтому чат из адреса становится активным сразу и регистрация панели привязывается к нему без ручного выбора чата. Split-раскладка полностью общая с Web Reader: тот же стейт вкладок `chatView` («Чат»/«Сайт» до 768 px), тот же `resizePreview` и **тот же** ключ `localStorage` `voicechat.previewWidth` — отдельной сохранённой ширины у Playwright Reader нет. Стили лежат рядом с reader-правилами в `packages/ui/src/styles/app.css`; регрессии refresh и изоляции покрыты в `packages/ui/src/App.dom.test.tsx`.

Обычный сайдбар эти чаты пока не прячет: он фильтрует список условием «не `web-recorder` и без `previewUrl`», под которое Playwright-чаты не попадают, — «Playwright Reader N» видны в общем списке бесед. На сервере привязка такого разговора к проекту запрещена: `setConversationProject` возвращает `null` при непустом `projectId`.

## Разговор и ход модели

`newConversation`, `selectConversation`, rename/delete/search работают через `window.api`. Обычный `newConversation()` открывает локальный черновик без id и записи в SQLite; повторные нажатия только сбрасывают состояние. Единственная точка персистенции такого чата — `ensureConversation()` при первой отправке: `POST /api/conversations/draft` одной SQLite-транзакцией создаёт разговор, применяет выбранный `projectId` и проектные машину/папку/навыки, сохраняет первую реплику и возвращает разговор с сообщениями. Клиент сохраняет ключ идемпотентности до успешного ответа, поэтому повтор после сетевого сбоя не создаёт дубль, а текст и вложения очищаются только после успеха. Заголовок берётся из текста первой реплики, при одних вложениях — из их имён; после ответа маршрут становится `/chat/:id`, а строка появляется в Sidebar. Специальный `web-recorder` по-прежнему создаётся сразу, как и независимые lifecycle чатов задач, kanban-ассистента и возобновлённых CLI-сессий.

При миграции `cleanup-empty-manual-drafts-v1` один раз удаляются только пустые строки с точным заголовком «Новый разговор» и полностью дефолтными полями: без проекта, задачи, `assistant_kind`, CLI-сессии, настроек выполнения/LLM/KB/preview и сообщений. Переименованные, настроенные и служебные разговоры сохраняются. Списки, поиск и чтение по-прежнему ограничиваются сервером по `user_id`; клиентская логика черновика не участвует в изоляции.

Выбор разговора загружает сообщения и восстанавливает его индивидуальные настройки. Фильтр проекта хранится в localStorage и ограничивает sidebar, но не меняет владение данными на сервере.

`submitText()` валидирует draft/attachments, фиксирует цель выполнения, сохраняет пользовательское сообщение и отправляет LLM-запрос. Композер остаётся доступен в состояниях ожидания, транскрибации, стриминга и озвучки (кроме записи с микрофона): текст, вложения и preview можно отправить, не дожидаясь `idle`. В активном состоянии стор не начинает второй локальный ход и не выполняет utility-команду, а передаёт сохранённую реплику через `sendClaudePrompt`; кнопка и Enter помечены для пользователя как добавление в очередь. Источники поведения — `packages/ui/src/store/domains/chatStore.ts` и `packages/ui/src/components/VoiceBar.tsx`.

`TurnManager` в `apps/server/src/turns.ts` допускает только один активный ход на `conversationId`. Дополнительный `claude.send` сохраняется в SQLite-таблице `conversation_turn_queue`; `message_id` имеет UNIQUE-ограничение и служит ключом идемпотентности повторной доставки из нескольких вкладок. Payload содержит сегменты, upload-id вложений, снимок цели выполнения и контекст Web Reader. Связанная строка `messages` при постановке получает `state = 'queued'` и исключается из `listMessages` и полнотекстового поиска; время создания не используется как позиция ленты. Опубликованные строки имеют независимый `history_position`, а legacy-сообщения миграция помечает опубликованными и заполняет им позиции из прежнего SQLite-порядка.

После сохранения AI-ответа `takeQueuedTurn` одной SQLite-транзакцией выбирает первый FIFO-элемент, переводит то же сообщение (с исходным `messageId`, отредактированным текстом и вложениями) в `published`, назначает позицию после ответа и удаляет строку очереди. `TurnManager` рассылает `claude.queue` с опубликованным сообщением и только затем запускает следующий ход в microtask. Store удаляет из основной ленты все `messageId`, присутствующие в снапшоте очереди, добавляет опубликованное сообщение с дедупликацией по id; поэтому reload, reconnect и несколько окон видят одинаковую серверную последовательность.

UI показывает блок «В очереди»: текст, число вложений, позицию, статус и действия «Редактировать», «Удалить», «Отправить сейчас». Редактирование меняет существующее сообщение и payload без дубля; удаление одной транзакцией удаляет очередь и пользовательскую реплику. При ошибке текущий вопрос возвращается со статусом `failed`, очередь ставится на паузу, а прочие ожидающие сообщения остаются скрытыми из истории. Обычный Stop завершает CLI, игнорирует поздние токены, сохраняет partial AI-сообщением с `meta.interrupted` и ставит очередь на явную паузу. «Отправить сейчас» использует отдельный путь: снимает выбранное дополнение без обычной публикации, прерывает активный ход, создаёт понятную пользовательскую реплику с секциями «Исходный вопрос» и «Дополнение», объединяет вложения и запускает ровно один новый ход; остальные элементы сохраняют порядок. Таблицы очереди и `conversation_turn_control` переживают reconnect и штатный restart сервера.

Поток `claude.token/activity/usage` обновляет live-состояние только соответствующего разговора. Если пользователь переключился в другой чат, генерация продолжается в `activeTurns`; возврат показывает накопленный partial. `claude.done` использует уже сохранённое сервером сообщение, когда оно пришло в событии, и не создаёт дубль. Error/cancel очищают только относящийся к ходу live-state. `executePlan` и `answerQuestions` превращают выбор пользователя в новый запрос по контракту служебных блоков.

### Единая строка состояния активного запроса

Единственное видимое представление lifecycle активного LLM-запроса находится возле композера в `packages/ui/src/components/VoiceBar.tsx`. Локальная `requestPhase` переводит один DOM-элемент между отправкой, обработкой, стримингом, остановкой и краткими итогами: ожидание определяется `state === 'thinking'`, начало ответа — пропом `replyStarted`, а ошибка приходит из `state.error` через `App.tsx`. Повторные realtime-события обновляют эту же строку, завершение без ошибки сразу убирает её, а ошибка или отмена показываются 1,5 секунды. Отдельный скрытый `voice-announce` остаётся только доступным объявлением голосового цикла и не является второй видимой строкой.

`ChatColumn` больше не рисует карточку ожидания и нижний lifecycle-статус внутри стримящегося пузыря: в ленте остаются сам partial-ответ и `MessageTimeline`. В развёрнутом `VoiceBar` у активной строки одна кнопка с `aria-label="Остановить ответ"`; первый вызов ставит фазу `stopping`, блокирует кнопку через `disabled`/`aria-busy` и защищён `cancelSent` от повторной отмены. В свёрнутом композере тот же статус и та же единственная остановка доступны без разворачивания. CSS в `packages/ui/src/styles/app.css` разрешает тексту строки сжиматься с многоточием, а кнопку оставляет несжимаемой.

Строка состояния не меняет управление очередью: поле, Enter и кнопка отправки остаются доступны во время ожидания и стриминга, а следующая реплика уходит существующим серверным путём очереди. DOM-регрессии отправки, ожидания, стриминга, завершения, ошибки, отмены, повторных событий и кликов, клавиатуры, очереди и узкой ширины находятся в `packages/ui/src/components/VoiceBar.dom.test.tsx`; отсутствие прежних дублей в ленте закрепляет `packages/ui/src/components/ChatColumn.dom.test.tsx`.

Счётчики входящих, исходящих и кэшированных токенов показываются в footer каждого
сохранённого AI-сообщения. Пока ход активен, тот же формат показывает `liveUsage`;
точная частота обновления зависит от событий CLI (Claude — в потоке, Codex — итог
`turn.completed`).

Сообщения можно редактировать и удалять через REST. Экспорт в Markdown/JSON выполняется чистыми shared-функциями и browser download bridge.

## Список бесед обновляется по событиям

Сайдбар — проекция серверной видимости: чат задачи, уехавшей в «Готово», сервер
из списка убирает (`NOT_DONE_TASK_CHAT`, см. [projects.md](projects.md#чаты-завершённых-задач-скрыты-из-списка-бесед)).
Раньше список перезапрашивали только действия пользователя (отправка, выбор,
переименование, поиск) и `bootstrap()`, поэтому открытая страница о смене
видимости не узнавала: строка завершённой задачи висела до перезагрузки, а
вернувшийся в работу чат до неё же не появлялся.

Теперь перезапрос дёргают и события (`chatStore.ts` + порт из `projectsStore`):

- `applyCiDone` — ран финализирован, карточка уехала по колонкам;
- `applyCiSummary` с терминальным статусом (`isTerminalCiStatus`) — сводка
  приходит на **все** соединения пользователя, а не только подписчикам ленты,
  и для страницы без открытой ленты это единственный сигнал о конце рана;
- `applyChatMessage` для **неактивного** чата — раньше метод молча выходил, а
  теперь обновляет сайдбар: строка чата задачи поднимается по `updatedAt`, а
  свежесозданный чат в списке появляется (в открытый чат реплика по-прежнему
  дописывается прямо в ленту);
- `applyBoardUpdate` — только когда изменился набор задач в колонках с
  семантикой `done` или `cancelled` (`taskChatVisibilityIds`/
  `sameTaskChatVisibility`): переезд между обычными рабочими колонками список не
  трогает.

Что видно — по-прежнему считает сервер: клиент только перечитывает список.
Кадры `ci.*` идут потоком (лог, шаги), поэтому все поводы проходят через
`scheduleConversationsRefresh()` — окно склейки `CONVERSATIONS_REFRESH_DEBOUNCE_MS`,
и пачка терминальных кадров одного рана стоит одного `conversations:list`.
Таймер этого окна и debounce поиска сообщений (`searchTimer`) намеренно создаются
самим `chatStore`, а не через `createStoreCore.timer()`: смена разговора и
`cancelRequest()` вызывают общий `core.clearTimers()` для таймеров живого хода.
Если зарегистрировать там и эти два debounce, очистка оставит их локальные ссылки
ненулевыми; новый refresh больше не запланируется, а поиск потеряет ожидаемый
запуск. Оба таймера отдельно снимаются при `dispose()`, поисковый — ещё и при
следующем запросе.

Скелетон при этом не мигает (`conversationsStatus` + `loadView`). Для скрытого
`done`-чата прежнее закрепление открытой строки сохраняется. Для `cancelled`
серверный badge запрещает закрепление: строка исчезает, но `activeId`, сообщения,
черновик и активный ход остаются. Прямо открытый отменённый чат после загрузки
`TaskChatContext` также удаляется из локального списка, а шапка показывает отметку
«Задача отменена».

`applyBoardUpdate` не подменяет открытую доску кадром другого проекта, но всё
равно планирует серверный refresh списка: переключение проектов и фоновые
изменения колонок не могут раскрыть отменённые разговоры. Для открытой доски
refresh ограничен фактическим изменением наборов `done`/`cancelled`.

В тестах стора отложенный перезапрос надо гасить: `CONVERSATIONS_REFRESH_DEBOUNCE_MS`
экспортирован (промотать окно фейковыми таймерами), а `dispose()` снимает таймер —
иначе он утекает в соседний кейс и дёргает fake API уже после его проверок. Проводка
событий проверяется в `appRuntime.sidebar.test.ts`, сам фильтр видимости — в
`appRuntime.chat.test.ts`.

## Голосовой конвейер

`lib/featureFlags.ts` содержит временный глобальный gate `VOICE_INPUT_ENABLED`. При выключенном gate `VoiceBar` показывает неактивный микрофон, store отклоняет ручной и автоматический запуск захвата, а `SettingsModal` блокирует STT, выбор микрофона, диаризацию, hands-free и barge-in. Текстовый ввод и TTS остаются доступны.

`browserAudio.ts` получает MediaStream выбранного устройства. Worklet/source переводит вход в mono PCM16 требуемой частоты и шлёт бинарные чанки. RMS поступает в VAD и индикатор.

Все переходы выполняются через shared `transition()`. Store исполняет эффекты: start/stop capture, начать/закончить STT, послать prompt, поставить TTS в очередь. Ручное присваивание voice-state вне перехода опасно: ломает barge-in и тесты автомата.

Partial STT обновляет живые сегменты; final формирует draft/сообщение и запускает thinking в зависимости от режима. Hands-free использует пороги и таймеры `vad.ts`. Во время speaking обнаружение речи вызывает barge-in: плеер и серверный TTS отменяются, начинается новый захват.

Текст LLM режется на законченные произносимые фразы по мере стрима. `ttsPlayer` гарантирует последовательное воспроизведение, учитывает source-complete и завершает состояние лишь после последнего аудио. Markdown, code fences и служебные блоки не озвучиваются.

## Компоненты и поверхности

`App.tsx` соединяет основной layout и глобальные popup-поверхности. `Sidebar` показывает разговоры, поиск, фильтр проекта и режим работы чата; его карточки только открывают или удаляют разговор, а не переименовывают его. Переименование доступно только из шапки открытого чата через `ChatColumn.onRenameTitle`. Пункт «История LLM» открывает объединённый `EnginesObserver` по неизменному `#/claude-code`; он показывает сессии Claude/Codex, их модель, токены и оценку стоимости, а его `ToolFrame` носит то же название. `ChatColumn` рендерит timeline, streaming response, activity/usage и edit/delete действия. `VoiceBar` содержит композер, вложения, микрофон и cancel.

**Карточка чата подписана режимом, а не lifecycle-статусом.** Ручного селекта
«планируется/разрабатывается» в строке больше нет: `.cstatus` показывает слово
режима разговора — «план», «разработка», а при полном доступе «чат» или
«задача» (`chatModeLabel` в `@shared/types`). «Задача» показывается только
если у `Conversation` есть `taskId`; у обычного чата в том же режиме — «чат».
Это свойство самой беседы, а не `taskBadges`, которые загружаются отдельно, поэтому
подпись не меняется при дозагрузке бейджей. Пока идёт ход (`workingIds`), строка
синяя, с мигающей точкой `.cstatus-dot` и префиксом: «идет план»
(`activeStatusLabel`); в простое — то же слово серым и без точки.
Разговор со своим `permissionMode === null` наследует общие настройки, поэтому
`Sidebar` получает их пропом `defaultPermissionMode`
(`state.settings.permissionMode`) — иначе карточка врала бы про действующий
режим. Сам lifecycle-статус (`Conversation.status`) никуда не делся: его
по-прежнему проставляет стор после успешного хода (`setConversationStatus`
осталась в API стора и в мосте), просто точки входа для ручной смены в UI
больше нет.

Поиск в сайдбаре двухрежимный — переключатель «Беседы | Сообщения» (`.searchscope`).
«Беседы» фильтруют список по названию и тексту (`conversations:search`, как было).
«Сообщения» — полнотекстовый поиск по всей истории (`messages:search`, FTS5):
запрос уходит через 250 мс после последнего нажатия, предыдущий отменяется
транспортом, а ответы обесцененных запросов стор отбрасывает по номеру
(`searchSeq`). Панель `MessageResults` в `Sidebar.tsx` знает четыре состояния:
подсказка про синтаксис (пустой запрос), скелетоны (`.msgfound--skeleton`),
«Ничего не найдено» и ошибка с кнопкой «Повторить». Ошибка поиска живёт **в
панели, а не в тосте**: она рядом с полем ввода, и печатать можно дальше.
Сниппет приходит с метками `<mark>` вокруг совпадений, но вставлять его как HTML
нельзя (в сообщениях бывает и код, и разметка) — `splitSnippet` (`lib/snippet.ts`)
режет строку на куски, а `<mark>` рисует React. Клик по карточке: стор запоминает
`highlightMessageId`, `App` переходит в беседу, а `ChatColumn` прокручивает к
`[data-mid]` и держит подсветку `.msg--found` две секунды, после чего гасит её
через `onHighlightDone`. Поиск подчиняется фильтру проекта сайдбара
(`projectId`, где `null` — беседы без проекта).

Строка чата, привязанного к задаче канбана, в `Sidebar` выглядит как задача:
иконка типа, ключ `PRJ-42` и лозенга статуса последнего CI-рана (`.ctask`), слева
accent-полоска (`.convo--task`), а рамка подсвечивается классами `.convo--ci-*` —
тем же `ciCardPulse`, что и карточка на доске. Пропсы — `taskBadges` (метки по id
беседы, стор `taskChatBadges`) и `ciSummaries` (сводки по `taskId`); подсветка
работает без открытой доски, детали — в
[features/ci-runner.md](features/ci-runner.md). Шапка открытого чата
(`chat/TaskChatHeader`) подсвечивается так же и берёт живую сводку пропсом
`summary`, откатываясь на статус из `TaskChatContext`, если сводки ещё нет.

**Виджет задачи — свойство открытого чата, а не состояние стора.** Чат
открывается по адресу, и залипший виджет прошлой задачи в новом разговоре —
типовой баг этого места. Поэтому в `TaskChatContext` есть `conversationId`
(сервер кладёт туда id запрошенного чата), а `App` рисует шапку только при
`state.taskChatContext.conversationId === state.activeId`: опоздавший ответ на
уже закрытый чат нарисовать нечем. Вторая половина инварианта — в сторе: любая
смена `activeId` (`selectConversation`, `newConversation`, автосоздание чата в
`ensureConversation`, `resumeCcSession`/`resumeCxSession`) чистит per-chat
состояние одним хелпером — `chatScopedReset()` (лента + контекст задачи) или
`chatSwitchReset()` (плюс живое состояние хода: `liveSegments`, `consoleLog`,
`liveActivity`, `voice`, `streamingReply`, `lastTurnMeta`, `liveUsage`). Новая
точка перехода добавляется через них, а не копипастой полей — иначе следующий
раз про виджет опять забудут.

`SettingsModal` управляет STT/TTS, моделями/голосами, аудиоустройством и поведением. Недоступные по памяти capabilities не просто скрываются: сервер всё равно является последним gate.

## Web Reader — отдельная страница

На 2026-08-08 в UI нет страницы или компонентов Figma Make: `plans/figma-make-analog.md` фиксирует план, а не реализованную поверхность. Ближайший работающий отдельный маршрут с интерактивным iframe — Web Reader; он показывает внешний сайт через `/api/preview`, а не файлы или артефакты сгенерированного приложения. Новая Make-страница должна остаться отдельной поверхностью `packages/ui` и использовать существующий `useHashRoute`, но её каталог, редактор, превью и ревизии в коде ещё отсутствуют.

Обычный чат не монтирует браузерную панель: `App.tsx` рендерит его как `.chat-page` с одним `ChatColumn`. Пользовательское название отдельной страницы — **Web Reader**, её канонический hash-маршрут — `#/web-reader/:id`. Старые ссылки `#/web-recorder/:id` остаются входной точкой, но сразу заменяются через `navigate(..., { replace: true })` на новый URL. Пункт «Web Reader» с доступным названием находится в `Sidebar` сразу после «Консоли» (и в компактном наборе иконок). Он вызывает экспортированный `openWebReaderWorkspace`: функция формирует URL текущего приложения с hash `#/web-reader` и открывает его через `window.open(..., '_blank', 'noopener,noreferrer')`, поэтому маршрут и экран исходного чата не меняются. Новая вкладка сама выбирает существующий Reader-разговор либо создаёт его и монтирует самостоятельную split-поверхность; она не добавляет второй чат в DOM исходной страницы и не зависит от её локального React-состояния.

Принадлежность нового разговора определяется типизированным `Conversation.assistantKind === 'web-recorder'`: внутреннее значение типа намеренно не переименовано, `newConversation('web-recorder')` передаёт его через IPC/REST, а SQLite сохраняет в `conversations.assistant_kind`. Список Web Reader также принимает миграционные разговоры с собственным `previewUrl`, поэтому их история и URL доступны без изменения записи. Если ID из `#/web-reader/:id` не принадлежит этому набору, приложение не открывает обычный чат как Reader и не создаёт лишний разговор: после готовности списка оно заменяет адрес первым подходящим Reader-разговором, а только при отсутствии таких разговоров создаёт новый (создание защищено in-flight флагом от повторов). Основной сайдбар исключает оба вида, чтобы они не смешивались с обычными чатами; набор reader-чатов считает стор — предикат `isReaderConversation` и состояние `state.readerConversations` из полного `conversations:list`, независимое от фильтра проекта в сайдбаре (см. «Отдельный режим Web Reader»).

Страница Web Reader переиспользует тот же store, `ChatColumn` и композер: над чатом размещены селектор только Reader-разговоров и кнопка создания, а выбор в селекторе меняет `#/web-reader/:id`. Новые reader-чаты получают различимые имена «Web Reader N»; при активном чате вне списка селектор показывает плейсхолдер «Чат не выбран», не подсвечивая первый пункт. Справа `WebReaderHost` подключает независимое приложение по публичному `postMessage`-контракту; путь сборки iframe остаётся `/web-recorder/`. Хост передаёт URL активного разговора (либо project fallback) и сохраняет изменённый URL через `conversations:setPreviewUrl`. На десктопе области разделены перетаскиваемым разделителем с сохранением `voicechat.previewWidth` в `localStorage`; при ширине до 768 px остаётся один из экранов, переключаемый вкладками «Чат» и «Сайт», без размонтирования второго.

Browser-действие от моста исполняется только когда `conversationId` совпадает с `state.activeId` и открыта страница Web Reader. Вне неё действие получает явный отказ, поэтому обычный чат и старый iframe не могут принять `open/read/find/click/type`. Исполнитель DOM-действий регистрирует только смонтированный `WebReaderHost`; при смене активного разговора выбранный элемент очищается.

В браузере iframe открывает same-origin URL `/api/preview?url=<encoded external URL>` без Bearer-токена в query string. HttpOnly-cookie `vc_preview_session` (`Path=/api/preview`, `SameSite=Strict`) устанавливают два роута: `POST /api/session/login` при входе и `POST /api/session/preview`, который выпускает cookie из действующего Bearer-токена — он нужен сессиям, восстановленным из `localStorage` без повторного login, и после перезапуска браузера (cookie сессионная), иначе любой сайт в превью получал 401. Роут лежит под публичным префиксом `/api/session/`, поэтому Bearer проверяет сам и без него отвечает 401 без cookie. `PreviewPane` не монтирует iframe, пока `window.session.ensurePreview` (web-мост `packages/ui/src/remote/index.ts`) не подтвердит выпуск cookie; при отказе показывается статус «войдите заново», кнопка «Обновить» повторяет попытку, а без session-моста (desktop) гейт открыт сразу. Глобальный auth preHandler использует cookie только для точного пути `/api/preview`. На остальных защищённых API эта cookie не действует, и там по-прежнему нужен `Authorization: Bearer`. `POST /api/session/logout` удаляет preview-cookie через `Max-Age=0`. Источник серверного контракта — `apps/server/src/users/auth.ts`, форма iframe URL и гейт — в `packages/ui/src/WebPreview.dom.test.tsx`. Важная оговорка: `ensurePreview` вызывает только `PreviewPane`, а она в приложении больше не монтируется (см. «Действия модели в превью»). На живом маршруте Web Reader iframe открывает уже рекордер, никакого клиентского гейта у него нет — он рассчитывает на cookie, выпущенную при login или `POST /api/session/preview`; при протухшей cookie сайт в превью получит 401 от прокси, и рекордер покажет это как ошибку загрузки страницы.

`PreviewPane` дополняет адресную строку обновлением iframe, открытием исходного URL во внешней вкладке и тумблером «Выбор элемента». Инспектор общается только с текущим `iframe.contentWindow` и только на origin приложения: родитель отправляет `{ type: 'voicechat.preview.inspector.v1', enabled }`, iframe возвращает `{ type: 'voicechat.preview.element-selected.v1', payload }`; обе формы проходят runtime-проверку. Esc в родителе или iframe выключает режим, причём iframe сообщает выключенное состояние назад тем же command-сообщением. Payload содержит tag/id/classes/data-атрибуты, selector и ancestry, rect/viewport/pageUrl, ограниченные text/outerHTML, computed styles и необязательные данные screenshot.

Выбранный элемент хранится до следующей успешной отправки как чип композера рядом с файлами; новый выбор заменяет старый, крестик удаляет его. В пользовательском `Message.meta.previewElement` сохраняется полный payload, поэтому история после перезагрузки показывает краткую строку элемента/страницы и раскрываемый JSON. Перед ходом `withPreviewElementContext` добавляет payload в отдельный JSON-блок между `BEGIN/END UNTRUSTED WEB PREVIEW ELEMENT` с запретом трактовать содержимое страницы как инструкции; холодная пересборка истории восстанавливает такой блок из meta. Старые сообщения без meta остаются валидными.

`MachineStatus`, `AgentCard`, `AgentCommands` обслуживают регистрацию, токен, policy, install/update и диагностику. `MachineStatus` — единственная поверхность парка машин: там же живут удаление машины (корзина → раскрытая строка с предупреждением и «Удалить»/«Отмена») и раскрывающийся по «▸» редактор политики строки — `AgentCard` (каталоги, паттерны команд, навыки; правки уходят сразу, без «Сохранить»). Своей шапки и сворачивания у `AgentCard` больше нет: раскрытием управляет строка таблицы, а токен и удаление — её же кнопки. `MachineUtility` выбирает `MachineConsole` или `FileExplorer`; `MachineTerminal` использует xterm и PTY bridge. Шапка у всех трёх одна — `MachineUtilityHeader` (машина со статусом видна всегда, бейджи запретов политики, переключатель «консоль/терминал ↔ проводник» в обе стороны и ссылка на `#/machines`); своего селектора машины виджеты больше не рисуют, детали — в [machines.md](machines.md), раздел «Шапка утилиты машины». У однострочной `MachineConsole` есть история команд по машине (проп `historyStore` от стора — переживает закрытие утилиты), кнопка «Стоп» для текущей команды и копирование сеанса из шапки тула; подробности — в [machines.md](machines.md), раздел «Однострочная консоль машины».

`CcObserver` и `CodexObserver` отображают внешние CLI-сессии и могут возобновить их как разговор. `UsersAdmin` — страница `#/users`: у admin это дашборд со сводкой всех пользователей (один `usage-summary` запрос), а `#/users/:name` открывает карточку выбранного пользователя. В карточке admin доступны вкладки доступа к моделям, машин, использования и истории; обычный пользователь открывает только собственную карточку через `/api/me/*` и не видит вкладку машин, управление учётками и реестр исполнителей. Карточка расхода фильтрует серверный отчёт пресетами 7/30 дней или «всё время» и конкретным разговором; смена группировки hour/day/week сохраняет оба фильтра. Итоги, модели и UTC-бакеты приходят одним `UsageReport`, а `byConversation` всегда содержит весь выбранный период, чтобы варианты селекта не исчезали после фильтрации. Если в выборке есть Codex-ответ без цены CLI и строки тарифа, `costIncomplete` заменяет показ цены на «—», чтобы известная часть агрегата не выглядела точной стоимостью. Полная страница доступна отдельно в Storybook как `Admin/User page` (`UsersAdmin.stories.tsx`). `openUsers()` в сторе грузит оба среза параллельно (`refreshAdminUsers()` + `refreshAdminLlmEngines()`), но статус/ошибка у них раздельные: падение реестра не стирает список пользователей и наоборот. Персональную ветку (одна собственная карточка вместо списка) `openUsers()` включает только для **заведомо не-админа** — `currentUser` есть и его роль не `admin`; пока пользователь ещё не загружен (`currentUser === null`), идёт обычная админская загрузка, иначе страница открывалась бы пустой. Для исполнителей стор держит ещё и `adminLlmEngineHealth` — последний снимок проверки по `engineId`; удаление записи сразу вычищает её health-кэш. `ProjectPage` (общая шапка с вкладками «Канбан»/«Настройки» и мобильной кнопкой открытия общего сайдбара), `ProjectBoard`, `ProjectSettings`, `TaskCard` реализуют членство, машины и канбан. Перетаскивание на доске — общий движок pointer-жеста `lib/dnd.ts` (мышь, палец, стилус) плюс перенос с клавиатуры и объявления в `aria-live`; подробности — в [projects.md](projects.md), раздел «Перетаскивание карточек и колонок».

`KnowledgeBase` показывает статус, темы, поиск и документы серверной read-only KB. `QuestionsForm` рендерит одиночный/множественный выбор. `MessageImage` читает файл сервера или машины согласно источнику. `Markdown` поддерживает GFM и подсветку; им же отрисовано описание задачи в карточке канбана (см. [projects.md](projects.md)) — компонент не привязан к ленте чата, кегли под место вызова задаются CSS обёртки.

## Скролл экрана: у документа его нет

Раскладка приложения — «экран ровно во вьюпорт, скроллится внутренность»: `.app` — сетка на `height: 100vh` (`100dvh` на телефоне) с `overflow: hidden`, а внутри у каждой поверхности своя цепочка `display: flex` + `flex: 1` + `min-height: 0` до единственного элемента с `overflow-y: auto` (чат — `.main` → `.scroll`; страница тула — `.toolpage` → `.proj-detail` / `.jboard-wrap` → `.jboard` → `.jcol` → `.jcol-body`). Пропущенный `min-height: 0` в середине цепочки — типовая причина того, что список не сжимается: у flex-элемента минимум по содержимому, и он выпирает наружу.

Автопрокруткой `.scroll` владеет `ChatColumn`. Нижняя граница определяется не равенством, а расстоянием `scrollHeight - scrollTop - clientHeight <= 100`: в этой зоне новые токены, сообщения и поздние изменения высоты содержимого продолжают вести ленту вниз. `ResizeObserver` следит за Markdown, кодом, изображениями и раскрываемыми блоками; resize окна и `visualViewport` учитывает мобильную клавиатуру. Эти источники прокручивают только при включённом follow-режиме.

Колесо/тачпад, touch-жест, pointer на scrollbar и клавиатурная прокрутка отмечают ручное намерение, а последующий `scroll` немедленно выключает follow выше порога. Программная установка `scrollTop` защищена отдельным флагом и не считается ручным действием. Пока пользователь читает выше, рост содержимого не меняет `scrollTop`; один boolean непросмотренного содержимого показывает доступную с клавиатуры кнопку «↓ К новому сообщению» отдельной строкой над композером (без счётчика токенов и без перехвата фокуса). Кнопка, самостоятельный возврат к концу и новая пользовательская реплика снова включают follow.

Позиция и follow-флаг сохраняются в `sessionStorage` под `voicechat:chat-scroll:v1` отдельно по `conversationId`, который `App` передаёт в `ChatColumn`. Поэтому переключение и reload восстанавливают ручное чтение, новый разговор открывается внизу, а фоновые события другого разговора не меняют DOM активной ленты. DOM-регрессии порога, токенов, кнопки, самостоятельного возврата, нового хода и двух разговоров находятся в `components/ChatColumn.dom.test.tsx`.

У колонки чата та же цепочка и своя ловушка: шапка задачи (`.taskchat`) — обычный
элемент `.main`, и раскрытая лента рана растягивала её на своё содержимое. Лента
сообщений садилась на минимум (одни отступы `.scroll`), остаток уезжал за нижний
край, а страницу не прокрутить — у `.app` `overflow: hidden`, и композер
становился недоступен (360×640, тридцать шагов в ленте: `.voicebar` кончалась на
741px при экране 640px). Поэтому у `.taskchat` есть потолок **в процентах от
колонки** (45%, на телефоне 40%), а лента рана забирает его остаток
(`flex: 1 1 auto; min-height: 0; overflow: auto`). Потолок в `vh` тут неверен по
построению: `vh` мобильный браузер считает от «большого» вьюпорта, без адресной
строки, а колонка живёт в `100dvh` — 45vh внутри 100dvh больше сорока пяти
процентов колонки. Инвариант держит `styles/chatScroll.test.ts` (по тексту
`app.css`, как у доски), живьём проверено headless-браузером.

Полностраничная рамка `.toolpage` тянется по клетке сетки (`height: 100%`), а не по `100vh`: у `.app` на узком экране высота считается в `dvh`, и рамка на `vh` оказывалась выше своей клетки — низ колонки уезжал под край экрана. Та же причина, что у `.vc-dialog--phone`/`.ccobs` (там `dvh` появился раньше).

У обычной канбан-доски ограничение высоты непрерывно проходит от grid-корня `.app` через `.toolpage.projpage`, `.jboard-wrap` и `.jboard` до flex-колонки `.jcol`; на каждом промежуточном flex/grid-элементе разрешено сжатие через `min-height: 0` и скрыт вертикальный overflow. Поэтому `.jboard` владеет только горизонтальной прокруткой колонок, а вертикальный scroll-контейнер каждой колонки — её `.jcol-body` с собственной позицией прокрутки и локальным overscroll. Шапка и форма создания задачи имеют `flex: none` и остаются на месте. Режим свимлейнов намеренно отдельный: общий вертикальный скролл остаётся у `.jboard--lanes`, а ячейки `.jcol--incell` сохраняют авто-высоту и видимый overflow. Источник правил и регрессионных инвариантов — `packages/ui/src/styles/app.css` и `packages/ui/src/styles/boardScroll.test.ts`.

Отдельная ловушка, не связанная с flex: **`position: absolute` без позиционированного предка считается от страницы, и `overflow: hidden` предков его не обрезает.** На этом канбан скроллил html вместо колонки: у каждой карточки есть скринридерная подсказка `.vc-sr-only` (абсолютная, 1×1px), блок-контейнером ей была страница, и сорок карточек растягивали документ на 6000px, хотя `.jcol-body` их клипал. Лечится двумя объявлениями: `position: relative` у `.jcard` (подсказка живёт в своей карточке) и у `.app` (страховка на весь интерфейс — окна уходят порталом в `body`, а слой переноса `.vc-draglayer` фиксированный, им это правило безразлично). В jsdom такое не поймать — раскладки там нет; инвариант держит `styles/boardScroll.test.ts` по тексту `app.css`, а живьём это проверяется headless-браузером (доска на 40 карточек: `document.scrollingElement.scrollHeight === clientHeight`).

## Свёрнутые панели чата

Колонка чата зажата между двумя панелями постоянной высоты: сверху виджет задачи
(`chat/TaskChatHeader`), снизу композер (`VoiceBar`). На телефоне вдвоём они
оставляли ленте сообщений полторы реплики, поэтому каждая сворачивается в одну
строку:

- **Виджет задачи** свёрнутый показывает ключ и заголовок задачи, лозенгу статуса
  рана и «Открыть задачу»; уходят крошки Проект/Эпик/Стори, мета (этап, режим,
  таймер, машина, папка) и лента рана. Статус остаётся намеренно — ради него в
  шапку и смотрят.
- **Композер** свёрнутый — строка-заглушка с тем, что в нём осталось: черновик,
  иначе число вложений, иначе состояние хода (`composerPeek` в `lib/view.ts`).
  Красная кнопка остановки в строке сохраняется: обрывать ход модели или запись
  нужно одним нажатием, а не через разворот. Живая область `voice-announce`
  тоже остаётся — читалка не должна замолкать оттого, что панель убрали.

Состояние панелей нигде не хранится — ни в localStorage, ни в сторе: это обычный
`useState` внутри компонента. Виджет задачи по-прежнему открывается свёрнутым.
Начальное состояние композера приложение выбирает через
`useMediaQuery(CHAT_COMPOSER_QUERY)`, где запрос `(max-width: 768px)` совпадает с
мобильными правилами `VoiceBar` в `styles/app.css`: на телефоне композер
свёрнут, на ширине больше 768 px поле ввода сразу присутствует в DOM. Изменение
ширины обновляет значение media query, но не перезаписывает уже созданное
локальное состояние и ручной выбор пользователя.

Проп `defaultCollapsed` у `VoiceBar` сохранён для Storybook и изолированных
компонентных тестов. Явный клик по `composer-expand` разворачивает панель и через
callback ref сразу переводит фокус в появившийся `textarea`; обычное открытие
десктопного чата фокус не захватывает. Черновик и вложения принадлежат внешнему
стору/пропам, поэтому сворачивание только меняет разметку и не очищает их.

В интеграционных тестах отсутствие поля ввода теперь означает мобильный
viewport. На десктопе тест может сразу обращаться к `textarea`; мобильный тест
сначала кликает `composer-expand` и проверяет фокус.

## Панель «Использование БЗ»

Кнопка 📚 в `.mhead-right` компонента `ChatColumn`: бейдж показывает новые
обращения после серверной границы просмотра (`unreadCount`), скрывается при нуле
и с 100 отображает `99+`. Точное число новых обращений уже есть в `aria-label`,
поэтому бейдж скрыт от скринридера; при активном обращении вместо него `Dots`.
Исторический `totals.queries` по-прежнему показывается только внутри панели. Панель — `components/kb/KbUsagePanel.tsx` (`ToolFrame variant='modal'`):
вкладки «Этот чат» / «По проекту», сводка с оговоркой, что токены БЗ — оценка
`chars/4`, таблица разделов (сортировка объявлена `aria-sort`, название раздела —
кнопка, а не клик по `<tr>`) и лента событий со статусом «запрашивает…».

Данные — только пропсами: снапшот просит стор (`loadKbUsage`,
`loadProjectKbUsage`), живые кадры принимает `applyKbUsageQuery` (upsert по id,
отсечка по `seq`). Успешная загрузка открытой панели отмечает `lastSeq` снапшота
через сервер; ошибка загрузки границу не меняет. Терминальные события при открытой
панели отмечаются сразу, а закрытое окно на новом кадре перечитывает серверный
снапшот, чтобы синхронизировать отметку между вкладками и устройствами. Для чатов до фичи и для desktop без моста `window.kb` отчёт
собирает чистая функция `lib/kbUsage.ts:buildKbUsageFromMessages` из
`meta.request.kbContext`; склейка отбрасывает ход, который сервер уже посчитал.
Ссылки ведут на `#/kb/:documentId`. Подробности — `features/kb-usage.md`.

Вне чата те же обращения показывает врез `components/kb/KbUsageBrief.tsx`: в
ленте рана (`RunFeed`) — по текущему рану, в модалке задачи (`TaskModal`) — по
всем её ранам. Это не панель: три числа, до восьми разделов ссылками
`#/kb/:documentId` и лозенг режима («БЗ выключена», «по запросу модели») —
пустота объясняется настройкой, а не поведением модели. Данные грузит сам
компонент через `lib/useRemoteReport.ts` (тот же хук грузит отчёт по расходу
модели в разделе «Отчёт» карточки; моста может не быть — desktop без CI;
ошибка показывается строкой и экран не роняет: статистика не важнее того, ради
чего экран открыли). Перечитывается по ключу: лента — на завершении рана,
модалка — на смене статуса последнего рана. В ленте панели чата обращение из
рана помечено «CI-ран» и по клику открывает ленту этого рана (`onOpenRun` →
`actions.openCiRun`). Режим базы знаний для ранов проекта задаётся селектором
«CI: база знаний в ране» в `ProjectSettings` — рядом пояснение, что на чаты
проекта он не влияет и применяется со следующего рана. Пока ран не терминален,
`RunFeed` сам делает секундный React-тик: длительность текущего шага и итоговая
длительность в шапке растут даже без новых строк лога; терминальные значения
берутся из сохранённых `durationMs` и больше не меняются. Проп `now` остаётся
точкой контроля времени для DOM-тестов.

Тем же способом устроен раздел «Отчёт» карточки задачи —
`components/ci/CiReport.tsx`: плитки итогов (стоимость, токены с разбивкой по
кэшу, число запросов к модели, время рана и работы модели), таблица шагов рана со
статусом, попыткой и длительностью (вложенные вызовы команд моделью — отступом,
как в `RunFeed`) и переключатель ранов с «Итогом по задаче», когда ранов больше
одного. Компонент чистый: данные приходят пропсами (грузит `useRemoteReport`
через `window.ci.getTaskReport`), своё состояние — только выбранный ран. Раздел
рендерится лишь у завершённого рана: пока ран идёт, цифры устаревают на глазах, и
смотреть надо ленту. Форматирование — `ci/ciFormat.ts` (`fmtDuration`, `fmtUsd`,
`fmtTokens`). Подробности — `features/ci-runner.md`.

Плитки отчёта договариваются о том, чего они НЕ знают, — иначе прочерк и ноль
читаются одинаково. У стоимости две разные подписи: «оценка по прайсу»
(`costEstimated` — CLI цену не сообщил, посчитал агрегатор) и «оценка по прайсу,
итог занижен: у части ходов модель неизвестна» (`costUnderstated` — прайса нет
вовсе). У токенов приписка «вход приведён к „без кэша“» (`inputNormalized`), когда
в сумме есть старые строки codex с другой семантикой входа. «Работа модели» при
нуле рисует прочерк (`fmtDuration(totals.modelActiveMs || null)`): ноль здесь
означает «CLI не сообщил длительность ни по одному ходу», а не «модель работала
0 мс». Строка «Инструменты: N вызовов, из них чтений M, правок K» с разбивкой
`bash/read/grep/edit/БЗ` рендерится только при `toolCalls !== null`; у ранов до
этой метрики её нет вовсе, и нули на её месте читались бы как поломка. Отказы
(`toolCalls.denied`) идут припиской «· отказов N» и только когда они были: отказ —
не вид инструмента, а исход вызова, сам вызов уже посчитан своим видом, поэтому в
«N вызовов» он не входит, а «отказов 0» читалось бы как ещё один инструмент. В
«Итоге по задаче» счётчик складывается `sumCiToolCalls` — раны без счётчика просто
не участвуют. Сториз на оба случая — `UnderstatedCost` и `NoToolCalls`.

## Модальные окна, popup и доступность

Модальное окно одно на всё приложение — `Dialog` из `@voicechat/ui-kit` (`packages/ui-kit/src/Dialog.tsx`; копия под удаление — `packages/ui/src/components/ui/Dialog.tsx`). Оно рендерится порталом в `document.body`, даёт оверлей и контейнер `role=dialog` `aria-modal=true` (имя — из заголовка через `aria-labelledby`, либо проп `ariaLabel`, если видимый заголовок длиннее нужного), ловушку фокуса по Tab/Shift+Tab, автофокус на первый элемент содержимого (не на крестик — иначе Enter сразу закрывает) или на `initialFocusRef`, возврат фокуса на кнопку-открывашку при закрытии, закрытие по Esc и по клику в фон (`closeOnOverlay`, для форм с несохранёнными данными — `false`), блокировку скролла `body` с компенсацией ширины полосы прокрутки, размеры `size` (`sm` 480 / `md` 640 / `lg` 1120 / `full`), слоты `title`/`actions`/`footer` и полный экран на телефоне. Своя логика закрытия (подтверждение несохранённого, как в `PromptBuilder`) — проп `onEscape`: его получают и Esc, и крестик, и клик по фону. Через `Dialog` работают `SettingsModal`, `TaskModal`, `MessageMeta`, `PromptBuilder`, `OnboardingModal`; своих оверлеев у них нет. Классы — `.vc-dialog-overlay` / `.vc-dialog` / `.vc-dialog--{sm,md,lg,full,phone}` (раньше это были пять разных наборов: `.modal`, `.jmodal-frame` на `.ccobs`, `.metamodal`, `.pb-overlay`/`.pb-dialog` и своя разметка онбординга). Класс окна (`.jmodal-frame`) задаёт только внутреннюю раскладку и, если надо, свои размеры — правила ниже `.vc-dialog--*` в файле.

`useDialogStack` (`packages/ui-kit/src/useDialogStack.ts`, экспортируется из `@voicechat/ui-kit` — им пользуется и продуктовый `ToolFrame`) — общий стек открытых окон: слой живёт, пока открыто окно, z-index выдаётся по глубине (`1200 + 10·depth`), Esc обрабатывает **только верхний** слой (из карточки задачи открывается AI-помощник — Esc закрывает помощника, карточка остаётся), скролл `body` разблокируется, когда снят последний слой. Слушатель Esc один на весь стек — иначе каждое окно глушило бы событие своим `stopPropagation`, и «кому достанется» зависело бы от порядка подписки. Перехват на `window` в фазе capture + `stopPropagation`: так не срабатывают глобальные хоткеи (`useHotkeys` слушает всплытие). Один видимый оверлей = один слой: `Dialog` и `PopupFrame` регистрируют его сами, `ToolFrame` — только для вариантов без оверлея (`page`, развёрнутая `embedded`-карточка), потому что его `modal` уже держит слой через `PopupFrame`. Верхний слой без обработчика Esc пропускает событие дальше — на этом живут встроенные карточки тулов.

Тема дублируется на `<html>` (эффект в `App.tsx`, то же в `.storybook/preview.tsx`): токены `[data-theme='dark']` объявлены на `.app`, а окна рендерятся вне `.app` и без этого остались бы светлыми.

Всплывающие панели инструментов — `ToolFrame` поверх `PopupFrame` (overlay `.ovl`, `role=dialog`, заголовок, разворот на весь экран). Не создавать отдельную реализацию ни окна, ни панели.

## Горячие клавиши, командная палитра и шпаргалка

Клавиши описаны **картой биндингов** — `lib/useHotkeys.ts` больше не знает жёстко про две клавиши. Биндинг — это `{ combo, onDown, onUp?, inInput?, ignoreModifiers?, enabled? }`; разбор комбинации, сверка с событием и подпись для показа человеку лежат в `lib/hotkeys.ts` (чистые функции, их читают и хук, и шпаргалка, и кнопка «⌘K» в сайдбаре). `mod` в комбинации — «команда платформы»: при сверке подходят и `metaKey`, и `ctrlKey`, при показе — `⌘` на macOS и `Ctrl` на остальных (`formatCombo`). Пробел и Esc сверяются по `event.code` (раскладка на них не влияет), буквы — по `event.key` (⌘K на русской раскладке даёт `key: 'k'`).

Правила, которые легко нарушить:

- **Клавиша без модификатора в поле ввода не перехватывается** (`isTyping()`), иначе в композере не набрать ни пробел, ни «?». Комбинации с модификатором перехватываются везде — у них проп `inInput: true`.
- **Пробел и Esc обязаны работать ровно как до карты**: у них `ignoreModifiers` (раньше проверялся только `e.code`, и случайно зажатый Ctrl push-to-talk не ломал), защита от автоповтора — и по `event.repeat`, и по «клавиша уже зажата», а `keyup` завершает **только** начатое нажатием (`held`), не смотрит ни на `enabled`, ни на фокус. Push-to-talk — критичный сценарий, регрессия недопустима; поведение прибито тестами `lib/useHotkeys.test.tsx`.
- **Общий флаг `enabled` гасит только голосовые клавиши** (пробел/Esc — например, при открытом модале настроек). У остальных биндингов свой `enabled()`, проверяемый в момент нажатия.
- **Во время записи голоса `⌘K` и `?` игнорируются** (`buildHotkeyBindings` в `lib/appCommands.ts`). Решение — «игнорировать», а не «сначала остановить запись»: молча оборвать реплику хуже, чем не открыть окно. Повторное `⌘K` палитру закрывает.

Реестр команд — `lib/commands.ts`, обычное замыкание без React (как стор; React подключается через `lib/useCommands.ts`). Источник — **функция**, а не готовый массив: команды замыкают пропсы и состояние стора, и массив устарел бы в момент регистрации. Экраны регистрируют свои команды сами через `useCommandSource` (канбан — «Создать задачу» в первой видимой колонке, лента CI-рана — «Повторить последний ран»), и регистрация живёт столько, сколько смонтирован экран: в палитре нет команд, которые сейчас некуда применить. Дубли по `id` склеиваются, побеждает зарегистрированный позже, — одна и та же лента рана бывает на странице дважды (модалка и шапка связанного чата). Базовый набор плюс пункты по данным (беседы, проекты, задачи открытой доски, машины) собирает `buildAppCommands` в `lib/appCommands.ts`, а `App` только передаёт ему состояние и колбэки.

`CommandPalette` (`⌘K` / `Ctrl+K`, кнопка «⌘K» рядом с поиском в сайдбаре) — поверх общего `Dialog`, поэтому портал, ловушка фокуса, Esc и возврат фокуса на открывашку достаются бесплатно. Разделы — «Действия», «Беседы», «Проекты», «Задачи», «Машины». Поиск нечёткий (`lib/fuzzy.ts`): подпоследовательность с весом за начало слова и за совпадение подряд, индексы совпавших букв идут в подсветку `mark.cmdk-hit`. Считается динамическим программированием, а не жадным проходом: жадный выбирает первое совпадение, и «кп» в «Командная палитра» подсветилось бы как «Ко…мандная». Сначала сверяется название (его и подсвечиваем), потом `keywords` и `hint` — так задача находится и по «#42», и по словам названия; ключ вида `GC-42` входит в само название, поэтому «42» тоже подсвечивается. Задачи берутся из открытой доски (других в памяти нет). Выдача **ограничена** `limitPerSection` (по умолчанию 8), под группой написано, сколько скрыто: виртуализация здесь лишняя — сотню строк без запроса показывать всё равно бессмысленно, а с запросом список сужается. «Недавние» (последние 5 `id` в `localStorage`, ключ `vc:commands:recent`) идут отдельной группой сверху при пустом запросе и не дублируются в своём разделе. Навигация ↑/↓ по кругу, `Home`/`End`, `Enter` — выполнить, мышь работает наравне (`onMouseMove` переносит выбор, чтобы `Enter` выполнил то, на что смотрит курсор).

`HotkeysCheatSheet` (`?` вне полей ввода) генерируется **из того же реестра**: команда объявляет `hotkey` — и сама появляется в шпаргалке. Второго списка «для документации» нет: он бы разъехался с настоящими биндингами. Выключенные команды тут показываются — шпаргалка это документация, а не список применимого сейчас (иначе «удерживайте пробел» пропадал бы ровно во время записи).

В Electron конфликта с меню приложения нет: `apps/desktop` не вызывает `Menu.setApplicationMenu` и не регистрирует `globalShortcut` — только меню трея, а в дефолтном меню Electron `⌘K` не занят.

Тесты: `lib/fuzzy.test.ts`, `lib/hotkeys.test.ts`, `lib/commands.test.ts`, `lib/appCommands.test.ts`, `lib/useHotkeys.test.tsx`, `components/CommandPalette.dom.test.tsx`, `components/HotkeysCheatSheet.dom.test.tsx`, `App.commands.dom.test.tsx` (клавиши в собранном приложении) плюс проверки реестра в `KanbanBoard.dom.test.tsx` и `RunFeed.dom.test.tsx`. Сториз — `CommandPalette.stories.tsx` (в том числе `HugeList` на 600 бесед) и `HotkeysCheatSheet.stories.tsx`.

## Библиотека универсальных примитивов @voicechat/ui-kit

`packages/ui-kit` — отдельный workspace-пакет `@voicechat/ui-kit` (`private`, `type: module`, версия 0.1.0). Он плоский: все примитивы лежат прямо в `src/`, без подкаталогов, единственный публичный вход — `src/index.ts`, единственный стиль — `src/styles.css`. Поле `exports` в `package.json` содержит ровно две записи (`"."` и `"./styles.css"`), поэтому внутренние пути потребителю не видны — импорт `@voicechat/ui-kit/src/Dialog` не разрешится. Из index экспортируются `Button`/`IconButton`, `Dialog` + `useDialogStack` (`DIALOG_Z_BASE`, `DIALOG_Z_STEP`, `dialogStackDepth`), `ConfirmDialog` + `ConfirmProvider`/`useConfirm`, `ToastProvider`/`useToast` (`TOAST_DURATION_MS`, `TOAST_VISIBLE_MAX`), `UiProviders`, `Skeleton`/`RefreshIndicator`, `EmptyState`, `ErrorState` и их типы. `mediaQuery.ts` (`MOBILE_QUERY`, `useMediaQuery`) переехал в пакет, но остаётся внутренним — в index его нет; у `packages/ui` свой `lib/mediaQuery.ts` с тем же содержимым.

Поведение примитивов перенос не менял: файлы совпадают с прежними побайтово, кроме относительного пути к `mediaQuery` в `Dialog.tsx`/`Toast.tsx` и вырезанного продуктового `SidebarToggle` (он остался в `packages/ui/src/components/ui/IconButton.tsx` вместе с локальным импортом старой `Button`). Поэтому варианты и `loading` кнопки, portal/focus trap/Escape `Dialog`, безопасный фокус и `requireText` у `ConfirmDialog`, очередь тостов и состояния loading/empty/error описаны в разделах ниже без оговорок «в новом пакете иначе».

**Старые копии на месте, и это не re-export.** `packages/ui/src/components/ui/*` не удалён: там лежат полные копии примитивов и их DOM-тесты, то есть каждый примитив сейчас существует в двух экземплярах и тестируется дважды. Живой код из старых копий тянет только `SidebarToggle` (`ProjectPage`, `ChatColumn`); все остальные потребители в `packages/ui` — экраны, `src/test/uiRender.tsx`, `src/test/a11y.dom.test.tsx`, `.storybook/preview.tsx` и все `components/ui/*.stories.tsx` — переключены на `import { … } from '@voicechat/ui-kit'`. Новый код обязан импортировать из пакета; старые файлы — временный хвост под удаление, а не источник истины.

Стили тоже задублированы. `src/styles.css` пакета самодостаточен: токены `:root` и `[data-theme='dark']`, базовая типографика, `.vc-btn*`, `.vc-dialog*`/`.mdhead`/`.mdh`, `.vc-confirm*`, `.vc-toast*`, `.vc-skel*`/`.vc-refresh*`, `.vc-state*`, общие focus/disabled/loading и `prefers-reduced-motion`. Он подключён строкой `@import '@voicechat/ui-kit/styles.css'` в начале `packages/ui/src/styles/global.css`, но те же правила и токены по-прежнему живут в `packages/ui/src/styles/app.css`, который грузится после, — значит вид приложения (web, Electron renderer, Web Recorder) определяет всё ещё `app.css`, и правку боевого стиля примитива надо делать там же, иначе она не проявится. Продуктовые стили (layout, Sidebar, ChatColumn, канбан, CI, машины, KB, администрирование) из `app.css` не выносились вовсе.

Границу пакета сторожит `packages/ui-kit/src/architecture.test.ts` — обычный vitest-тест, а не отдельный механизм: он читает исходники `src` (кроме каталога `test` и `*.test.*`) и падает на подстроках `@voicechat/ui`, `apps/`, `voiceStore`/`useVoiceStore`, `remote/`, `window.api|ci|fs|files|agents|pty|audio|stt|tts|claude|codex|kb`, `new WebSocket`/`EventSource(`/`from 'electron`, `ChatAI/`, `bridge|transport|http`, а вторым тестом сверяет, что `exports` в `package.json` остался ровно из двух записей. Отсюда практическое следствие: продуктовое слово в комментарии или имени переменной внутри `src` роняет тест так же, как настоящий импорт.

Свои гейты у пакета собственные: `npm run -w @voicechat/ui-kit typecheck` (`tsc --noEmit`, строгий, сториз исключены) и `npm run -w @voicechat/ui-kit test` (vitest, jsdom, `src/test/setup.ts` с полифилами matchMedia/PointerEvent — 8 файлов, 49 тестов, ~18 с). Корневые `npm run typecheck`/`npm run test` подхватывают пакет автоматически через `--workspaces`. А вот `scripts/affected-check.mjs` про `packages/ui-kit` не знает: пути пакета не совпадают ни с одной записью `PACKAGES`, поэтому любой файл из него распознаётся как «нераспознанный критичный путь» и включает **полный** гейт по всем пакетам. Проверка не теряется, но точечного прогона у ui-kit нет — при добавлении пакета в карту это нужно учесть.

Разрешение имени `@voicechat/ui-kit` — обычный симлинк npm-workspaces в `node_modules/@voicechat/`. Он создаётся установкой, а не переключением ветки: после `git checkout` без `npm install` `npm run -w @voicechat/ui typecheck` падает `TS2307: Cannot find module '@voicechat/ui-kit'` (первым — на `src/test/uiRender.tsx`). Запись в `package-lock.json` и зависимость `"@voicechat/ui-kit": "*"` в `packages/ui/package.json` уже есть; отдельных правок vite-конфигов `apps/web`, Electron renderer и Web Recorder перенос не потребовал — Vite транспилирует исходники пакета как обычный workspace-исходник.

Новый примитив добавляют так: файл в `packages/ui-kit/src`, явный экспорт в `src/index.ts`, стили — в `src/styles.css` на семантических токенах (и, пока копии не удалены, зеркально в `app.css`), DOM-тест рядом. Story живёт в общей витрине `packages/ui` (`src/components/ui/*.stories.tsx`) и обязана импортировать компонент через публичный `@voicechat/ui-kit` — отдельного Storybook у пакета нет и пока не планируется. Инвентаризация, снятая перед переносом (зависимости, CSS-классы, тесты и сториз по каждому элементу), — `packages/ui-kit/docs/inventory.md`.

## Пакет @voicechat/projects-app: контракты, store и маршруты

`packages/projects-app` — второй выделенный workspace-пакет (`private`, `type: module`, 0.1.0), устроенный по образцу ui-kit: `exports` ровно из двух записей (`"."` → `src/index.ts` и `"./styles.css"`), поэтому глубокий импорт `@voicechat/projects-app/src/store/projectsStore` не разрешается. Внутри — подкаталоги `kanban/` (нормализация и fixtures доски), `routes/`, `store/`, файл контрактов `contracts.ts` и компонент-оболочка `ProjectsApp.tsx`. Из index наружу отдаются `ProjectsApp`, `ProjectsProvider`/`useProjectsStore`/`useProjectsActions`/`useProjectsNavigation`, `createProjectsStore`, `parseProjectsRoute`/`buildProjectsRoute`/`projectRouteId`, `normalizeBoard`/`normalizeColumn`/`normalizeTask`, fixtures `make*`/`noopHandlers` и типы (`ProjectsClient`, `ProjectsHost`, `ProjectsChatPort`, `ProjectsRoute`, `ProjectsState`, `ProjectsNavigationModel` и входные типы мутаций). Зависимости объявлены на `@voicechat/shared`, `@voicechat/ui-kit` и React, но ui-kit пока не импортируется ни одним файлом пакета — своих экранов в нём ещё нет.

**Что уже перенесено, а что нет.** Реально переехали только чистые части канбана: `normalize.ts` вместе со своим тестом и `fixtures.ts`; в `packages/ui/src/components/kanban/` от них остались однострочные реэкспорты из публичного входа пакета, так что Storybook и компоненты `packages/ui` продолжают импортировать прежние пути. Всё остальное — `ProjectsApp`, `ProjectsProvider`, `createProjectsStore`, `styles.css` (в нём один блок `:where(.projects-app)`) — потребителей не имеет: экраны проектов живут в `packages/ui` и работают на доменном `projectsStore` из `packages/ui/src/store/domains`. Из host-а в приложении задействован единственный вызов `parseProjectsRoute` в `App.tsx` (подробности проектной маршрутизации — [projects.md](projects.md#фронтенд)).

`contracts.ts` описывает первый срез транспорта, а не весь раздел: `ProjectsClient` покрывает список/чтение/создание/обновление/удаление проектов, доску и подписку на неё, CRUD колонок и задач, `moveTask`, `reorderColumns` и получение чата задачи (`ensureTaskChat`/`openTaskChat`). Методов CI, QA, подготовки, merge, releases и ассистента в интерфейсе ещё нет — они добавляются вместе с переносом соответствующих панелей. `ProjectsHost` даёт модулю `navigate`, `chat: ProjectsChatPort` (открыть разговор, отрендерить встроенный чат, необязательно — создать проектный разговор) и необязательный рендер тумблера сайдбара; `ProjectsNavigationModel` — тот самый маленький read model для Sidebar.

Адаптер к существующим мостам — `packages/ui/src/projects/createProjectsClient.ts` (экспортируется из `packages/ui/src/index.ts`): он принимает `RendererApi` и необязательный `RendererBoardBridge` и раскладывает контракт по прежним IPC-ключам, ничего не переписывая на сервере. Две неровности стоят упоминания: `updateColumn` разбирается на два вызова (`columns:setHidden` для видимости и `columns:rename` для имени и WIP-лимита), а `ensureTaskChat` и `openTaskChat` сегодня одинаково дергают `tasks:openChat` — идемпотентность по-прежнему обеспечивает сервер. Без переданного board-моста `subscribeBoard` возвращает пустую отписку, то есть в Electron живой синхронизации так же нет, как и раньше.

`createProjectsStore(client)` — замыкание без React с `getState`/`subscribe`/`actions`/`navigation`. Гонки закрывает один счётчик `request`: его инкрементят `loadProjects`, `openProject`, `reloadBoard`, `closeProject` и `dispose`, и ответ применяется, только если токен всё ещё текущий, а `activeProjectId` не сменился, — поэтому опоздавший ответ прошлого проекта молча отбрасывается. `openProject` сначала снимает старую board-подписку и обнуляет detail/board/openTaskId, затем параллельно тянет проект и доску и подписывается заново; `null` из `getProject` превращается в ошибку `Project not found`. Подписка фильтрует чужие события по `event.projectId`, `closeProject` и `dispose` её снимают (dispose ещё и чистит слушателей и запрещает дальнейшие `set`), `setIncludeCompleted` пересоздаёт подписку и перечитывает доску.

Оптимистичность реализована так: `moveTask` пересчитывает `position` как середину между соседями целевой колонки (перемещаемая задача переносится в конец массива `tasks` — порядок в массиве не значим, значим `position`), `reorderColumns` раскладывает переданный порядок в `position = index * 1024`. Ошибка сервера в обоих случаях идёт в общий `rollbackOrReload`: сначала в состояние возвращается снапшот доски и текст ошибки, потом безусловно вызывается `reloadBoard` — то есть после неудачи гарантированно происходит второе обращение `getBoard` и сверка с сервером. `updateTask` не оптимистичен: он ждёт ответ и подменяет задачу в доске. Всё это проверяется `store/projectsStore.test.ts` на фейковом `ProjectsClient` (загрузка и снятие подписки, отбрасывание устаревшего ответа, оптимистичный move плюс игнор события чужого проекта, rollback с повторным `getBoard`).

React-адаптер — `store/ProjectsProvider.tsx`: контекст со store, `useProjectsStore(selector?)` поверх `useSyncExternalStore` (подписка идёт на весь state, селектор лишь выбирает срез, мемоизации нет), `useProjectsActions` и `useProjectsNavigation({ createProject, navigate })`; все три бросают понятную ошибку вне провайдера. `ProjectsApp` — тонкая оболочка с render-пропом: держит `div.projects-app`, синхронизирует маршрут в store, догружает список проектов и открывает/закрывает проект по `projectRouteId(route)`. `routes/projectsRoute.ts` — чистый parser/builder: понимает и `#/…`, и `/…`, декодирует сегменты, возвращает `null` на любом лишнем сегменте, а `{ kind: 'index' }` — для `#/projects`; round-trip всех семи адресов плюс отказы проверяет `routes/projectsRoute.test.ts`.

Границу сторожит `src/architecture.test.ts` (тем же приёмом, что и в ui-kit): он обходит `src` кроме каталога `test` и `*.test.*`/`*.stories.*` и падает на `@voicechat/ui`, `voiceStore`/`useVoiceStore`, `apps/web|desktop`, `window.`/`window[`, `fetch(`, `new WebSocket`, `ipcRenderer`, `from 'electron`, а вторым тестом сверяет, что `exports` остался из двух записей. Запрет на `@voicechat/ui` здесь ещё и защита от цикла: обратная зависимость `"@voicechat/projects-app": "*"` уже прописана в `packages/ui/package.json`. Гейты пакета свои — `npm run -w @voicechat/projects-app typecheck` (строгий `tsc`, сториз исключены, алиас `@shared/*` на исходники shared) и `npm run -w @voicechat/projects-app test` (vitest, jsdom, `src/test/setup.ts` с полифилами matchMedia/PointerEvent; сейчас четыре тестовых файла). Корневые `npm run typecheck`/`test` берут пакет через `--workspaces`, а `scripts/affected-check.mjs` про него, как и про ui-kit, не знает — его пути считаются нераспознанными и включают полный гейт. Имя разрешается симлинком npm-workspaces, поэтому после переключения ветки без `npm install` `packages/ui` падает на `TS2307: Cannot find module '@voicechat/projects-app'`.

## Кнопки

Кнопка одна на всё приложение — `Button` из `@voicechat/ui-kit` (`packages/ui-kit/src/Button.tsx`): `variant` (`primary` | `secondary` | `ghost` | `danger`), `size` (`sm` | `md`), `loading`, `fullWidth`, `iconLeft`/`iconRight`, `forwardRef`, `type="button"` по умолчанию (кнопка внутри формы не отправляет её неожиданно). `loading` рисует спиннер вместо `iconLeft`, ставит `aria-busy` и блокирует кнопку — это и защита от двойной отправки; так работают «Сохранить» в настройках разговора, «Выбрать» в пикере директории и палочка генерации в `PromptBuilder`. Кнопка без видимой подписи — `IconButton` рядом: в её типах `aria-label` и `title` **обязательные** (сборка падает без них), потому что одного `aria-label` мало — браузер его не показывает.

До этого в `app.css` жило около тридцати независимых `*btn`-классов (`.newbtn`, `.delbtn`, `.msgbtn`, `.ci-btn`, `.mst-btn`, `.footbtn`, `.vdl`, `.login-submit`, `.qsubmit`, `.ob-start`, `.modeldl`…). Следствия были ровно те, которых ждёшь: «Удалить» и «Отмена» выглядели по-разному на канбане, в CI-панели и в настройках; четыре «основные» кнопки были четырёх разных синих (`var(--accent)`, `#3d64c8`, `#5068d8`, `#2f3b5c`); `.btn-primary` вообще не имел базового правила и рисовался дефолтом браузера; часть классов не была переопределена под тёмную тему; фокус-кольцо для клавиатуры было не у всех.

Стили — один блок `.vc-btn` + модификаторы, целиком на токенах, поэтому тёмная тема достаётся без отдельных правил, а `:focus-visible`-кольцо есть у каждого варианта. Для кнопок добавлены токены `--accent-fg`, `--danger`, `--danger-fg`, `--surface-hover`, `--accent-soft` — в `:root` **и** в `[data-theme='dark']`; в тёмной теме акцент и красный светлые, поэтому подпись на них тёмная (`--accent-fg: #191916`), иначе кнопка «выцветает». Геометрию и оттенок под конкретное место дают модификаторы рядом (`.vc-btn--circle` — круглые кнопки композера 48/44px, `.vc-btn--danger-quiet` — крестик «удалить», который краснеет только под курсором) и контекст (`.mfoot .vc-btn--ghost` приглушает мелкие действия под сообщением, `.util-head-btns .vc-btn--icon` увеличивает глиф в шапке окна). Новых `*btn`-классов не заводим. Иконки композера (`MicIcon`, `SendIcon`, `StopIcon`, `WandIcon`) рисуются `currentColor` — цвет приходит от варианта кнопки; раньше белый глиф был вбит в SVG и в тёмной теме пропадал.

Матрица «вариант × размер × состояние (обычная / hover / focus-visible / disabled / loading)» сразу в двух темах — `Button.stories.tsx`. Состояния под курсором и фокусом показаны классами-крючками `.is-hover`/`.is-focus`: в `app.css` они стоят в тех же правилах, что и сами псевдоклассы, поэтому матрица не может разойтись с боевым видом.

Формы должны иметь связанные label, ошибки — видимый текст. Мобильная версия поддерживает выдвижной sidebar и полноэкранные popup.

## Состояния загрузки, пустоты и ошибки

Три примитива в `components/ui`: `Skeleton` (+ `RefreshIndicator`), `EmptyState`, `ErrorState`. До них каждый экран показывал ожидание и пустоту по-своему: `.pb-skeletons` со своим градиентом и `@keyframes pb-shine` в `PromptBuilder`, `.msgloading` с точками в чате, `.skelline` в поиске по сообщениям, «Загрузка доски…» простым текстом на канбане, серые «Нет машин»/«Пусто» в проводнике и консоли, а `.pb-empty` был единственным оформленным пустым экраном. Ошибка чтения в большинстве мест не показывалась вообще: список оставался пустым, и пользователь не мог отличить «пусто» от «сломалось» — промах уходил только тостом, а тост живёт секунды.

**Правило переходов одно и живёт в коде**: `loadView(status, hasData)` (`lib/loadState.ts`) превращает пару «состояние запроса + есть ли данные» в то, что рисует экран — `skeleton | empty | error | data` плюс флаги `refreshing` и `staleError`. Ключевые следствия: скелетон показывается **только пока данных нет** (в том числе на `idle`, потому что запрос уходит в эффекте и «Пусто» на один кадр было бы неправдой); при повторной загрузке уже показанного списка контент не подменяется — рядом появляется неблокирующий `RefreshIndicator`; ошибка при показанных данных не стирает их, а ложится баннером `ErrorState compact` сверху. Чистая функция покрыта `lib/loadState.test.ts`.

`Skeleton` — варианты `line` (ширина), `block` (высота), `card` (рамка + строки внутри), `list` (`count` элементов, `itemClassName`). **Геометрия обязана совпадать с контентом**: высота карточки задачи (70px, класс `.jcard-skel` — та же тень и радиус, что у `.jcard`), высота `.convo` в сайдбаре (76px), ряда таблицы, свёрнутого шага CI-ленты (34px), строки проводника (30px). Разошлись высоты — при подстановке данных дёргается вся раскладка. Анимация — бегущий блик на токенах `--skeleton-base`/`--skeleton-shine` (в `:root` и в тёмной теме, поэтому отдельного правила для тёмной нет — у `.pb-skeletons` градиент был вбит светлым `#ddd`) и целиком отключается медиазапросом `prefers-reduced-motion: reduce` вместе со спиннером индикатора. Сами косточки `aria-hidden`, а «занятость» области экран помечает `aria-busy`.

`EmptyState` — иконка, заголовок, пояснение, необязательное действие. **Текст объясняет следующий шаг**: «Пока нет бесед — начните первую» + кнопка «Новый разговор», «Колонок пока нет — создайте первую» («колонка — это статус задачи»), «Команд пока нет — создайте первую», «Здесь пока пусто» в колонке канбана («перетащите карточку или создайте задачу»), «Нет машин — добавьте первую». Формулировка «нет данных» не говорит, что делать, и не отличима от поломки.

`ErrorState` — короткое сообщение, техническая деталь под `<details>Подробнее</details>` (её нужно уметь скопировать, но не показывать первой) и «Повторить»; контейнер `role="alert"`. Повтор дают чтению и идемпотентной правке — то же правило, что у `fail(err, retry)`. Тост никуда не делся: он для момента, `ErrorState` — для экрана, который иначе выглядит пустым.

Где применено: список бесед и поиск по сообщениям в `Sidebar`, история сообщений в `ChatColumn` (скелетон реплик той же геометрии, что у `.msg`), `KanbanBoard`/`ProjectBoard` (скелетон доски из колонок и карточек, пустая доска, пустая колонка, ошибка с «Повторить»), `FileExplorer`, `KnowledgeBase`, `ci/RunFeed` и `CiCommands`, `UsersAdmin`, `MachineStatus`, `MachineConsole` (там же «Повторить» перезапускает саму команду), `PromptBuilder`. Состояние загрузки лежит в сторе рядом с данными — `conversationsStatus`/`conversationsError`, `adminUsersStatus`, `ciStatus`, `agentsStatus`, `boardError`, `loading`/`error` в `ciRuns[runId]` — и приходит на экран пропсом: компоненты по-прежнему ничего не грузят сами. `refreshAgents` перестал глотать ошибку в `console.warn` — иначе меню «Машины» выглядело как «машин нет».

Тёмный терминал консоли машины (`.consout` — почти чёрный в обеих темах) перекрашивает состояния под свою палитру: без этого в светлой теме текст был бы чёрным на чёрном.

Сториз: `UI/Skeleton` (варианты + сравнение геометрии с настоящей карточкой), `UI/EmptyState`, `UI/ErrorState`, а также по три состояния экрана у `Kanban/KanbanBoard` (`Loading`, `EmptyBoard`, `ErrorState`, плюс `Refreshing` и `ErrorWithBoard`) и `CI/RunFeed` (`Loading`, `Empty`, `LoadError`, плюс `WithSteps` и `StaleError`).

## Подтверждения и уведомления

Нативных `window.confirm`/`alert` в интерфейсе нет: они не знают про тему, блокируют поток, в Electron выглядят чужим окном ОС и в тестах только мокаются. Вместо них два примитива в `components/ui`.

**Подтверждение** — `ConfirmDialog` поверх `Dialog` (`size="sm"`): заголовок-вопрос, пояснение, `confirmLabel`, `variant: 'danger' | 'default'`. Автофокус — на безопасном элементе: кнопке «Отмена», а в режиме `requireText` — на поле ввода (Enter сразу после открытия ничего не удаляет). `requireText` включает подтверждение только после того, как набрано название объекта (сверка без регистра и краевых пробелов) — так закрыты необратимые операции: удаление колонки со всеми задачами и откат незакоммиченных файлов в CI. По месту подтверждение читается как обычный вопрос — хук `useConfirm()` отдаёт промис:

```ts
if (!(await confirm({ title: 'Удалить «Задача A»?', variant: 'danger', confirmLabel: 'Удалить' }))) return
```

Окно рисует `ConfirmProvider` (один на приложение): вопрос приходит с любой глубины дерева, а слой и Esc достаются ему сами — стек `useDialogStack` общий, поэтому подтверждение из карточки задачи или AI-помощника встаёт поверх них.

**Тосты** — `ToastProvider` + `useToast()` (`toast.success/error/info(text, { action, duration })`). Стек в правом нижнем углу, на телефоне — во всю ширину снизу, но **над композером**: высоту `.voicebar` компонент меряет сам (`avoidSelector`, `App` передаёт `.voicebar`), поэтому на страницах-утилитах, где композера нет, тосты прижаты к низу. Успех и факт закрываются через 4 с, ошибка — только крестиком (её нужно успеть прочитать и скопировать); наведение мышью останавливает отсчёт, иначе тост с кнопкой «Повторить» исчезает из-под курсора. Видно не больше трёх, остальные ждут очереди. Контейнер — живая область `aria-live="polite"`, смонтированная всегда (иначе скринридер не заметит появления текста) и не перехватывающая клики (`pointer-events: none`); ошибка повышает себя до `role="alert"` + `aria-live="assertive"`. Крестик подписан `aria-label` и `title`, Esc внутри тоста закрывает его (обработчик локальный, чтобы не перебивать Esc окон).

**Канал ошибок.** Промах вызова моста больше не тонет: домен кладёт его в очередь `notices` оболочки (хелпер `fail(err, retry?)` в `shellStore`), `App` показывает тостом и снимает из очереди. Кнопка «Повторить» появляется, если задан `retry` — только у чтения и идемпотентной правки (загрузка доски, проектов, CI-рана, `update*`/`set*`); создание, удаление и запуск рана повтора не получают, иначе после «упало, но применилось» получится дубль. Баннер `error` оболочки остался за голосом, ходом модели и загрузками — он живёт в колонке чата, а ошибки страниц проектов, CI и машин туда не видны. Успех показываем там, где результата не видно: «Скопировано», «Настройки сохранены», «Команда удалена».

В тестах подтверждение кликается, а не мокается: экраны рендерятся через `render` из `src/test/uiRender.tsx` (обёртка `UiProviders`), полное приложение свои провайдеры ставит само.

Слои по z-index (чтобы панели не перекрывали друг друга): `.side-backdrop` 50 < выдвижной sidebar `.side` 60 < панели тулов (`.ovl`, `.util-embed--fs`) 70 < `.convsettings` 90 < `.ci-console` 1000 < окна `Dialog` 1200 и выше (глубина стека) < тосты `.vc-toasts` 2000 (ошибка относится и к тому, что сделали в окне, иначе она оказывалась под ним). Плюс любой переход по маршруту закрывает выдвижной sidebar (эффект в `App.tsx` по `path` из `useHashRoute`) — иначе забытая открытой панель висит поверх страницы.

Полноэкранный режим на телефоне: у окон `Dialog` его включает сам компонент по `useMediaQuery(MOBILE_QUERY)` (720px) — класс `.vc-dialog--phone`; у модальных тулов `ToolFrame` (`.ccobs`) — медиазапрос `max-width: 768px`. Высота в обоих случаях `100dvh`, потому что `88vh` уезжает под адресную строку браузера. Кнопка «на весь экран» у тулов там скрыта.

Merge живёт в отдельной вкладке «Merge» карточки (`components/ci/MergePanel.tsx`): блок запуска с селектором машины (пустое значение — серверный дефолт, машина workspace; офлайн-машины задизейблены), живая лента `MergeRunFeed` (WS `merge.snapshot` + fallback-опрос каждые 3 с), история попыток задачи (`listMergeRuns`, клик открывает ленту выбранной) и таблица копий репозиториев по машинам с бейджами типа/состояния (удалённые — за переключателем). Лента оформлена как CI-ран: статус-бейдж (`merge-badge--ok|err|warn|run`), SHA-чипы, вертикальный степпер стадий (`merge-step`), плашка ошибки с рекомендацией и конфликтами, лог и вывод проверок — терминальные `details`-блоки (`merge-terminal`), свёрнутые у завершённого рана. Из ленты доступны retry, отмена, «Мержить текущий head ветки» (retry с `unpin` при stale) и «Выпустить на прод» после успеха. Терминальный исход merge-рана стор показывает тостом (подписка на `merge.snapshot` в `createVoiceStore`, дедуп по ран+статус). Кнопка в `jmodal-main` заменена подсказкой о вкладке; выбранный `agentId` идёт через `onStartMerge(taskId, agentId)` → `startMergeRun` стора. Стили — блок `.merge-*` в `styles/app.css`; сториз состояний — `MergePanel.stories.tsx` (попадают в общий axe-прогон). Серверная сторона — `features/merge-runner.md`.

Карточка задачи (`TaskModal`) на телефоне повторяет мобильную Jira: статус и исполнитель строкой под заголовком, остальные поля — в свёрнутой секции «Подробности», действия шапки (чат, флаг, удаление) — в ⋯-меню, CI-блок и настройки воркфлоу остаются видимыми. Это разная разметка, а не только стили, поэтому ширина проверяется хуком `useMediaQuery(MOBILE_QUERY)` (`lib/mediaQuery.ts`); граница 720px дублируется в `app.css` — правится вместе. В тестах `matchMedia` по умолчанию «десктопный» (шим в `src/test/setup.ts`), мобильные кейсы подставляют свой.

Авторастущие textarea используют `useAutoGrow`: высота берётся из `scrollHeight`, ограничивается 2–4 строками, затем включается scroll. Это учитывает как переносы, так и явные переводы строк.

## Выбор начала разработки

Отправка из композера всегда вызывает `submitText`: UI не выводит намерение разработки из текста пользователя. Только корректный структурированный `taskLaunch` в завершённом ответе создаёт предложение; обычный или некорректный текст ничего не открывает. `App.tsx` обрабатывает предложение только на маршруте активного чата и, если чат привязан к проекту, сразу открывает стандартную `TaskModal` в режиме несохранённого редактируемого черновика с названием, подробным описанием и критериями приёмки. Промежуточной таблицы или окна выбора нет.

При открытии предложение получает персистентный статус `opened` в метаданных сообщения. Поэтому закрытие карточки ничего не создаёт и тот же блок не открывается повторно после перезагрузки; несколько предложений открываются по очереди. У карточки три исхода: «Создать в TODO» создаёт задачу в колонке с `semanticType === 'backlog'`, «Создать в InProgress» использует `createTaskAndStartCi`, а «Работать в текущем чате» не создаёт задачу. После каждого успешного выбора UI отправляет модели отдельный следующий ход с выбранным вариантом. Исполнитель по умолчанию — имя текущего пользователя, навыки — проектные навыки по умолчанию для task, а provider и model берутся из пользовательских `settings` (`llmProvider` и соответствующая Claude/Codex-модель), а не из настроек открытого чата.

## Remote-слой

`remote/session.ts` хранит bearer token в localStorage. `httpApi.ts` добавляет Authorization, декодирует ошибки и очищает сессию при 401. `wsClient.ts` строит ws/wss URL, передаёт токен, переподключается и восстанавливает подписки. `decode.ts` проверяет JSON/бинарные события до передачи в callbacks.

`remote/index.ts` устанавливает все `window.*` мосты и связывает события сокета со store callbacks. Установка должна произойти до монтирования `App`, иначе store увидит отсутствующие мосты.

`VITE_SERVER_URL` задаёт отдельный backend. Пустая строка означает same-origin; Vite dev проксирует API/WS, production server раздаёт web build. URL нормализуется без завершающего `/`.

## Тестирование UI

Логика store тестируется прямыми действиями с подставленными мостами и детерминированными таймерами. DOM-тесты используют `src/test/fakeApi.ts`; проверяют цепочку «действие пользователя → вызов bridge → новое состояние экрана». Аудио/VAD/TTS тестируются как отдельные чистые модули.

Фейковый мост держит те же инварианты, что сервер, иначе баг в тесте не
воспроизводится: `conversations:taskContext` в `fakeApi.ts` больше не заглушка
`null`, а честная сборка контекста по `conv.taskId` (ключ — общей shared-функцией
`issueKey`, `run: null`), и с `conversationId` запрошенного чата. Из-за этого
DOM-тест умеет открыть чат задачи по адресу и проверить, что виджет исчезает
после «+ Новый» (`App.projects.dom.test.tsx`), а подмена `conversationId` на чужой
чат воспроизводит гонку с опоздавшим ответом.

Тот же принцип держит и структуру доски: `createProject` в `fakeApi.ts` засевает
канонический системный workflow целиком — `backlog`, `preparation`, `ready`,
`development`, `component_qa`, `integration_tests`, `automated_qa`, `manual_qa`,
`awaiting_merge`, `merge`, `done` и замыкающую `decision_required`, — без legacy
`testing`/`qa_preparation`, как это делает серверный шаблон нового проекта.
Storybook-фикстура `makeDefaultColumns()` (`components/kanban/fixtures.ts`) даёт
тот же набор с id вида `col-<semanticType>`, поэтому сториз канбана адресуют

Проверки store сравнивают `semanticType`, а не подписи колонок
(`appRuntime.projects.test.ts`): имя пользователь переименовывает, машинный смысл
— нет; созданная пользователем колонка получает семантику `custom` и встаёт после

## AI-помощник формулировки

Переиспользуемые `PromptBuilder` и `useAiAssist` живут в `packages/ui/src/components/prompt-builder/` и экспортируются из `@voicechat/ui`. Компонент транспорт-нейтрален: генератор, модификаторы, применение и персистентность приходят через props. ## Веб-рекордер

Правая панель ChatAI имеет продуктовое имя «Веб-рекордер», но теперь это iframe-host `WebReaderHost` в `packages/ui/src/App.tsx`, который открывает самостоятельное приложение по `/web-recorder/`. ChatAI хранит URL разговора как override и берёт URL проекта как fallback; рекордер получает это значение от host-а. Сам рекордер открывает сайт только в same-origin iframe `GET /api/preview?url=…`, а не внешний URL напрямую, и при вводе принимает лишь `http`/`https`.

Маршрут принимает только HTTP/HTTPS и расположен в `apps/server/src/routes/previewProxy.ts`; авторизация iframe — через preview-cookie, а не Bearer (`Authorization` в запрос iframe не попадает), детали — в разделе «Сплит чата с веб-превью» выше. Перед каждым запросом и непосредственно в DNS lookup он проверяет все resolved IP: loopback, unspecified, private, link-local, multicast/reserved и IPv6 ULA запрещены. Кастомный lookup обязан соблюдать форму, которую запросил HTTP-клиент Node: при `options.all === true` возвращается весь массив `LookupAddress`, иначе — один адрес. Раньше lookup всегда передавал callback одиночный адрес, даже когда Node запросил массив; это приводило к `ERR_INVALID_IP_ADDRESS` и доступные сайты превращались в `preview_unavailable`. Теперь `publicLookupResult` сначала отвергает весь DNS-ответ, если пуст хотя бы один результат или среди адресов есть непубличный, и только затем возвращает массив либо первый адрес в требуемой форме. То же ограничение применяется к каждому из максимум пяти redirect.

Для доступного внешнего сайта прокси сохраняет исходный HTTP-статус и возвращает тело через `/api/preview`; HTML/CSS преобразуется: относительные ссылки, ресурсы, формы, `srcset` и `url()` в `<style>`/inline `style=""` переписываются обратно через прокси. Тело POST принимается с любым content-type сырым (JSON, form-urlencoded, multipart), поэтому и submit формы, и `fetch`/XHR/`sendBeacon` страницы — их вместе с History-навигацией переписывает context shim — не покидают SSRF-границу; детали в [server-internals.md](server-internals.md#прокси-веб-превью). Ответ ограничен 10 секундами и 5 MiB. Ошибки загрузки остаются структурированными: `{ error: 'preview_unavailable', message }`; известные ограничения дают своё понятное сообщение, а прочие сбои — «Сайт недоступен».

Внешние cookies не выдаются браузеру: `Set-Cookie` остаётся в серверном контексте, разделённом по пользователю, и возвращается исходному сайту только после проверки domain/path/secure/expiry. Поэтому внешний сайт не может прочитать `vc_preview_session` или токены ChatAI. Перед исполняемыми ресурсами HTML получает context shim: `localStorage` и `sessionStorage` получают префикс внешнего origin, а `indexedDB.open`/`deleteDatabase` — префикс имени базы. Так состояния двух сайтов не смешиваются при едином origin прокси, обычный reload сохраняет localStorage/IndexedDB, а sessionStorage живёт в браузерной сессии.

В каждый HTML-ответ прокси перед закрывающим `body` (или в конец документа, если тега нет) инъецирует автономный инспектор из `apps/server/src/routes/previewProxy.ts`. Режим включается кнопкой-тумблером в тулбаре или `Alt+I`, выключается повторным переключением либо `Esc`; родитель передаёт состояние сообщением `voicechat.preview.inspector.v1`. При наведении скрипт рисует не перехватывающий события overlay с именем элемента и его размерами. Клик в capture-фазе блокирует штатное действие страницы, фиксирует элемент и отправляет `voicechat.preview.element-selected.v1`; выключение и `pagehide` снимают capture-обработчики и удаляют overlay.

Протокол и runtime-валидатор находятся в `packages/shared/src/previewInspector.ts`. Инспектор принимает команды только от `parent` с тем же origin, а UI принимает результат только с origin приложения и от `contentWindow` собственного iframe, после чего проверяет всю структуру через `isPreviewElementMessage`. Payload содержит уникализируемый CSS selector, цепочку предков, tag/id/classes/data-атрибуты, геометрию и viewport, URL страницы, HTML и текст элемента и ограниченный срез computed styles; `outerHTML` ограничен 8000 символами, текст — 2000, массивы и набор data-атрибутов — 64 элементами. Выбранный элемент показывается под iframe как имя, размеры и selector.

### Независимый Веб-рекордер и контракт хоста

Веб-рекордер собирается и запускается отдельно как workspace `@voicechat/web-recorder` (`apps/web-recorder`, Vite, порт dev `5274`). Его entry `src/main.tsx` монтирует собственный `Recorder`, а состояние открытого URL, записи и редактирования сценария остаётся внутри этого приложения. Для общих токенов и классов рекордер подключает `@voicechat/ui/app.css`; компоненты и store ChatAI он не импортирует.

ChatAI показывает только iframe-host `WebReaderHost` в `packages/ui/src/App.tsx`; адрес standalone build — `/web-recorder/`. Единственный публичный контракт интеграции — `packages/shared/src/webRecorder.ts`: envelopes `voicechat.web-recorder.v1` `set-url`, `run-action` от хоста и `ready`, `page-status`, `save-url`, `element`, `action-result` от рекордера. `page-status` несёт состояние внутреннего iframe (`empty`, `loading`, `ready`, `error`), URL и проверенную ошибку загрузки. URL сохраняет ChatAI, выбранный элемент и результат DOM-действия возвращаются host-у, поэтому ChatAI не импортирует внутренние компоненты или состояние рекордера.

Production-сборка Vite задаёт `base: '/web-recorder/'`, поэтому ссылки из `apps/web-recorder/dist/index.html` ведут в `/web-recorder/assets/`. Docker build отдельно выполняет build workspaces `@voicechat/web` и `@voicechat/web-recorder`; runtime передаёт Fastify каталоги через `VC_WEB_DIR` и `VC_WEB_RECORDER_DIR`. Сервер сначала регистрирует recorder static-root с prefix `/web-recorder/`, затем корень ChatAI; основной SPA-fallback исключает весь recorder prefix. Поэтому `/web-recorder/` и его assets не могут получить `index.html` ChatAI, а отсутствующий recorder asset отвечает 404. Оба frontend-приложения остаются на одном origin и используют общие `/api/*`, `/ws` и `/api/preview` без отдельного backend или контейнера.

### Действия модели в превью (mcp__browser__*)

Ход разговора получает MCP-сервер `browser` (эндпоинт `/mcp/preview`, `apps/server/src/mcp/previewMcp.ts`) с инструментами `open`, `read`, `find`, `click`, `type`: открыть URL в панели превью, прочитать структурированное содержимое страницы (заголовки/ссылки/кнопки/поля + текстовая выжимка), найти элементы по видимому тексту или CSS-селектору, кликнуть, ввести текст (`submit: true` отправляет форму). Протокол, лимиты и валидаторы — `packages/shared/src/previewActions.ts`; хинт модели — `previewToolHint()` (подключают `apps/llm-runner/src/cli/claudeCli.ts` и `codexCli.ts` вместе с `LlmRequest.previewMcpUrl`).

Сервер действий не исполняет: `PreviewActionRelay` транслирует вызов кадром WS `preview.action` всем клиентам пользователя и ждёт `preview.result` — первый успех, все отказы или таймаут 20 с. Токен `?turn=` выдаёт и снимает `turns.ts` (брокер `previewToolBroker`), как у инструментов БЗ. Действия ограничены активной страницей пользователя: обрабатывает их только клиент, у которого совпали `conversationId`, активный чат, зарегистрированный для этого же разговора `WebReaderHost` и маршрут Web Reader или Playwright Reader (`AppBody` в `packages/ui/src/App.tsx`, мост `window.preview` из `packages/ui/src/remote/index.ts`); остальные вкладки сразу отвечают отказом, поэтому команды и ответы параллельных чатов не смешиваются. `open` сначала сохраняет URL именно этого разговора, переводит host в `loading` и завершается только после `ready` внутренней страницы. Инъецированный `previewProxy.ts`-скрипт сообщает `voicechat.preview.page-ready.v1` после установки DOM-моста и `voicechat.preview.page-loading.v1` на `beforeunload`; recorder переводит это в `page-status`. DOM-команды, пришедшие сразу после `open` или перехода по клику, host держит в очереди до `ready`, затем посылает рекордеру как `run-action`; рекордер пересылает их своему iframe как `voicechat.preview.action.v1` и возвращает `action-result` с тем же `requestId`. Каждое клиентское ожидание имеет 10-секундный таймер; результат, ошибка загрузки, закрытие панели и тайм-аут очищают запись и таймер. Диагностика различает: неоткрытую/неактивную панель; страницу, которая не стала готова за время команды; сетевую/DNS/HTTP-ошибку прокси или страницу без инъецированного моста; молчащий клиентский мост при формально открытой панели. Серверный relay отдельно ограничивает ожидание 20 секундами, удаляет pending-запрос и сообщает именно об отсутствии ответа клиентского моста. Поиск по тексту выбирает глубочайшее совпадение и поднимается до кликабельного предка, `type` ставит значение нативным сеттером с событиями `input`/`change`, `read` не отдаёт значения парольных полей, ссылки возвращаются без прокси-обёртки `/api/preview`.

Проверок в `AppBody` теперь две, и их формулировки различимы: чужой или не-Reader-маршрут получает «Этот чат сейчас не открыт на странице Reader — панель превью недоступна», а открытый Reader без подключённой панели того же разговора — «Панель превью активного чата не открыта или ещё не подключена». Вторая проверка сравнивает `conversationId` с тем, что сохранён в `previewRunnerRef` вместе с runner-ом: `registerPreviewRunner` записывает пару `{ conversationId: state.activeId, runner }`, а на снятие регистрации обнуляет ссылку только если она принадлежит текущему чату, — иначе размонтирование старого host-а стирало бы регистрацию уже переключённого чата. Тексты самого host-а («Панель Web Reader не открыта или ещё не подключена», «Панель открыта, но в ней нет страницы — сначала вызови open») приходят на шаг позже и означают уже другое: панель найдена, но не готова.

Править цепочку нужно в `WebReaderHost`: это единственная панель, которая монтируется на маршрутах `#/web-reader` и `#/playwright-reader` и регистрирует исполнителя через `onRegisterActionRunner`. Старая `PreviewPane` (алиас-экспорт `WebPreview`) в приложении больше не рендерится — она осталась экспортом ради DOM-тестов и сториз вместе со своим отдельным исполнителем действий и своими текстами ошибок («В панели превью нет загруженной страницы», «Страница превью не ответила»). Поиск по тексту ошибки поэтому легко уводит в неиспользуемый код; в живом пути формулировки другие, они перечислены в `WebReaderHost` и в `PreviewActionRelay`.

У рекордера есть собственный гейт готовности (`apps/web-recorder/src/Recorder.tsx`): `run-action`, пришедшая до `page-ready`, сразу получает отказ «Страница ещё загружается» — очередь держит только host, рекордер команды не буферизует. `set-url` сбрасывает флаг готовности и немедленно отвечает `page-status` (`loading` для адреса, `empty` для `null`). Ошибку загрузки рекордер определяет по `onLoad` внутреннего iframe без пришедшего ready: он читает same-origin `contentDocument` и, если тело — структурированный ответ прокси `{ error: 'preview_unavailable', message }`, отдаёт host-у именно `message`; иначе сообщает, что сайт вернул страницу без инъецированного моста (HTML без внедрённого скрипта). `onError` iframe даёт отдельную сетевую ошибку. Так host различает недоступный сайт и молчащий мост, не смешивая их с таймаутом.

Готовность страницы приходит от инъецированного скрипта синхронно при его выполнении в конце `<body>` (не по `window.load`) и до того, как скрипт ставит свой `message`-обработчик; доставка `postMessage` асинхронна, поэтому обработчик успевает встать раньше первой команды host-а. При переходе старый документ шлёт `page-loading` на `beforeunload` и снимает обработчики на `pagehide`, новый — свой `page-ready`, поэтому `read` после клика с навигацией ждёт готовности новой страницы, а не отвечает от умершего документа. Край, который стоит помнить: повторный `open` того же адреса не меняет prop `url`, host не шлёт `set-url`, iframe не перезагружается и нового `ready` не будет — вызов завершится 10-секундным таймаутом «страница всё ещё загружается». Регресс-покрытие цепочки — `packages/ui/src/WebPreview.dom.test.tsx`, блок `WebReaderHost action lifecycle`: open→read с ожиданием готовности, find→click и read после навигации, ошибка сайта и очистка ожиданий при размонтировании панели.

### Запись и повторный запуск сценария

`Recorder` в самостоятельном приложении включает запись сообщением `voicechat.preview.record.v1`; инъецированный скрипт iframe в capture-фазе отправляет клики по кликабельной цели и события `input` для `input`, `textarea`, `select` и contenteditable. Рекордер принимает сообщения только с origin приложения и от `contentWindow` собственного iframe, добавляет шаги с CSS-селектором к локальному редактируемому списку. Для пароля, autocomplete current/new-password и полей, чьи `name`/`id` похожи на секрет, токен, карту или CVV, значение не передаётся: шаг помечается `sensitive`, отображается маской и не воспроизводится автоматически.

Кнопка «Запустить» последовательно посылает каждый несекретный шаг через `voicechat.preview.action.v1`, то есть использует тот же DOM-исполнитель, что и MCP-действия модели. Селекторы и значения обычных полей можно править до запуска. URL, запись и сценарий живут только в состоянии рекордера; ChatAI их не импортирует и не хранит, кроме URL превью разговора, который сохраняется через сообщение `save-url`.

## Граница `@voicechat/operations-app`

Новый workspace `packages/operations-app` задаёт публичную границу Operations: экспортирует React-независимую фабрику store, transport-agnostic clients и межмодульные порты, безопасный каталог машин, маршруты, navigation model, React context/hooks и стили. Подробная карта экспортов, state ownership и текущей степени подключения находится в [operations-app.md](operations-app.md).

На этом срезе host подключил только `parseOperationsRoute` и stylesheet в `packages/ui/src/App.tsx`; существующие продуктовые реализации Machines, terminal/explorer, EnginesObserver, KB и CI остаются в `packages/ui`. Экспорты из `surfaces.tsx` — простые секционные оболочки с заголовком и `children`, а Storybook stories показывают текстовые состояния. Поэтому пакет уже является архитектурной точкой интеграции, но ещё не заменяет старые host-компоненты полноценными Operations surfaces.

## Граница `@voicechat/admin-app`

`packages/admin-app` — workspace `@voicechat/admin-app` с публичным корнем и `./styles.css`. В пакет перенесены `UsersAdmin`, React-независимая фабрика `createAdminStore`, transport-agnostic `AdminClient`, Session/Operations ports и parser/builder маршрутов `#/users`. Host подключает экран лениво через `import('@voicechat/admin-app')`, проверяет роль до открытия и использует только публичные экспорты. Стили импортируют `@voicechat/ui-kit/styles.css`, имеют собственную светлую/тёмную token-based раскладку и mobile breakpoint, не зависят от полного `app.css`.
