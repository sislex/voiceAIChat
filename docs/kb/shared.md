# Общий пакет: типы, контракты и чистая логика

`packages/shared` — единственный источник истины для данных, которыми обмениваются UI, сервер, desktop и компаньон-агент. Пакет не имеет runtime-зависимостей, не обращается к DOM, сети, файловой системе или процессам и экспортирует исходный TypeScript через `src/index.ts`. Изменение публичного поведения начинается здесь, затем реализуется на обеих сторонах транспорта.

`llm.ts` — контракт LLM: `LlmRequest`/`LlmClient` (их собирает сервер) плюс
протокол исполнителя v1: тело `LlmRunBody`, кадры `LlmRunFrame`,
`parseLlmRunFrame`, `LlmRunnerHealth`, пути `LLM_RUNNER`. Он здесь именно потому,
что берегов два: промпт собирает сервер, argv по нему — `apps/llm-runner`. Рядом
`kbToolHint` в `kb.ts` — системный хинт про `mcp__kb__*` попадает в argv CLI.

## Базовая модель данных

`Conversation` хранит серверные настройки конкретного чата: цель выполнения (`execTarget`), рабочий каталог, выбранные skills, LLM provider/model, permission mode, режим KB, проект и lifecycle-статус. Настройки чата намеренно отделены от глобального `Settings`: изменение одного разговора не меняет другие. Для веб-превью `previewUrl` — override разговора, а `projectPreviewUrl` — проектный fallback в том же снапшоте; override имеет приоритет. `ProjectSummary.previewUrl` хранит проектный адрес по умолчанию. Вид разговора типизирован: `assistantKind` — это `AssistantKind | null` (`web-recorder`, `playwright-reader`, `kanban`), а не свободная строка. Рядом в `types.ts` лежат контракты браузерной сессии Playwright Reader (`Browser*`) и три чистые функции для кадров и координат — описаны в [features/playwright-reader.md](features/playwright-reader.md), пока их использует только `apps/browser-runner`.

`Message` содержит текст, роль, время, движок, метаданные хода и фактическую цель выполнения реплики. Последнее важно для истории: будущая смена машины разговора не переписывает сведения о том, где исполнялась старая команда.

`Settings` описывает пользовательские настройки голоса, микрофона, Whisper, TTS, hands-free/VAD, поведения интерфейса и TTL временных managed-генераций. `generatedFilesTtlDays` задаётся целым числом 1–3650, а `DEFAULT_SETTINGS` устанавливает 30 дней; сервер валидирует и сохраняет значение на пользователя, UI использует тот же общий контракт.

Роль пользователя ограничивает доступные LLM. `isModelAllowed` проверяет выбор, `clampModelForRole` приводит сохранённую или запрошенную модель к разрешённой. Проверять нужно и UI, и сервер: скрытая кнопка не является границей безопасности.

## REST и WebSocket

Все пути берутся из объекта `REST`, строки вручную не дублируются. Динамические функции пути применяют `encodeURIComponent` там, где идентификатор может содержать пользовательский ввод. Типы request/response лежат рядом с доменом, а не в реализации fetch.

`ClientMessage` и `ServerMessage` — discriminated unions с полем `t`. `CLIENT_MESSAGE_TYPES` и `SERVER_MESSAGE_TYPES` являются runtime-перечнями и проверяются contract-тестами: новый вариант union обязан попасть и в соответствующий список. `preparation.run.updated` — лёгкая адресная инвалидация REST-истории подготовки с обязательными `projectId`, `taskId` и `runId`; полную запись рана WS не дублирует.

Аудио микрофона передаётся бинарными PCM16-кадрами; управляющие события — JSON. TTS может использовать бинарный кадр с заголовком. Кодирование/декодирование должно оставаться симметричным между `protocol.ts`, серверным `ws.ts` и `packages/ui/src/remote/decode.ts`.

Ходы LLM адресованы `conversationId`. `ActiveTurn` переносит partial text, activity и usage при reconnect, поэтому клиент не должен считать WebSocket владельцем генерации.

## Мосты UI

`ipc.ts` определяет фасады `RendererApi`, `RendererAudioBridge`, `RendererSttBridge`, `RendererClaudeBridge`, `RendererTtsBridge`, `RendererCcBridge`, `RendererCodexBridge`, `RendererAgentsBridge`, `RendererBoardBridge`, `RendererSessionBridge`, `RendererFsBridge` и `RendererPtyBridge`. Они публикуются в глобальном `Window` через `packages/ui/src/global.d.ts`. Web-реализация `RendererBoardBridge` также даёт `onPreparationRunUpdated` и `onReconnect`; последний не срабатывает на первом успешном соединении.

Имена методов исторически похожи на Electron IPC (`conversation:list`, `claude:send`), но это логические команды, не обязательный транспорт. Web реализует их через HTTP/WS, desktop устанавливает те же remote-мосты в renderer. Компонент не должен вызывать `fetch`, `WebSocket` или `ipcRenderer` напрямую.

## Протокол компаньон-агента

Сервер отправляет агенту exec/fs/pty-команды с корреляционными идентификаторами. Агент отвечает чанками stdout/stderr, итогом, результатом файловой операции или PTY-событием. `AgentRegistry` сопоставляет ответы ожидающим Promise/слушателям.

`AgentPolicy` содержит режим и allow/deny-правила. `evaluateAgentCommand` — чистый общий policy gate для однострочного exec. Живой PTY считается отдельно доверенным интерактивным shell и не пропускает каждую строку через этот evaluator.

`AGENT_VERSION` — версия распространяемого bundle. `TOOL_MIN_VERSION` связывает возможность с минимальной версией агента. При добавлении capability меняются оба значения, иначе сервер может послать старому клиенту неизвестное сообщение.

## Чистые конвейеры

Голосовой автомат принимает событие и возвращает новое состояние/эффекты; он не запускает микрофон или плеер сам. Side effects исполняет UI-store. Это сохраняет тестируемость переходов `idle → listening → transcribing → thinking → speaking` и прерывания озвучки новой речью.

Числа отчётов считают чистые функции, а не SQL и не компонент: итоги расхода
CI-рана (`ciUsageTotals`, `sumCiUsageTotals`, `ciTaskTotals` в `ci.ts`) складывают
токены, запросы и время работы модели одинаково на сервере и в UI, а стоимость
берут от CLI либо оценивают по `pricing.ts` и помечают итог приблизительным.
Оценка живёт только в агрегаторе: в БД её не хранят, иначе смена цен переписала
бы историю задним числом. Тесты на такие функции идут на числах, без моков.

Прайс в `pricing.ts` — не «публичные ориентиры по памяти», а подгонка под факт. Он намеренно остаётся отдельным от SQLite `model_prices`: shared-пакет не имеет доступа к БД, и этой чистой таблицей по-прежнему считают CI-раны и импортированные CLI-сессии; админская правка влияет только на chat usageReport (`costFromPrices`).
Opus и fable сверены с `total_cost_usd`, который CLI назвал на реальных ходах
(строки `ci_run_usage` с непустой `cost_usd`): opus — 5/25/0.5/10, fable —
10/50/1/20 USD за 1M токенов вход/выход/чтение кэша/запись кэша. Запись кэша
взята по ЧАСОВОМУ TTL (2× вход): развести TTL по счётчикам нельзя, CLI отдаёт
один `cache_creation_input_tokens` без разбивки `ephemeral_5m`/`ephemeral_1h`, —
а пятиминутный тариф с фактом не сходится. Строки sonnet, haiku и GPT
непроверенные, и об этом прямо написано в файле: ходов с настоящей ценой по ним
нет (codex своей цены не сообщает вовсе). Тест `pricing.test.ts` сверяет расчёт с
фактической ценой конкретных ходов, допуск 2% — сдвинется прайс, покраснеет он.
До 02.08.2026 таблица давала opus 15/75/1.5/18.75 и завышала его втрое; заметить
это было неоткуда, потому что у claude в отчёт идёт настоящая цена, а вся оценка
достаётся codex, — поэтому сверка теперь печатается в отчёте замера.

Там же сводятся семантики, которые у движков разные: `ciUsageInputTokens`
приводит вход строки к «без кэша» (исторические строки codex несут его вместе с
прочитанным кэшем), а `classifyCiToolCall` сводит имена инструментов
(`mcp__remote__read` у claude, `remote:read` у codex, `Read` у встроенного) к
одному виду — иначе разбивку вызовов по движкам нельзя сравнивать. Пометки итога
различают «оценка по прайсу» (`costEstimated`) и «прайса нет вовсе, сумма занижена»
(`costUnderstated`): второе — не то же самое, и молчаливого нуля быть не должно.

Stream-парсеры принимают строки событий CLI и нормализуют различия Claude/Codex. Необработанные события могут идти в диагностический лог, но пользовательский текст и usage должны извлекаться только распознанными ветками.

Промпт собирается централизованно. Здесь добавляются история, speaker labels, пути вложений, контекст проекта/KB и инструкции для `tool/questions/image`. Служебные fenced-блоки затем вырезаются из произносимого текста, чтобы TTS не читал JSON.

### Запрос запуска разработки

Перед изменением проекта `CHANGE_AUTHORIZATION_HINT` в `prompt.ts` предписывает модели спросить разрешение через завершающий fenced-блок `task-launch`. Чистый `parseTaskLaunchRequest` принимает только валидный JSON с непустыми `title`, `description` и `acceptanceCriteria`, отделяет его от текста ответа и возвращает одиночный `TaskLaunchRequest` либо несколько `TaskLaunchProposal` со стабильными в пределах ответа идентификаторами. Обычные слова о задаче не являются сигналом. `task-launch` входит в `SERVICE_FENCES`, поэтому служебный JSON не озвучивается.

Непустота каждого текстового поля проверяется через `trim()`, но возвращаемое значение не обрезается. Поэтому `title`, `description` и `acceptanceCriteria` переходят из JSON дословно, включая крайние переводы строк, Markdown-отступы, списки, заголовки, кавычки и блоки кода; источник поведения и регрессия находятся в `packages/shared/src/prompt.ts` и `packages/shared/src/prompt.test.ts`.

Одиночный `TaskLaunchRequest` хранится в `TurnMeta.taskLaunch`, несколько предложений — в `TurnMeta.taskLaunches`: сервер добавляет их в merged meta до сохранения AI-сообщения. `claude.done` доставляет обычные `meta` и `message`, без отдельного поля предложения в `ServerMessage`, `IpcEventMap` или remote-мосте. Поэтому карточки восстанавливаются из истории вместе с сообщением, а UI связывает действие создания с конкретным предложением, а не с общим или последним состоянием сообщения.

## Правило изменения контракта

1. Добавить или изменить тип в тематическом shared-модуле.
2. Обновить runtime-список типов сообщений, если меняется WS.
3. Добавить unit/contract-тест без моков.
4. Реализовать серверную сторону и remote bridge.
5. Обновить fake API UI и поведенческий тест компонента/стора.
6. Для agent-протокола обновить версию и проверить старый агент.

Гейт: `npm run -w @voicechat/shared typecheck && npm run -w @voicechat/shared test`.
