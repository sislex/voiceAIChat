# Словарь терминов

Короткие определения слов, которые встречаются в задачах, планах, журналах и
переписке с оператором. Подробности — в темах, на которые стоят ссылки.
Английский термин в скобках — тот, что встречается в коде и журналах.

## Роли и участники

- **Владелец (owner)** — человек, хозяин аккаунта и проектов Sislexa. Ставит задачи,
  принимает решения о продукте, может сливать PR в `main` и при необходимости выполнять
  команды на проде. Владелец делегировал оператору выпуск и деплой.
- **Оператор (operator)** — Claude в сессии с токеном оператора Delivery Control. Ведёт
  прогоны: пишет планы, настраивает задачи, принимает результаты с доказательствами,
  выпускает пакеты, закрепляет версии, деплоит прод. Не воркер и не модель внутри задачи.
  См. [Delivery Control](#delivery-control-прогоны-задач) и [конвенции](conventions.md).
- **Координатор (coordinator)** — серверная часть Delivery Control на отдельном хосте
  (доступен через туннель `127.0.0.1:18798`). Хранит прогоны, задачи и попытки, раздаёт
  попытки воркерам, собирает события и артефакты, синхронизирует задачи на доски Kanban,
  раз в несколько часов или по команде переносит `dev → main`.
- **Воркер (worker)** — процесс Delivery Control на машине разработки (MacBook, M1).
  Берёт попытку задачи: готовит изолированный чекаут, запускает модель с описанием задачи,
  прогоняет гейт задачи и отдаёт патч координатору. На машине несколько слотов (`w0…wN`).
- **Интегратор (integrator)** — особый воркер, который вливает принятые патчи в ветку `dev`
  репозитория, прогоняя гейт задачи на свежей голове ветки. Отдельные слоты
  (`…-integrator-w0…`).
- **Авторемонт окружения (environment repair, задачи `ENV-…`)** — задача, которую
  координатор заводит сам, если гейт упал по причине, похожей на проблему окружения.
  Часто шум; пока она висит, повтор исходной задачи заблокирован.
- **Агент (agent, `sislexa-agent`)** — программа на машине пользователя. Держит WebSocket
  к ядру и выполняет по его команде: shell-команды (`exec`), файловые операции, терминал
  (PTY), TCP-туннели, запуск dev-процессов стендов. Без агента машина «не в сети».
  См. [машины](machines.md).
- **Машина (machine)** — зарегистрированный агент с хранилищем (`~/ChatAI` по умолчанию),
  подключённый к проектам. У машины есть `path` (рабочая копия проекта) и `reposRoot`
  (каталог репозиториев).
- **Ассистент / модель** — LLM, которая ведёт ход (turn) в беседе: Claude или GPT через
  LLM Runner. Инструменты модели — MCP (`mcp__make__*`, `mcp__remote__bash` и т. п.).
- **Пользователь, участник проекта, admin, developer** — роли учётной записи и членство в
  проекте; от них зависят права на запись в репозиторий, машины и стенды.
  См. [auth/data](data-auth.md).

## Сервисы и репозитории

- **Sislexa** — продукт в целом. **Ядро (Core, `sislex/voiceAIChat`)** — Fastify-сервер,
  база данных, авторизация, беседы, оркестрация остальных сервисов.
  См. [архитектуру](architecture.md).
- **Core UI (`sislexa-core-ui`)** — веб-интерфейс ядра; ядро раздаёт его из закреплённого
  пакета. **Desktop** — настольное приложение со встроенным рендерером и агентом.
- **Make (`sislex/make`)** — приложение «веб-проект с ассистентом»: мастерская файлов,
  превью, редактор, инструменты ассистента. **Панель Make (make-ui)** — его интерфейс,
  который ядро встраивает в Core UI.
- **Kanban (`sislexa-kanban`)** — проекты, доски и задачи, машины проекта, окружения и
  стенды разработки. Ядро проксирует `/api/projects/*` в Kanban.
- **Identity** (учётные записи и сессии), **Billing**, **Analytics**, **LLM Runner**
  (запуск моделей), **Web Reader** и **Playwright Reader** (чтение сайтов), **Image Studio**
  (картинки), **Voice** (STT/TTS) — отдельные сервисы со своими репозиториями.
- **Shared (`@voicechat/shared`)** — пакет контрактов: типы REST/WS, реестры сообщений,
  реестр компонентов стендов. Меняется первым, потом сервер и потребители.
  **Контракты (`*-contracts`)** — такие же пакеты у Make, Reader, Image Studio и др.
- **Delivery Control (`sislexa-delivery-control`)** — система прогонов задач: координатор,
  воркеры, интегратор, CLI `control.mjs`.
- **Компонент (component)** — приложение из каталога (`APPLICATION_CATALOG`), у которого
  есть версия, образ или фронтенд-артефакт и зависимости. **Component runtime** —
  токены и гранты, по которым компоненты ходят друг к другу.

## Окружения и стенды разработки

- **Окружение (environment)** — развёрнутый экземпляр системы проекта. **Production** —
  внешнее окружение прода, настройками которого управляет оператор. **Managed** — compose-
  окружение, которое Kanban разворачивает на машине. **Базовое окружение (base
  environment, `dev-base-m2`)** — managed-окружение из копии прод-базы, поверх которого
  живут стенды. См. [деплой](deploy.md#managed-stands).
- **Стенд разработки (dev stand)** — базовое окружение плюс манифест: для каждого
  компонента точный SHA и источник (`base` | `dev` | `live`). Компонент можно подменить
  сборкой из ветки/SHA (**override**) или запустить из рабочей копии (**живой режим,
  live**) — тогда правки видны сразу благодаря горячему обновлению.
- **Шлюз стенда (stand gateway, порт 23000)** — процесс на машине стенда, который по
  префиксам маршрутов отправляет запросы либо к подменённому компоненту, либо в базовое
  окружение. Адреса стенда — LAN и Tailscale.
- **Прокси доступа к стенду (`VC_STAND_PROXY_PORTS`, 8790–8794 на проде)** — ядро прода
  выдаёт участнику проекта порт на том же хосте и пробрасывает запросы к шлюзу стенда
  через туннель агента. Так стенд открывается внутри превью Make с cookie-сессией.
- **`dev:component`** — команда репозитория, запускающая компонент в режиме разработки
  (Vite с HMR, `tsx watch`). **Dev build id** — `<версия>-dev.<sha12>`, такие сборки не
  попадают в выпуски.
- **Рабочая копия (working copy, worktree)** — каталог с исходниками на машине. Git
  worktree — дополнительная рабочая копия того же репозитория на своей ветке. **Рабочая
  копия беседы Make** — worktree `<reposRoot>/make-worktrees/<conversationId>` проекта-
  хозяина стенда на ветке `make/<slug>-<id>`.
- **Мастерская (workshop)** — файлы беседы Make на сервере (`<dataDir>/make/<conversationId>`),
  их показывает превью, когда стенд не подключён.
- **Горячее обновление (HMR, hot module replacement)** — Vite подменяет изменённый модуль
  или стиль в открытой странице без перезагрузки.

## Выпуск и доставка

- **Ветки**: `main` — проверенная; `dev` — «непроверенный main», куда интегратор вливает
  задачи; `release/0.1.N` — ветка выпуска ядра; `make/<slug>` — ветки бесед Make.
  **Перенос (promotion) `dev → main`** — по расписанию или по команде, с полным гейтом.
- **Гейты (gates)** — наборы проверок с кодом выхода. `gate:task` — только изменённый
  модуль, бюджет 100 тестов / 60 с; `gate:quick` — typecheck и затронутые тесты;
  `gate` / `gate:all` — полный набор, включая браузерные; `gate:release` — плюс
  производительность и системные проверки владельцев; `kb:check` — свежесть базы знаний.
  См. [testing](testing-operations.md).
- **Регрессия релиза (release regression)** — `gate:release` на MacBook перед деплоем
  ветки выпуска. **Release Center** — экран проекта «Релизы» в Core UI: собрать релиз,
  задеплоить, откатить. **Деплой (deploy)** — выкат релиза на прод `89.125.68.35`.
- **Выпуск (release) пакета** — публикация архива и образа в GitHub Releases / GHCR из
  чистого клона (`owner-release-publish`). **Релизный поезд (release train)** — скрипт,
  который делает выпуск и закрепление по цепочке приложений.
- **Вендор (vendor)** — не человек, а каталог `vendor/` в репозитории ядра: в нём лежат
  копии архивов (`*.tgz`) сторонних для ядра пакетов — Core UI, Make, контрактов, агента,
  Desktop и других. Слово от английского *vendor* («поставщик»): «вендорить» значит
  положить чужой пакет внутрь своего репозитория, чтобы сборка не зависела от npm и
  сети. Имя файла несёт версию и начало sha256 (`sislexa-make-1.4.6-f9a821d8da13.tgz`),
  а `vendor/owner-artifacts.json` — происхождение каждого архива. В `package.json` такие
  зависимости записаны как `file:../../vendor/<архив>`.
- **Закрепление (pin, «пин»)** — фиксация точной версии зависимости или образа, чтобы
  сборка и деплой всегда брали одно и то же. Для пакетов: положить архив в `vendor/`,
  прописать его в `package.json` (`file:…`), `package-lock.json`,
  `dependency-snapshots.json` и `vendor/owner-artifacts.json`. Для сервисов-образов
  (Kanban, Make, Reader): записать версию и коммит в `deploy/tools.lock.json` и тег образа
  в `docker-compose.yml`. Делает `release-composition apply --dir <каталог с выпусками>`;
  контракты закрепляет `contracts-release.mjs`. Без закрепления новый выпуск пакета в
  ядро не попадёт: ядро собирается только из того, что закреплено. Противоположность —
  плавающая версия (`^1.4.0`, `latest`), которой в ядре не бывает.
- **Владельческие артефакты (owner artifacts)** — архивы и образы, собранные владельцем, а
  не CI; у каждого есть происхождение (репозиторий, коммит, sha256).
- **Compose, overlay** — `docker-compose.yml` и дополнительные файлы (`deploy/compose.*.yml`,
  `/etc/voicechat/*.yml`), перечисленные в `COMPOSE_FILE` прода; **профиль** включает
  группу сервисов. **Образ (image)** — собранный контейнер с тегом по коммиту.

## Delivery Control: прогоны задач

- **План (plan)** — файл `docs/plans/<run>.md` с решениями, общим контрактом и таблицей
  задач `| B01 | Репозиторий | Зависимости | Описание |`. Копия плана кладётся в
  репозиторий задачи — воркер видит только свой репозиторий и описание.
- **Прогон (run)** — импортированный план с идентификатором (`make-stand-v1`).
  **Этап (stage)** — группа задач без зависимостей друг от друга (`B*` — этап 0, `C*` —
  этап 1). **Задача (task)** — единица работы для одного репозитория. **Попытка
  (attempt)** — один запуск модели по задаче на воркере; до трёх попыток.
- **Патч попытки (`changes.patch`)** — результат работы модели; его вливает интегратор или
  вручную оператор. **Артефакты** — отчёт попытки, патч, журналы.
- **Приёмка с доказательствами (owner-reduced evidence)** — оператор прогоняет гейт на
  коммите слияния, кладёт журнал и JSON в `docs/evidence/` Delivery Control и
  подтверждает задачу и этап (`sislexa-owner-accept`, `sislexa-stage-accept`).
- **Журнал (journal)** — файл с записью каждой операторской команды к координатору;
  повторить команду с тем же журналом нельзя. **Inbox** — очередь команд для машины,
  которая недоступна по ssh (M1).
- **Настройка задачи (configure)** — базовый SHA, разрешённые пути, команды подготовки
  (`npm ci`) и гейта, ресурсы.

## База знаний

- **База знаний (KB, `docs/kb`)** — темы с описанием поведения; у каждой темы есть `areas`
  — пути, за которыми следит проверка свежести. **Touch** — отметить тему сверенной,
  **log** — запись журнала изменений, **index** — пересобрать `README.md`.
  См. [kb-workflow](kb-workflow.md).

## Техника

- **Куча (heap)** — память процесса Node.js (движок V8) под объекты JavaScript. У кучи
  есть потолок: по умолчанию ~половина лимита памяти контейнера, задаётся
  `--max-old-space-size`. «Heap out of memory» — объекты не помещаются в потолок, процесс
  падает и перезапускается. **Сборка мусора (GC, Mark-Compact)** — V8 освобождает
  недостижимые объекты; строки «Last few GCs» в журнале показывают, что сборка уже не
  помогает. **Снимок кучи (heap snapshot)** — файл со всеми объектами на момент снимка,
  по нему ищут, что именно занимало память.
- **RSS** — вся память процесса, включая кучу, буферы и код. **Утечка памяти** — рост,
  который не возвращается после сборки мусора; **всплеск** — временный рост под нагрузкой.
- **Обратное давление (backpressure)** — получатель читает медленнее, чем отправитель
  пишет; без ограничения данные копятся в памяти отправителя. `writableLength`, верхняя и
  нижняя «ватерлинии» (high/low-water mark) — как ядро ограничивает буфер.
- **NDJSON** — построчный JSON в потоке (`exec-stream`). **SSE** — поток событий сервера.
  **WebSocket** — двусторонний канал (агент ↔ ядро, HMR). **PTY** — терминал внутри агента.
  **Туннель (tunnel)** — TCP-проброс через агента на порт его машины.
- **Сессия и CSRF** — сессия живёт в HttpOnly-cookie `vc_session`; мутации должны нести
  заголовок `x-vc-csrf`, равный читаемой cookie `vc_csrf` (double-submit). **Origin** —
  схема+хост+порт страницы; чужой origin ядро отклоняет (`origin_denied`).
- **SHA / коммит** — идентификатор состояния репозитория; **detached HEAD** — рабочая копия
  на коммите без ветки; **bare mirror** — репозиторий без рабочей копии для быстрых
  клонов; **cherry-pick** — перенос одного коммита в другую ветку; **PR** — pull request.
- **Коды ошибок сети**: `ECONNREFUSED` — на порту никто не слушает; `ECONNRESET` —
  соединение оборвала другая сторона; `EADDRINUSE` — порт уже занят (частая причина
  падений тестов с фиксированными портами на одной машине).
- **OOM** — out of memory, нехватка памяти; `mem_limit` — лимит памяти контейнера.
- **Vite** — dev-сервер и сборщик фронтенда; **tsx watch** — запуск TypeScript с
  перезапуском при изменениях; **Storybook** — витрина компонентов интерфейса.
- **MCP** — протокол инструментов модели; **ход (turn)** — один запрос к модели с её
  действиями; **хинт** — системная подсказка модели.
