# dev-lane-v1 — быстрый контур разработки: ветка dev, гейт задачи и стенды разработки на M1/M2

Ран `dev-lane-v1`. Запускается после `kb-service-v1`.

Сейчас от слияния задачи до ручной проверки проходит 40–90 минут: подготовка рабочей копии воркера
(`npm ci` с нуля, около 5 минут), быстрый гейт 5–15 минут и его повтор оператором (песочница воркера не
даёт гейту вызывать `git`), цепочка архивов и закреплений (shared → Core → Core UI/Kanban → Desktop), полный
гейт при правке корневых файлов и регрессия релиза 20–40 минут на M1. Пример 2026-10-05: исправление ввода
чата прошло 6 PR и 3 выпуска до проверки на проде.

## Решение владельца (2026-10-05)

1. Задачи сливаются в ветку `dev` («непротестированный main») каждого репозитория. Перевод `dev → main` —
   по расписанию и по команде, с полным гейтом, архивами, закреплениями и релизом.
2. Гейт задачи — только изменённый модуль: проверка типов и связанные тесты, не более 1000 тестов и не
   более 300 секунд (5 минут; решение владельца 2026-10-07, было 60 секунд), без браузерных и системных
   наборов других модулей.
3. Запуск приложения не зависит от завершения тестов: результат виден во время работы. Интерфейс — с
   горячим обновлением, backend перезапускается только для изменённого сервиса, остальное берётся из
   готового базового стенда. Для ручной проверки не нужны выпуск npm-пакета, образ Docker и релизный гейт.
   Пример: правка ввода чата — Core UI из ветки задачи поверх готовых Core и Make; правка backend Make —
   подменяется только Make.
4. Подменяемая часть запускается не в Docker, а в режиме разработки из рабочей копии (vite, tsx watch).
5. Стенд описывается составом с точными SHA по каждому репозиторию; имени ветки недостаточно. Сборки
   разработки имеют собственные идентификаторы и не подменяют опубликованные релизные архивы.
6. Стенды разработки работают на M1 и M2 на копии прод-базы и доступны через Tailscale и домашнюю сеть.
7. Задачи не дробить мельче: делить только по репозиториям для параллельной работы, с интеграционными
   требованиями в каждой части.

## Общий контракт (для всех задач)

- **Компоненты стенда**: `core` (voiceAIChat: сервер, порт 8787), `core-ui` (sislexa-core-ui: веб-интерфейс),
  `make` (sislex/make, 8788, префиксы `/api/make`, `/api/preview/make`, `/api/preview/make-shared`, `/p/`, `/s/`),
  `kanban` (sislexa-kanban, внутренний сервис ядра через `VC_KANBAN_URL`), `playwright-reader`
  (8797, `/api/browser`), `image-studio` (8796, `/api/image-studio`, `/g/`).
- **Состав стенда** `DevStandManifest` (B01): `{ schemaVersion: 1, standId, machineId, baseEnvironmentId,
  components: Record<ComponentId, { repository, sha, source: 'base' | 'dev', devBuildId?, url?, startedAt? }> }`.
  `sha` — полный 40-символьный SHA, обязателен для каждого компонента.
- **Идентификатор сборки разработки**: `<версия пакета>-dev.<первые 12 символов SHA>` (например
  `1.5.3-dev.862e4f2ada90`). Release composition, проверки закреплений и сверка рендерера Desktop отклоняют
  такие версии; сборки разработки не попадают в `vendor/`, GitHub Releases и реестр образов.
- **Запуск компонента в режиме разработки**: каждый репозиторий даёт `npm run dev:component` — процесс из
  рабочей копии с перезапуском при изменениях. Переменные: `PORT` (порт процесса),
  `SISLEXA_STAND_URL` (адрес шлюза стенда, куда процесс шлёт запросы к остальным компонентам),
  `SISLEXA_DEV_BUILD_ID`, `VC_DATA_DIR`/`VC_DB_URL` для компонентов с данными. Готовность — `GET /api/health`
  (для `core-ui` — ответ HTML на `/`).
- **Гейт задачи**: каждый репозиторий даёт `npm run gate:task -- --base <sha>` с кодом выхода 0/1 и строкой
  `GATE-TASK: tests=<n> seconds=<s>`; при превышении бюджета (1000 тестов или 300 секунд —
  5 минут, решение владельца 2026-10-07) выводит список
  лишних тестов и падает с кодом 2, чтобы их перенесли в полный контур.
