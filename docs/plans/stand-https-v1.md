# stand-https-v1 — стенд по HTTPS, самообновление агентов, уборка стендов, меньше ручной интеграции

Ран `stand-https-v1`. Ветка задач — `dev`. Задачи выполняют воркеры MacBook (M2); M1 выключен.
Продолжение [release-reliability-v1](release-reliability-v1.md) и [install-probe-v1](install-probe-v1.md).

## Что замечено 2026-10-14 (Core 0.1.458, Make 1.7.3, агенты 0.24.5)

1. **Стенд и Storybook пустые на `https://89.125.68.35`.** `apps/server/src/standProxy.ts` `StandProxy.access()` всегда строит
   адрес аренды `'http://' + hostname + ':' + port` (порты `VC_STAND_PROXY_PORTS=8790-8794` публикует сам `voicechat`, без TLS).
   На HTTPS-странице кадр `http://…:8790/` блокируется как смешанный контент; к тому же cookie сессии на HTTPS — `__Secure-vc_session`
   (Secure) и на `http://` не уходит (аренда ответила бы 401). Тег инспектора строится из `req.socket.encrypted` — за Caddy тоже `http`.
2. **Агенты не обновляются сами.** Core раздаёт 0.24.5 (`/api/agents/script`), серверы сидели на 0.23.0, пока их не обновили руками.
   В протоколе есть только уведомление `agent.updateAvailable` (шлётся лишь при нехватке версии для инструмента); установщик
   (`installers/unixInstall.ts` репозитория агента) уже умеет `.new.cjs` → `.prev` → перезапуск супервизором. Юнит systemd без
   `KillMode=process`: перезапуск агента убивает и процессы стендов.
3. **Удаление стенда оставляет процессы.** После удаления `dev-e8785e82-33f` осиротевший `vite` держал 127.0.0.1:23001, новый стенд
   упал `Port 23001 is unavailable`. Kanban `apps/server/src/environments/devStands.ts` `remove()` останавливает только компоненты из
   своей базы и шлёт `devProcess.stop {standId:'<id>-gateway'}` (агент так шлюзы не ключует); агент `devProcess.ts` `stop()`
   вызывает `terminate` только при наличии `runtime.child` — записи, восстановленные после рестарта без живого child, теряют процесс.
4. **Make: подключение стенда к ветке беседы неочевидно.** Список «Existing branch» берётся из рабочей копии проекта без fetch
   (`localCore.ts` `runProjectGit` → `git/scripts.ts` `branchesScript`), ветки беседы `make/conversation-…` там нет; безопасный путь —
   «New branch» с именем существующей ветки (Core `standWorkspace.ts` переиспользует рабочую копию) — выглядит опасно.
5. **Make: «Commits behind dev: unknown»** до нажатия «Update from dev» — `behind` приходит только из `POST …/sync-dev` (с merge).
   ↑/↓ в Repository считаются к `@{upstream}`, а у ветки стенда upstream — `origin/dev` (`worktree add -b … origin/dev`), поэтому
   после Pull счётчик не меняется.
6. **Core UI: плашка «Разговор не найден: возможно, он удалён.»** остаётся после перехода в другой разговор
   (`packages/chat-app/src/store/chatStore.ts` `performSelectConversation` → общий `setError`, переключение её не снимает).
7. **Интегратор отклоняет патчи из-за конфликтов только в сгенерированных частях базы знаний** (`docs/kb/README.md`, строки
   `checked:`/`updated:` во front matter) — release-reliability-v1 B04 вливали вручную.
8. **Подготовка воркера зависит от IPv6 до GitHub.** `npm ci` в песочнице качал готовую сборку `better-sqlite3` по IPv6 и падал
   по таймауту; `environment()` (`src/worker/attempt.ts`) даёт каждой попытке пустой `npm_config_cache` — кэш `_prebuilds` всегда холодный.

## Решения

- **Аренды стенда — через Caddy с TLS.** Корневой `Caddyfile`: один сайт на все порты аренды
  `https://{$VC_PUBLIC_HOST}:8790, …:8794 { tls internal; reverse_proxy voicechat:{http.request.port} }`; `deploy/docker-compose.yml`
  публикует 8790–8794 у `caddy`, у `voicechat` — только `expose`. Core: `StandProxyDeps.publicScheme` из
  `VC_STAND_PROXY_PUBLIC_SCHEME` (по умолчанию протокол `VC_PUBLIC_URL`, иначе `http`), адрес аренды строится с этой схемой; тег инспектора —
  `new URL('/api/make/inspector.js', lease.origin)`.
- **Самообновление агента.** Контракт `@sislexa/agent-contracts`: `ServerToAgent {t:'agent.update', version, sha256}`,
  `AgentToServer {t:'agent.updateResult', status:'applied'|'skipped_unsupervised'|'failed'|'rolled_back', message}`, поле
  `supervisor` в `agent.register`. Агент (`apps/agent/src/selfUpdate.ts`): только при супервизоре (`VC_AGENT_SUPERVISOR=systemd|launchd`
  из `run.sh`), скачать `/api/agents/script` в `.new.cjs`, проверить sha256 и `node --check`, `.cjs` → `.prev`, записать
  `update-pending.json`, выйти (супервизор перезапустит); `run.sh` откатывает на `.prev`, если ожидание старше 90 с без подтверждения;
  подтверждение — после `agent.registered`; не чаще раза в час на версию и не во время операции со стендом. Юнит systemd —
  `KillMode=process`. Core после регистрации шлёт `agent.update`, если раздаваемая версия новее (`servedAgent() → {version, sha256}`).
- **Уборка стенда.** Контракт: `devProcess.stopStand {standId}` — агент останавливает все процессы и шлюзы `id`, `id-live`, `id-gateway`,
  удаляет их рабочие копии и записи реестра; процесс без `child` убивается после сверки маркера (`readProcessMarker`); порт, занятый
  процессом с маркером этого агента, которого нет в реестре, освобождается; процессы без маркера не трогаются. Kanban `remove()`
  вызывает `stopStand` (для старых агентов — прежний цикл по компонентам) и не шлёт `-gateway`.
- **Make и Core для ветки беседы:** Core отдаёт `conversationWorktree?: {branch}` (чтение `worktree list` у `make-worktrees/<id>`) и
  `GET /api/projects/:id/dev-stands/:standId/sync-dev/status` → `{behind}` (fetch + `rev-list --count HEAD..origin/dev`, без merge);
  ветка стенда после первого push получает upstream `origin/<ветка>`. Make: первая опция «Рабочая копия беседы (make/conversation-…)»,
  «New branch» с занятым именем скрыт; `behind` запрашивается при открытии вкладки и после Pull/Push/Refresh.
- **Интегратор сам разрешает конфликты KB**, если все конфликтные файлы — `docs/kb/README.md`, `docs/kb/log/*` или только
  `checked:`/`updated:` во front matter `docs/kb/*.md`: README — версия цели и регенерация `kb:index`, front matter — строка кандидата,
  журнал — объединение; любой другой конфликт — прежний отказ.
- **Подготовка воркера:** `NODE_OPTIONS` получает `--dns-result-order=ipv4first` (дописывается к существующему, в т.ч. в
  `browser-gate-runtime.ts`); `_prebuilds` npm-кэша попытки засевается из кэша машины и сохраняется обратно.
