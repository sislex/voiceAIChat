# Независимые проверки, релизы и деплой приложений

Дата: 2026-09-10. Статус: шаги 1–6 и 8 выполнены, шаг 7 частично; итоговый гейт зелёный. Ветка `feat/application-independent-releases`.
Основание: пользователь хочет проверять изменяемое отделённое приложение отдельно,
выпускать каждую часть независимо и объявлять минимальные поддерживаемые версии
зависимостей. База реализации: `8c54ade4b623748f7aac032aa10f6e77c58724fe`.

## Исходные препятствия

Ниже — исходное состояние до этой реализации; актуальные границы и результаты
проверок перечислены в конце плана.

- `scripts/affected-check.mjs` смешивает зависимости от исходного кода и границы
  продуктов. Правка Make втягивает server, правка Reader UI — общий UI и web.
  Корневой lock-файл включает полный fallback; `npm run gate` всегда общий.
- Make, Image Studio и Playwright Reader имеют собственные workspace, тесты и
  standalone-процессы. Однако server зависит от их исходников; даже remote Make
  импортирует runtime-экспорты `@voicechat/make` в `makeBridge/remote.ts`.
- Reader-пакеты и новый runtime уже существуют, но настоящий `App.tsx` ещё
  импортирует BrowserSessionPane, MakePane и ImageStudioPane из общего UI.
  Lazy import даёт отдельный chunk одной сборки, а не отдельный выпуск приложения.
- `Dockerfile` начинает с COPY всего checkout, общего npm ci и сборки web/recorder;
  runtime-стадии получают общий `/app`. Свой target пока не даёт независимой сборки.
- `ProjectRelease` не содержит идентификатора компонента; ветки строго
  `release/x.y.z`, подготовка и deploy блокируются по projectId. Штатный deploy.sh
  вызывает `docker compose up -d --build` для всего проекта.
- Compose использует общую VC_RELEASE_VERSION и локальные имена образов.
  `version: 0.1.0` и внутренние зависимости `*` в package.json не являются
  каталогом реально установленных версий сервисов и их совместимости.
- Make хранит свои файлы, но читает пользователей/разговоры через MakeCore;
  выделение процесса не означает независимость от авторизации и данных ядра.

## Целевая единица выпуска

Монорепозиторий сохраняется. Репозиторий, npm-пакет и единица выпуска — разные
сущности: один выпуск приложения может включать backend и UI-артефакт, а библиотека
контрактов не обязана быть отдельным запущенным сервисом.

В каталоге приложений фиксируются id, владелец путей, пакеты, публичные контракты,
команды проверки/сборки, артефакты, compose-сервисы, health endpoint, конфигурация
и владение данными. Для каждого приложения отдельно отмечается готовность
границ к изолированным тестам, сборке и deploy. Папка apps сама по себе не даёт
эту готовность. Web Reader backend вынесен из apps/server в отдельное приложение
в продолжении от 2026-09-10 (см. ниже).

Первый кандидат — backend Make. Затем Image Studio и Playwright Reader;
browser-runner выпускается отдельно от оркестратора Playwright Reader.
LLM/STT/TTS/automation runners также имеют собственные единицы выпуска.
Оболочка web и ещё не перенесённые продуктовые панели пока принадлежат общему
frontend-выпуску. Desktop, agent и tray учитываются как клиентские дистрибутивы,
с собственными артефактами и совместимостью с сервером.

## Правило проверок

| Изменение | Обязательные проверки |
|---|---|
| Внутренняя логика отделённого приложения | Его typecheck, полный набор тестов, boundary/contract tests и сборка; его E2E при изменении поведения UI/браузера |
| Публичный API/события приложения | Его проверки + адресные контрактные проверки затронутых потребителей |
| Общая библиотека/контракт | Её проверки + выбранные потребители по фактическому графу |
| Общий host, runtime, инфраструктура или схема общих данных | Проверки реально затронутых приложений; полный набор только если область нельзя доказать |
| Релиз приложения | Полный гейт этого приложения и матрица заявленной совместимости на точном SHA/артефакте |

Внутреннее исправление Make не должно запускать все тесты чата, канбана и STT.
При изменении API нельзя пропускать совместимость, но для неё нужны небольшие
наборы контрактов, а не все серверные тесты. Embedded-сборка остаётся отдельным
потребителем и получает свой интеграционный гейт, когда меняется её контракт.

Реализованы команды: `gate:app -- make`, `gate:changed`, `gate:all`;
`gate:fast` использует рабочий diff от HEAD. Выбор выводит причину каждого набора
и сохраняет ненулевой exit code при ошибке. Lock-файл анализируется по изменённым
пакетам и их зависимостям; неизвестное влияние честно включает широкий гейт.
Файлы вне каталога, удаление/перенос путей и изменение общих конфигов не должны
давать ложный нулевой выбор. Нужны тесты самого планировщика.

## Версии и совместимость

Выпуск хранит applicationId, собственную releaseVersion, git SHA, неизменяемые
идентификаторы артефактов (для образов digest), версии публичных API и снимок
требований к другим приложениям. Каталог окружения отдельно хранит фактически
установленные версии, digest и результаты health/compatibility.

Пример будущего требования, а не номера существующих выпусков:
`make 1.7.0` требует `core >=1.4.0 <2.0.0`. Нижняя граница выражает минимальную
поддержку; верхняя не позволяет считать заведомо неизвестный major совместимым.
Версия API отличается от версии реализации: обычное исправление приложения
может не менять API. Все требования фиксируются внутри артефакта выпуска,
а не только в изменяемой конфигурации актуальной main.

Перед deploy сравнивается весь предполагаемый состав окружения: зависимости
кандидата и ограничения уже установленных потребителей. Неизвестная версия или
отсутствующая обязательная зависимость блокирует изменение; необязательные
возможности описываются отдельно. Для новой возможности в совместимом API можно
объявлять capability, не повышая искусственно версию всех сервисов.

Минимальную версию подтверждают контрактные тесты против соответствующего
выпущенного артефакта, а также актуальной поддерживаемой версии. Циклические
runtime-зависимости ядро ↔ приложение требуют окна обратной совместимости:
если безопасного последовательного обновления нет, нужен явный согласованный
набор выпусков, а не произвольный топологический порядок.

## Релиз и deploy

Release Center получает выбор приложения, его текущую/доступную версию,
требования, статус совместимости, историю подготовок и deploy-попыток.
Новые ветки могут иметь вид `release/make/1.7.0`, теги — `make/v1.7.0`.
Старые `release/x.y.z` сохраняются как legacy-выпуски всего проекта; это требует
расширения shared-контракта, БД, маршрутов и UI, а не только нового regex.

Сборка создаёт только артефакты выбранного приложения. Deploy берёт уже проверенный
артефакт по digest, а не пересобирает main на production. Шаги: preflight прав и
окружения → проверка совместимости → получение артефакта → замена нужного сервиса
→ проверка его версии/digest/health и короткая проверка связей → запись результата.
Остальные сервисы сохраняют версии и container id. Подготовка может идти независимо;
перекрывающиеся deploy-планы блокируются по окружению и затронутым сервисам,
чтобы параллельные проверки зависимостей не использовали устаревший состав.

Откат использует предыдущий точный артефакт, повторно проверяет совместимость
составов и допустимость схемы/данных. Общие миграции не должны запускаться скрыто
при релизе приложения: владелец схемы и окно чтения старой/новой версии явные.
Для собственного UI нужен отдельный build и доставка версионированных assets
через host manifest или маршруты приложения, с проверкой версии host API.
Этот этап реализован для Make, Image Studio, Playwright Reader и Web Reader: App
загружает самостоятельные артефакты панелей через проверяемый host manifest.

## Порядок внедрения и критерии готовности

1. [x] Каталог приложений и shared-контракты версии/зависимостей. Отдельно описать
   зависимости сборки, runtime и контрактных тестов; определить миграцию legacy.
   Критерий: каждый продуктовый путь имеет владельца, неизвестные/пересекающиеся
   владельцы отклоняются, несовместимые версии выявляются чистыми тестами.
2. [x] Завершить границу Make: вынести клиент/контракты из runtime-реализации,
   выделить контрактные проверки мостов, обеспечить standalone-стенд с портами
   ядра. Критерий: внутренняя правка Make не меняет публичный контракт и не требует
   полного server/UI-набора; интеграция local/HTTP проверена адресно.
3. [x] Внедрить планировщик гейтов на пилоте Make, сначала сравнив выбор с нынешним
   графом. Согласованно обновить корневой и пакетные AGENTS, conventions, CI,
   merge- и release-runner. Критерий: обычная правка Make запускает только его
   гейт; изменение API, shared и непонятный root diff не скрывает нужные проверки.
4. [x] Изолировать Make Docker-сборку, добавить собственную версию, digest и
   runtime metadata. Критерий: сборка не запускает web/Storybook/Whisper;
   смена Make не меняет артефакт ядра. Провести реальную сборку и запуск.
5. [x] Расширить Release Center, БД и deployment planner на компонентный выпуск.
   Критерий: проверены старая/новая БД, legacy-история, выбор приложения,
   минимальная и несовместимая версии, обратные зависимости, повтор запроса,
   параллельные deploy, рестарт менеджера, health failure и допустимый rollback.
6. [x] Провести пилот Make на изолированном staging со старым ядром, повторить
   на минимально поддерживаемом ядре. Критерий: Make обновился, ядро и остальные
   контейнеры не перезапускались, версии в UI соответствуют реальным digest.
7. [ ] Перевести оставшиеся самостоятельные backend/runner-приложения через тот
   же каталог и инструменты. Для пока встроенных модулей сначала закончить
   границу процесса; одинаковая папка или сервис Compose не заменяет этот шаг.
8. [x] Перенести продуктовые панели, тесты, стили и runtime-композицию из общего
   UI в приложения, добавить независимые frontend-артефакты и manifest хоста.
   Критерий: правка UI приложения проверяется и публикуется без пересборки shell;
   запуск web/desktop использует новый путь, а не дублирующий legacy App.

Начинать следует с шагов 1–3, затем сделать первый реальный независимый релиз
backend Make (4–6). Отдельный репозиторий не является предварительным условием.
Изменения проверяются локально. Production-публикация не выполняется.

## Результат реализации

- Каталог разделяет владельцев исходников, зависимости npm-сборки, runtime и
  адресные контрактные проверки. `make-contracts` отделён от реализации Make;
  remote-мост ядра не импортирует Make runtime. Планировщик учитывает обе стороны
  lock-diff, peer/optional/transitive dependencies, удаления и неизвестные пути.
  Внутренний Make diff выбирает Make; общая инфраструктура включает полный гейт.
- Изолированные образы и контрактные driver есть у Make, Image Studio,
  Playwright Reader API, browser-runner, LLM, STT, TTS и четырёх UI-приложений.
  Metadata содержит собственные release/API/data версии, SHA, диапазоны и
  capabilities; выпуск привязан к digest и матрице minimum/current. UI требует
  одновременно backend и core; driver запускает артефакт через собранную оболочку
  baseline, а не текущий исходник загрузчика.
- Release Center, shared/REST/IPC, миграция БД и durable lock поддерживают
  подготовку на точном SHA, выбор приложения/окружения, идемпотентность,
  согласованные наборы, проверку прямых и обратных зависимостей, restart reconcile,
  проверку фактических связей, автоматический и явный rollback. Неопределённый
  результат сохраняет блокировку; изменение target не разрешает повторный deploy.
  Legacy-история сохранена. После регистрации компонентного production-состава
  старый общий deploy блокируется, чтобы не пересобрать независимые сервисы.
- MakePane, MakeSharedView, ImageStudioPane и BrowserSessionPane с тестами и
  стилями перенесены в свои пакеты. Web Reader использует собственный артефакт.
  Общие редакторы, frame-компоненты и чистые UI-примитивы живут в ui-foundation.
  Реальный App web/desktop получает панели через host API, проверку диапазона,
  SRI и регистрацию версии. Ошибка панели не ломает чат; старые hashed assets
  сохраняются для открытых вкладок и поздней загрузки Monaco.
- Примеры изолированного состава и конфигурации: `docs/examples/application-releases/`.
  Операционная инструкция: `docs/kb/features/releases.md`; устройство UI:
  `docs/kb/ui.md`. Для первого перехода предусмотрена общая сборка `core --baseline`.

## Подтверждение на реальных артефактах

- Backend-пилот Make 1.0.0 → 1.1.0 прошёл с двумя ядрами: бизнес-кодом исходного
  HEAD и текущим кодом. Для исторического ядра добавлен только тестовый адаптер
  health metadata. Номера версий синтетические, образы помечены development и
  размещались только в локальном loopback registry; это не опубликованные релизы.
- В каждом составе проверены настоящий RPC, неизменность container ID ядра и
  контрольного сервиса, сохранность файла Make в томе, намеренный отказ из-за
  неверного внутреннего секрета, восстановление прежнего digest и явный rollback.
- Frontend-пилот на полном собранном web-host: Make UI 1.0.0 → 1.1.0 и rollback.
  Не изменились container ID ядра и Make, а также SHA256 bundle оболочки.
  Открытая вкладка получила старые assets и поздно загрузила Monaco; новая вкладка
  загрузила новый manifest. Chromium не зарегистрировал ошибок страницы.
- Native-контракты Image Studio, Reader API, Chromium, LLM, STT и TTS выполнены
  в настоящих отдельных Docker-контейнерах. LLM проверяет CLI и HTTP-протокол,
  STT — Whisper/модели/WS; внешняя авторизация CLI и распознавание со скачанной
  моделью не заявляются проверенными. TTS действительно синтезирует WAV Piper.
- Проверены старая файловая БД и сохранение legacy-истории, блокировки после
  переоткрытия БД, повтор запросов, конкурентные планы, рестарты менеджера,
  несовместимые версии/API/data, обратные ограничения и смена target.
  Release Center проверен в Chromium на desktop/mobile; четыре панели — в браузере,
  Make UI также через `file://` desktop. Все четыре UI-driver прошли с реальными
  Docker-артефактами через полный baseline-host; историческое ядро без gateway
  было намеренно отклонено. Итоговый `gate:fast` завершился с кодом 0: все типы, 8440 тестов пакетов,
  87 тестов инструментов, сборки четырёх UI/web/Storybook и 44 E2E. Desktop
  typecheck/build прошли отдельно. Подробности — в журнале KB.

## Оставшаяся граница шага 7

В каталог и общий механизм переведены все уже работоспособные самостоятельные
backend/runner-приложения. Полностью шаг 7 не закрыт: automation-runner имеет
исходный `executor_adapter_not_configured`, поэтому независимый deploy запрещён;
нужно отдельно реализовать его исполнитель. Встроенные канбан,
админка и машины, а также core/web и клиентские дистрибутивы учтены в каталоге,
но не объявлены готовыми к независимому deploy. Перенос их процессов и данных
не подменён новым Docker target. После компонентного перехода ядро обновляют
через контролируемую baseline-миграцию, пока его независимая граница не завершена.

Для реальной площадки требуются собственные baseline-версии/digest, registry,
секреты, привязки существующих томов и матрицы совместимости на этих артефактах.
Проверка локальных development-образов не создаёт вымышленные production-baseline.
Production-публикация не выполнялась. Git-изменения подготовлены к публикации
в ветке `feat/application-independent-releases` по отдельной просьбе пользователя.


## Продолжение: границы Reader (2026-09-10)

- Web Reader API/MCP/прокси и его тесты перенесены в `apps/web-reader`;
  `apps/web-recorder` входит в тот же самостоятельный образ. Общая БД и импорт
  серверной конфигурации устранены: данные, авторизация и машины идут через RPC.
- `web-reader-contracts`, `playwright-reader-contracts`, `browser-contracts`
  отделяют реализацию API от core и движка Chromium. В двух API-образах Reader
  нет исходников ядра, общего UI, Chromium и драйверов БД.
- `web-reader` имеет собственный выпуск/driver/deploy; требует API core >=1.1.0.
  UI-панели `web-reader-ui`/`playwright-reader-ui` и `browser-runner` сохраняют
  собственные релизы. Диапазоны фиксируются манифестами, включая верхние границы.
- Селектор частных изменений выбирает только свой Reader. Изменения публичных
  контрактов добавляют потребителей; изменение корневой сборки требует общего гейта.
- Docker-контракты проверены с отдельным ядром и настоящим Chromium; браузерный
  вход на собственный проект проверяется для embedded и remote Web Reader.
  Реальные production baseline/registry по-прежнему задаются оператором.
