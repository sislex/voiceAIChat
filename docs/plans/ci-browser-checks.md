# Браузерные проверки на стадии разработки (development-ран канбана)

Цель: при запуске задачи в разработку можно указать, что модель проверяет
результат **в браузере на выбранной машине** — тем же словарём действий
`mcp__browser__*`, которым она управляет Web Reader и Playwright Reader.

Выбранная машина уже известна ходу: `conversation.execTarget` разворачивается в
алиас `<agentId>.machine.internal` (`previewMcp.ts`), а `machineOf` в
`server.ts` проверяет доступ. Разрыв ровно в двух местах: действие уходит в
`PreviewActionRelay` (браузер пользователя, где страницы рана нет), а
изолированный Chromium не резолвит `*.machine.internal`.

## Режимы

- `off` — как сейчас: браузерных инструментов у хода рана нет.
- `chromium` — действия исполняет изолированный Chromium `browser-runner`
  (движок Playwright Reader и этапа Automated QA).
- `user_panel` — действия уходят в живую панель Web Reader пользователя;
  режим для случая «человек сидит рядом и смотрит».

## Шаги

- [x] **1. Контракт (`packages/shared/src/ci.ts`).** `CiBrowserCheckMode`,
      `CiBrowserCheck { mode, devServerPort, startPath }`, дефолты,
      `normalizeCiBrowserCheck`, `ciBrowserCheckUrl(check, agentId)` —
      единственный источник адреса для сервера и UI. Тесты в `ci.test.ts`.
- [x] **2. Хранение и REST.** Таблица `ci_task_browser_checks` (образец —
      `ci_task_process_stages`), методы `getTaskBrowserCheck` /
      `setTaskBrowserCheck`, поле `browserCheck` в GET/PUT
      `/api/projects/:id/tasks/:taskId/ci`. Снимка режима в `ci_runs` **нет**
      осознанно: режим влияет только на транспорт действия в момент вызова, и
      зафиксированное в ране значение всё равно не описывало бы, куда уйдёт
      следующее действие.
- [x] **3. Транспорт до машины.** На пути Chromium адрес
      `http://<agentId>.machine.internal:<port>/` переписывается в серверный
      прокси превью (`/api/preview?url=…`) с одноразовым токеном рана; в
      `browser-runner` добавляется алиас внутреннего адреса сервера.
      SSRF-гейт не ослабляется: во внутреннюю сеть пускает оператор.
- [x] **4. Гейт транспорта (`server.ts` `browserExecutor`).** Условие
      расширяется: reader-разговор **или** ход рана с `mode: 'chromium'`.
      Ключ сессии — по задаче, а не по `runId` (иначе профиль Chromium
      остаётся в томе после каждого прогона). Сессия гасится при любом
      терминальном исходе рана.
- [x] **5. Хинт модели.** Отдельный текст для хода рана: страница живёт между
      вызовами, dev-сервер поднимается через `mcp__remote__bash`, адрес —
      `http://machine.internal:<порт>/`. При `off` браузерные инструменты из
      хода убираются, иначе модель упирается в таймаут relay.
- [x] **6. Настройка в UI.** Переключатель режима и порт в `CiTaskSettings`
      рядом с этапами процесса, бейдж в карточке задачи.
- [x] **7. Видимость результата.** Кадр пишется файлом в
      `<dataDir>/ci-browser-shots/<runId>/<n>.png`, в лог рана уходит системная
      строка со ссылкой (`REST.ciRunBrowserShot`), уборка — при старте и раз в
      сутки. Превью картинкой в `RunFeed` осознанно не делали: формат ленты
      текстовый, и ради одной фичи новый тип события не вводим.
- [ ] **8. Закрепление.** Пройденная проверка предлагается к записи сценарием
      Automated QA (механизм записи уже готов).

## Второй круг, если понадобится

Прокси превью инъектирует шимы и переписывает адреса — страница отличается от
той, что увидит пользователь. Честный вариант: серверный TCP-listener поверх
готового `tunnel.connect` (`agentProtocol.ts`; агентская сторона реализована),
тогда Chromium получает страницу без rewrite.

## Гейт
