# stand-fixes-v1 — ошибки, найденные на стенде разработки

Ран `stand-fixes-v1`. Ветка задач — `dev`.

Владелец, 2026-10-08: при проверке стенда M1 (`dev-86c476d9-38a`) найденные ошибки — заводить задачами и
исправлять. Стенд: базовое окружение с Core 0.1.412 на копии прод-базы, Core UI и Make из рабочих копий `dev`.

| B01 | core-ui | — | Board must load when the subprojects endpoint is unavailable. `loadBoardProjects` in `packages/ui/src/store/domains/projectsStore.ts` awaits `client['projects:subprojects']({ id })` (`GET /api/projects/:id/subprojects`) without handling errors. Against a Core that does not have the route yet (dev stand Core 0.1.412 answers 404) the board stays on skeletons and the UI shows «Доступ к проекту закрыт: он удалён или вас исключили из участников», although `GET /api/projects/:id` and the board itself are fine. Treat 404/405/501 from the subprojects call as «no subprojects» (catalog = the project itself, selection = [id]) and do not surface the project-access error for it; keep the existing handling of a real 403/404 on the project itself. Other errors of the optional call must not block the board either (log/keep single-project catalog). Add store tests: subprojects 404 → board loads with a single project and no access-closed notification; project 403 still shows it. Gate: `npm run gate:task -- --base <sha>`. |
| B02 | Agent | — | Dev stand component replacement must update the stand manifest. On M1 a replacement of `core-ui` (stand `dev-86c476d9-38a`, operation `b2c0db47-5b5b-45c7-a187-5765ef1f7c27`, reported `succeeded`) started the new dev process (sha `dae2f832…`, port 23002, `npm run dev:component`) and stopped the old one (sha `7f572030…`, port 23003), but `~/.voicechat/dev/stands/<standId>/manifest.json` still had `components['core-ui']` with the old `sha`, `url` `http://127.0.0.1:23003` and `devBuildId` `0.0.0-dev.7f5720304ba0`, so the gateway answered `dev_upstream_unavailable` for every page. The manifest is written by `writeManifest` in `apps/agent/src/devProcess.ts` (atomic temp file + rename; the gateway rereads it per request and rejects a component whose `devBuildId` sha12 differs from `sha`). Make a successful replacement atomically switch the manifest to the new component (`sha`, `url`, `devBuildId`, `startedAt`) once the new process is ready and before the old one is stopped; on failure keep the old process and manifest. Report the operation as succeeded only after the manifest switch. Tests with a fake spawn/readiness: replacement updates the manifest before stopping the old process, failed readiness keeps the old manifest and process, manifest stays valid for the gateway reader. Gate: `npm run gate:task -- --base <sha>`. |
